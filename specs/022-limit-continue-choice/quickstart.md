# Quickstart: 022 — 예산 소진을 막힘과 갈라 말한다

**Created**: 2026-09-28

이 기능이 실제로 동작하는지 **사람이 손으로** 확인하는 절차. 자동 검증이 덮지 못하는
것(문구가 읽히는지, 적어야 하는 것으로 보이지 않는지, 수치가 판단에 쓸 만한지)을 본다.

---

## 사전 준비

```bash
# 백엔드
cd backend && .venv/bin/python -m uvicorn itb.api.app:app --reload

# 프론트
cd frontend && npm run dev
```

AI 작성 경로를 쓰므로 자격 증명이 필요하다. 없으면 개발용 드라이버를 쓴다.

```bash
export ITB_AI_DRIVER=claude-code   # 이미 로그인된 Claude Code 를 쓴다
```

**상한에 빨리 닿게 하려면** 임시로 `MAX_TOOL_CALLS` 를 낮춘다 (확인 후 되돌릴 것).

```bash
# backend/src/itb/authoring/tools.py — MAX_TOOL_CALLS = 40 을 6 정도로
```

낮추지 않으려면 §2 의 긴 지시문을 그대로 쓴다 — 실제로 상한에 닿는다.

---

## §1. 예산 소진이 다른 막힘과 갈린다 (US2 · FR-012·FR-013·FR-016)

1. 새 테스트를 만들고 AI 작성을 시작한다.
2. 상한에 닿을 때까지 둔다.
3. **확인**
   - 제목이 「AI 가 막혔습니다」가 **아니다** — 예산이 떨어졌음으로 읽힌다
   - **알려 주기 칸이 없다** — 적어야 하는 것으로 보이지 않는다
   - 이어가기 버튼의 글자가 「다시」가 아니라 「이어서」로 읽힌다
   - 「이 동작 건너뛰기」가 **보이지 않는다**

4. 이번엔 **요소를 못 찾게** 만든다 — 화면에 없는 버튼을 누르라고 지시한다.
5. **확인 (회귀)**
   - 화면이 **지금까지와 똑같다** — 「AI 가 막혔습니다」, 알려 주기 칸, 선택지 다섯
   - 질문이 있으면 질문이 보인다

§1 이 이 기능의 핵심 위험을 본다. 기존 막힘 화면이 바뀌면 020·011 이 쌓은 것이 무너진다.

---

## §2. 이어가면 남은 일을 한다 (US1 · FR-006 · **SC-001**)

**가장 중요한 절이다.** 문구가 아니라 동작을 본다.

1. 등록·목록·수정·삭제가 든 긴 지시문을 준다. 예:

   ```
   로그인한 뒤 목록 화면으로 간다.
   [등록] 등록 버튼을 누르고 이름에 「검증용 항목」을 입력하고 저장한다.
   [목록] 검색창에 「검증용」을 입력해 검색한다.
   [수정] 방금 만든 항목을 열어 이름을 「검증용 항목 2」로 바꾸고 저장한다.
   [삭제] 그 항목을 체크해 삭제하고 확인을 누른다.
   ```

2. 등록 구간을 지난 뒤 상한에 닿게 한다.
3. Step 목록을 **적어 둔다** — 몇 개이고 마지막이 무엇인지.
4. 이어가기를 누른다.
5. **확인**
   - AI 가 **등록을 다시 하지 않는다** — 같은 이름의 항목이 두 개 만들어지지 않는다
   - 목록·수정 구간으로 **진행한다**
   - 3번에서 적어 둔 Step 이 **그대로 남아 있다**

이 절이 통과하지 않으면 기능이 없는 것보다 나쁘다 — 사용자가 이어가기를 누를 때마다
데이터가 중복 생성된다.

---

## §3. 판단할 근거가 보인다 (US3 · FR-017~FR-021)

1. §2 를 이어서, 두 번째로 상한에 닿게 한다.
2. **확인**
   - 누적 동작 수가 **합쳐져** 보인다 — 첫 번째 막힘의 수치보다 크다
   - Step 수가 보인다
   - 이어간 뒤 Step 이 늘었으면 진전 없음 안내가 **뜨지 않는다**

3. 이번엔 **진전이 없는 상황**을 만든다 — 존재하지 않는 화면을 계속 찾게 하는 지시로
   이어간다.
4. **확인**
   - 진전 없음 안내가 **뜬다**
   - 그래도 **이어가기 버튼은 눌린다** (FR-021 — 안내는 막지 않는다)

5. 첫 번째 막힘(§1의 3번)으로 돌아가 보면, 그때는 진전 없음 안내가 **없었어야** 한다 —
   첫 시도는 비교할 직전 값이 없다.

---

## §4. 새로 고쳐도 남는다 (FR-022)

1. 예산 소진으로 막힌 상태에서 브라우저를 **새로 고친다**.
2. 세션으로 다시 들어온다.
3. **확인**
   - 예산 소진 화면이 그대로다 — 제목·선택지·누적 수치·진전 안내
   - 알려 주기 칸이 여전히 없다

이 절은 `BlockedView` 가 새 필드를 싣는지 본다. 이벤트에만 실으면 여기서 수치가 사라진다.

---

## §5. 누적이 새 지시에서 0 으로 돌아간다 (data-model §5)

1. 예산 소진 상태에서 **끝내기**를 누르거나, 작성을 마친다.
2. 같은 세션에서 **새 지시문**을 준다.
3. 상한에 닿게 한다.
4. **확인** — 누적 동작 수가 앞 지시문의 것을 이어받지 않는다

---

## §6. 두 상한이 같게 보인다 (FR-004)

도구 호출 상한과 드라이버 turn 상한 양쪽을 각각 닿게 해 **화면이 구별되지 않는지**
확인한다.

```bash
# 도구 호출 상한: MAX_TOOL_CALLS 를 낮춘다
# 드라이버 turn 상한: MAX_DRIVER_TURNS 를 낮춘다 (ITB_AI_DRIVER=claude-code 필요)
```

사용자는 어느 쪽에 닿았는지 알 필요가 없다. 사유 문구가 달라도 **할 수 있는 일과 화면
구조가 같아야** 한다.

## 자동 검증

```bash
cd backend && bash scripts/test-backend.sh     # 병렬 계층 + 순차 계층
cd frontend && npm test
cd backend && .venv/bin/lint-imports           # 헌법 원칙 II 계약
cd backend && .venv/bin/python -m ruff check src tests
```

**기존 실패를 새 실패와 섞지 말 것.** 이 기능 시작 시점(브랜치 `022-limit-continue-choice`
분기점)에 이미 실패하던 것:

- `tests/abnormal/test_ui_surface.py` — AS-009 · AS-025 · AS-037 · AS-046
- ruff — `src/itb/api/routes/steps.py`, `src/itb/execution/assertion_builder.py`,
  `src/itb/execution/step_executor.py`, `tests/integration/test_negative_assertion.py`
- `frontend/tests/ScreenSweep.test.ts` — 2건. **순회 보고서가 낡았다**(화면 코드를 고친
  뒤 `backend/.venv/bin/python scripts/screen_sweep.py` 를 다시 돌리지 않았다). 022 의
  변경을 stash 하고 확인해 **이 기능 이전부터 실패하던 것**임을 확인했다

전부 021 작업분이며 이 기능과 무관하다.

**다만 ScreenSweep 은 022 도 다시 돌려야 한다** — 이 기능이 `WorkArea.tsx` 를 고쳤으므로,
021 이 순회를 돌려 보고서를 갱신하면 022 의 변경도 함께 반영해야 한다. 이 기능만으로는
그 실패를 없앨 수 없다 (021 의 변경분이 섞여 있다).
