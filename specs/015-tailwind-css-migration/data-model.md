# Data Model: Tailwind CSS 전환

**Feature**: 015 | **Date**: 2026-09-10 | **Phase**: 1

이 기능은 사용자 데이터를 다루지 않는다. 저장소도, 스키마도, 마이그레이션도 없다.
여기서 「모델」은 **전환을 성립시키는 개념들과 그 사이의 규칙**이다. 이것을 적어 두는
이유는 각 개념이 어디에 살고 무엇을 침범하면 안 되는지가 이 기능의 전부이기 때문이다.

---

## 개념 지도

```
확정 디자인 (docs/design/008-visual-language/*.dc.html)
        │  extract_canon.py 가 추출 · 사람이 손대지 않는다
        ▼
   시각 토큰  ──────────────────────────┐  값은 여기에만 있다
   theme/tokens.css :root {…}           │
        │                               │
        │ @import + @theme inline       │ (참조만. 값 복제 없음)
        ▼                               │
   Tailwind 테마 이름                    │
   theme/tailwind.css                   │
        │                               │
        │ 유틸리티 클래스로 소비          │
        ▼                               │
   부품 컴포넌트 (src/ui/*)  ◄───────────┘
        │
        │ 화면이 조립
        ▼
   화면 (src/pages/*, src/components/*)
        ▲
        │ 배치를 내려받는다 (자기 크기를 모른다)
        │
   배치 표 (lib/layout.ts)  Record<Phase, …>
```

## 1. 시각 토큰 (Visual Token)

| 항목 | 내용 |
|---|---|
| **사는 곳** | `frontend/src/theme/tokens.css` 의 `:root` |
| **누가 만드나** | `scripts/extract_canon.py` — 확정 디자인 18장에서 추출. 사람이 고치지 않는다 |
| **이 기능에서** | **읽기만 한다.** 값을 더하지도 바꾸지도 않는다 (FR-003) |
| **불변식** | 같은 값이 이 파일 밖에 다시 적히면 위반 (FR-001) |

예: `--pass:#1A7F45` · `--hair:#E3E6EB` · `--radius` · `--font-sans` · `--e-2`

---

## 2. Tailwind 테마 이름 (Theme Name)

| 항목 | 내용 |
|---|---|
| **사는 곳** | `frontend/src/theme/tailwind.css` 의 `@theme inline` — **신규** |
| **무엇인가** | 시각 토큰에 Tailwind 규약의 이름을 다시 붙인 것. `--color-pass: var(--pass)` |
| **값을 갖는가** | **아니다.** 오른쪽은 항상 `var(정본토큰)` 이다 |
| **불변식** | 리터럴 값이 나타나면 위반 (FR-016). 가드가 센다 |

값이 없다는 것이 이 개념의 핵심 성질이다. 값이 없으면 정본과 어긋날 수 없다 —
규칙으로 금지하는 대신 **구조로 불가능하게** 만든다.

---

## 3. 부품 컴포넌트 (UI Part)

| 항목 | 내용 |
|---|---|
| **사는 곳** | `frontend/src/ui/` — **신규** |
| **어디서 왔나** | 해체된 의미 클래스 109개 (`.btn`·`.chip`·`.notice`·`.modal`…) |
| **무엇을 아는가** | 자기 모습만. **도메인을 모른다** — Step 도 Phase 도 Project 도 모른다 |
| **무엇을 모르는가** | 자기가 놓일 자리의 크기. 그것은 배치 표의 관할 |
| **불변식** | 같은 종류의 부품은 정의가 한 곳이다 (SC-010). 화면이 부품 모양을 조립하지 않는다 |

**`components/` 와의 경계**: 도메인을 아는가로 가른다. `ui/Button` 은 아무 데서나 쓰이고,
`components/StepRow` 는 Step 을 안다. 이 경계가 흐려지면 `ui/` 가 두 번째 화면 디렉터리가
된다.

## 4. 배치 표 (Layout Table)

| 항목 | 내용 |
|---|---|
| **사는 곳** | `frontend/src/lib/layout.ts` — **기존. 구조를 유지한다** |
| **형태** | `Record<Phase, VerticalSplit>` · `Record<Phase, SlotName>` |
| **왜 표인가** | 007 S-12 — 컴포넌트가 자기 크기를 스스로 정했다가 편집 국면에서 두 자리가 뒤바뀐 결함. 판단이 흩어져 있으면 어느 한 파일만 보고는 결함이 보이지 않는다 |
| **이 기능에서 바뀌는 것** | **출력 형식만.** 스타일 객체 → 클래스 문자열 |
| **이 기능에서 바뀌지 않는 것** | `Record<Phase, …>` 라는 형태(FR-020a) · 부모가 자식에 내려주는 흐름(FR-020b) |

**새로 더하는 것** — 표의 값을 클래스로 옮기는 대응. 이것도 전수 `Record` 다:

```ts
const SPLIT_CLASS: Record<VerticalSplit, string> = { fill: …, content: … };
```

`VerticalSplit` 이 유한 합집합이므로 이 표도 컴파일 시점에 전수를 요구한다.
**국면이 늘어나도, 배치 종류가 늘어나도 빠뜨릴 수 없다.**

## 5. 인라인 스타일 예외 (Inline Style Exception)

| 항목 | 내용 |
|---|---|
| **사는 곳** | `frontend/src/theme/exceptions.ts` — **기존 등록부를 재사용** |
| **무엇이 자격이 있나** | **런타임 계산값만** (FR-005). 진행률 막대 너비, 드래그 위치, 실측 기반 크기 |
| **자격이 없는 것** | "옮기기 번거로워서" · "나중에" · "이 화면만" |
| **필수 항목** | `file` · `pattern` · `axis` · `reason`. `reason` 이 비면 등록이 아니다 (008 C-12) |
| **불변식** | 등록되지 않은 예외는 존재할 수 없다. 죽은 예외는 가드가 보고한다 |

전환 전 455곳 중 몇 개가 여기 남을지는 지금 알 수 없다. **개수를 미리 정하지 않는다** —
목표 숫자를 정하면 자격 없는 것을 끼워 넣거나 자격 있는 것을 억지로 옮기게 된다.

## 6. 행선지 대응 (Class Migration Entry)

| 항목 | 내용 |
|---|---|
| **사는 곳** | `specs/015-tailwind-css-migration/contracts/class-migration.md` |
| **한 행** | `클래스 이름 \| 사용처 수 \| 행선지 \| 상태` |
| **왜 필요한가** | SC-009 「미상 0건」. 109개는 머릿속에 담기지 않고 전환은 여러 커밋에 걸친다 |
| **기계가 세는 것** | `tokens.css` 에 남은 의미 클래스 수 == 이 표의 「미완료」 행 수 |

표만 갱신하고 코드를 안 옮기는 것과 그 반대를 둘 다 잡는다.

## 7. 회귀 가드 (Regression Guard)

전환 후 이 기능이 남기는 장치 넷. **각각이 막는 실패가 다르다.**

| 가드 | 막는 실패 | 어디서 |
|---|---|---|
| **G-A 값 리터럴** | 색·치수를 화면 코드에 다시 적음 | `count-violations.mjs` (기존 축 확장) |
| **G-B 클래스 실재** | 클래스 이름 오타 · Tailwind 가 클래스를 못 찾아 조용히 무스타일 | 신규. 빌드 산출 CSS 조회 |
| **G-C 체계 혼용** | 한 요소에 의미 클래스와 유틸리티가 동시에 걸려 우선순위 다툼 | 신규. 전환 진행률 계기이기도 하다 |
| **G-D 행선지 일치** | 대응표와 코드가 어긋남 | 신규 |

**G-B 가 이 목록에서 가장 중요하다.** 나머지 셋은 규율을 지키는 장치지만, G-B 는
**아무도 확인하지 않던 실패**를 잡는다 — `toHaveClass("basis-[460px]")` 는 오타가 있어도
통과하고, 화면은 스타일 없이 렌더된다. 인라인 스타일 시절에는 이 실패 자체가 없었다.

## 상태 전이 — 클래스 하나의 일생

```
  미착수 ──► 행선지 결정 ──► 부품/유틸리티로 구현 ──► 사용처 전량 교체 ──► 정의 삭제 ──► 완료
             (대응표 기재)                              (G-C 가 혼용 감시)   (tokens.css)
```

**「정의 삭제」 전에는 완료가 아니다.** 새 부품을 만들고 옛 클래스를 남겨 두면 두 체계가
공존한 채 굳는다 — 그것이 007 이 겪은 「전사(轉寫)」 실패의 형태다.
