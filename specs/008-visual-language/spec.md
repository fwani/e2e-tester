# Feature Specification: v1 잔재를 걷어내고 v2「계기판」을 코드에 세운다

**Feature Branch**: `008-visual-language`

**Created**: 2026-09-08

**Status**: Draft

**Input**: User description: "위에서 분석한것 처럼 old 디자인의 잔재는 다 제거하고 새디자인 적용하라"

## 문제의 실제 모습

디자인은 이미 v2「계기판」으로 확정됐다 (`docs/design/008-visual-language/` 18장, 2026-09-08 채택).
코드도 옮겼다고 기록돼 있다 — `replacement-map.md` §4 는 7건 중 6건 완료로 적었다.
**그런데 화면은 여전히 v1 을 절반쯤 입고 있다.**

아래는 추측이 아니라 `frontend/src` 전수 조사 결과다. 각 요구사항 끝의 `(V-nn)` 은 이 관찰 번호다.

### 왜 이렇게 됐나

세 가지가 겹쳤다. 셋 다 **방침의 결과**이지 실수가 아니다.

1. **전달 매체가 값이지 계약이 아니다.** `replacement-map.md` §4-5번이 "이 파일들은 v1 dc.html 의
   인라인 값을 **전사**했다 … 값과 주석을 함께 옮긴다" 를 방침으로 채택했다. 전사는 1회성이라
   다음 변경에서 즉시 깨진다. 실제로 v1→v2 전환에서 기하(3px→1px, 모서리 추가)는 옮겨졌지만
   색과 구조는 v1 이 남았다 — 전사 항목을 사람이 하나씩 골라야 했기 때문이다.
2. **대조 기준이 통계값이다** (V-10). 눈으로 보면 명백한 차이를 표가 세지 않는다.
3. **가드가 소비처를 보지 않는다** (V-09). 정의는 지키는데 사용은 안 지킨다.

이 기능은 **V-03~V-08 을 고치는 데서 멈추지 않는다.** 같은 방식으로 고치면 다음 디자인
개정에서 같은 자리에 같은 어긋남이 다시 생긴다. 원인 셋을 함께 없애는 것이 범위다.

## User Scenarios & Testing *(mandatory)*

이 제품의 사용자는 두 부류다. **제품 사용자**(테스트를 만들고 돌리는 사람)와 **화면을 고치는
개발자**다. v1 잔재는 앞쪽에게는 읽기 어려운 화면으로, 뒤쪽에게는 고칠 곳을 찾지 못하는
비용으로 나타난다.

### User Story 1 - 목록 화면이 v2 로 보이고, 그 값이 한 곳에만 있다 (Priority: P1)

제품을 열면 가장 먼저 보는 화면이 테스트 목록이다. 지금은 검정 표 머리와 잉크 테두리, 크림색
띠가 섞인 v1/v2 혼합이고, 행마다 잉크로 채운 버튼이 두세 개라 어느 것이 주 동작인지 알 수
없다. 결말은 실패만 배경색으로 표시돼 통과와 미실행이 구분되지 않는다.

이 이야기가 끝나면 목록 화면(테스트 있음 / 0개 두 상태)이 디자인과 같아지고, **그 화면을 그리는
코드에는 색·치수·글꼴 값이 하나도 남지 않는다.** 시각 언어는 스타일 시트 한 곳에만 존재한다.

**Why this priority**: 첫 화면이고, 이 이야기가 시각 언어의 정본(재사용 클래스 시트)을 세운다.
나머지 화면은 그것을 소비하기만 하면 된다. 여기서 클래스 시트가 서지 않으면 US2·US3 은 다시
전사가 된다.

**Independent Test**: 목록 화면과 `TestList.dc.html`·`EmptyList.dc.html` 을 나란히 놓고
대조한다. 동시에 `pages/TestList.tsx` 에서 색상 값과 치수 값이 0인지 센다. 둘 다 통과하면
이 이야기는 단독으로 가치를 낸다 — 다른 화면이 아직 v1 이어도 목록은 옳다.

**Acceptance Scenarios**:

1. **Given** 통과·실패·실행 중·미실행이 섞인 테스트 목록, **When** 목록 화면을 연다, **Then**
   각 행의 왼쪽에 결말을 나타내는 3px 마커가 보이고, 네 결말이 색과 표식으로 서로 구분된다 (V-05)
2. **Given** 목록 화면, **When** 화면 전체를 본다, **Then** 잉크로 채운 조작은 주 동작 하나뿐이고
   나머지 조작은 중립 형태다 (V-04)
3. **Given** 목록 화면, **When** 결말 필터 칩과 정렬 조작을 찾는다, **Then** 디자인이 정의한
   필터 4종과 정렬 조작이 있고 실제로 목록을 거른다 (V-07)
4. **Given** 테스트가 0개인 프로젝트, **When** 목록 화면을 연다, **Then** `EmptyList.dc.html` 이
   정의한 빈 상태 화면이 보인다
5. **Given** `pages/TestList.tsx`, **When** 색상 값을 센다, **Then** 0개다 (V-02)
6. **Given** 기존 목록 기능(검색·이름 변경·삭제 확인·실행·결과 보기·세션 복귀), **When**
   각각을 조작한다, **Then** 이전과 똑같이 동작하고 문구도 같다

### User Story 2 - 통합 작업 화면 여덟 국면이 v2 로 보인다 (Priority: P2)

테스트를 만들고·녹화하고·돌리고·멈추고·이어받고·고치고·결과를 보는 일이 전부 한 껍데기
안에서 일어난다 (007). 이 껍데기가 화면 사용 시간의 대부분을 차지하고, v1 잔재도 여기에 가장
많다 — 크림·골드 계열 색 대부분이 `WorkArea` · `ActionButton` · `PhaseBar` · `NoticeStack` 에
있다.

이 이야기가 끝나면 여덟 국면(만들기·녹화·AI 작성·AI 막힘·이어받기·실행·일시정지·실행 종료)과
편집 국면, Step 상세가 각자의 dc.html 과 같아진다.

**Why this priority**: 가장 큰 표면이고 잔재가 가장 많다. 다만 US1 이 세운 클래스 시트가
있어야 전사로 되돌아가지 않으므로 두 번째다.

**Independent Test**: 아홉 개 국면 각각을 제품에서 띄우고 대응 dc.html 과 대조한다. 국면
전환(만들기→녹화→실행→일시정지→이어받기→종료)을 한 번 완주해 정보가 사라지지 않았는지 본다.

**Acceptance Scenarios**:

1. **Given** 각 국면, **When** 화면을 연다, **Then** 껍데기 치수가 계약 표(`ui-contract.md` §1-2)와
   같다 — 헤더 56 · 국면 띠 48 · 알림 32 · 조작 32 · Step 행 52 · Step 패널 460 · 상세 겹침 640
2. **Given** Step 목록, **When** 통과·실패·실행 중·선택 상태의 행을 본다, **Then** 각 상태가
   왼쪽 마커와 바탕으로 구분되고 디자인의 `.srow` 변형과 같다
3. **Given** 어느 국면이든, **When** 알림·오류·확인 문구를 띄운다, **Then** `States.dc.html` 이
   정의한 형태와 문구 규칙을 따른다
4. **Given** 워크벤치를 그리는 컴포넌트들, **When** 색상 값을 센다, **Then** 0개다
5. **Given** 국면을 처음부터 끝까지 한 번 완주, **When** 각 국면에서 보이던 정보를 확인한다,
   **Then** 이전 판에서 보이던 정보·조작·문구가 하나도 사라지지 않았다

### User Story 3 - 남은 화면 여섯 장이 v2 로 보인다 (Priority: P3)

프로젝트 설정(제품의 첫 화면)·키 관리·비밀 값·결과 보기가 남는다. 이 중 셋은 v1 시절에 디자인
없이 구현됐고 008 에서 처음 디자인이 생겼다 (`replacement-map.md` §3).

**Why this priority**: 사용 빈도가 낮고 US1 의 클래스 시트를 그대로 소비하므로 마지막이다.
다만 프로젝트 설정은 **첫 실행 때 반드시 지나가는 화면**이라 빼면 안 된다.

**Independent Test**: 여섯 화면을 각각 띄우고 대응 dc.html 과 대조한다. 비밀 값 화면은 값이
가려진 상태가 유지되는지 함께 본다.

**Acceptance Scenarios**:

1. **Given** 프로젝트가 아직 없는 상태, **When** 제품을 처음 연다, **Then** `ProjectSetup.dc.html`
   과 같은 화면이 보인다
2. **Given** 키 관리·비밀 값 화면, **When** 화면을 연다, **Then** `Keys.dc.html`·`Secrets.dc.html`
   과 같고, 비밀 값은 여전히 가려진 채로 표시된다
3. **Given** 실패로 끝난 실행의 결과 화면, **When** 화면을 연다, **Then** `Result.dc.html` 과 같고
   실패 사유·시도한 locator 표·산출물이 이전과 같이 도달 가능하다
4. **Given** 이 여섯 화면의 코드, **When** 색상 값을 센다, **Then** 0개다

### User Story 4 - 다음번에 다시 어긋나지 않는다 (Priority: P4)

US1~US3 은 지금의 어긋남을 고친다. 이 이야기는 **같은 어긋남이 다시 생기지 않게** 한다.
화면 코드가 시각 언어를 우회하면 자동 검사가 멈추고, 대조표는 통계값 대신 디자인이 실제로
주장하는 규칙을 세며, 18장의 판정이 실제로 채워진다.

**Why this priority**: 앞의 셋이 끝나야 검사할 대상이 생긴다. 하지만 **이 이야기가 없으면 이번
작업은 세 번째 반복이 된다** — 001·002 가 같은 자리에서 미완으로 남았다 (V-11).

**Independent Test**: 화면 코드에 색상 값을 하나 일부러 넣고 검사를 돌린다. 검사가 실패하면
가드가 선 것이다. 대조표 18장에 `미판정`이 0건인지 센다.

**Acceptance Scenarios**:

1. **Given** 어느 화면 코드든, **When** 색상 값을 직접 적는다, **Then** 자동 검사가 실패하고
   어느 파일 어느 줄인지 알려준다 (V-09)
2. **Given** 디자인 파일이 바뀐다, **When** 검사를 돌린다, **Then** 기준값 추출이 먼저 멈춰
   기준과 코드가 함께 갱신되도록 강제한다
3. **Given** 대조표, **When** 축을 읽는다, **Then** `div 141개` 같은 통계값이 아니라 "행 결말은
   왼쪽 3px 마커로 표시한다" 같은 **디자인이 주장하는 규칙**이 항목이다 (V-10)
4. **Given** 대조표 18장, **When** 판정 칸을 센다, **Then** `미판정`과 `불일치`가 각각 0건이다 (V-11)

### Edge Cases

- **디자인에 대응 화면이 없는 상태를 만나면?** 로딩 중, 삭제 확인, 정의 파일 읽기 실패, 네트워크
  끊김, 세션 유실은 dc.html 18장 어디에도 없다. 없는 것을 지어내지 않되 화면은 비어 있을 수
  없으므로, v2 문법(클래스 시트)만으로 그리고 근거를 `undefined-states.md` 에 기록한다 (DC-009).
- **디자인이 정의한 색이 접근성 기준에 미달하면?** v2 팔레트는 대비비가 문서화돼 있다
  (`--ink-3` 4.6:1 등). 미달하는 조합이 발견되면 값을 임의로 바꾸지 않고 불일치로 기록한 뒤
  디자인 개정으로 처리한다 — 코드가 디자인을 조용히 고치는 것이 002 라운드가 만든 결함이었다.
- **한 화면이 여러 dc.html 에 걸치면?** 통합 작업 화면은 여덟 국면이 같은 껍데기의 상태다.
  껍데기는 한 벌이어야 하고(007 FR-229·SC-001), 국면별 대조는 그 한 벌의 상태를 본다.
- **잔존색이 의도적 예외였다면?** 17종 각각의 사용처를 확인해 판정한다. 예외로 남길 값은 근거와
  함께 등록하고, 등록되지 않은 예외는 없다 (FR-267).
- **디자인 파일을 브라우저에서 열 수 없으면?** `*.dc.html` 이 참조하는 `./support.js` 가 저장소에
  없다. 대조 절차가 실행 불가능하면 완료 판정 자체가 성립하지 않으므로, 대조에 쓸 수 있는
  경로를 먼저 확보한다 (FR-280).
- **화면 폭이 기준 1440 보다 좁으면?** 기존 최소 기준 폭 규칙을 그대로 유지한다. 이 기능은
  반응형 동작을 새로 정의하지 않는다.

## Requirements *(mandatory)*

FR 번호는 저장소 전체에서 이어진다. 007 이 FR-262 까지 썼으므로 FR-263 부터다.

### 시각 언어의 정본 (한 곳에만 둔다)

- **FR-263**: 시각 언어의 값(색·치수·간격·모서리·그림자·글꼴·상태 표현)은 **스타일 시트 한
  곳에만** 존재해야 한다. 화면 코드는 그 값을 다시 적지 않고 이름으로 참조한다 (V-01·V-02)
- **FR-264**: 확정 디자인이 정의한 재사용 형태는 **이름과 뜻을 그대로 유지한 채** 정본 시트에
  옮겨져야 한다. 대상은 dc.html 이 선언한 27종이다 — 조작(`.btn` 과 `primary`·`danger`·`off`·`sm`
  변형) · 상태 칩(`.chip` 과 `pass`·`fail`·`warn`·`run`·`ai` 변형) · Step 행(`.srow` 와
  `pass`·`fail`·`run`·`sel` 변형) · 패널(`.pane`) · 라벨(`.lbl`) · 껍데기 층(`.hdr`·`.phase`·
  `.notice`·`.body`·`.left`·`.steps`·`.steps-hd`) · 보조(`.mono`·`.why`) (V-01)
- **FR-265**: 화면 코드에 **색상 값을 직접 적을 수 없다.** 치수·글꼴·모서리·그림자도 정본이
  정의한 이름으로만 쓴다 (V-02·V-04·V-06)
- **FR-266**: 확정 디자인에 나타나지 않는 값을 정본에 추가할 수 없다. 값을 더하려면 먼저
  디자인에서 그 값을 찾아야 한다 (DC-001·DC-007 유지)
- **FR-267**: 정본을 벗어나야 하는 값은 **근거와 함께 예외로 등록**되어야 한다. 등록되지 않은
  예외는 존재할 수 없다

### v1 잔재 제거

- **FR-268**: v2 팔레트에 없는 색 17종이 제품 화면에서 **0개**가 되어야 한다 (V-03)
- **FR-269**: 잉크(`#14171C`)를 패널 테두리나 표 머리 바탕으로 쓸 수 없다. 패널 테두리는
  `--hair`, 조작 테두리는 `--hair-2` 다. **잉크 채움은 한 화면에 주 동작 하나**에만 쓴다 (V-04)
- **FR-270**: 글자 크기는 확정 디자인이 쓰는 단계(11·12·13px 중심)를 따라야 한다. 같은 뜻의
  글자가 디자인보다 크게 표시될 수 없다 (V-06)
- **FR-271**: 목록과 Step 목록의 행은 **왼쪽 3px 마커**로 결말을 나타내야 하며, 통과·실패·실행
  중·미실행·선택이 색과 형태를 함께 써서 서로 구분되어야 한다. 색만으로 구분하지 않는다 (V-05)
- **FR-272**: 확정 디자인이 정의한 요소를 뺄 수 없다. 목록 화면의 결말 필터 4종(전체·통과·실패·
  미실행)과 정렬 조작이 있어야 하며 실제로 목록에 작용해야 한다 (V-07·DC-007)
- **FR-273**: 표 머리와 행은 **같은 격자**를 공유해야 한다. 열 폭은 확정 디자인 값을 따른다 (V-08)

### 정보를 잃지 않는다

- **FR-274**: 이 기능으로 사용자에게 보이는 **정보·조작·문구가 하나도 사라지지 않아야 한다.**
  이번 작업은 시각 언어의 적용이지 기능 변경이 아니다
- **FR-275**: 기존 자동 검사가 **하나도 실패하지 않아야 한다.** 검사를 삭제·비활성화·약화해서
  통과시킬 수 없다 (헌법 품질 게이트 4)
- **FR-276**: 확정 디자인에 대응 화면이 없는 상태(로딩·확인·오류·유실 등)는 v2 문법만으로 그리고,
  **근거와 함께 기록**되어야 한다 (DC-009)
- **FR-277**: 비밀 값과 민감 입력의 가림 표시는 이 작업 전후로 달라지지 않아야 한다 (헌법 보안 제약)

### 우회를 자동으로 막는다

- **FR-278**: **화면 코드가 정본을 우회하면 자동 검사가 실패해야 한다.** 검사 대상은 화면을
  그리는 코드 전체이며, 일부 파일만 표본으로 보지 않는다 (V-09)
- **FR-279**: 검사 실패는 **어느 파일의 어느 줄인지** 알려주어야 한다. 수치만 보고하는 검사는
  고칠 곳을 알려주지 못한다
- **FR-280**: 확정 디자인 파일이 바뀌면 **기준값 추출이 먼저 멈춰야 한다.** 기준과 코드가 따로
  움직일 수 없다 (현행 동작 유지)

### 대조를 실제로 끝낸다

- **FR-281**: 대조표의 축은 **확정 디자인이 주장하는 규칙**이어야 한다. 요소 개수·색 등장 횟수
  같은 통계값은 규칙을 대신할 수 없다 (V-10)
- **FR-282**: 대조 항목은 **누가 판정하는지**를 명시해야 한다 — 기계가 셀 수 있는 항목과 사람이
  봐야 하는 항목을 구분한다. 사람이 봐야 하는 항목은 화면당 최소로 유지한다 (V-11)
- **FR-283**: 대조 절차가 **실행 가능해야 한다.** 확정 디자인 화면을 실제로 열어 볼 수 없으면
  대조는 성립하지 않는다
- **FR-284**: 확정 디자인 18장 전부에 대해 대조 판정이 채워져야 하며, `미판정`과 `불일치`가 각각
  0건이어야 한다 (V-11·DC-012)

### Key Entities

- **시각 언어 정본**: 색·치수·간격·기하·글꼴·상태 표현과 재사용 형태 27종의 유일한 정의처.
  확정 디자인 18장에서만 값을 받는다
- **확정 디자인**: `docs/design/008-visual-language/` 의 화면 18장. 코드가 따르는 기준이며 코드가
  고치지 않는다
- **대조표**: 화면 하나당 한 장. 축·기준값·관측값·판정·근거를 담는다. 완료 조건은 `미판정`·
  `불일치` 0건
- **예외 등록부**: 정본을 벗어나야 하는 값과 그 근거. 등록되지 않은 예외는 존재할 수 없다
- **미정의 상태 기록**: 확정 디자인에 대응 화면이 없는 화면 상태와 그 근거

## Success Criteria *(mandatory)*

SC 번호는 다른 기능과 겹치지 않는 구간을 쓴다 (001·004·007=0xx, 002=1xx, 003·005=2xx, 006=3xx).

### Measurable Outcomes

- **SC-401**: 확정 디자인 18장 전부에 대해 대조 판정이 채워지고 `미판정`·`불일치`가 각각 **0건**이다
- **SC-402**: 화면을 그리는 코드에서 **색상 값을 직접 적은 곳이 0개**다 (현재 327곳)
- **SC-403**: v2 팔레트에 없는 색이 제품 화면에서 **0종**이다 (현재 17종)
- **SC-404**: 시각 언어의 값이 **두 곳에 존재하지 않는다** — 정본 시트의 어떤 값도 화면 코드에
  중복해 적혀 있지 않다
- **SC-405**: 화면 코드가 정본을 우회하면 자동 검사가 **반드시 실패한다.** 일부러 위반을 심어
  검사가 실패하는 것을 확인한다
- **SC-406**: 이 기능 전후로 사용자에게 보이는 **정보·조작·문구의 가짓수가 줄지 않는다.** 목록·
  통합 작업 화면 아홉 국면·나머지 여섯 화면 각각에서 확인한다
- **SC-407**: 기존 자동 검사가 **전부 통과**한다. 기준선은 2026-09-08 커밋 `b033ee0` 의
  프런트엔드 검사 **50개 파일 · 657건 전부 통과**이며, 이 수보다 줄어들 수 없다. 삭제·
  비활성화된 검사가 0건이다
- **SC-408**: 확정 디자인이 정의한 요소 중 코드에 없는 것이 **0개**다 (현재: 목록 필터 4종·정렬
  조작이 없다)
- **SC-409**: 900px 높이 화면에서 Step 목록이 보여주는 행 수가 확정 디자인과 같다 (13행). v1 의
  5행에서 v2 가 노린 밀도가 실제로 나온다
- **SC-410**: 결말 네 가지(통과·실패·실행 중·미실행)가 색을 못 보는 상태에서도 서로 구분된다 —
  형태나 표식이 색과 함께 쓰인다

## Assumptions

기능 설명이 정하지 않은 것에 대해 아래를 전제했다. 전제가 틀리면 요구사항이 바뀐다.

- **판정 주체**: FR-284 의 완료 조건(미판정 0건)을 사람 리뷰어 대기로 두면 이번에도 미완으로
  남는다 — 001 T156 과 002 T099 가 같은 이유로 남았고 SC-108 은 지금도 미충족이다 (V-11).
  따라서 **대조 축을 기계가 셀 수 있는 규칙으로 최대한 옮기고**(FR-281·FR-282), 사람 눈이 반드시
  필요한 항목만 최소로 남겨 사용자가 판정하는 것으로 전제한다. 이 전제를 바꾸려면(예: 외부
  리뷰어 지정) 완료 조건도 함께 바꿔야 한다
- **디자인은 고치지 않는다**: 확정 디자인 18장은 이 기능의 입력이다. 코드가 디자인과 다르면
  코드를 고친다. 디자인 쪽 문제가 발견되면 불일치로 기록하고 별도 개정으로 넘긴다
- **동작 범위**: 기능 동작·API·데이터 모델·백엔드는 이 기능의 범위가 아니다. 화면이 무엇을
  보여주는지는 그대로고, 어떻게 보이는지만 바뀐다
- **필터·정렬의 동작**: FR-272 의 필터 4종과 정렬은 확정 디자인이 형태만 정의했다. 동작은 목록
  화면 안에서 즉시 반영되는 것으로 전제한다(서버 재조회 여부는 계획 단계에서 정한다)
- **반응형**: 최소 기준 폭 1440 규칙을 유지한다. 좁은 화면 대응은 이 기능이 새로 정의하지 않는다
- **_retired 디렉터리**: `docs/design/_retired/` 는 과거 판정을 다시 읽기 위한 기록이며 이 기능의
  기준이 아니다. 이 기능은 그 디렉터리를 참조하지 않는다
- **기준선 측정 시점**: 이 문서의 모든 수치(437·327·46·17·61·509 등)는 2026-09-08 커밋 `b033ee0`
  기준이다. 같은 시점의 프런트엔드 자동 검사는 50개 파일 · 657건이 전부 통과한다

## Out of Scope

- 반응형·모바일 화면 정의
- 다크 모드
- 새 화면·새 기능·새 조작의 추가 (확정 디자인에 있는데 코드에 없는 것을 채우는 것은 범위 안이다)
- 백엔드·API·데이터 모델 변경
- 확정 디자인 18장 자체의 개정
- `docs/design/_retired/` 정리
