# Feature Specification: shadcn/ui 부품 체계 전환과 화면 깨짐 전수 수정

**Feature Branch**: `feat/ui-component-style`

**Created**: 2026-09-14

**Status**: Draft

**Input**: User description: "현재 단순 tailwindcss 기반으로 작성된 ui들을 shadcn기반으로 모두 리팩토링하고 화면에 직접 접근해서 ui가 깨지는영역에 대해 모두 대응하도록 진행"

## 배경 — 무엇을 바꾸고 무엇을 바꾸지 않는가

### 이 명세가 여는 것

015 「Tailwind CSS 전환」은 FR-007 에서 **컴포넌트 라이브러리(shadcn/ui 등)를 도입하지 않는다**고
적었다. 017 은 그 문을 연다. 015 FR-007 은 이 명세로 대체된다.

지금의 부품 층은 `frontend/src/ui/` 의 손으로 만든 7개 파일(`Button`·`Chip`·`Field`·`Notice`·
`Surface`·`Table`·`StepRow`)이다. 화면 코드는 그것을 부르기도 하고(`<Button` 90곳·`<Chip` 37곳),
원시 요소를 직접 쓰기도 한다(`<button` 58곳·`<input` 59곳·`<select` 4곳·`<textarea` 7곳·
체크박스 7곳·라디오 4곳·대화상자 역할 5곳·표 5곳). 대화상자·메뉴·선택형 조작의 **동작**
(초점 이동과 가두기, Esc, 바깥 클릭, 화살표 이동)은 화면마다 따로 조립되어 있다.

### 2026-09-14 사용자 결정 — 모습은 바꾸지 않는다

1. **시각 언어는 008 정본 「계기판」을 유지한다.** shadcn/ui 는 **구조·동작 층**으로만 들인다.
   shadcn 이 쓰는 의미 토큰 이름은 정본 토큰을 **참조하는 별칭**으로만 존재한다. shadcn 기본
   모습 — 중립 팔레트, 큰 모서리, 흐림(opacity)으로 표현하는 비활성, 두꺼운 초점 링,
   36px 조작 높이 — 은 화면에 나타나지 않는다.
2. **speckit 절차로 진행한다** — spec → plan → tasks → implement → converge.

그래서 이 작업의 성공은 두 겹이다. **유지보수자**에게는 부품이 한 체계에서 오고 동작이
표준화된다. **제품 사용자**에게는 아래 「깨짐」이 사라지는 것 말고는 **아무 일도 일어나지
않는다.**

### 전환 전 실측 — 화면에서 확인한 깨짐

2026-09-14, 사용자 자산과 격리된 제품 인스턴스(임시 데이터 디렉터리·시드 테스트 6개·초안 1개·
픽스처 앱을 상대로 실제로 돌린 통과/실패 결과)를 띄우고 뷰포트 1280×800·1440×900·1920×1080·
2560×1440 에서 화면 13종을 열어 캡처하고, 조작 요소가 다른 요소에 덮이는지(중심점 판정)·
상자 밖으로 넘치는지·단어 중간에서 줄바꿈되는지를 쟀다. 검출기의 오탐(행 높이 계산·아이콘
기준선·의도된 겹침 패널)은 사람이 캡처를 보고 걸러냈다.

| # | 화면 | 깨짐 | 폭 | 영향 |

  의미 토큰은 정본 토큰의 별칭이다 (FR-006~FR-008).

## User Scenarios & Testing *(mandatory)*

"사용자"는 두 부류다. **제품 사용자**(ITB 화면으로 테스트를 만들고 고치는 사람)와
**유지보수자**(이 화면 코드를 고치는 사람).

### User Story 1 - 보이는 조작은 누를 수 있다 (Priority: P1)

제품 사용자가 결과·녹화·목록 화면에서 알림이 떠 있어도 국면 띠와 알림 띠의 조작을 누를 수
있다. 알림은 조작을 가리지 않는 자리에 뜬다.

**Why this priority**: B-01·B-02 는 사용자가 지금 겪는 **작업 차단**이다. 실패한 Step 부터 다시
돌리거나 녹화를 저장·중지하는 것이 이 제품의 핵심 흐름이고, 그 조작이 알림 밑에 깔린다.
부품 전환과 독립적으로 고칠 수 있고 가장 먼저 가치를 준다.

**Independent Test**: 결과 화면(실패 결과)과 녹화 화면(연결 끊김 알림)과 목록 화면(진행 중
세션)을 지원 폭 네 가지에서 열고, 국면 띠와 알림 띠의 조작 전부가 다른 요소에 덮이지 않는지
중심점으로 판정한다. 부품 전환이 하나도 되지 않았어도 이 확인은 성립한다.

**Acceptance Scenarios**:

1. **Given** 실패한 결과 화면에 「01~04 는 건너뜁니다」 알림이 떠 있고, **When** 사용자가
   「Step 05부터 실행」을 누르면, **Then** 알림이 아니라 그 조작이 눌린다.
2. **Given** 녹화 중 실시간 연결이 끊겨 알림이 떠 있고, **When** 사용자가 「저장」이나 「중지」를
   누르면, **Then** 그 조작이 눌린다.
3. **Given** 테스트 목록에 진행 중인 세션 띠와 세션 알림이 함께 있고, **When** 사용자가 띠의
   「이어서 보기」를 누르면, **Then** 그 조작이 눌린다.
4. **Given** 알림이 여러 개 쌓였고, **When** 화면 높이가 800px 이면, **Then** 알림 층은 조작 줄을
   덮지 않고 자기 영역 안에서 스크롤된다.

### User Story 2 - 부품이 한 체계에서 온다 (Priority: P2)

유지보수자가 버튼·입력·선택·체크박스·라디오·대화상자·메뉴·탭·칩·알림·표를 쓸 때, 그것은
shadcn/ui 방식의 부품 층 **한 곳**에서 온다. 부품의 모습은 008 정본이고, 동작(키보드·초점·
보조기술 알림)은 표준화된다. 제품 사용자에게는 모습이 달라지지 않는다.

**Why this priority**: 이 작업의 본체다. 다만 P1 은 이것 없이도 고칠 수 있으므로 뒤에 둔다.

**Independent Test**: 전환 전후 같은 데이터·같은 뷰포트에서 화면을 열고 계산된 스타일을
대조해 등록된 의도 차이 외에 차이가 없는지 확인한다. 화면 코드에서 원시 조작 요소에 직접
모양을 입힌 곳이 문서화된 예외 외에 없는지 센다. 대화상자와 메뉴를 키보드만으로 열고 닫는다.

**Acceptance Scenarios**:

1. **Given** 전환이 끝났고, **When** 유지보수자가 강조 버튼의 모습을 고치려 하면, **Then** 고칠
   곳은 부품 정의 한 곳이고 화면 코드 어디에도 그 버튼의 모양 값이 없다.
2. **Given** 삭제 확인 대화상자가 열렸고, **When** 사용자가 Tab 을 반복해 누르면, **Then** 초점이
   대화상자 밖으로 나가지 않고, Esc 를 누르면 닫히며 초점이 대화상자를 연 조작으로 돌아온다.
3. **Given** 테스트 행 메뉴(⋮)가 있고, **When** 사용자가 키보드로 메뉴를 열면, **Then** 화살표로
   항목을 오가고 Esc 로 닫을 수 있다.
4. **Given** 쓸 수 없는 조작이 있고, **When** 화면을 그리면, **Then** 그 조작은 감춰지지 않고
   점선 형태로 자리를 지키며 옆에 사유 문구가 남는다 (006 ui-contract §2).
5. **Given** 전환이 끝났고, **When** 부품을 화면에 그리면, **Then** 모서리·색·비활성 표현·초점
   링이 008 정본과 같고 shadcn 기본 모습의 흔적이 없다.

### User Story 3 - 깨진 배치가 사라진다 (Priority: P3)

제품 사용자가 지원 폭 어디서든 단어 중간에서 끊긴 조작 이름, 상자 밖으로 넘친 안내 문구,
쪼그라든 입력칸, 어긋난 표 머리를 보지 않는다. 편집 국면에서 Step 목록을 충분히 보고
패널의 모든 입력칸에 닿을 수 있다.

**Why this priority**: 작업을 막지는 않지만 신뢰를 깎는다 (B-03~B-11). 새 부품 층 위에서 고치면
같은 종류의 깨짐이 부품 정의 한 곳에서 막히므로 US2 뒤에 둔다.

**Independent Test**: 격리 인스턴스를 지원 폭 네 가지로 순회해 B-03~B-11 각각을 다시 재고,
전부 「고침」 또는 「사유가 적힌 의도된 예외」로 판정되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 1440×900 편집 국면에서 Step 이 17개이고, **When** 화면을 열면, **Then** Step 목록이
   8행 이상 보이고 시작 주소·AI 지시문 칸에 스크롤로 닿을 수 있다.
2. **Given** 만들기 국면에서 아직 브라우저를 열지 않았고, **When** 화면을 열면, **Then** 빈 미러
   자리의 안내 문구가 상자 안에 있다.
3. **Given** 테스트 두 개를 골랐고, **When** 선택 띠가 나타나면, **Then** 「2개 선택됨」이 한 줄이고
   「그룹으로 옮기기」 선택칸이 자기 쓰임에 맞는 폭이다.
4. **Given** 조작 이름이 자리보다 길고, **When** 화면을 그리면, **Then** 단어 중간에서 줄바꿈되지
   않고 말줄임으로 잘리며 전체 문구를 확인할 수단이 있다.
5. **Given** 1920·2560 폭이고, **When** 목록·작업·설정 화면을 오가면, **Then** 화면 종류마다
   정해진 넓은 창 정책 하나를 따른다 (FR-021).

### User Story 4 - 깨짐이 다시 들어오지 않는다 (Priority: P4)

유지보수자가 부품에 정본 밖 모서리·색·흐림 비활성·기본 초점 링을 넣거나, 화면 코드가 원시
조작 요소에 직접 모양을 입히면 자동 테스트가 먼저 막는다. 화면 깨짐 점검은 한 번의 명령으로
반복할 수 있다.

**Why this priority**: 015 가 겪었듯 전환은 「한 번 정리했다」로 끝나면 다음 개정에서 무너진다
(2026-09-11 「버튼과 글자가 모두 흰색」). US2·US3 의 결과를 지키는 장치다.

**Independent Test**: 부품 하나에 shadcn 기본 모서리 값을 일부러 넣고 자동 테스트가 실패하는지
확인한 뒤 되돌린다. 화면 깨짐 점검을 다시 돌려 같은 결과가 나오는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 가드가 갱신되어 있고, **When** 누군가 부품에 정본에 없는 모서리 값이나 흐림 비활성을
   넣으면, **Then** 자동 테스트가 실패한다.
2. **Given** 가드가 갱신되어 있고, **When** 화면 코드에 모양을 입힌 원시 `<button>` 이 새로
   들어오면, **Then** 자동 테스트가 실패한다 (문서화된 예외 제외).
3. **Given** 점검 절차가 있고, **When** 유지보수자가 그것을 실행하면, **Then** 대상 화면 목록·폭·
   검출 결과·캡처가 남는다.

### Edge Cases

- **정본 요소 규칙이 새 부품으로 번진다** — 정본은 `button{}`·`input,select,textarea{}`·`label{}`
  에 높이·테두리·그림자·대문자 모노 라벨을 준다. 새 부품이 내부적으로 `<button>`(체크박스·
  선택 트리거·탭)이나 `<label>` 을 쓰면 그 규칙을 받는다. B-08 이 이미 이 형태로 보인다.
- **부품이 문서 밖(포털)에 그려진다** — 대화상자·메뉴·선택 목록이 `#root` 밖에 붙으면 겹침
  순서가 토스트 층(z 60)·Step 상세 겹침·가림막과 다투고, 렌더 컨테이너 안만 뒤지는 기존
  테스트가 요소를 찾지 못한다.
- **미러 입력** — 대화상자가 열려 초점을 가두는 동안 미러로 키 입력이 새면 대상 앱에 조작이
  기록된다. 반대로 대화상자가 없을 때 초점 관리가 미러의 IME 칸(`.ime-capture`)을 빼앗으면
  한글 입력이 끊긴다 (010 · `DetailBlocksMirrorInput`).
- **비활성 조작의 사유** — shadcn 기본 비활성은 흐림 + 포인터 차단이다. 포인터 차단은 사유를
  담은 툴팁·title 을 막는다. 이 제품은 비활성을 점선으로 말하고 사유를 옆에 둔다.
- **네이티브 선택칸을 대체할 때** — 키보드 선택·첫 글자 검색·폼 값 제출이 약해지면 안 된다.
  기존 테스트가 네이티브 선택 조작으로 판정하는 곳이 있다.
- **한국어 줄바꿈** — 한국어는 기본 규칙에서 글자 단위로 끊긴다 (B-07 「선 / 택됨」). 자르기와
  전체 문구 확인 수단이 함께 있어야 한다.
- **긴 값** — 200자 테스트 이름, 50 Step, 긴 그룹 이름, 시트 200개 가져오기, 알림 여러 개 동시.
- **넓은 창과 좁은 창** — 2560 폭에서 빈 공간, 1280 폭(1440 미만)에서 가로 스크롤과 초점 이동에
  따른 밀림 (B-11). 브라우저 확대 125%·150% 는 CSS 폭이 줄어드는 것과 같다.
- **움직임** — shadcn 부품은 열림·닫힘 애니메이션을 기본으로 갖는다. 정본에는 움직임 언어가
  없다.
- **아이콘** — shadcn 은 아이콘 묶음을 전제로 한다. 지금 화면은 글자 기호(↑ ↓ + × ⋮ ▶ ✓)를 쓴다.
- **테스트가 붙잡는 통로** — `data-variant`·`data-tone`·`data-row-menu`·`data-phase-pill` 같은
  속성과 접근 가능한 이름이 새 부품에서도 **실제로 그려지는 요소**에 남아야 한다.
- **jsdom** — 표준 동작 부품은 jsdom 에 없는 포인터 캡처·`ResizeObserver`·`scrollIntoView` 를
  부른다. 테스트 환경이 그것을 채우지 않으면 테스트가 부품이 아니라 환경 때문에 실패한다.

## Requirements *(mandatory)*

### Functional Requirements

**부품 체계**

- **FR-001**: 조작·표시 부품 — 버튼, 텍스트 입력, 여러 줄 입력, 선택, 체크박스, 라디오, 대화상자,
  메뉴, 탭·분절 선택, 칩, 알림·토스트, 표, 툴팁 — 은 shadcn/ui 방식의 부품 층 **한 곳**에서 온다.
- **FR-002**: 화면 코드는 원시 조작 요소(`button`·`input`·`select`·`textarea`·체크박스·라디오·
  대화상자 역할)에 직접 모양을 입히지 않는다. 예외(미러의 IME 칸, 보이지 않는 파일 입력,
  미러 면처럼 부품이 될 수 없는 것)는 사유와 함께 한 곳에서 셀 수 있어야 한다.
- **FR-003**: 전환이 끝나면 옛 부품 층(`frontend/src/ui/` 의 손으로 만든 부품)과 새 부품 층이
  **공존하지 않는다.** 같은 종류의 부품 정의는 하나다 (015 SC-010 계승).
- **FR-004**: 부품의 변종(강조·위험·비활성·조용함, 크기, 상태 색)은 부품의 변종 표에서만 정한다.
  한 요소에 같은 속성이 두 번 붙어 **나중에 적은 쪽이 지는** 경우가 없어야 한다 (015 G-E 계승).
- **FR-005**: 기존 테스트와 실측이 붙잡는 통로 — `data-*` 속성, 역할, 접근 가능한 이름 — 는 새
  부품에서도 실제로 그려지는 요소에 남는다.

**시각 언어 보존**

- **FR-006**: 부품의 모습은 008 정본을 따른다 — 모서리 3px·2px·6px, 조작 높이 32px·26px, 정본
  팔레트, IBM Plex Sans KR·IBM Plex Mono, 자리를 지키는 점선 비활성, 2px 실행색 초점 윤곽선.
- **FR-007**: shadcn 의미 토큰 이름을 쓰는 곳의 값은 정본 토큰 **참조**뿐이다. 새 값 0 (015 FR-001·
  `TailwindThemeLiteral` 계승).
- **FR-008**: shadcn 기본 모습(중립 팔레트, 정본 밖 모서리, 흐림 비활성, 두꺼운 초점 링, 36px 조작
  높이)이 화면에 나타나지 않는다.
- **FR-009**: 정본 파이프라인(`extract_canon.py` → `tokens.css` → `split-canon.mjs` →
  `tokens.app.css`)과 정본 파일의 정본 구획은 바뀌지 않는다. L1 대조가 계속 통과한다.
- **FR-010**: 정본에 없는 움직임·아이콘 묶음·다크 모드를 새로 들이지 않는다. 부품이 요구하는
  표식(체크 표시·펼침 표시)은 지금 화면이 쓰는 기호 수준에서 표현한다.

**동작과 접근성**

- **FR-011**: 대화상자는 열리면 초점을 안으로 옮기고 가두며, Esc 로 닫히고(되돌릴 수 없는 조작을
  실행하지 않고 닫는다), 닫히면 초점을 연 조작으로 되돌린다.
- **FR-012**: 메뉴는 키보드로 열고, 화살표로 항목을 오가고, Esc·바깥 클릭으로 닫힌다.
- **FR-013**: 선택형 조작(탭·분절 선택·라디오·체크박스)은 현재 상태를 보조기술에 알린다.
- **FR-014**: 쓸 수 없는 조작은 감추지 않고 사유 문구가 옆에 남는다. 비활성 상태가 사유 확인
  수단을 막지 않는다 (006 ui-contract §2).
- **FR-015**: 키보드 초점 표시가 사라진 조작 요소가 없다 (015 SC-008 · `FocusRing` 계승).
- **FR-016**: 대화상자·Step 상세 겹침이 떠 있으면 미러로 입력이 새지 않고, 떠 있지 않으면 미러의
  클릭·스크롤·한글 조합 입력이 전환 전과 같이 동작한다 (010).
- **FR-017**: 선택 부품의 키보드 선택·첫 글자 이동이 전환 전보다 약해지지 않는다.

**화면 깨짐**

- **FR-018**: 지원 폭에서 보이는 조작 요소가 다른 요소에 덮여 누를 수 없는 경우가 없다. 대화상자와
  겹침 패널이 **의도적으로** 가리는 뒤쪽은 제외하며, 그 제외는 판정 절차에 명시된다.
  - **FR-018a**: 알림 층은 머리띠와 국면 띠의 조작을 덮지 않는다 (B-01).
  - **FR-018b**: 알림은 흐름 안 알림 띠의 조작을 덮지 않는다. 흐름 안 띠가 이미 같은 사실을 말하면
    알림이 같은 사실을 되풀이하지 않는다 (B-02).
- **FR-019**: 조작·라벨·칩·표 머리의 한국어 문구는 단어 중간에서 줄바꿈되지 않는다. 자리가 모자라면
  말줄임으로 자르고 전체 문구를 확인할 수단을 둔다 (B-05·B-07).
- **FR-020**: 상자 안의 안내 문구는 상자 밖으로 넘치지 않는다 (B-04). 입력칸은 쓰임에 맞는 최소
  폭 아래로 줄지 않고, 선택칸은 남은 폭 전체로 늘어나지 않는다 (B-06·B-07).
- **FR-021**: 넓은 창(1440 초과)에서 화면 종류마다 정책이 하나로 정해지고 문서화된다 (B-10).
  정책은 둘뿐이다 (2026-09-14 사용자 결정):
  - **데이터 화면은 창 폭을 채운다** — 테스트 목록·초안·가져오기 미리보기와 작업 화면(만들기·녹화·
    실행·일시정지·편집·결과). 늘어난 폭은 가변 칸(이름·대상 앱 영역)이 가져가고 고정 칸(Step 패널
    460px 등)은 그대로다.
  - **폼 화면은 읽기 좋은 폭으로 가운데 선다** — 프로젝트 목록·프로젝트 만들기·비밀 값·키 관리.
- **FR-022**: 좁은 창(1440 미만)에서는 재배치하지 않고 스크롤한다는 DC-011 을 유지하되, 조작에
  초점이 가서 가로로 밀린 화면이 머리띠를 창 밖에 남기지 않는다 (B-11).
- **FR-023**: 1440×900 편집·만들기 국면에서 Step 목록이 8행 이상 보이고, Step 패널의 모든 입력칸에
  스크롤로 닿을 수 있다 (B-03).
- **FR-024**: 같은 종류 요소는 한 화면 안에서 같은 크기다 (B-08). 표의 머리 칸과 본문 칸은 같은 열에
  서고, 머리 글꼴은 표 안에서 한 가지다 (B-09).

**검증**

- **FR-025**: 화면 깨짐 점검은 반복 가능한 절차다 — 사용자 자산과 격리된 인스턴스, 시드 데이터,
  지원 폭 네 가지, 대상 화면 목록. 실행하면 검출 결과와 캡처가 남는다.
- **FR-026**: 전환 전 실측 깨짐(B-01~B-11)과 전환 중 새로 찾은 깨짐 각각에 「고침」 또는 「사유가
  적힌 의도된 예외」 판정이 남는다.
- **FR-027**: 위 깨짐 수정과 FR-011~FR-013 의 동작 개선을 뺀 나머지 화면은 전환 전후 모습이 같다.
  확인은 계산된 스타일 대조로 하고, 차이는 사유와 함께 등록해야만 허용된다 (015 L2 계승).
- **FR-028**: 기존 프론트엔드 자동 테스트는 전량 통과한다. 판정 방법을 바꿔야 하는 테스트는
  **무엇을 검증하던 테스트인지가 바뀌지 않는 선에서만** 고치고, 무엇을 왜 고쳤는지 남긴다
  (헌법 Quality Gate 4).
- **FR-029**: 부품에 정본 밖 모서리·색·흐림 비활성·기본 초점 링이 들어오면 자동 테스트가 실패한다.
- **FR-030**: 화면 코드에 모양을 입힌 원시 조작 요소가 새로 들어오면 자동 테스트가 실패한다
  (FR-002 예외 제외).
- **FR-031**: 배포 산출물이 과하게 늘지 않는다 — 스타일 산출물은 전환 전 대비 10% 이내,
  스크립트 산출물은 30% 이내(압축 기준). *2026-09-15 plan 단계에서 25% → 30% 로 고쳤다 — 실측 근거는
  research R12.*

### Key Entities

- **부품 (Primitive)**: 버튼·선택·대화상자처럼 화면이 조립에 쓰는 단위. 구조와 동작은 표준 동작
  부품에서, 모습은 정본 스킨에서 온다. 종류마다 정의가 하나다.
- **정본 스킨 (Canon Skin)**: shadcn 의미 토큰 이름 → 정본 토큰의 대응. 값이 없고 참조만 있다.
- **원시 요소 예외 (Raw Element Exception)**: 부품이 될 수 없어 원시 요소에 모양을 입힌 자리.
  사유와 함께 집계된다.
- **깨짐 기록 (Breakage Record)**: 화면·폭·종류(덮임·넘침·줄바꿈·잘림·정책)·요소·판정
  (고침/의도된 예외)·사유.
- **의도된 차이 (Intended Difference)**: 전환 전후 대조에서 허용된 시각 차이. 사유 없이 등록할 수
  없다.

## Assumptions

- **대상은 데스크톱 로컬 도구다.** 지원 폭은 1280~2560, 높이 800~1440 으로 본다. 1440 은 확정
  디자인의 기준 폭이고(DC-011), 1280 은 흔한 노트북 폭이자 1600 창을 125% 확대한 폭이다.
  휴대폰·태블릿은 범위 밖이다.
- **「8행」은 판단값이다.** 전환 전 편집 국면은 1440×900 에서 6~7행이었고, 확정 디자인은 52px 행을
  「900px 창에서 13행」으로 설계했다. 조작 영역을 남기면서 닿을 수 있는 하한으로 8을 둔다.
- **shadcn/ui 는 부품 원본을 저장소 안으로 가져와 고치는 방식이다.** 표준 동작 부품(대화상자·메뉴·
  선택 등의 동작 층)은 실행 의존성으로 들어온다. React 를 대체하지 않으므로 헌법 Stack 조항의 교체가
  아니라고 보며, `plan.md` Constitution Check 에서 명시적으로 다룬다.
- **015 의 가드와 대조 장치는 유지·확장한다** — G-A~G-E, L1, L2. 부품 층이 바뀌어도 그 가드가 막던
  사고(값 복제·흰 버튼·의미 클래스 혼용)는 그대로 막는다.
- **알림 문구·화면 문구는 바꾸지 않는다.** 줄바꿈·잘림을 고치기 위한 표시 방식만 바꾼다. 문구 변경이
  필요해 보이면 기록하고 남긴다.
- **화면 깨짐 점검 도구는 제품 기능이 아니라 개발 검증 절차다.** 헌법이 범위 밖으로 둔 「visual
  regression」 은 제품이 사용자에게 제공하는 기능을 말하며, 이 절차와 무관하다.
- **관측했으나 범위 밖**: 프로젝트가 열리지 않은 상태의 `/api/project` 404 와 결과가 없는 테스트의
  결과 조회 404 가 브라우저 콘솔 오류로 찍힌다. 화면 깨짐이 아니라 요청 계약의 문제이므로 017 에서
  다루지 않는다.
- **범위 밖**: 디자인 변경(깨짐 수정 제외), 새 화면, 다크 모드, 새 움직임 언어, 아이콘 묶음 도입,
  백엔드 변경.
