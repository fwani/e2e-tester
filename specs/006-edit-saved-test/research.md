# Phase 0 조사 — 저장된 테스트를 고치는 길

**Feature**: 006-edit-saved-test | **Date**: 2026-09-07

명세의 미확정 사항과 설계가 갈리는 지점만 다룬다. 각 항목은 결정 · 근거 · 기각한 대안으로
적는다. 근거는 모두 이 저장소의 실제 코드를 읽어 확인한 것이다.

---

## R1. 편집 화면 — 새 화면인가, 정의 보기 화면이 편집 가능해지는가

**결정**: **정의 보기 화면(`TestDefinition`)이 편집 가능해진다.** 새 화면을 만들지 않는다.

**근거**

- 그 화면은 이미 저장된 정의를 읽어 Step 목록·Step 상세·locator 후보 표를 그린다
  (`frontend/src/pages/TestDefinition.tsx`). 편집에 필요한 표시의 대부분이 이미 있다.
- FR-179 가 "어느 진입점으로 들어와도 같은 화면" 을 요구한다. 편집 화면을 새로 만들면
  「정의 보기」와 「편집」이 같은 것을 두 벌로 그리게 되고, 진입점 3개(목록·결과·정의 보기)가
  서로 다른 화면으로 갈 위험이 생긴다.
- 그 화면의 파일 머리 주석이 존재 이유를 이렇게 적어 두었다 — "실행하지 않고 볼 수 있어야
  한다. 이 화면이 생기기 전에는 Step 목록과 후보를 보려면 재실행 세션을 시작해야 했다."
  편집도 정확히 같은 논리의 연장이다.

**기각한 대안**

- *새 `EditTest` 화면*: 표시 코드 중복. 「보기」와 「편집」 사이를 오가는 전환도 사용자에게
  의미 없는 단계다 — 사용자는 "고치려고" 들어온다.
- *모달·인라인 편집만*: locator 후보 표와 Step 상세를 함께 봐야 하므로 좁은 모달에 맞지 않다.

**따르는 것**: 화면은 하나이고 **모드가 둘**이다 — 읽기 전용(실행 중이거나 정의가 깨졌을 때)과
편집 가능. 모드 전환은 화면 이동이 아니다.

## R2. 편집 연산 — 어디에 두는가

**결정**: **기존 `itb.execution.step_edits` 를 그대로 쓴다.** 새 편집 모듈을 만들지 않는다.

**근거**

그 모듈은 이미 브라우저를 모른다. 파일 머리 주석이 그 제약을 명시한다 —

> 이 모듈은 브라우저를 알지 못한다. Playwright 를 임포트하지 않고, 세션도 받지 않는다.
> 받는 것은 Step 목록과 실행 위치뿐이고, 돌려주는 것은 새 목록·새 위치·경고 목록이다.

즉 **세션 없는 편집에 필요한 핵심은 이미 존재하며 순수하다.** 세션 라우터
(`routes/steps.py`)가 하는 일은 요청 검증 · 세션 반영 · 이벤트 발행 세 가지뿐이고, 연산은
이 모듈에 있다. 정의 편집 경로는 같은 함수를 부르고 "세션 반영" 자리에 "파일 저장"을 놓는다.

**기각한 대안**: *정의용 편집 모듈 신설* — 같은 규칙(순서 목록 불일치 거절, 값을 갖지 않는
Step 종류 거절, id 재사용 회피)을 두 벌 유지하게 된다. 사용자 지시("두 벌로 만들지 말 것")와
헌법 원칙 I 의 취지에 정면으로 어긋난다.

## R3. 저장 API 형태 — 무엇을 실어 보내는가

**결정**: **저장 요청은 편집 결과가 아니라 편집 연산 목록을 실어 보낸다.** 초안은 화면이
연산 목록으로 들고, 저장은 `PUT` 한 번이다. 서버는 저장된 정의를 읽어 그 연산을
**`step_edits` 로 적용**하고, 결과를 검증한 뒤 원자적으로 쓴다.

- `GET /api/tests/{test_id}/definition` → `{ test, revision, editable, blocked_by }`
- `PUT /api/tests/{test_id}/definition` → `{ revision, name?, edits: [...] }`

**근거 — 전체 결과를 보내면 규칙이 두 벌이 된다**

처음에는 `{ name, steps }` 로 편집된 정의 전체를 보내는 안을 택했다. 그것을 쓰면 **편집
규칙의 구현이 프론트로 넘어간다** — 어느 Step 종류가 입력값을 갖는지(`ValueNotSupportedError`),
순서 목록이 현재 집합과 일치해야 한다는 것(`ReorderMismatchError`), Step id 를 어떻게
재사용하지 않는지(`allocate_step_id`)를 프론트가 스스로 지켜야 하고, 서버는 결과만 본다.
그것이 정확히 사용자가 금지한 "두 벌" 이고 R2 에서 피하려던 것이다.

연산 목록을 보내면 **`step_edits` 가 실제로 유일한 구현이 된다.** 서버가 규칙의 주인이고,
프론트는 화면에 미리보기를 그릴 뿐 규칙을 판정하지 않는다.

**근거 — 서버에 초안 상태를 만들지 않는다**

연산 목록은 클라이언트가 든다. 저장 전 상태를 서버에 두면 새 서버 상태(초안 저장소)가 생기고,
그것은 "저장하지 않은 것" 을 저장하는 자기모순이다. 연산이 곧 변경 단위이므로 FR-189(변경
건수)와 FR-190(개별 되돌리기)이 자연스럽게 따라온다 — 되돌리기는 그 연산을 목록에서 빼는 것이다.

**근거 — 실행 위치가 없으므로 경고가 사라진다**

`step_edits` 는 `current_step_index` 로 "이미 실행된 구간을 고쳤다" 경고를 만든다. 정의 편집에는
실행 위치가 없으므로 `current_step_index=0` 으로 부른다 — 어떤 인덱스도 그보다 앞일 수 없어
경고가 하나도 생기지 않는다. **그 모듈을 고치지 않고 그대로 쓸 수 있다.**

**기각한 대안**

- *편집 결과 전체를 `PUT`*: 위의 이유로 기각.
- *`POST/PATCH/DELETE /api/tests/{id}/steps/...` 연산별 개별 엔드포인트*: 라우터 표면이 두 벌이
  된다. 게다가 저장 시점이 흩어져 "저장하지 않은 변경" 이라는 개념 자체가 성립하지 않는다
  (FR-189·FR-208 이 요구하는 것을 만들 수 없다).
- *`PATCH /api/tests/{id}` 확장*: 지금 이름 변경 전용이며 응답이 `Test` 다. 여기에 편집을
  실으면 기존 호출자의 계약이 흔들린다. 새 경로를 두고 기존 것은 건드리지 않는다.

**따르는 작은 변경**: `update_step()` 에 `tab` 인자를 더한다 (FR-183 이 대상 탭 수정을 요구한다).
지금은 `label`·`value`·`timeout_ms` 만 받는다. 편집 핵심이 한 곳이므로 인자를 그곳에 더하는
것이 맞다 — 정의 경로만을 위한 분기를 만들지 않는다. 세션 라우터의 요청 모델은 건드리지 않으므로
세션 경로의 계약은 그대로다.

## R4. 외부 변경 감지 — 무엇을 revision 으로 쓰는가

**결정**: **정의 파일 내용의 SHA-256 해시**를 `revision` 으로 쓴다. `GET` 이 실어 주고 `PUT`
이 되돌려 보내며, 불일치면 `409` 로 거절하고 현재 내용을 함께 준다.

**근거**

- 사용자가 편집기로 YAML 을 직접 고치는 것은 이 제품에서 정상 사용이다 — 헌법 원칙 V 가
  정의를 사람이 읽는 평문으로 두고 사용자의 버전 관리에 맡기는 이유가 그것이다. 따라서
  "내가 읽은 뒤에 파일이 바뀌었는가" 는 실제로 일어나는 일이다.
- 해시는 파일시스템에 의존하지 않는다. 내용이 같으면 같고 다르면 다르다.

**기각한 대안**

- *mtime*: 해상도(초 단위 파일시스템)와 복사·체크아웃으로 실제 변경 없이 바뀐다. 거짓 충돌은
  사용자가 곧 무시하게 되고, 그러면 감지 자체가 무의미해진다.
- *감지하지 않고 항상 덮어쓰기*: 사용자의 직접 수정을 조용히 지운다. FR-209 위반.

## R5. 변수 파생 로직 — 어디에 두는가

**결정**: `routes/sessions.py` 의 `_variables_for()` 를 **순수 함수로 도메인 계층에 옮기고**
세션 저장과 정의 저장이 그것을 함께 쓴다.

**근거**

그 함수는 이미 미묘한 판정을 담고 있다 — 불러온 정의의 변수를 출발점으로 삼고, 이 세션에서
포착한 민감 값과 비밀 파일의 봉인 이름을 보고 민감 여부를 정한다. 함수 주석이 그 이유를 적어
두었다: "세션에서 새로 포착한 것만 보면, 불러온 테스트의 민감 변수가 비민감·빈 값으로
강등되어 재실행이 빈 값을 채운다 (FR-082 위반이자 조용한 실패다)."

정의 편집도 값을 고치면서 `{{NAME}}` 참조를 새로 만들거나 없앨 수 있다. 같은 판정이 필요하고,
**두 벌이면 한쪽에서 민감 표시가 강등된다** — FR-214 가 막으려는 바로 그것이다.

**기각한 대안**: *정의 저장에서는 변수 목록을 그대로 둔다* — 참조를 새로 만든 편집이 변수
정의에 반영되지 않아 실행 시 빈 값으로 조용히 실패한다 (FR-216 이 경고로 알리려는 상황을
경고조차 낼 수 없게 된다).

## R6. FR-187(후보 우선순위 선택) — **범위에서 제외한다**

**결정**: **FR-187 을 이 기능의 범위에서 뺀다.** 그 필요는 US3 의 「다시 집기」(살아 있는
브라우저)로 충족한다. 명세를 수정해 제외를 명시한다.

**근거 — 헌법 충돌**

헌법 원칙 IV 는 해석 순서를 MUST 로 고정한다.

> Resolution MUST follow this priority order:
> `testId` → `role` + accessible name → `label` → `text` → stable attribute → CSS.

코드도 그렇게 되어 있다 — `backend/src/itb/locator/strategy.py` 의 `PRIORITY` 튜플이
"제품 내 실행과 생성 코드 양쪽의 유일한 기준" 이다. **Step 마다 우선순위를 뒤집는 것은 이
MUST 를 어기는 것**이고, 원칙 IV 를 고치는 것은 기능 결정이 아니라 헌법 개정 절차의 대상이다.

**근거 — 거짓 VERIFIED 문제**

같은 파일의 `_strategy_for()` 는 **`status` 가 `VERIFIED` 인 후보만** 전략으로 만든다.
따라서 사용자가 후보 값을 손으로 고쳐도, 상태가 `VERIFIED` 가 아니면 실행에 쓰이지 않는다.
브라우저 없이 검증할 방법은 없다. 그러므로 선택지는 둘뿐이다.

1. 손으로 넣은 값을 `VERIFIED` 로 적는다 → **거짓말이다.** FR-019a("후보 상태는 기록 시점
   검증 결과")를 부수고, SC-008(사용 가능 후보 수) 측정을 부풀린다. `Candidate.usable` 주석이
   "`AMBIGUOUS` 를 사용 가능으로 세면 SC-008 측정이 부풀려진다" 고 적어 둔 것과 같은 종류의
   오염이다.
2. `VERIFIED` 가 아닌 상태로 남긴다 → 사용자는 고쳤다고 믿는데 실행은 그 값을 쓰지 않는다.
   **조용한 무효 편집**이다.

둘 다 이 명세가 없애려는 문제(화면이 말하는 것과 실제가 다름)를 새로 만든다.

**그러면 사용자의 필요는 어디서 채우는가**: US3 의 「브라우저 열어 Step nn 에서 멈추기」 →
다시 집기. 그 경로는 실제 요소에서 후보를 다시 수집하고 검증하므로 원칙 IV 를 지키면서 목적을
달성한다. FR-202 가 요구하는 "왜 브라우저가 필요한지" 의 답이 이것이며, 편집 화면은 그 이유를
locator 표 자리에서 밝혀야 한다.

**명세 반영**: `spec.md` 의 FR-187 을 「범위에서 제외」로 표시하고 이유와 대체 경로를 적었다.
FR-191(편집 불가 항목을 시각적으로 구분) 이 이 결정을 화면에서 정직하게 만든다.

## R7. 「브라우저 열어 Step nn 에서 멈추기」 — 어떻게 그 지점에서 멈추는가

**결정**: 세션 생성 요청에 `pause_before_index` 를 더한다. 러너는 선행 Step 을 **실행한 뒤**
그 인덱스 **직전**에서 기존 `PAUSED` 상태로 들어간다. 새 상태·새 모드를 만들지 않는다.

**근거**

- 다시 집기는 그 Step 이 다루는 요소가 **화면에 있어야** 성립한다. 아무것도 실행하지 않고
  멈추면 로그인 전 화면에서 대시보드 요소를 집으라는 말이 된다. 그래서 선행 Step 은 실행한다.
- 멈춤 지점이 "실행한 뒤" 가 아니라 "직전" 인 이유: 고치려는 Step 은 대개 **실패하는 Step**
  이다. 실행한 뒤에 멈추면 고치기 전에 실패가 먼저 난다.
- 붙일 자리가 이미 있다. `RunEngine._pace(next_index)` 가 Step 경계마다 불리고, 004 의
  `한 스텝씩`(`auto_pause(pacing)`)이 바로 여기서 `Command.PAUSE` 를 적용한다. 목표 인덱스
  비교를 같은 자리에 두면 **같은 경계·같은 상태 전이**를 쓴다.

**기각한 대안**

- *`한 스텝씩` 속도로 실행하게 안내*: 지금도 가능하지만 사용자가 Step 06 까지 다섯 번
  「계속하기」를 눌러야 한다. 게다가 속도 취향을 바꿔 버린다(FR-109 로 다음 실행에 유지된다).
- *새 세션 모드 `edit`*: 상태 기계에 새 상태가 늘어난다. 005 research R7 이 같은 이유로 새
  상태 추가를 기각했고, 그 판단을 흔들 이유가 없다.

## R8. 저장하지 않은 초안의 보관 — 새로고침을 넘겨 살릴 것인가

**결정**: 초안은 **화면 메모리에만** 둔다. 화면을 떠나는 조작(앱 안 이동)은 인앱 확인으로,
새로고침·탭 닫기는 브라우저 기본 이탈 확인으로 막는다. 브라우저 저장소에 초안을 넣지 않는다.

**근거**

- 정의 파일이 유일한 진실이다(원칙 I·V). 브라우저 저장소에 남은 낡은 초안은 그 뒤 파일이
  바뀌면 **어느 쪽이 맞는지 화면이 말할 수 없는 상태**를 만든다. R4 의 충돌 감지가 저장
  시점에만 작동하므로, 초안을 오래 살려 둘수록 충돌이 늘고 사용자가 그 대화를 무시하게 된다.
- FR-208 이 요구하는 것은 "조용히 버리지 않는 것" 이다. 이탈 확인이 그것을 만족한다.

**기각한 대안**: *`localStorage` 에 테스트별 초안 보관* — 위의 이유. 민감 값 평문이 초안에
들어갈 일은 없지만(참조만 다룬다, FR-212), 그 사실과 무관하게 진실이 둘이 되는 것이 문제다.

## R9. 실행 중 판정 — 무엇을 근거로 거절하는가

**결정**: `state.sessions.reservation_for_test(test_id)` 를 그대로 읽는다. 새 판정 기준을
만들지 않는다.

**근거**

005 가 이미 이 예약을 세션 생성 경계의 유일한 기준으로 세웠고(FR-128, 락 안에서 확인·예약),
거절 응답의 형태(`SESSION_ALREADY_ACTIVE` + `next_action` + `session_id`)도 정해져 있다.
편집 거절은 같은 형태를 쓴다 — 프론트의 「실행 중인 세션 보기」 버튼이 `error.sessionId` 하나로
동작하므로(`App.tsx`) 화면 쪽 추가 작업이 거의 없다.

**하지 말 것**: "열린 세션이 있는가" 를 별도로 세는 것. 재점검 리포트 N-02 가 그 결과였다 —
목록 행 배지가 저장된 결말이 아니라 열린 세션의 존재를 보고 있어서 배너와 다른 말을 했다.

## R10. 민감 값 — 편집 화면이 다룰 수 있는 범위

**결정**: 편집 화면은 **참조 문자열(`{{NAME}}`)만** 다룬다. 평문 리터럴로 바꾸는 편집을
거절하고, 값 자체는 비밀 값 화면으로 보낸다. 세션 편집의 민감화 경로
(`PatchStepRequest.sensitive`)는 세션 전용으로 남긴다.

**근거**

- 그 경로는 공개키와 `SecretStore` 가 필요하다(평문을 참조로 옮기고 봉인한다). 정의 편집에는
  평문이 애초에 없으므로 옮길 것이 없다.
- FR-212·FR-215 가 요구하는 것은 평문이 편집 화면·요청·로그에 나타나지 않는 것이다. 참조만
  다루면 그 요구가 **구조적으로** 지켜진다 — 마스킹을 잊는 코드 경로가 생기지 않는다.

**기각한 대안**: *편집 화면에서 비밀 값도 함께 수정* — 비밀 값 화면(`SecretValues`)이 이미
그 일을 한다. 두 곳에서 같은 것을 쓰면 봉인 규칙을 두 곳에서 지켜야 한다.
