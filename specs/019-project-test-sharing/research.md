# Phase 0 Research: 프로젝트·테스트 공유용 내보내기·가져오기

**Feature**: `019-project-test-sharing` | **Date**: 2026-09-23

Technical Context 에 남은 NEEDS CLARIFICATION 은 없다. 아래는 설계가 갈리는 지점마다 무엇을
고르고 무엇을 버렸는지의 기록이다.

---

## R1. 묶음 파일 형식 — 단일 평문 YAML

**Decision**: 묶음은 **YAML 문서 하나**다. 확장자 `.itbshare.yaml`, MIME `application/yaml`.
매니페스트(형식 버전·도구 버전·만든 시각·프로젝트 설정·그룹)와 테스트 정의 목록이 한 문서에 있다.

**Rationale**:

- **이미 YAML 이다.** `tests/*.yaml` 과 `itb-project.yaml` 이 YAML 이므로 변환이 없다. 변환이
  없으면 왕복에서 잃을 것도 없다 (SC-003).
- **받은 사람이 열어 볼 수 있다.** 이것 자체가 보안 속성이다 — 가져오기 전에 어떤 URL 이 들어
  있는지, 어떤 평문 값이 있는지 텍스트 편집기로 확인할 수 있다. 헌법 원칙 V 의 "문서화된,
  사람이 읽을 수 있는 평문" 과 같은 방향이다.
- **새 의존성이 없다.** PyYAML 은 이미 있다.
- **담을 이진 자료가 없다.** 스크린샷·실행 산출물을 싣지 않기로 했으므로(FR-005) 아카이브가
  해결할 문제가 애초에 없다.

**크기 근거**: 테스트 하나가 스텝 30개·로케이터 후보 포함 약 20KB. 50건이면 1MB, 2,000건이면
40MB 로 상한(20MB)에 걸린다 — 상한이 실질적으로 테스트 1,000건 근처에서 먼저 걸리는 것이 의도다.

**Alternatives considered**:

- **zip 아카이브(`.itbshare`)** — 기각. 압축 폭탄 방어(014 가 `MAX_UNCOMPRESSED_BYTES`·
  `MAX_COMPRESSION_RATIO` 로 감당한 문제)를 새로 떠안으면서, 내용을 사람이 못 읽게 된다.
  이진 자료를 싣게 되는 날 재검토한다.
- **JSON** — 기각. 형식으로는 동등하지만 저장소의 정본이 YAML 이므로 한쪽만 JSON 이면 같은 것을
  두 형식으로 다루게 된다. 주석을 넣을 수 없어 파일 머리에 "이 파일에는 비밀번호가 들어 있지
  않습니다" 같은 안내를 둘 수 없다는 점도 작지 않다.
- **디렉터리 통째 복사 안내(기능 없이 문서로만)** — 기각. 스펙 개요의 세 가지 문제(민감 값·
  목록 미등록·식별자 충돌) 중 어느 것도 해결하지 못한다.

## R2. 형식 버전 — 묶음 버전과 DSL 버전을 분리

**Decision**: 매니페스트에 `bundle_version: 1` 을 둔다. 테스트 정의 안의 `dsl_version` 은
**건드리지 않는다**. 가져오기는 두 가지를 따로 본다.

- `bundle_version` 이 이 도구가 아는 값보다 크면 → 거부 (FR-030, US2 AS5)
- 각 테스트의 `dsl_version` 은 기존 `Test._check_refs` 가 거부한다 — 새 코드가 필요 없다

**Rationale**: 묶음의 봉투가 바뀌는 일(매니페스트에 필드가 늘어남)과 스텝 모델이 바뀌는 일은
주기가 다르다. 한 숫자로 묶으면 봉투를 고칠 때마다 모든 테스트 파일의 버전을 올려야 한다.
014 가 `Test.description` 을 추가하면서 `dsl_version` 을 올리지 않기로 한 것과 같은 이유다.

**Alternatives considered**: 단일 버전 — 기각(위). 버전 없음 — 기각. 받는 쪽이 읽을 수 있는지
판단할 근거가 파일 안에 없으면 부분 복원이나 조용한 실패로 간다.

## R3. 민감 값 미포함 보장 — 구조로 막는다

**Decision**: 세 겹으로 막는다.

1. **스키마**: `Variable._no_plaintext_secret` 이 `sensitive=True` 인 변수의 `value` 를 거부한다.
   `Test` 를 그대로 직렬화하는 한 민감 값이 들어갈 자리가 없다. 이미 있는 불변식이다.
2. **임포트 계약**: `.importlinter` 에 계약을 추가한다 —
   `itb.sharing` 은 `itb.secrets` 를 임포트할 수 없다. 암호문을 읽을 경로 자체가 없어진다.
3. **테스트**: 내보낸 묶음 바이트를 `secrets.local.yaml` 의 모든 암호문 및 알려진 평문 값과
   대조해 하나도 나타나지 않음을 확인한다 (SC-004).

**Rationale**: "담지 않기로 했다" 는 약속은 리팩터링 한 번에 깨진다. 헌법이 원칙 II 를 런타임
플래그가 아니라 임포트 경계로 막은 것과 같은 판단이다. 계약이 있으면 누군가 편의를 위해
`SecretStore` 를 끌어오는 순간 빌드가 실패한다.

**교차 참조가 필요한 곳은 라우터가 맡는다.** 가져오기 계획은 "이 변수에 이미 값이 있는가"
(FR-046)를 알아야 하는데, 그 조회는 `itb.api.routes.sharing` 이 `SecretStore.has(name)` 로
한다 — 라우터는 두 쪽을 다 임포트할 수 있다. `itb.sharing` 은 이름만 다루고 값에 닿지 않는다.

**Alternatives considered**:

- **묶음을 만들 때 민감 값을 걸러내는 필터** — 기각. 필터는 통과 경로가 존재함을 전제한다.
  자리 자체가 없는 편이 강하다.
- **암호구로 감싸 함께 전달** — 스펙 Clarifications 에서 기각됨. 선택지로 두는 순간 실수로
  담아 보내는 경로가 열린다.

## R4. YAML 파싱 안전 — 별칭 금지 로더

**Decision**: `yaml.safe_load` 를 그대로 쓰지 않고, **앵커/별칭 조합을 거부하는 로더**로 읽는다.
`SafeLoader` 를 상속해 `compose_node` 에서 별칭을 만나면 오류를 낸다. 파싱 **전에** 바이트
상한(20MB)을 먼저 검사한다.

**Rationale**: `safe_load` 는 임의 객체 생성은 막지만 **별칭 폭탄**(billion laughs)은 막지
못한다. 수백 바이트짜리 문서가 수 GB 로 전개될 수 있다. 이 파일은 사람이 보낸 외부 입력이고,
헌법은 모든 외부 입력을 경계에서 검증할 것을 요구한다. 정상적인 묶음은 별칭을 쓰지 않으므로
잃는 것이 없다 — 우리가 만든 파일은 `yaml.safe_dump(default_flow_style=False)` 로 나온다.

**막는 시점이 중요하다.** 014 가 `MAX_UNCOMPRESSED_BYTES` 를 열기 **전에** 판정한 것과 같다.
전개된 뒤에 재면 재지 않은 것과 같다.

**Alternatives considered**:

- `safe_load` 만 — 기각(위).
- 정규식으로 `&`·`*` 사전 차단 — 기각. 문자열 값 안의 `*` 를 오탐한다. 파서 층에서 막는 것이
  정확하다.
- 스트리밍 파서 — 기각. 단일 문서에 상한이 있으므로 복잡도만 늘어난다.

## R5. 가져오기의 원자성 — 새 프로젝트와 기존 프로젝트를 다르게 다룬다

**Decision**: 두 경로가 원자성을 얻는 방법이 다르다.

- **새 프로젝트로 가져오기**: 작업 공간 안의 **임시 디렉터리**에 프로젝트를 완성한 뒤
  `os.replace` 로 최종 이름에 옮긴다. 실패하면 임시 디렉터리를 지운다. 레지스트리 등록은
  **옮기기가 성공한 뒤** 마지막에 한다 — 순서가 반대면 목록에 없는 프로젝트가 생긴다.
- **기존 프로젝트로 가져오기**: `itb.storage.test_moves.run_all(validate, do, undo)` 를 쓴다.
  `validate` 가 전체를 먼저 보고, `do` 가 테스트 파일을 하나씩 쓰고, 실패하면 `undo` 가 쓴
  파일을 지운다. `AllOrNothingError` / `PartialFailureError` 구분이 이미 있다.

**Rationale**: 이미 있는 것을 쓴다. `run_all` 은 013 의 테스트 이동이 같은 문제를 풀며 만든
것이고, 되돌리지 못한 경우를 별도 예외로 구분하는 부분까지 우리가 필요로 하는 모양이다.
새 프로젝트는 되돌릴 대상이 디렉터리 하나뿐이라 `run_all` 보다 `os.replace` 가 단순하다.

**그룹 등록은 테스트보다 먼저**: `itb-project.yaml` 의 `groups` 를 먼저 갱신하고 테스트를 쓴다.
반대 순서면 그룹 없는 접두어를 가진 테스트가 잠시 존재한다. 실패 시 프로젝트 파일도 되돌린다.

**Alternatives considered**: 임시 디렉터리 없이 바로 쓰고 실패 시 삭제 — 기각. 쓰는 도중 서버가
죽으면 반쯤 만들어진 프로젝트가 목록에 남는다. `os.replace` 는 같은 파일시스템 안에서 원자적이다.

## R6. 식별자 충돌 해소 — 들어오는 쪽이 양보한다

**Decision**: 겹치면 **들어오는 테스트에 새 번호를 준다.** 기존 테스트는 손대지 않는다.
번호는 기존 `repository.allocate_test_id` 의 규칙(그룹마다 1번부터, 빈 번호 채움)을 따른다.
바뀐 것은 전부 결과에 `TC-001 → TC-007` 형태로 보고한다.

**그룹 대응 규칙** (FR-027, 이름 기준):

| 대상 프로젝트의 상태 | 처리 |
|---|---|
| 같은 **이름**의 그룹이 있다 | 그 그룹의 접두어로 들어간다. 접두어가 달라도 이름이 같으면 같은 그룹이다. |
| 같은 이름이 없고 접두어도 비어 있다 | 묶음의 접두어 그대로 그룹을 만든다. |
| 같은 이름은 없는데 **접두어가 다른 이름에 쓰이고 있다** | 대체 접두어를 만든다 (`USER` → `USER2` → `USER3`, 8자 상한 안에서). 만들 수 없으면 그 그룹을 건너뛰고 사유를 보고한다. |
| 그룹 없는 테스트(`TC-`) | 대상의 `TC-` 공간으로 들어간다. `TC` 는 예약 접두어이며 그룹이 아니다. |

**Rationale**: 이름이 사람이 읽는 정체성이고 접두어는 식별자용 짧은 값이다(`TestGroup` 주석).
두 사람이 같은 그룹을 각자 `USER`·`USR` 로 만들었을 때 이름이 같으면 같은 그룹으로 보는 것이
사용자의 기대에 맞는다. 반대로 접두어만 같고 이름이 다르면 다른 그룹이다 — 그 경우 접두어를
양보하는 쪽은 들어오는 쪽이다.

**용량 초과**: 그룹의 999 번이 다 차면 그 그룹은 들어갈 수 없다. 014 가 `CapacityView` 로
**확정 전에** 알리는 것과 같이, 계획 단계에서 그룹별 여유를 보고한다. 확정 도중 바닥나는 상태를
만들지 않는다.

**Alternatives considered**:

- 기존 것을 덮어쓰기 — 기각. FR-025 가 금지한다. 되돌릴 수 없는 손실이다.
- 사용자에게 매 충돌마다 묻기 — 기각. 50건이면 50번 묻게 된다. 규칙으로 처리하고 **결과를
  전부 보여 주는** 편이 낫다. 마음에 들지 않으면 이름은 나중에 고칠 수 있다.

## R7. 필요 민감 변수의 산출과 표시

**Decision**: 묶음에는 `required_values` 를 **매니페스트에 미리 계산해 담는다.** 각 항목은
이름·`sensitive`·`declared` 와 쓰이는 자리 목록(`test_id`, `step_id`, `step_label`, `field`)이다.
**민감 변수 전부**와 **값이 빈 비민감 변수**가 함께 들어간다 — 받는 사람에게는 둘 다 「채워야
실행되는 것」이고 다른 것은 저장 위치뿐이다 (FR-040). 가져오는 쪽은 이
목록을 **믿지 않고** 테스트 정의에서 다시 계산해 대조한다 — 어긋나면 정의 쪽을 정본으로 삼고
경고한다.

**Rationale**:

- 미리 담는 이유는 **가져오기 전에 보여 주기 위해서**다 (FR-022). 파일을 열어 본 사람도 이
  목록만 보면 "내 계정 비밀번호가 필요하겠구나" 를 안다.
- 다시 계산하는 이유는 **파일이 손으로 편집될 수 있어서**다. 매니페스트를 정본으로 삼으면
  참조는 있는데 목록에 없는 변수가 조용히 빠진다 (스펙 Edge Case).
- **선언이 아예 없는 참조는 거부하지 않고 보충한다** (FR-047). `Test._check_refs` 가 그런
  테스트를 거부하므로, 보충은 **도메인 검증보다 먼저** 돈다. 거부하면 사용자는 「무엇을
  고쳐야 하는지」 대신 「읽을 수 없다」만 받는다. 보충은 없는 값을 지어내는 것이 아니라 빈
  자리를 드러내는 것이며, 민감 변수라면 채우기 전까지 실행이 막힌다 (data-model §6).

**자리 계산**: `Step.value`, `Step.assertion.value`, `Step.url` 세 자리를 본다 —
`referenced_variable_names` 가 이미 보는 자리와 같다. 그 함수는 이름 집합만 주므로,
자리별로 필요한 이 기능은 같은 세 자리를 도는 얇은 함수를 `itb.sharing.bundle` 에 둔다.
**자리 목록은 한 곳에서 온다** — `itb.domain.test_case` 에 `VARIABLE_VALUE_FIELDS` 상수를 두고
양쪽이 그것을 돈다. 세 자리를 두 곳에 베껴 두면 네 번째 자리가 생기는 날 한쪽만 바뀐다.

**Alternatives considered**: 매니페스트 없이 매번 계산 — 기각. 가져오기 **전** 미리보기에서도
계산할 수 있으므로 기능상 가능하지만, 파일만 받은 사람이 열어 봤을 때 요약이 없다.

## R8. 새 패키지 `itb.sharing` — `itb.portability` 에 합치지 않는다

**Decision**: 별도 패키지로 둔다. `itb.portability`(엑셀, 014)는 건드리지 않는다.

**Rationale**: 014 가 세운 경계가 **"엑셀은 테스트의 두 번째 표현이 아니다"** 이고, 그래서
엑셀 가져오기는 `Test` 가 아니라 `Draft` 를 만든다 — 스텝을 만들 수 없기 때문이다.
공유 묶음은 정반대로 **스텝을 그대로 옮기는 것이 존재 이유**다. 같은 패키지에 두면 두 정책이
한 자리에서 부딪히고, 엑셀 경로가 스텝을 다루게 되는 길이 열린다.

**계획 보관소의 중복은 허용한다.** 모양이 같은 `plan_store.py` 가 두 벌이 되지만, 담는 타입이
다르고 합치려면 기존 엑셀 경로를 건드려야 한다. plan.md 의 Complexity Tracking 에 기록해 둔다.

**Alternatives considered**: `itb.portability.sharing` 하위 패키지 — 기각. 임포트 계약을
패키지 단위로 걸기 어려워지고(`itb.portability` 전체가 `itb.secrets` 금지 대상이 된다),
014 의 경계 설명이 흐려진다.

## R9. 출처 표시(FR-028)를 어디에 두는가 — `Test` 의 선택 필드

**Decision**: `Test` 에 `imported_from: ImportProvenance | None = None` 을 추가한다.
`ImportProvenance` 는 `source_file`(표시용 이름), `imported_at`, `original_id` 를 갖는다.
`dsl_version` 은 **올리지 않는다.**

**Rationale**:

- 헌법 원칙 I 이 provenance 를 **메타데이터로** 기록하는 것을 명시적으로 허용한다. 실행에
  관여하지 않으므로 스텝 모델을 오염시키지 않는다.
- 기본값 `None` 이면 기존 `tests/*.yaml` 이 그대로 읽힌다. `dsl_version` 을 올리면
  `Test._check_refs` 가 기존 파일을 전부 거절한다 — 014 가 `description` 을 추가할 때 이미
  확인한 함정이다.
- 묶음 매니페스트에만 두지 않는 이유는 **묶음이 사라진 뒤에도 알아야** 하기 때문이다. 반년 뒤
  "이 테스트 어디서 왔지" 는 테스트 파일에 답이 있어야 한다.

**내보낼 때는 비운다.** 묶음에 실리는 테스트의 `imported_from` 은 `None` 으로 만든다 — A→B→C
로 전달될 때 B 의 가져오기 기록이 C 에게 갈 이유가 없고, 원본 파일 이름이 사내 경로를 흘릴 수
있다. `original_id` 는 **가져오는 쪽이** 묶음 안의 `id` 로 채운다.

**Alternatives considered**: 별도 사이드카 파일 — 기각. 커밋 대상 파일이 하나 늘고 테스트와
어긋날 수 있다. 저장하지 않음 — 기각. FR-028 이 요구한다.

## R10. 실행 전 차단(FR-044)을 어디에 거는가

**Decision**: **세션 생성 시점**(`POST /api/sessions`)에 건다. 민감 변수를 참조하는데
`SecretStore` 에 값이 없고 동일 이름 환경 변수도 없으면 409 로 거절하고 빠진 이름을 실어 보낸다.
더해 `GET /api/tests/{test_id}/readiness` 로 목록 화면이 **누르기 전에** 상태를 보여 준다.

**Rationale**: 지금은 `VariableResolver` 가 그 스텝에 **도달했을 때** 실패한다 — 브라우저가
뜨고, 로그인 화면까지 가고, 거기서 멈춘다. 받은 사람은 자기 환경 문제인지 테스트 문제인지
구분할 수 없다. 앞에서 막으면 브라우저를 띄우지 않고 "이 값이 필요합니다" 만 남는다.

**해석 순서를 그대로 따라 판정한다.** 환경 변수가 1순위이므로(`resolver.py`), 환경 변수에 값이
있으면 `SecretStore` 가 비어 있어도 막지 않는다. 판정 로직을 `VariableResolver` 와 같은
순서로 두되, **값을 읽지 않고 있는지만 본다** — 판정하려고 복호화하면 잠긴 키에서 실패한다.

**Alternatives considered**:

- 러너 안에서 첫 스텝 전에 검사 — 기각. 브라우저가 이미 떠 있다. 원칙 III 가 세션을 살려 두라고
  요구하므로 여기서 실패하면 빈 세션이 남는다.
- 막지 않고 경고만 — 기각. FR-044 가 막으라고 요구한다. 조용한 실패를 금지하는 헌법 보안
  요건과도 어긋난다.

## R11. 내보내기 확인 요약에 무엇을 담는가 (FR-006·US4)

**Decision**: 파일을 만들지 않는 별도 조회(`GET /api/share/export/preview`)가 아래를 준다.

- 테스트 수, 그룹 수
- **평문으로 나가는 입력값** — 값을 가진 스텝마다 `(test_id, step_id, step_label, field, value)`.
  `{{VAR}}` 참조는 값이 아니므로 제외한다. 값이 긴 것은 앞 120자만.
- 시작 URL (프로젝트 기본값 + 테스트별로 다른 것)
- 필요 민감 변수 이름
- 읽을 수 없어 빠지는 테스트 (있다면)

**마스킹하지 않는다.** 내보내는 사람 자신의 프로젝트이고, **값을 보여 주는 것이 이 화면의 목적**
이다. 가려 놓으면 사번이 섞여 있어도 발견할 수 없다.

**Rationale**: 내보내기는 되돌릴 수 없다. 014 가 `GET /api/export/warnings` 로 "무엇이 바뀌는지"
를 파일 생성 없이 먼저 보여 준 것과 같은 자리이되, 이쪽은 **무엇이 나가는지**를 본다.

**읽을 수 없는 테스트는 내보내기를 막지 않는다.** 014 의 `_collect` 와 같은 판단 — 깨진 파일
하나 때문에 아무것도 못 하게 되면 사용자는 그것을 고치기 전까지 갇힌다. 빠진다는 사실을 요약과
결과 양쪽에 남긴다.

**Alternatives considered**: 값을 마스킹해 보여 주기 — 기각(위). 확인 단계 없이 바로 내려받기 —
기각. US4 가 이 기능의 유일한 방어선이라고 말한다.

## R12. 상한값

| 값 | 크기 | 근거 |
|---|---|---|
| `MAX_BUNDLE_BYTES` | 20MB | 테스트 약 1,000건. 그 이상은 한 번에 공유할 단위가 아니다. 파싱 전에 판정한다. |
| `MAX_BUNDLE_TESTS` | 2,000 | 바이트 상한을 통과해도 건수로 다시 막는다. 그룹 10개 × 999 를 넘는 크기는 대상 프로젝트가 수용할 수 없다. |
| `MAX_BUNDLE_GROUPS` | 100 | `Project.groups` 에 별도 상한이 없으므로 여기서 건다. |
| `SHARE_PLAN_TTL_SECONDS` | 1,800 (30분) | 014 와 같은 값·같은 근거 — 계획은 메모리에만 있고 확정 전에는 아무것도 만들지 않는다. |
| `MAX_SHARE_PLANS` | 8 | 014 와 같음. 넘으면 오래된 것부터 버린다. |

**그룹당 테스트 999 는 여기 두지 않는다.** `itb.domain.test_case.MAX_TEST_NUMBER` 를 참조한다 —
014 의 `limits.py` 가 세운 원칙(값이 같은 게 아니라 출처가 하나)을 그대로 따른다.

## R13. 프론트엔드 — 신규 화면 2개, 기존 것을 재사용

**Decision**:

- **`ShareExport.tsx`** — 대상 선택(전체/고른 것) → 확인 요약 → 내려받기. `TestList` 의 선택
  상태를 넘겨받는다.
- **`ShareImport.tsx`** — 파일 선택 → 계획 → 확정 → 결과 + 민감 값 입력. 014 의
  `ImportPreview.tsx` 가 만든 계획·확정 화면 구조를 따르되 파일이 다르므로 별도 화면이다.
- **민감 값 입력은 기존 `SecretValues.tsx` 의 입력 구성요소를 재사용한다.** 값을 봉인해
  저장하는 호출(`PUT /api/secrets/{name}`)이 이미 있으므로 새 엔드포인트를 만들지 않는다.
- 내려받기는 014 의 blob 처리 방식을 그대로 쓴다 (`Content-Disposition`, RFC 5987 파일명).

**Rationale**: 민감 값을 다루는 화면이 두 벌이 되면 마스킹·오류 처리가 갈린다. 봉인 경로는
하나여야 한다.

**진입점**: `TestList` 에 「공유용 내보내기」(엑셀 내보내기와 나란히, 이름으로 구별),
`ProjectsRoute` 에 「공유 파일에서 가져오기」. 열린 프로젝트가 있으면 `TestList` 에도
「이 프로젝트로 가져오기」를 둔다 (US5).

**Alternatives considered**: 014 화면에 탭으로 얹기 — 기각. 엑셀과 공유 묶음은 결과가 다르다
(초안 vs 실행 가능한 테스트). 한 화면에 두면 사용자가 무엇을 받게 되는지 혼동한다.
