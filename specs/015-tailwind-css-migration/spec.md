# Feature Specification: Tailwind CSS 전환

**Feature Branch**: `015-tailwind-css-migration`

**Created**: 2026-09-10

**Status**: Draft

**Input**: User description: "프론트엔드 스타일링을 Tailwind CSS 로 전환한다. 기존 디자인 토큰(tokens.css 의 CSS 변수)은 유지하고 Tailwind theme 으로 매핑한다. 인라인 style 을 쓰는 파일을 전면적으로 Tailwind 유틸리티 클래스로 전환한다. 시각적 결과는 전환 전후가 동일해야 한다. shadcn/ui 도입은 범위 밖."

---

## 배경 — 지금 이 코드베이스의 스타일링은 두 갈래다

명세를 읽기 전에 알아야 할 사실이 하나 있다. 이 화면 코드는 "인라인 스타일만 쓰는 코드"가
아니다. **두 체계가 공존한다.**

| 체계 | 규모 | 성격 |
|---|---|---|
| `theme/tokens.css` 의 의미 클래스 | 클래스 139개 (`.btn`·`.chip`·`.notice`·`.modal` 등) | 008 이 세운 **정본**. 화면 코드는 `className` 으로 소비하고 값을 다시 적지 않는다 |
| 컴포넌트의 인라인 `style={{...}}` | 출현 455회 / `.tsx` 39개 | 정본 규율 **밖**에 있는 부분. 레이아웃·간격·크기가 주로 여기에 있다 |

그리고 `tokens.css` 앞부분(1~203줄)은 손으로 쓴 파일이 아니다.
`frontend/scripts/extract_canon.py` 가 `docs/design/008-visual-language/*.dc.html` 18장의
`<style>` 에서 **추출**한 결과이고, 그 18장이 글자 하나까지 같음을 스크립트가 먼저 단언한다.
회귀 가드 테스트 2개(`DesignTokens.test.tsx`·`CanonMatchesDesign.test.ts`)가 이 규율을 강제한다.

따라서 이번 작업의 실체는 "스타일 없는 코드에 Tailwind 를 도입한다"가 아니라,
**이미 있는 정본 체계를 깨지 않으면서 정본 밖에 남은 455곳을 정본 안으로 끌어들이는 것**이다.
Tailwind 는 그 수단이다. 이 구분이 흐려지면 008 이 해결한 문제(값 리터럴 338개·토큰 사용률 12%)가
Tailwind 유틸리티라는 새 옷을 입고 그대로 돌아온다.

---

## User Scenarios & Testing *(mandatory)*

여기서 말하는 "사용자"는 두 부류다. **유지보수자**(이 코드에 손대는 사람)와
**제품 사용자**(ITB 화면을 쓰는 사람)다. 이 작업은 유지보수자를 위한 것이지만,
제품 사용자에게는 **아무 일도 일어나지 않아야** 성공이다.

### User Story 1 - 토큰을 Tailwind 로 소비하는 길이 하나 뚫린다 (Priority: P1)

유지보수자가 Tailwind 유틸리티 클래스를 쓰면 그 값이 `tokens.css` 의 정본 토큰에서 온다.
색·간격·글꼴·모서리·그림자를 Tailwind 이름으로 부를 수 있고, 그 이름이 가리키는 값은
정본 한 곳에만 있다. 이 길이 뚫린 것을 확인하기 위해 화면 하나를 시범 전환한다.

**Why this priority**: 이 길이 없으면 나머지 전환은 값 리터럴을 유틸리티 클래스에 다시 적는
일이 된다. 순서를 바꿀 수 없다 — 매핑이 먼저고 전환이 나중이다.

**Independent Test**: 시범 전환한 화면 하나를 전·후로 비교해 시각 차이가 없고, 그 화면의
스타일이 전부 Tailwind 클래스로 표현되며, 사용된 Tailwind 이름들이 정본 토큰으로 되짚어지는지
확인한다. 나머지 38개 파일이 그대로여도 이 확인은 성립한다.

**Acceptance Scenarios**:

1. **Given** `tokens.css` 에 `--pass:#1A7F45` 가 정의되어 있고, **When** 유지보수자가 어떤
   요소에 통과 색을 입히려 하면, **Then** Tailwind 이름 하나로 그 색을 지정할 수 있고
   코드 어디에도 `#1A7F45` 를 적지 않는다.
2. **Given** 시범 전환 대상 화면이 하나 선택되어 있고, **When** 전환 전후의 렌더 결과를
   비교하면, **Then** 색·간격·타이포·레이아웃에 차이가 없다.
3. **Given** 정본 토큰 값 하나가 `extract_canon.py` 재실행으로 바뀌고, **When** 화면을 다시
   그리면, **Then** 그 토큰을 쓰는 Tailwind 클래스의 결과도 함께 바뀐다 (값이 복제되지 않았다는 증거).

---

### User Story 2 - 정본 밖에 남은 인라인 스타일이 사라진다 (Priority: P2)

유지보수자가 어떤 요소의 스타일을 고치려 할 때, 찾아야 할 곳이 한 군데다.
`style={{...}}` 455곳이 사라지고 스타일은 클래스로만 표현된다.

**Why this priority**: 이것이 이번 작업의 본체다. 다만 P1 의 매핑 없이는 시작할 수 없다.

**Independent Test**: 저장소에서 `style={{` 을 검색해 의도적으로 남긴 예외 외에 결과가 없고,
기존 자동 테스트 전량이 통과하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 전환이 끝났고, **When** `frontend/src` 전체에서 인라인 `style` 속성을 검색하면,
   **Then** 남은 것은 문서화된 예외뿐이다 (런타임 계산값 — 예: 진행률 막대 너비).
2. **Given** 전환이 끝났고, **When** 기존 프론트엔드 자동 테스트를 전부 실행하면,
   **Then** 전환 전과 같은 결과가 나온다 (통과하던 것이 통과한다).
3. **Given** 어떤 컴포넌트가 조건에 따라 다른 모습을 갖고 있었고, **When** 전환 후 같은 조건을
   만들면, **Then** 같은 모습이 나온다 (조건부 스타일이 유실되지 않았다).

---

### User Story 3 - 값 리터럴 금지가 새 체계에서도 강제된다 (Priority: P3)

유지보수자가 실수로 색 코드나 px 값을 화면 코드에 적으면, 사람이 리뷰에서 잡기 전에
테스트가 먼저 막는다.

**Why this priority**: 008 이 얻은 규율을 지키는 장치다. 이것이 없으면 이번 전환은
"한 번 정리했다"로 끝나고 다음 개정에서 다시 무너진다 — 008 문서가 007 에서 겪었다고
기록한 바로 그 실패다.

**Independent Test**: 화면 코드에 색 리터럴을 일부러 하나 넣고 테스트를 돌려 실패하는지
확인한다. 그 후 되돌린다.

**Acceptance Scenarios**:

1. **Given** 회귀 가드가 갱신되어 있고, **When** 누군가 `.tsx` 에 `#RRGGBB` 색 리터럴을
   추가하면, **Then** 자동 테스트가 실패한다.
2. **Given** 회귀 가드가 갱신되어 있고, **When** `extract_canon.py` 를 다시 실행해도
   정본이 바뀌지 않으면, **Then** 정본 일치 테스트가 계속 통과한다.
3. **Given** Tailwind 설정이 정본 토큰을 참조하고 있고, **When** 설정에 정본에 없는 새 값이
   직접 적히면, **Then** 자동 테스트가 그것을 지적한다.
4. **Given** 의미 클래스가 해체되어 `.btn` 같은 이름이 더는 없고, **When** 기존
   `VisualLanguage.test.tsx` 가 클래스 이름으로 소비를 확인하던 방식이 성립하지 않게 되면,
   **Then** 그 테스트는 **같은 것을 다른 방법으로** 검증하도록 고쳐진다 — 삭제되지 않는다.
   (무엇을 검증하던 테스트였는지가 기록으로 남아야 한다.)

### Edge Cases

- **런타임에 계산되는 값** — 진행률 막대 너비, 드래그 중 위치, 미러 화면의 실측 기반 크기처럼
  값이 렌더 시점에 정해지는 스타일은 유틸리티 클래스로 표현할 수 없다. 이런 곳은 인라인
  스타일을 남기되 **왜 남겼는지**를 코드에 적고, 예외 목록으로 관리한다. 예외를 세지 않으면
  "인라인 0건" 목표가 편법의 은신처가 된다.
- **정본 클래스와 유틸리티가 같은 속성을 다투는 경우** — `.btn` 이 지정한 padding 을 유틸리티가
  덮어써야 할 때 어느 쪽이 이기는지가 예측 가능해야 한다. `tokens.css` 주석이 기록한 대로 이
  프로젝트는 이미 CSS 우선순위 사고(`.tint-*` 가 졌던 일, 기준 크기가 `height` 를 이긴 일)를
  겪었다. 같은 실패가 Tailwind 도입으로 재발하면 안 된다.
- **한글 폰트와 IME** — `IBM Plex Sans KR` 사용과 `.ime-capture` 같은 한글 입력 처리 스타일이
  전환 후에도 동일하게 동작해야 한다.
- **jsdom 환경의 테스트** — 기존 테스트 상당수가 스타일을 직접 읽어 판정한다
  (`StepRowLayout`·`PhaseBarWidth`·`ToastPlacement`·`VerticalSplit`·`WorkbenchHeight` 등).
  인라인 스타일을 클래스로 바꾸면 jsdom 이 계산해 주는 값이 달라져 **테스트가 무너질 수 있다.**
  이때 테스트를 지우거나 약화시켜 통과시키는 것은 헌법 Quality Gate 4 위반이다.
- **의미 클래스 해체가 회귀 가드를 무너뜨린다** — `VisualLanguage.test.tsx` 는 화면 코드가
  `className` 으로 정본을 *소비하는지*를 확인한다. 소비할 클래스 자체가 사라지면 이 테스트의
  전제가 없어진다. 테스트를 지우는 것이 아니라 **같은 목적을 새 체계에서 확인하는 방법**으로
  갈아끼워야 한다 (FR-013·US3 시나리오 4).
- **해체가 일관성을 흩뜨린다** — `.btn` 이 사라지고 버튼 20개가 각자 유틸리티를 나열하게 되면,
  다음에 누군가 버튼 하나만 고쳐 20개가 서로 달라진다. 클래스가 대신하던 일관성 보장을
  컴포넌트 추출이 이어받지 못하면, 이번 전환은 008 이 고친 문제를 되살린다.
- **빌드 산출물 크기** — 사용하지 않는 유틸리티가 번들에 실려 배포 크기가 늘어나면 안 된다.
- **정본 재추출과의 충돌** — `extract_canon.py` 가 앞으로도 `tokens.css` 를 덮어쓴다.
  Tailwind 설정이 그 파일 안에 손으로 쓴 내용을 넣으면 다음 추출에서 지워진다.

## Requirements *(mandatory)*

### Functional Requirements

**토큰 정본 보존**

- **FR-001**: 시각 언어의 값(색·간격·타이포·모서리·그림자·승강)은 정본 한 곳에만 존재해야 한다.
  Tailwind 설정은 그 값을 **참조**할 뿐 복제하지 않는다.
- **FR-002**: `extract_canon.py` 로 정본을 다시 뽑는 흐름이 전환 후에도 동작해야 한다.
  Tailwind 도입이 이 스크립트의 출력 대상을 손으로 고쳐야만 성립하는 구조가 되어서는 안 된다.
- **FR-003**: 정본에 없는 새로운 시각 값을 이번 작업에서 만들지 않는다. 전환 과정에서 필요해
  보이는 값이 나오면 정본에 이미 있는 값으로 표현하거나, 없다면 그 사실을 기록하고 남긴다.

**전환 범위**

- **FR-004**: 화면 코드의 인라인 `style` 속성은 문서화된 예외를 제외하고 제거되어야 한다.
- **FR-005**: 인라인 스타일을 남기는 예외는 **런타임 계산값에 한정**하며, 각 예외는 이유가
  코드에 적혀 있고 한곳에서 셀 수 있어야 한다.
- **FR-006**: 기존 의미 클래스 139개는 **전면 해체**한다 (2026-09-10 사용자 결정).
  각 클래스가 지정하던 스타일은 유틸리티 클래스 조합으로 표현하고, 여러 곳에서 반복되는
  조합은 CSS 클래스가 아니라 **React 컴포넌트로 추출**한다. 해체 후 `tokens.css` 에 남는 것은
  정본 토큰 정의이며, 부품 단위 스타일 규칙은 남지 않는다.
- **FR-006a**: 해체는 클래스 단위로 추적 가능해야 한다 — 139개 각각이 어디로 갔는지
  (어느 컴포넌트 / 어느 유틸리티 조합) 대응이 남아야 한다. 이것이 없으면 시각 동일성을
  사후에 검증할 방법이 없다.
- **FR-006b**: 해체 과정에서 **부품의 시각적 정체성이 유실되지 않아야 한다.** 같은 종류의
  버튼 두 개가 서로 다른 유틸리티 조합을 갖게 되면, 클래스가 보장하던 일관성이 사라진다.
  반복 조합의 컴포넌트 추출은 선택이 아니라 이 요건을 만족시키는 수단이다.
- **FR-007**: 컴포넌트 라이브러리(shadcn/ui 등)를 도입하지 않는다.

**시각 동일성**

- **FR-008**: 전환 전후로 제품 사용자가 보는 화면에 차이가 없어야 한다 — 색·간격·타이포·
  레이아웃·상태별 표현(통과/실패/경고/일시정지/지목) 모두.
- **FR-009**: 상호작용 상태(hover·focus·선택·비활성)의 표현이 보존되어야 한다.
  특히 키보드 초점 표시는 접근성 요건이므로 유실 시 회귀다.
- **FR-010**: 한글 입력(IME) 관련 스타일과 폰트 지정이 보존되어야 한다.
- **FR-011**: 시각 동일성은 **말이 아니라 확인 절차**로 뒷받침되어야 한다. 어떤 화면을
  어떤 방법으로 대조했는지가 기록으로 남아야 한다.

**기존 테스트 보존**

- **FR-012**: 기존 프론트엔드 자동 테스트는 전환 후에도 전량 통과해야 한다.
- **FR-013**: 스타일 표현 방식 변경 때문에 판정 방법을 바꿔야 하는 테스트는, **무엇을 검증하던
  테스트인지가 바뀌지 않는 선에서만** 고친다. 테스트를 삭제·건너뛰기·약화시켜 통과시키지 않는다
  (헌법 Quality Gate 4).
- **FR-014**: 테스트를 고쳤다면 무엇을 왜 고쳤는지가 기록되어야 한다.

**회귀 방지**

- **FR-015**: 화면 코드에 시각 값 리터럴(색 코드·px 등)이 새로 들어오는 것을 자동 테스트가
  막아야 한다.
- **FR-016**: Tailwind 설정에 정본에 없는 값이 직접 적히는 것을 자동 테스트가 막아야 한다.
- **FR-017**: 사용되지 않는 스타일이 배포 산출물에 실리지 않아야 한다.

**충돌 규칙**

- **FR-018**: 의미 클래스와 유틸리티 클래스가 같은 속성을 지정할 때 어느 쪽이 이기는지가
  문서화되고, 그 규칙이 테스트로 확인되어야 한다.

### Key Entities

- **시각 토큰 (Visual Token)**: 색·간격·타이포·모서리·그림자·승강 값 하나에 붙은 이름.
  정본은 `docs/design/008-visual-language/*.dc.html` 에서 추출된다. 이번 작업은 값을 바꾸지
  않고 **부르는 방법**을 하나 더 만든다.
- **의미 클래스 (Semantic Class)**: `.btn`·`.chip`·`.notice` 처럼 UI 부품에 이름을 붙인 클래스.
  현재 139개. 이번 작업에서 유지 여부가 결정된다.
- **인라인 스타일 예외 (Inline Style Exception)**: 런타임 계산 때문에 클래스로 표현할 수 없어
  의도적으로 남긴 인라인 스타일. 이유와 함께 집계된다.
- **회귀 가드 (Regression Guard)**: 값 리터럴 유입과 정본 이탈을 막는 자동 테스트.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 제품 사용자가 전환 전후 화면에서 차이를 발견하지 못한다 — 대조한 화면 전부에서
  색·간격·타이포·레이아웃 차이 0건.
- **SC-002**: 화면 코드의 인라인 스타일이 455곳에서 **문서화된 예외 건수**로 줄어든다.
  예외로 남긴 것은 전부 런타임 계산값이며, 그 사유가 각각 적혀 있다.
- **SC-003**: 기존 프론트엔드 자동 테스트가 전환 후 전량 통과한다. 삭제·건너뛴 테스트 0건.
- **SC-004**: 시각 값 리터럴을 화면 코드에 새로 넣으면 자동 테스트가 실패한다 — 일부러 넣어
  확인한다.
- **SC-005**: 시각 언어의 값이 정본 밖에서 중복 정의된 곳이 0건이다.
- **SC-006**: 유지보수자가 어떤 요소의 스타일을 고칠 때 찾아야 할 곳이 컴포넌트 파일 하나와
  정본 하나로 한정된다 — 세 번째 장소가 없다.
- **SC-007**: 배포 산출물의 스타일 크기가 전환 전 대비 늘지 않는다.
- **SC-009**: 해체된 의미 클래스 139개 전부에 대해 "어디로 갔는지"가 대응표로 남는다 —
  미상 0건.
- **SC-010**: 같은 종류의 부품(버튼·칩·알림 등)이 화면마다 다른 모습을 갖는 일이 없다 —
  부품 종류별로 정의가 한 곳이다.
- **SC-008**: 키보드만으로 조작할 때 초점 위치가 전환 전과 동일하게 보인다 — 초점 표시가
  사라진 요소 0건.

## Assumptions

- **정본 파이프라인은 유지한다.** `extract_canon.py` → `tokens.css` 흐름과 그것을 지키는 회귀
  가드 테스트는 008 이 실제 실패(값 리터럴 338개·토큰 사용률 12%)를 겪고 세운 장치다.
  Tailwind 도입이 이 장치를 대체하는 것이 아니라, 그 장치가 만든 토큰을 소비하는 방법을
  하나 더 여는 것으로 본다.
- **다크 모드는 현재 없다.** `tokens.css` 에 `prefers-color-scheme` 이나 `[data-theme]`
  분기가 없고 `:root` 단일 팔레트만 있다. 따라서 "다크/라이트 테마 동작 보존"은 **현재 없는
  것을 보존하는 것**이며, 이번 작업에서 다크 모드를 새로 만들지 않는다. 다만 나중에 추가할 때
  Tailwind 쪽이 걸림돌이 되지 않는 형태를 택한다.
- **시각 동일성 검증에 스크린샷 회귀 도구를 새로 도입하지 않는다.** 이 저장소에는 아직 그
  장치가 없고, 이번 작업에 그것까지 넣으면 범위가 두 배가 된다. 대신 기존 자동 테스트 전량
  통과 + 화면별 사람 대조(이 저장소의 기존 관행인 `docs/PENDING-HUMAN-VERIFICATION.md`)로
  판정한다. 이는 한계이며, 판정이 사람 눈에 의존한다는 점을 성공 기준에 정직하게 반영했다.
- **React 19 + Vite 6 + TypeScript 5.7 구성은 바꾸지 않는다.** Tailwind 는 이 구성 위에 얹는다.
- **헌법 Stack 조항 관련**: 헌법은 "Frontend: React" 를 고정 스택으로 정하고 변경 시 개정을
  요구한다. Tailwind 는 React 를 대체하지 않는 스타일링 도구이므로 스택 교체가 아니라고
  본다. 다만 이 판단은 `plan.md` 의 Constitution Check 에서 명시적으로 다뤄야 한다.
  ⚠️ **확인 필요** — 유지보수자 판단이 다르면 개정 절차가 선행되어야 한다.
- **의미 클래스 전면 해체는 사용자가 대가를 알고 내린 결정이다** (2026-09-10).
  이 방침은 세 선택지 중 작업량과 시각 회귀 위험이 가장 크고, 회귀 가드 테스트 재설계를
  강제한다. 그 대신 스타일 체계가 하나로 남는다. 명세는 이 선택을 전제로 쓰였으며,
  위험을 줄이는 책임은 plan 의 전환 순서와 검증 절차에 있다.
- **`tokens.css` 의 역할이 줄어든다.** 해체 후 이 파일에 남는 것은 정본 토큰 정의이고,
  부품 스타일 규칙은 남지 않는다. `extract_canon.py` 가 생성하는 「정본」 구획은 그대로
  유지되므로 (FR-002) 이 축소는 정본 파이프라인과 충돌하지 않는다 — 다만 파일 앞머리의
  긴 주석이 설명하는 "화면 코드는 className 으로 소비한다"는 문장은 사실과 달라지므로
  갱신되어야 한다.
- **범위 밖**: 디자인 변경, 새 화면, 컴포넌트 라이브러리 도입, 다크 모드 신설,
  스크린샷 회귀 테스트 도입, 백엔드 변경.
