**Feature Branch**: `001-interactive-ai-test-builder` (기존 브랜치에서 이어짐)

**Spec Directory**: `specs/003-error-path-hardening`

**Created**: 2026-09-04

**Status**: Draft

**Input**: User description: "지금 테스트들이 성공 케이스에 대한 유닛테스트만 있어서, 문제가 있다. 일부러 고장내서, 혹은 다른 입력, 다른 버튼을 눌러서, 에러가 나게 해서, 이 에러가 원래 발생하는 것인지, 아니면, 본 프로젝트가 문제가 있어서 나는것인지 체크하는게 이번에 개발해야할것으로 보인다."

## 이 라운드의 성격

이 명세는 **새 기능을 정의하지 않는다.** 002 가 정상 경로를 다뤘다면 이 라운드는 **이상 경로** 판이다.
이미 만든 것이 이상 입력·이상 순서·외부 실패·동시 조작 앞에서 무너지지 않는지 확인하고,
무너지는 지점을 바로잡는 것이 전부다.

판별 대상은 **e2e-tester 제품 자체**다. 사용자가 만든 테스트가 대상 애플리케이션에서 만난
에러를 분류해 주는 제품 기능이 아니다 — 그것은 이 라운드의 범위가 아니다.

### 문제의 실체

지금 도구를 이상하게 조작하면 에러가 난다. 그런데 그 에러가

- **제품이 규칙에 따라 제대로 막은 것**인지 (사용자가 고칠 수 있다), 아니면
- **제품이 처리하지 못하고 깨진 것**인지 (사용자가 고칠 수 없다)

구분되지 않는다. 매번 사람이 코드를 열어 봐야 안다.

이것은 추정이 아니라 확인된 사실이다. 예기치 못한 예외를 받는 최종 처리기는 응답 코드로
`DEFINITION_INVALID` 를 붙인다 — 사용자가 잘못된 값을 넣어 **정상적으로 거부당했을 때와 같은
코드**다. 응답을 받은 쪽(프런트엔드, 자동 테스트, 사람)은 둘을 구별할 방법이 없다.

### 이 라운드의 요구사항 종류

| 종류 | 접두사 | 뜻 |
|---|---|---|
| 에러 처리 규약 | `EC-` | 어떤 에러가 "막은 것"이고 어떤 것이 "깨진 것"인지 제품 전체가 일관되게 구분해 드러내는 규칙 |
| 이상 경로 동작 | `AP-` | 이상 조작을 받았을 때 제품이 성립시켜야 하는 동작 |
| 회귀 방지 | `RG-1xx` | 이 라운드가 이미 동작하던 것을 깨뜨리지 않는다는 조건 |

001 · 002 의 요구사항은 **여전히 유효하며 이 문서가 대체하지 않는다.**

## 판정 규칙 — 정상인가 결함인가 *(이 라운드의 핵심 개념)*

이상 조작 하나를 가한 결과는 **축 3개를 모두 만족할 때만 정상**이다. 하나라도 어긋나면 결함이다.

| 축 | 정상 | 결함 |
|---|---|---|
| **① 응답의 형태** | 구조화된 거부 — 무엇이 잘못됐는지 가리키는 식별자 + 사람이 읽는 이유 + 다음 행동 | 처리되지 않은 내부 오류, 내부 경로·스택 노출, 무응답, **조용한 성공**(실패했는데 성공처럼 보임) |
| **② 사용자 관점** | 화면에서 무엇이 잘못됐고 무엇을 하면 되는지 알 수 있다 | 화면이 멈추거나, 아무 반응이 없거나, 진행할 방법이 없다 |
| **③ 상태 보존** | 에러 뒤에도 직전까지의 작업(녹화한 Step, 편집 중인 테스트, 열린 세션)이 남아 있고 이어서 할 수 있다 | 작업이 유실되거나 세션이 엉켜 되살릴 수 없다 |

축 ③ 은 002 에서 실제로 터진 유형이다 — "녹화 중지 시 결과 유실". 그때는 정상 경로에서 났다.
이 라운드는 이상 경로에서 같은 일이 나는지를 본다.

**시나리오마다 기대 응답을 명세에 미리 적어 두고 대조하는 방식은 쓰지 않는다.** 위 3축이 판정
기준이며, 개별 시나리오의 기대값은 이 3축에서 도출된다. 기대값을 시나리오마다 손으로 적으면
명세가 구현을 베끼게 되고, 구현이 틀렸을 때 기대값도 같이 틀린다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 에러를 만나면 그것이 내 잘못인지 도구 잘못인지 안다 (Priority: P1)

사용자가 무언가를 하다 에러를 만났다. 화면은 그 에러가 **도구가 규칙에 따라 막은 것**인지
(그렇다면 사용자가 입력을 고쳐 다시 하면 된다) **도구가 깨진 것**인지(그렇다면 사용자가 할 수
있는 일은 없고 보고해야 한다)를 구분해 알려 준다. 어느 쪽이든 다음에 무엇을 하면 되는지가 함께
나온다.

**Why this priority**: 이것이 없으면 나머지 스토리의 판정이 성립하지 않는다. "이 에러가 정상인가
결함인가"를 사람이 매번 코드를 열어 판단해야 하고, 자동 테스트도 그 구분을 검사할 수 없다.
규약이 먼저 서야 이상 조작을 돌린 결과를 기계적으로 판정할 수 있다.

**Independent Test**: 이상 조작을 하나만 가해도(예: 빈 이름으로 테스트 저장) 응답과 화면에서
분류·이유·다음 행동 세 가지를 확인할 수 있다. 다른 스토리를 구현하지 않아도 검증된다.

**Acceptance Scenarios**:

1. **Given** 사용자가 규칙에 어긋나는 값을 입력했다, **When** 그 요청이 거부된다, **Then** 결과는 "막은 것"으로 분류되어 표시되고, 어떤 값이 왜 안 되는지와 무엇으로 고치면 되는지가 화면에 나온다
2. **Given** 도구 내부에서 처리되지 않은 오류가 발생했다, **When** 사용자가 그 결과를 받는다, **Then** 결과는 "깨진 것"으로 분류되어 표시되고, 내부 경로·스택은 노출되지 않으며, 사용자가 지금 무엇을 할 수 있는지(작업 보존 여부, 보고 방법)가 함께 나온다
3. **Given** 어떤 에러든 발생했다, **When** 응답을 받은 쪽이 그것을 읽는다, **Then** 분류는 메시지 문구를 해석하지 않고도 판별된다

---

### User Story 2 - 잘못된 값을 넣어도 도구가 깨지지 않는다 (Priority: P1)

사용자가 빈 값, 형식이 틀린 주소, 아주 긴 문자열, 특수문자나 이모지, 이미 있는 이름, 상위 경로를
가리키는 경로를 넣는다. 도구는 그것을 거부하되 깨지지 않고, 사용자가 무엇을 고쳐야 하는지
알려 준다.

**Why this priority**: 사용자가 가장 자주 만드는 이상 상황이고, 조작 면 셋 모두에 해당한다.
경계 검증이 새는 곳은 대체로 여기서 먼저 드러난다.

**Independent Test**: 각 조작 면에 경계 입력을 넣어 3축을 확인한다. 다른 고장 유형과 독립이다.

**Acceptance Scenarios**:

1. **Given** 이름이 필요한 자리다, **When** 빈 값이나 공백만으로 저장한다, **Then** 거부되고 무엇을 채워야 하는지 나오며, 입력하던 다른 값은 화면에 남아 있다
2. **Given** 주소를 받는 자리다, **When** 형식이 아닌 문자열을 넣는다, **Then** 거부되고 어떤 형식이어야 하는지 나온다
3. **Given** 자유 입력 자리다, **When** 아주 긴 문자열이나 특수문자·이모지를 넣는다, **Then** 도구가 멈추거나 깨지지 않고, 받아들이든 거부하든 결과가 화면에 드러난다
4. **Given** 경로를 받는 자리다, **When** 상위 디렉터리를 가리키는 경로를 넣는다, **Then** 거부되고 왜 안 되는지 나오며 그 경로가 실제로 열리지 않는다
5. **Given** 이미 있는 이름이다, **When** 같은 이름으로 다시 만든다, **Then** 거부되고 기존 것이 덮어써지지 않는다

---

### User Story 3 - 순서를 어겨도 세션이 엉키지 않는다 (Priority: P1)

사용자가 정해진 순서를 벗어나 조작한다 — 시작하지 않은 것을 중지하고, 이미 끝난 세션을 다시
이어가려 하고, 없는 Step 을 고치려 하고, 버튼을 연달아 누르고, 화면을 벗어났다 돌아온다.
도구는 그때마다 지금 무엇이 가능한지 알려 주고, 진행 중이던 작업은 살아 있다.

**Why this priority**: Stateful Interactive Runner(헌법 원칙 III)가 이 제품의 중심이고, 상태를
가진 것은 순서 위반에 가장 약하다. 002 의 결함 5건 중 2건(녹화 중지 결과 유실, 프로젝트 인식
불가)이 상태 취급 문제였다.

**Independent Test**: 세션 하나를 만들어 순서를 어긴 조작을 차례로 가하고 3축을 확인한다.

**Acceptance Scenarios**:

1. **Given** 녹화를 시작하지 않았다, **When** 중지를 요청한다, **Then** 지금 녹화 중이 아님이 알려지고 세션은 그대로 쓸 수 있다
2. **Given** 세션이 이미 끝났다, **When** 이어가기를 요청한다, **Then** 끝난 세션임이 알려지고, 그 세션에서 만든 결과는 여전히 조회·저장할 수 있다
3. **Given** 존재하지 않는 Step 을 가리킨다, **When** 수정·삭제·순서 변경을 요청한다, **Then** 거부되고 나머지 Step 목록은 손상되지 않는다
4. **Given** 사용자가 실행 버튼을 빠르게 두 번 누른다, **When** 두 요청이 도착한다, **Then** 실행은 한 번만 일어나고 화면은 그것을 진행 중으로 보여 준다
5. **Given** 세션 진행 중 화면을 벗어났다, **When** 돌아온다, **Then** 세션이 아직 살아 있으면 이어서 할 수 있고, 끝났으면 왜 끝났는지 알 수 있다 — 어느 쪽이든 화면이 멈춘 채 남지 않는다

### User Story 4 - 바깥이 무너져도 내 작업은 남는다 (Priority: P2)

브라우저가 강제로 닫히고, 대상 사이트가 응답하지 않거나 아주 느리고, AI 응답이 오류이거나
시간 안에 오지 않는다. 도구 바깥에서 벌어진 일이지만 사용자는 그 사실을 알 수 있고, 그때까지
만든 것은 남아 있다.

**Why this priority**: 사용자가 통제할 수 없는 실패이므로 "무엇을 하면 되는지"가 특히 중요하다.
다만 재현에 별도 장치가 필요해 앞 두 스토리보다 비용이 크다.

**Independent Test**: 외부 경계 하나를 실패시키고(브라우저 강제 종료 등) 3축을 확인한다.

**Acceptance Scenarios**:

1. **Given** 세션이 브라우저를 쓰고 있다, **When** 브라우저가 강제로 닫힌다, **Then** 세션이 브라우저를 잃었음이 알려지고, 그때까지 기록한 Step 은 남아 있으며 저장할 수 있다
2. **Given** 대상 사이트가 응답하지 않는다, **When** 실행이 그 지점에 이른다, **Then** 무한정 기다리지 않고 끝나며, 결과는 대상 쪽 문제임을 가리킨다 — 도구가 깨진 것으로 보이지 않는다
3. **Given** AI 요청을 보냈다, **When** 오류가 오거나 시간 안에 응답이 없다, **Then** 그 사실이 화면에 드러나고 사용자는 다시 시도하거나 직접 이어받을 수 있으며, 이미 만들어진 Step 은 유지된다

---

### User Story 5 - 같은 것을 두 번 해도 하나만 일어난다 (Priority: P2)

사용자가 같은 테스트를 두 번 동시에 실행하거나, 창을 둘 열어 같은 세션을 양쪽에서 조작하거나,
저장이 끝나기 전에 도구를 닫는다. 도구는 충돌을 알려 주고 자산을 망가뜨리지 않는다.

**Why this priority**: 단독 로컬 도구라도 한 사람이 창을 둘 열면 바로 발생한다. 다만 앞선
유형들보다 빈도가 낮다.

**Independent Test**: 같은 대상에 동시 요청을 보내 3축과 자산 무결성을 확인한다.

**Acceptance Scenarios**:

1. **Given** 테스트가 실행 중이다, **When** 같은 테스트 실행을 다시 요청한다, **Then** 이미 실행 중임이 알려지고, 두 번째 요청이 첫 실행을 방해하지 않는다
2. **Given** 같은 세션을 두 화면에서 보고 있다, **When** 양쪽에서 서로 다른 조작을 한다, **Then** 어느 쪽도 조용히 무시되지 않고, 반영되지 않은 쪽은 왜 반영되지 않았는지 알 수 있다
3. **Given** 저장이 진행 중이다, **When** 그 도중에 종료·이탈이 일어난다, **Then** 저장 대상 파일이 절반만 쓰인 상태로 남지 않는다

---

### User Story 6 - 이번 라운드가 되던 것을 깨지 않는다 (Priority: P1)

001·002 에서 성립시킨 동작이 이 라운드 뒤에도 그대로 성립한다.

**Why this priority**: 에러 처리 규약은 제품 전역을 건드린다. 전역 변경은 정상 경로를 깨기 쉽다.

**Independent Test**: 001·002 의 기존 자동 검증을 그대로 돌려 통과를 확인한다.

**Acceptance Scenarios**:

1. **Given** 001·002 의 기존 자동 검증이 있다, **When** 이 라운드의 변경 뒤에 전부 돌린다, **Then** 실패가 없다
2. **Given** 이 라운드에서 확인한 이상 경로가 있다, **When** 이후 어떤 변경이 그것을 되돌린다, **Then** 자동 검증이 실패로 알려 준다

### Edge Cases

- 에러 처리 자체가 실패하면 어떻게 되는가 — 분류를 붙이는 과정에서 예외가 나면 사용자는 무엇을 보게 되는가
- 실시간 통로(관찰용 연결)가 끊긴 채 오류가 발생하면 사용자는 그 사실을 알 수 있는가 — 화면이 조용히 옛 상태로 남지 않는가
- 이상 조작이 비밀 값을 담은 자리에서 일어나면, 오류 메시지·상세·로그에 그 값이 새지 않는가
- 아주 긴 입력이 거부될 때, 거부 메시지 자체가 그 긴 입력을 그대로 되돌려 보내 화면을 망가뜨리지 않는가
- 이상 조작이 연달아 일어나면(거부된 요청을 즉시 반복) 도구가 누적 상태로 느려지거나 자원을 잃지 않는가
- "깨진 것"으로 분류된 오류가 실제로는 사용자가 고칠 수 있는 것이었을 때, 분류를 바로잡을 경로가 있는가

## Requirements *(mandatory)*

### 에러 처리 규약 (US1)

- **EC-001**: 사용자에게 도달하는 모든 오류는 **"막은 것"(제품이 규칙에 따라 의도적으로 거절)** 과 **"깨진 것"(제품이 처리하지 못함)** 중 하나로 분류되어야 한다. 분류되지 않는 오류가 있어서는 안 된다
- **EC-002**: 분류는 응답에 **명시적으로 실려** 전달되어야 한다. 받는 쪽이 메시지 문구를 해석하거나 상태 값을 추측해 분류를 유추하게 해서는 안 된다
- **EC-003**: "깨진 것" 은 "막은 것" 의 식별자를 재사용해서는 안 된다. 처리되지 않은 내부 오류에 정상 거부용 식별자를 붙이는 현재 동작은 이 요구를 위반한다
- **EC-004**: 모든 오류는 **다음 행동**을 포함해야 한다. "막은 것" 은 사용자가 고칠 수 있는 구체적 방법을, "깨진 것" 은 지금 작업이 보존되었는지와 무엇을 남겨 보고하면 되는지를 알린다
- **EC-005**: 오류의 어떤 부분에도 내부 파일 경로, 호출 스택, 비밀 값이 들어가서는 안 된다. 이는 화면·로그·저장된 결과 모두에 적용된다
- **EC-006**: 분류와 식별자 목록은 **한 곳에서만 정의**되고, 그 밖의 위치는 그것으로부터 생성되거나 그것에 대해 검증되어야 한다. 두 곳에서 손으로 유지되는 목록이 있어서는 안 된다
- **EC-007**: 실패한 조작이 성공한 것처럼 보여서는 안 된다. 요청이 거부되었거나 중간에 끊겼으면 화면과 저장된 상태 어느 쪽도 성공으로 남지 않는다
- **EC-008**: 요청·응답이 아닌 통로(진행 상황을 밀어 주는 실시간 연결 등)로 전달되는 오류도 같은 규약을 따라야 한다

### 이상 경로 공통 동작 (US2~US5)

- **AP-001**: 어떤 이상 조작에도 제품은 **무응답·처리되지 않은 내부 오류·조용한 성공** 중 어느 것도 내서는 안 된다 (판정축 ①)
- **AP-002**: 이상 조작 뒤에도 **직전까지의 작업이 보존**되어야 하며, 사용자가 이어서 진행할 수 있어야 한다. 보존할 수 없는 경우에는 무엇이 사라졌는지 알려야 한다 (판정축 ③)
- **AP-003**: 이상 조작의 결과는 **화면에 드러나야** 하며, 사용자가 다음에 무엇을 하면 되는지 알 수 있어야 한다. 조작이 아무 반응 없이 삼켜져서는 안 된다 (판정축 ②)
- **AP-004**: 위 세 요구는 **백엔드 요청 경계 · 화면 · 브라우저와 외부 연동 경계** 세 면 모두에서 성립해야 한다

### 잘못된 입력값 (US2)

- **AP-010**: 필수 값이 비었거나 공백뿐이면 거부되고, 무엇을 채워야 하는지 알려야 한다
- **AP-011**: 형식이 정해진 값(주소 등)이 형식에 맞지 않으면 거부되고, 어떤 형식이어야 하는지 알려야 한다
- **AP-012**: 아주 긴 입력과 특수문자·이모지가 들어와도 제품이 멈추거나 화면이 망가져서는 안 된다. 허용 한계가 있다면 그 한계가 사용자에게 알려져야 한다
- **AP-013**: 대상 범위 밖을 가리키는 경로는 거부되어야 하며, 그 경로가 실제로 열려서는 안 된다
- **AP-014**: 이미 존재하는 이름으로 만들기를 시도하면 거부되어야 하며, 기존 자산이 덮어써져서는 안 된다
- **AP-015**: 거부 메시지가 사용자가 넣은 원본 입력을 그대로 되돌려 화면을 훼손해서는 안 된다

### 순서·상태 위반 (US3)

- **AP-020**: 현재 상태에서 불가능한 조작은 거부되고, **지금 무엇이 가능한지**가 알려져야 한다
- **AP-021**: 존재하지 않는 대상(끝난 세션, 없는 Step, 없는 테스트)에 대한 조작은 거부되어야 하며, 주변 자산이 손상되어서는 안 된다
- **AP-022**: 같은 조작이 짧은 간격으로 반복 요청되어도(버튼 연타) **효과는 한 번만** 일어나야 한다
- **AP-023**: 사용자가 화면을 벗어났다 돌아왔을 때, 세션의 현재 상태가 화면에 반영되어야 한다. 화면이 옛 상태로 멈춰 있어서는 안 된다
- **AP-024**: 상태 위반으로 거부된 뒤에도 해당 세션은 계속 사용할 수 있어야 한다. 거부가 세션을 못 쓰게 만들어서는 안 된다

### 외부 환경 실패 (US4)

- **AP-030**: 브라우저를 잃으면 그 사실이 알려져야 하고, 그때까지 기록된 Step 은 남아 있어야 하며 저장할 수 있어야 한다
- **AP-031**: 대상 사이트가 응답하지 않거나 아주 느릴 때 무한정 기다려서는 안 된다. 결과는 그것이 **대상 쪽 사정**임을 가리켜야 하며 제품 결함으로 보이게 해서는 안 된다
- **AP-032**: AI 응답이 오류이거나 제때 오지 않으면 그 사실이 화면에 드러나야 하고, 사용자는 다시 시도하거나 직접 이어받을 수 있어야 하며, 이미 만들어진 Step 은 유지되어야 한다
- **AP-033**: 외부 실패에서 비롯된 오류는 "막은 것"·"깨진 것" 어느 쪽으로 분류되든 그 판단 근거가 사용자에게 드러나야 한다

### 동시성·중복 실행 (US5)

- **AP-040**: 이미 진행 중인 실행에 대해 같은 실행을 다시 요청하면 거부되어야 하고, 진행 중인 실행이 방해받아서는 안 된다
- **AP-041**: 같은 세션을 여러 화면에서 조작할 때, 반영되지 않은 조작은 **조용히 무시되지 않고** 그 사실이 알려져야 한다
- **AP-042**: 저장이 도중에 끊겨도 자산 파일이 **일부만 쓰인 상태로 남아서는 안 된다**

### 회귀 방지 (US6)

- **RG-101**: 이 라운드에서 확인한 이상 경로는 **자동 검증으로 고정**되어야 한다. 이후 변경이 그것을 되돌리면 검증이 실패해야 한다
- **RG-102**: 001·002 의 기존 자동 검증이 이 라운드 뒤에도 전부 통과해야 한다
- **RG-103**: 자동 검증은 **세 면 각각**(요청 경계 · 화면 · 외부 연동 경계)에 대해 존재해야 한다. 한 면만 덮고 나머지를 수동에 맡겨서는 안 된다
- **RG-104**: 규약 준수(EC-001~EC-008)는 개별 사례를 하나씩 확인하는 방식이 아니라, **모든 대상을 훑는 공통 점검**으로 검증되어야 한다. 새로 추가된 경로가 점검에서 빠지지 않아야 한다

### Key Entities

- **이상 조작 시나리오**: 어떤 면(요청 경계·화면·외부 경계)에, 어떤 고장 유형(잘못된 입력·순서 위반·외부 실패·동시성)을, 어떤 대상에 가하는지를 담은 하나의 조작. 판정 3축에 대한 결과를 가진다
- **에러 분류**: "막은 것" 또는 "깨진 것". 모든 사용자 대면 오류가 정확히 하나를 가진다
- **오류 표현**: 분류 · 식별자 · 사람이 읽는 이유 · 다음 행동으로 이루어진 사용자 대면 오류. 화면과 응답 양쪽에서 같은 내용을 전한다
- **시나리오 목록**: 이 라운드가 판정 대상으로 삼는 이상 조작의 전체 집합. 완료 판정의 기준이 된다

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-201**: 정의한 이상 조작 시나리오 **전건**이 판정 3축을 모두 만족한다. 미판정·불일치 0건
- **SC-202**: 이상 조작으로 인해 처리되지 않은 내부 오류, 내부 경로·스택 노출, 무응답이 발생하는 사례 **0건**
- **SC-203**: 이상 조작 뒤 사용자가 만든 작업이 유실되는 사례 **0건**. 보존할 수 없는 경우에도 무엇이 사라졌는지 알려진 사례가 100%
- **SC-204**: 오류를 받은 쪽이 **메시지 문구를 해석하지 않고** 분류("막은 것"/"깨진 것")를 판별할 수 있는 비율 100%
- **SC-205**: 조용한 성공(실패했는데 성공처럼 보임) 사례 **0건**
- **SC-206**: 시나리오 목록이 **고장 유형 4종 × 조작 면 3종** 의 12개 조합을 모두 덮으며, 각 조합에 최소 3건이 있다 (총 36건 이상)
- **SC-207**: 001·002 의 기존 자동 검증 **100% 통과**
- **SC-208**: 이 라운드에서 확인한 이상 경로 중 자동 검증으로 고정된 비율 100%
- **SC-209**: 오류 메시지·상세·로그·저장된 결과에서 비밀 값이 노출되는 사례 **0건**

## Assumptions

- **시나리오 목록은 이 라운드가 만든다.** 인터뷰에서 목록이 주어지지 않았으므로, 고장 유형 4종 × 조작 면 3종의 12개 조합을 체계적으로 훑어 도출한다. 각 조합 최소 3건, 총 36건 이상을 기준으로 삼는다 (SC-206). 조작 대상은 현재 제품이 실제로 가진 요청 경계와 화면에서 고른다
- **에러 처리 규약은 처음부터 만드는 것이 아니라 현재 있는 것을 확장한다.** 제품에는 이미 식별자 + 메시지 + 상세로 이루어진 오류 형태가 있다. 없는 것은 **분류**(막은 것/깨진 것)와 **다음 행동**이다. 규약은 기존 형태를 대체하지 않고 이 둘을 더하는 방향으로 정의한다
- **화면 면의 검증은 화면 단위 자동 검증으로 한다.** 제품에는 이미 화면 단위 자동 검증 수단이 갖춰져 있다. 전체 브라우저를 띄우는 방식은 이 라운드에 도입하지 않는다
- **외부 환경 실패는 실제 외부를 무너뜨리는 대신 경계를 대체해 재현한다.** 실제 브라우저를 강제 종료하거나 실제 AI 서비스를 오류 내는 방식은 재현이 불안정하다. 구체적 방법은 설계 단계에서 정한다
- **판정은 자동 검증이 한다.** 판정 3축 중 축 ②(사용자 관점)는 사람의 판단이 섞일 수 있으나, 이 라운드에서는 "무엇이 잘못됐는지와 다음 행동이 화면에 존재하는가"로 좁혀 자동으로 판정한다. 문구의 품질 평가는 범위 밖이다
- **분류를 바꾸는 것은 요구사항 변경이 아니다.** 어떤 오류가 "막은 것"인지 "깨진 것"인지는 구현을 보며 정해지며, 잘못 분류된 것을 바로잡는 것은 이 라운드의 정상 작업이다
- 브랜치는 001·002 와 같은 `001-interactive-ai-test-builder` 에 이어 쌓는다. 003 은 별도 스펙 디렉터리를 갖되 브랜치를 새로 만들지 않는다

## Dependencies

- **001 · 002 의 구현이 전제다.** 이 라운드는 그 위에서 이상 조작을 가한다. 두 라운드에서 만든 동작이 없으면 조작할 대상이 없다
- **기존 오류 형태와 그 계약 문서**에 의존한다. 규약은 그것을 확장한다
- **기존 자동 검증 자산**에 의존한다 (RG-102). 회귀 판정의 기준이다
- 헌법 원칙 III(Stateful Interactive Runner) 과 보안 제약의 오류 처리 조항이 판정 근거다. 이 라운드는 헌법을 개정하지 않는다
