# Quickstart: 005 검증 절차

**Feature**: `specs/005-ux-walkthrough-repair` | **Date**: 2026-09-07

이 기능이 고친 것을 확인하는 절차다. **리포트의 재현 절차를 그대로 다시 걷는 것**이
검증이다 — 같은 조작에서 같은 증상이 나오지 않아야 한다 (SC-221).

자동 테스트로 고정한 것과 사람이 봐야 하는 것을 구분해 적었다.

---

## 0. 준비

```bash
# 대상 앱 (표준 라이브러리만 쓴다)
python fixtures/sample-app/serve.py --port 4300

# 백엔드 — 로컬 인터페이스에만 바인딩
cd backend && uv run uvicorn itb.api.app:app --host 127.0.0.1 --port 4320

# 프론트엔드
cd frontend && npm run dev            # http://127.0.0.1:4310
```

실제 프로젝트 데이터를 건드리지 않으려면 격리된 `XDG_DATA_HOME`·`XDG_CONFIG_HOME` 로
띄운다.

### 검증 재료

리포트가 쓴 것과 같은 재료를 만든다.

| 테스트 | 구성 | 쓰이는 곳 |
|---|---|---|
| **TC-FAIL** | 7 Step. Step 01~05 는 통과(로그인 포함), **Step 06 은 존재하지 않는 `testId` 로 반드시 실패**하며 대기 예산을 소진한다(약 20초), Step 07 은 미실행으로 남는다 | US1·US2·US3·US4·US7 |
| **TC-PASS** | 5 Step. 항상 통과 | US1(성공 결과 열기)·US2(통과 표기) |

Step 06 의 20초 대기 구간이 중지·일시정지의 전이 동작을 관찰할 **유일한 창**이다.
이 창이 없으면 US3 을 검증할 수 없다.

## 1. 자동 테스트로 고정된 것

```bash
# 백엔드
cd backend && uv run pytest

# 스키마 생성물이 최신인지 (결말 값 추가 후 필수)
uv run python -m itb.schema.export && git diff --exit-code schema/

# 프론트엔드
cd frontend && npm run gen:types && npm test
```

| 요구사항 | 테스트가 단정하는 것 |
|---|---|
| FR-124·125 | 종료 세션이 남아 있어도 `POST /api/sessions` 가 201 이다 |
| FR-128·SC-213 | 같은 테스트로 동시 생성 5건 중 **정확히 1건만** 201, 나머지는 409 |
| FR-131·SC-215 | 실행 중 중지 → 저장된 `outcome == "stopped"`, 실패 집계에 없다 |
| FR-132 | 의도적 중지에서 `session_lost` 이벤트가 발행되지 않는다 |
| FR-136·137 | 실패 Step 이 있는 상태의 재개가 그 Step 을 지나가지 않는다. 건너뛰기 경로의 결말은 `partial_pass` |
| FR-152 | 부분 실행이 `result-full.json` 을 덮지 않는다 |
| FR-160~162·SC-218 | **정적 페이지 세션에서 구독을 늦게 붙여도 3초 안에 `mirror_frame` 이 도달한다** (현재는 0건) |
| FR-164 | 미러 감시 태스크의 예외가 실행에 전파되지 않는다 |
| FR-165 | 미러 모듈이 CDP `Input.*` 을 보내지 않는다 (허용 명령 화이트리스트 유지) |
| FR-171 | 세션 조회 응답의 `step_results` 로 화면이 이벤트 없이 복원된다 |
| FR-127·129·SC-214 | 클릭 직후(응답 전) 버튼이 비활성이고 준비 문구가 보인다. 5회 연타에 호출 1회 |
| FR-138 | `stepLabel()` 이 유일한 변환 지점이다. 목록·결과·실행 화면이 같은 번호를 낸다 |
| FR-142 | pause 응답 지연 중 전이 배지가 보인다. `pause_settled=false` 를 뷰가 싣는다 |
| FR-151 | `skipped` 와 `not_run` 이 서로 다른 표시이며 텍스트 라벨이 있다 |
| FR-154·155·156·SC-217 | 저장 성공 후 인라인 확인·제목 변경·버튼 라벨 변경. 확인에 추가 화면 이동이 필요하지 않다 |
| FR-166·167 | URL ↔ 화면 상태 양방향 변환. `popstate` 가 앱 내부 이동이다 |

## 2. 사람이 봐야 하는 것 (화면 배치·문구)

자동 테스트로 옮기기 어려운 것들이다. 각 항목은 리포트의 재현 절차와 같다.

### S1. 실패 → 재실행 왕복 (US1 · U-01·U-11·U-12·U-13)

1. TC-FAIL 을 목록에서 실행한다 → **클릭 직후 버튼이 비활성 + 「준비 중…」** 인지 본다
2. Step 06 에서 실패해 실행이 끝난다
3. 「결과 보기」로 결과 화면을 연다
4. **「처음부터 실행」을 누른다** → 노란 경고 없이 실행이 시작되어야 한다
5. 다시 결과 화면으로 돌아와 **「Step 06부터 실행」** 을 누른다 → 시작되어야 한다
6. 목록으로 나가 TC-FAIL 행에 **「실행」과 「결과 보기」가 모두** 있는지 본다
7. TC-PASS 를 실행해 통과시킨 뒤, 목록 행에서 **그 결과를 열 수 있는지** 본다

**기대**: 4·5 단계에서 거절이 없다. 6·7 단계에서 두 경로 모두 도달 가능.

### S2. 중지 (US2·US3 · U-03·U-08)

1. TC-FAIL 을 실행해 Step 06(20초 대기)에 들어간다
2. 「중지」를 누른다 → **「중지 중…」** 으로 바뀌는지 본다
3. 중지 후 화면을 본다

**기대**: 「초안」 없음. 세션 유실 오류 없음. 세션 식별자 노출 없음.
`중지 · Step 06 에서 중지 · 5 / 7 통과` 요약. 네 개의 다음 행동 버튼.

4. 목록의 그 행을 본다 → **실패로 집계되지 않았는지** 본다
5. TC-PASS 를 실행해 끝낸 뒤 실행 화면의 버튼을 본다 → **「닫기」이고 강조가 없는지**,
   누르면 **확인을 묻는지** 본다

### S3. 일시정지 전이 (US3 · U-04·U-05)

1. TC-FAIL 을 실행해 Step 06 에 들어간다
2. 「일시정지」를 누른다 → **0.3초 안에** 배지 `일시정지 중…`, 문구
   `현재 Step 이 끝나면 멈춥니다`, 남은 대기 시간이 보이는지 본다
3. 그 상태에서 **Step 편집 팔레트가 열려 있지 않은지**, **「중지」가 활성인지** 본다
4. 기다린다 → 실행이 실패로 끝난다 → **`PAUSED` 배지와 결말이 동시에 뜨지 않는지**,
   `멈추기 전에 실행이 끝났습니다` 와 실패 사유·「결과 자세히 보기」가 있는지 본다
5. 다시 실행해 Step 05 통과 후 일시정지가 **성립**하게 만든 뒤, 실패 Step 이 있는
   상태에서 「계속하기」를 본다 → **비활성 + 이유**인지 본다
6. 「실패한 Step 건너뛰고 계속」을 눌러 끝낸다 → 결말이 **`부분 성공`** 인지 본다

### S4. 부분 실행 (US4 · U-02·U-21)

1. TC-FAIL 결과 화면에서 **「Step 06부터 실행」** 라벨에 번호가 있는지 본다
2. 그 버튼 옆 보조 문구에 **건너뛰는 구간과 선행 상태 경고**가 있는지 본다
3. 누른다 → 실행 중 Step 목록에서 **01~05 가 「건너뜀」** 으로 보이는지 본다
4. 끝난 결과 요약이 **`실패 · 부분 실행 Step 06~07 · 0 / 2 · (01~05 건너뜀)`** 인지,
   `0 / 7` 이 아닌지 본다
5. 실패 진단 첫 줄이 **선행 Step 건너뜀을 먼저 지시**하는지 본다
   (대기 시간을 늘리라는 지시가 첫 줄이면 실패)
6. 결과 화면에서 **건너뜀(01~05)과 미실행(07)이 다른 표시**인지, 텍스트 라벨이 있는지 본다
7. 「최근 전체 실행: 5 / 7 통과」 보조 표시가 남아 있는지 본다

### S5. 저장 (US5 · U-09·U-10)

1. 직접 녹화로 Step 몇 개를 만든다
2. 이름을 넣고 「저장」을 **한 번** 누른다
3. **화면을 옮기지 않고** 저장 성공을 알 수 있는지 본다
4. 제목에 「초안」이 남아 있지 않은지, 버튼이 「변경 저장」이고 비활성인지 본다
5. 목록으로 나가 배너의 정리 버튼 확인 문구를 본다 → **`Step n개가 사라집니다`** 가
   아닌지 본다

### S6. 미리보기 (US6 · U-24)

1. 새 세션을 만든다 (대상 앱 첫 화면은 정적이다)
2. **대상 화면을 건드리지 않고** 미리보기 영역만 본다

**기대**: 3초 안에 대상 화면이 표시된다. 현재는 무한정 비어 있다.

3. Step 06 의 20초 대기 구간에서 미리보기가 **비지 않고 화면을 유지**하는지 본다
4. 실행 화면을 벗어났다 다시 들어와 **즉시 화면이 보이는지** 본다

### S7. 새로고침·뒤로가기 (US7 · U-15~U-18)

1. 결과 화면에서 **새로고침** → 같은 결과 화면으로 돌아오는지
2. 아무 화면에서 **뒤로가기** → 앱을 이탈하지 않는지 (`about:blank` 로 가면 실패)
3. 실행 중 새로고침 → 목록의 그 행이 **실행 중**으로 보이고 복귀 수단이 있는지
4. 실행 중 목록으로 나가 실행이 끝날 때까지 기다린다 → 배너가 **스스로 갱신**되는지
   (25초 안)
5. 끝난 세션을 다시 열어 Step별 **✓ 와 소요시간이 남아 있는지**

### S8. 컨트롤 설명 (US8 · U-22·U-23)

1. 결과 화면의 증거 탭 4개를 모두 확인한다 → 비활성 탭에 **이유**가 있는지, 빈 탭이
   **없다는 사실을 긍정문**으로 말하는지
2. 직접 녹화 중 헤더의 속도 컨트롤 라벨이 **「다음 실행 속도」** 인지

## 3. 회귀로 지켜야 하는 것

이 기능은 동작하는 제품을 고친다. 아래는 **깨지면 안 되는 기존 성질**이며, 각각 기존
테스트가 있다.

| 성질 | 근거 |
|---|---|
| 재실행 경로에 언어모델이 없다 | 헌법 원칙 II. 새 진단 문구는 전부 규칙 기반이다 |
| 일시정지가 브라우저 상태를 유지한다 | 헌법 원칙 III. 경계 대기 로직을 바꾸지 않는다 |
| 테스트당 동시 실행 1건 | FR-043. 이 기능은 그것을 **지키기 위한** 수정이다 |
| 중지가 화면을 떠나지 않는다 | DR-010. 결말 화면으로 남기되 화면 전환은 하지 않는다 |
| 미러가 입력을 전달하지 않는다 | FR-047a. 송신 쪽만 만진다 |
| 미러 실패가 실행에 무영향 | FR-047b |
| 저장된 정의에 속도가 기록되지 않는다 | 004 FR-110 |
| Step 간 간격이 대기 예산에 포함되지 않는다 | 004 FR-105 |

## 4. 판정

- **§1 이 전부 통과**하고
- **§2 의 S1~S8 에서 리포트의 증상이 재발하지 않으며**
- **§3 의 기존 성질이 유지되면**

이 기능은 완료다. §2 에서 하나라도 재발하면 그 항목의 U 번호를 들어 남은 작업으로
등록한다 — 조용히 넘기지 않는다.
