# Contract: 입력값 검증의 작성 표면

**Feature**: 023 | **헌법 원칙 I** (Unified Step Model) | 명세 FR-030~FR-036

세 작성 경로가 같은 정의를 만들어야 한다. 이 문서는 **각 경로가 무엇을 받고 무엇을
거절하는지**를 규정한다.

---

## 1. 경로별 지원 범위

| 경로 | 입력값 검증을 만들 수 있는가 | 왜 |
|---|---|---|
| 화면의 검증 추가 폼 | **가능** | 셀렉터로 대상을 지정한다 |
| AI 작성 (`assert_condition`) | **가능** | 요소 참조로 대상을 지정한다 |
| 저장된 테스트에 손으로 Step 삽입 | **불가능** | 그 경로는 대상 요소를 받는 필드가 하나도 없다 |

셋째 줄은 이번에 생기는 제약이 아니다. 손으로 넣는 Step 은 **살아 있는 페이지에서만 후보를
수집·검증할 수 있다**는 이유로 대상을 아예 받지 않도록 설계돼 있고, 입력값 검증은 대상이
필수(FR-002)라 교집합이 비어 있다. 명세의 범위 외 표에 적혀 있다.

**화면에서 이 사실이 읽혀야 한다.** 목록에 넣고 눌렀을 때 실패하게 두지 않는다.

---

## 2. 대상 성질에 따른 판정 — 두 경로가 같은 규칙을 쓴다

| 대상 | 판정 | 사용자가 보는 것 |
|---|---|---|
| `input` (text·email·number·tel·url·search·date·password…) | 받는다 | — |
| `textarea` | 받는다 | — |
| `select` | 받는다 | **안내**: 보이는 항목 이름이 아니라 내부 식별자를 비교한다 |
| `input[type=checkbox]` · `input[type=radio]` | **거절** | 왜 만들 수 없는지 |
| 그 밖의 태그 (`button`·`div`·`a`…) | **거절** | 왜 만들 수 없는지 |
| 태그를 읽지 못함 | 받는다 | — (실행 시점에 드러난다) |

### 거절은 Step 을 만들지 않는 것이다

경고를 띄우고 만드는 것이 아니다. 021 의 상태 검증 경고와 다르며, 그 차이에 이유가 있다.

| | 021 상태 검증의 판정 불가 대상 | 023 입력값 검증의 값 없는 대상 |
|---|---|---|
| 실행하면 | 「조작할 수 있다」로 **통과**한다 | **오류**로 끝난다 |
| 정당한 쓸모 | 있다 — ARIA 로 잠금을 표현하는 위젯 | 없다 |
| 그래서 | 막으면 정당한 경우까지 막힌다 → **경고** | 반드시 실패할 Step 이 남는다 → **거절** |

제품에 이미 같은 판단이 있다: 후보를 수집하지 못한 대상에 대해 「재실행에서 반드시
실패하므로, 만들어 두는 것이 사용자에게 더 나쁘다」.

### 거절 문구가 담아야 할 것

무엇을 할 수 없는지만이 아니라 **무엇을 대신 할 수 있는지**를 담는다.

| 대상 | 담을 내용 |
|---|---|
| 체크박스·라디오 | 값이 체크 여부와 무관하다는 사실 + 체크 상태 검증은 아직 없다는 사실 |
| 값 없는 태그 | 그 태그에는 값이 없다는 사실 + 화면 글자를 보려면 텍스트 검증이라는 안내 |

둘째 줄이 중요하다. **이 기능이 고치려는 실수의 반대 방향**이라, 여기서 텍스트 검증을
가리키지 않으면 사용자는 두 종류 사이를 오가며 헤맨다.

## 3. 비밀번호 칸 — 평문 비교 값을 거절한다

| 대상 | 비교 값 | 판정 |
|---|---|---|
| `input[type=password]` | `{{SECRET_PW}}` | 받는다 |
| `input[type=password]` | `hunter2` (평문) | **거절** |
| `input[type=password]` | `{{USERNAME}}` (민감하지 않은 변수) | **거절** — 평문과 같다. 정의 파일에 값이 남는다 |
| 그 밖의 대상 | 무엇이든 | 받는다 |

셋째 줄이 판단이 필요한 칸이다. **민감하지 않은 변수는 정의 파일에 값을 갖는다**
(`Variable._no_plaintext_secret` 이 막는 것은 민감 변수의 평문이다). 그러므로 비밀번호
칸의 값을 그것으로 비교하면 평문을 적은 것과 결과가 같다. 참조라는 형식이 아니라
**민감하다는 사실**이 기준이다.

### 거절 문구

무엇이 문제인지와 어떻게 하는지를 함께 담는다 — 「비밀번호 칸의 값은 정의 파일에 평문으로
남길 수 없습니다. 민감 변수(`SECRET_` 로 시작하는 이름)로 비교하세요.」

## 4. 화면 폼의 표면

### 종류 목록에서의 자리

```
요소가 보인다
요소가 없거나 보이지 않는다
요소를 조작할 수 있다
요소를 조작할 수 없다
─────────────
텍스트
입력값          ← 023
주소
```

**텍스트 바로 아래**에 둔다. 둘이 가장 헷갈리는 짝이고, 붙여 놓아야 고르는 순간 비교된다.
「요소에 대한 넷을 앞에, 값을 비교하는 것을 뒤에」라는 기존 순서 규칙도 지켜진다.

### 각 칸의 상태

| 칸 | `value` 를 골랐을 때 |
|---|---|
| 대상 요소 (CSS 셀렉터) | **보이고, 필수**다 |
| 비교 값 | **보이고, 필수**다 |
| 비교 방식 | **보인다** — 네 가지 모두 |
| 부정 비교 안내 | 021 의 관찰 기간 설명이 그대로 뜬다 |

### 문구

| 자리 | 내용 |
|---|---|
| 종류 이름 | **입력값** |
| 종류 설명 | 입력 칸·선택 목록에 **담긴 값**을 본다. 화면에 보이는 글자가 아니다 |
| 선택 목록 안내 | 보이는 항목 이름이 아니라 내부 식별자를 비교한다 |

종류 설명이 **텍스트 검증과의 차이를 직접 말한다.** 「입력값을 본다」만 쓰면 텍스트 검증을
고른 사람이 자기가 틀렸다는 것을 알 수 없다.

문구는 `frontend/src/lib/wording.ts` 가 소유한다 (021 FR-023). 폼과 목록이 각자 만들지
않는다.

## 5. 입력 칸에 텍스트 검증을 고른 경우 — 경고하되 막지 않는다

| 조건 | 무엇을 하는가 |
|---|---|
| `text` 검증 + 대상이 `input`·`textarea` | **경고한다.** Step 은 만든다 |
| `text` 검증 + 대상이 `select` | 경고하지 않는다 — 선택 목록은 자식 `option` 의 글자를 텍스트로 갖는다 |

막지 않는 이유는 하위 호환이다 (FR-030·FR-040). 이미 저장된 정의에 그런 조합이 있고,
거절로 바꾸면 그 테스트가 열리지 않는다.

### 경고 문구가 담아야 할 것

「이 대상에서는 언제나 빈 문자열로 관찰됩니다. 칸에 담긴 값을 보려면 **입력값 검증**을
쓰세요.」

021 의 `stateless_target_warning` 과 같은 통로(`add_edit_warning`)를 쓴다. **단, 그 통로는
지금 화면 폼 경로에만 연결돼 있다** — [research R3](../research.md). 023 이 더하는 판정은
두 경로가 모두 부르는 함수에 둔다.

## 6. AI 작성 도구의 표면

`assert_condition` 도구 설명(모델이 보는 유일한 안내)에 담을 것.

| 담을 내용 | 왜 |
|---|---|
| `kind` 목록에 `value` 추가 | 없으면 모델이 쓸 수 없다 |
| **입력 칸·선택 목록의 값을 볼 때는 `text` 가 아니라 `value`** | 이 기능이 고치려는 실수 자체다 (FR-034) |
| `value` 는 `element_ref` 가 필요하다 | 형태 규칙 |
| 비밀번호 칸은 민감 변수 참조로만 비교한다 | 모델이 평문을 적으려다 거절당하고 헤매지 않도록 |

기존 안내 중 **「기대와 달라도 Step 으로 기록된다. 값을 바꾸거나 조건을 뒤집어 다시 시도하면
안 된다」는 그대로 둔다.** 새 종류에도 같게 적용된다 (FR-009).

### 거절이 모델에게 어떻게 보이는가

`{"error": "..."}` 로 돌아가고, **도구 호출 횟수를 소모한다.** 그러므로 거절 문구는 모델이
다음에 무엇을 해야 하는지 알 수 있어야 한다 — 「체크박스는 값 검증 대상이 아닙니다」로
끝내면 모델은 같은 것을 다시 시도한다.

## 7. 표시 이름

| 조건 | 표시 이름 |
|---|---|
| `value` + `equals` + `E2E역할테스트` | `입력값이 'E2E역할테스트'와 같음 확인` |
| `value` + `contains` | `입력값이 '…'를 포함 확인` |
| `value` + `not_equals` | `입력값이 '…'와 다름 확인` |
| `value` + `not_contains` | `입력값이 '…'를 포함하지 않음 확인` |

기존 `text`·`url` 의 형태(`{주어}가 {값}{비교} 확인`)를 그대로 따른다. **비교 방식이 반드시
들어간다** — 021 이 「그것이 빠지면 긍정과 부정이 같아 보인다」고 정한 규칙이다.

주어가 `텍스트` 가 아니라 `입력값` 인 것이 목록에서 두 종류를 가르는 유일한 단서다.
