## R1 — 어긋남 표시를 어디에 두는가

**질문**: 「작성 시점에 이 검증이 통과하지 않았다」를 `AssertionStep` 전용 필드로 둘지,
모든 Step 이 갖는 공통 필드로 둘지, Step 밖의 사이드카 목록으로 둘지.

**결정**: `AssertionStep` 에만 두는 선택 필드. `mismatch: AuthoringMismatch | None = None`.

**근거**:

- **「어긋난 동작 Step」은 원리적으로 존재할 수 없다.** 동작 Step 은 실패하면 기록되지
  않는다 (FR-006). 공통 필드로 올리면 8개 Step 종류에 **영원히 `None` 인 칸**이 생기고,
  읽는 쪽은 그 칸이 왜 비어 있는지를 매번 판단해야 한다.
- **사이드카는 진실을 둘로 만든다.** 테스트 단위 「알려진 결함 목록」을 따로 두면 Step 을
  지웠을 때 목록에 유령이 남고, 공유·엑셀·내보내기가 각자 옮겨야 한다. 명세의
  Assumptions 가 「어긋남 표시는 Step 단위다」로 이미 못 박았다.
- **기대값은 새로 저장하지 않는다.** 기대값은 `assertion.value` 에 이미 있다. 새로 필요한
  것은 **그때 화면이 무엇이었는가**와 **어긋났다는 사실** 둘뿐이다. 기대값을 복제해 두면
  Step 편집으로 `assertion.value` 를 고쳤을 때 둘이 갈린다.
- **`None` 이 기존 정의를 그대로 통과시킨다.** `_StepBase` 는 `extra="forbid"` 라 새 필드를
  명시적으로 더해야 하고, 기본값 `None` 이면 020 이전에 저장된 모든 정의가 재검증을
  통과한다. 「표시 없음 = 작성 시점 통과」라는 명세의 호환 가정이 그대로 성립한다.

**헌법 원칙 I 점검**: 이 필드는 Provenance 와 같은 성질의 **부가 정보**다. 실행기는 이
필드를 읽지 않으며(FR-012), 사람이 만든 검증도 같은 필드를 갖는다(FR-011). 원칙이 허용하는
「MAY be recorded as metadata, MUST NOT change how the Step executes」에 정확히 해당한다.

**버린 대안**:

| 대안 | 버린 이유 |
|---|---|
| `_StepBase` 공통 필드 | 채워질 수 없는 칸이 8종에 생긴다 |
| 테스트 단위 사이드카 목록 | 진실이 둘. Step 삭제 시 유령. 공유·엑셀이 각자 옮겨야 함 |
| `assertion` 안에 넣기 | `Assertion` 은 **조건**이다. 「그때 어땠는가」는 조건이 아니라 이력이고, 생성기가 `Assertion` 만 읽으므로 섞이면 내보내기에 새어 나간다 |

## R2 — 관찰값으로 무엇을 저장하는가

**질문**: FR-008 의 「작성 시점 관찰값」을 어떤 형태로 남길 것인가. `visible`·`hidden`
검증에는 비교할 텍스트가 없다.

**결정**: 실행기가 실패할 때 만드는 **설명 문장**을 스크러빙해 저장한다. 4종 검증 전부에
같은 방식이 적용된다.

**근거**: `StepExecutor._assert_*` 는 이미 실패마다 사람이 읽을 문장을 만든다
(`_assert_text` 는 실제 텍스트를, `_assert_hidden` 은 보이고 있다는 사실을). 새 관찰
로직을 만들면 **같은 상황을 두 곳이 서로 다르게 설명**하게 되고, 화면의 문구와 실행 결과의
문구가 갈린다. 스크러빙은 `Scrubber` 를 그대로 쓴다 — FR-015 의 민감값 규칙이 자동으로
따라온다.

**상한**: 4000자. `Assertion.value` 의 상한과 같은 값을 쓴다 — 기대값보다 관찰값이 더 길게
남을 이유가 없고, 두 상한이 다르면 어느 쪽이 기준인지 설명할 말이 없다. 넘으면 잘라내고
`truncated: true` 를 남긴다 (FR-008).

## R3 — 도구 실행 경로를 어디서 가르는가

**질문**: `BrowserToolbox._execute()` 는 9개 Step 생성 도구가 모두 지나는 한 곳이다.
검증만 실패 시 기록하게 하려면 어디를 건드리는가.

**결정**: `_execute` 에 **실패 처리 정책 인자**를 더한다. `assert_condition` 만 그 인자를
켜서 부른다.

```
_execute(step, element, *, keep_on_failure: bool = False)
```

**근거**: 대안은 `assert_condition` 이 `_execute` 를 쓰지 않고 자기 경로를 갖는 것인데,
그러면 실행·진행 알림·새 탭 감지·상한 기록이 **복제**된다. 이 저장소가 반복해서 피해 온
실패 방식이 정확히 그것이다 (도구 표면이 둘로 갈린 경우, 스키마가 손으로 두 벌 유지된
경우). 복제된 순간 두 경로가 조용히 갈라지고, 갈라진 것을 검사가 잡지 못한다.

**도구 표면 계약은 건드리지 않는다.** `TOOL_NAMES` 16종, `STEP_PRODUCING_TOOLS` 9종,
Step 종류와의 1:1 대응이 그대로다. 바뀌는 것은 도구 하나의 **실패 처리**이지 표면이 아니다.

**반환 형태** (FR-010):

| 경우 | 반환 |
|---|---|
| 검증 통과 | `{"ok": true, "step": ...}` — 현행 |
| 검증 어긋남 | `{"ok": true, "assertion_failed": true, "note": "...값을 바꾸지 말고..."}` |
| 대상 없음 | `{"error": ...}` — 현행 (R4) |

`ok: true` 와 `assertion_failed: true` 를 **함께** 싣는 이유: 도구 호출로서는 성공했고
(Step 이 기록됐다), 검증 결과로서는 어긋났다. 둘은 다른 축이며, 한 축으로 뭉치면 모델이
「실패했으니 다시」로 읽는다.

## R4 — 대상 없음을 어긋남과 어떻게 가르는가

**질문**: FR-007. 검증 대상 요소를 찾지 못한 경우는 어긋남이 아니다.

**결정**: `assert_condition` 이 **Step 을 만들기 전에** 대상을 해석하는 기존 단계에서
갈린다. 지금도 `refs.get(element_ref)` 와 `collect_by_selector` 가 실패하면 `{"error": ...}`
를 돌려주고 Step 을 만들지 않는다 — **이 경로는 그대로 둔다.**

**근거**: 대상 없음은 「무엇을 관찰했는지 적을 수 없는 상태」다. 어긋남으로 기록하면
`observed` 가 빈 문자열인 거짓 기록이 만들어지고, 나중에 그것을 본 사람은 「화면이 비어
있었다」로 읽는다.

**주의할 경계**: 대상 참조는 있었는데 **실행 시점에** 요소가 사라진 경우
(`ElementNotFoundError` → `StepFailure`)는 어긋남이다 — `visible` 검증이 어긋났다는 것이
바로 그 뜻이다. 가르는 기준은 **언제 실패했는가**가 아니라 **무엇이 실패했는가**다:
참조 해석 실패 = 대상 없음, 검증 판정 실패 = 어긋남.

## R5 — 상한 계산에서 어긋남을 빼는 방법

**질문**: FR-009. 어긋남이 연속 실패 상한을 올리면 기대값 고수가 여전히 처벌된다.

**결정**: `AttemptLimits` 에 `record_mismatch(element)` 를 더한다. 이 메서드는
**연속 실패 계수와 `last_failed_element` 를 둘 다 건드리지 않는다.**

**근거**:

- `record_failure` 를 부르지 않는 것만으로는 부족하다. 아무것도 부르지 않으면 앞선 실패의
  `last_failed_element` 가 남아, 다음 실패가 **연속**으로 세어진다. 명시적 메서드를 두면
  「어긋남은 성공도 실패도 아니다」가 코드에 적힌다.
- `record_success` 를 부르지 **않는** 이유: 그것은 연속 실패를 **초기화**한다. 어긋남이
  다른 요소의 실패 흐름을 지우면 상한이 약해진다. 어긋남은 상한에 대해 중립이어야 한다.
- **총 호출 상한은 자동으로 유지된다.** `assert_condition` 진입 시 `record_call()` 이
  먼저 돌기 때문이다 (FR-009 후반부). 모델이 같은 검증을 무한히 시도해도 총 상한에서
  멈춘다.

## R6 — 막힘 사유 종류를 어떻게 더하는가

**질문**: FR-023. 「제품이 지시문과 다르게 동작해 막혔다」를 어떻게 표현하는가.

**결정**: `report_blocked` 에 **인자를 더한다.** 도구를 늘리지 않는다.

```
report_blocked(reason: str, question: str = "", kind: str = "needs_input")
```

`kind` 값 2개: `needs_input`(기본 · 현행 동작) · `product_mismatch`.

**근거**: 전례가 그대로 있다. `question` 필드도 같은 판단으로 추가됐다 — 「물을 것이
있다는 사실은 **막힘의 성질**이지 별개의 동작이 아니다」(`tools.py` `report_blocked`
docstring). 막힘의 원인 종류도 같은 성질이다. 도구를 늘리면
`STEP_PRODUCING_TOOLS` ↔ Step 종류의 1:1 대응을 검사하는 `test_tool_surface.py` 가
분류 표를 다시 짜야 한다.

**FR-024 강제**: `kind == product_mismatch` 이면 `question` 을 버린다. 도구 쪽에서 버리는
이유는, 모델이 규칙을 어겨 질문을 실어 보내도 화면에 답변 칸이 열리지 않아야 하기 때문이다.
지침에만 적어 두면 모델이 어길 때 막을 것이 없다.

**전파 경로**: `BrowserToolbox.blocked_kind` → `AgentOutcome.blocked_kind` →
`ai_blocked` 이벤트의 새 필드. 기존 소비자는 필드가 없어도 돌아야 하므로 기본값을 둔다.

## R7 — 실행 결과의 분류를 어디에 두는가

**질문**: FR-018~FR-022. 알려진 결함 / 회귀 / 해소됨을 어떻게 판정하고 어디에 남기는가.

**결정**: **판정은 순수 함수, 저장은 `StepResult` 의 필드.**

```
classify_assertion(step, result) -> AssertionClass | None
```

| `step.mismatch` | `result.outcome` | 분류 |
|---|---|---|
| 있음 | FAIL | `known_defect` |
| 없음 | FAIL | `regression` |
| 있음 | PASS | `resolved` |
| 그 외 · 검증 Step 이 아님 | — | `None` |

**왜 저장하는가**: 분류는 **정의와 결과 둘 다**를 봐야 나온다. 결과 파일
(`.runs/<테스트ID>/result.json`)만 들고 화면을 그리는 자리가 있고, 정의는 그 뒤에 바뀔 수
있다. 저장하지 않으면 어제 실행한 결과의 분류가 오늘 정의를 고친 것 때문에 달라진다 —
결과는 **그때의 사실**이어야 한다.

**왜 순수 함수로 판정하는가**: `decide_outcome` 이 세운 선례다. 판정을 여러 곳에 흩으면
화면과 저장된 결과가 어긋난다 (005 가 그것으로 U-03·U-05 를 겪었다).

**건수 요약은 저장하지 않는다.** `counts_by_class(steps)` 순수 함수로 그때그때 센다.
파생값을 저장하면 원본과 어긋날 자리가 생기고, `attempted_of` 가 이미 같은 방식이다.

**`Outcome` enum 은 건드리지 않는다** (FR-021). `decide_outcome` 도 그대로다.

## R8 — 실행을 계속 진행시키는 지점

**질문**: FR-033. 검증 실패가 실행을 멈추지 않게 하려면 어디를 고치는가.

**결정**: `runner.py` 의 `run_step()` 실패 경로에서, Step 이 `AssertionStep` 이면
`True` 를 돌려준다. **`failed_index` 와 `_failure_tab` 은 설정하지 않는다.**

**근거**:

- `run_step` 의 반환값이 이미 「계속 진행할지」다 (001 FR-049). 새 개념이 필요 없다.
- **`failed_index` 를 설정하지 않는 것이 핵심이다.** 그 값의 뜻은 「실패한 Step」이 아니라
  **「실행이 멈춘 자리」**다 — 재시도·건너뛰기·인수 UI 가 그 자리를 근거로 동작한다.
  검증 실패는 멈추지 않으므로 멈춘 자리가 아니다. 설정하면 여러 검증이 실패할 때 마지막
  것이 「멈춘 자리」가 되어, 사용자가 거기서 재시도를 누르면 엉뚱한 곳으로 간다.
- `step_failed` 이벤트는 **그대로 낸다.** 화면은 실패를 즉시 보여야 하고, 그 이벤트가
  멈춤을 뜻한 적은 없다.
- **결말은 대개 자동으로 실패다** (FR-036). `decide_outcome` 의 4번 규칙
  (`any FAIL → FAIL`)이 걸린다. **단, 한 자리를 고쳐야 한다** — 아래 R13.

**동작 Step 은 그대로 멈춘다** (FR-034). 분기는 `isinstance(step, AssertionStep)` 하나다.

**부작용 점검**: 뒤 Step 들이 `NOT_RUN` 대신 실제 결과를 갖게 되므로 `attempted_of` 의
분모가 커진다. 이것은 의도한 변화다 — 실제로 실행했으므로 분모에 있어야 한다.

## R10 — 스키마 단일 출처 경로

**결정**: 기존 경로를 그대로 쓴다. 새 작업이 없다.

```
backend/src/itb/domain/*.py  (Pydantic v2 · 권위)
  → uv run python -m itb.schema.export    → backend/schema/*.json
  → npm run gen:types                     → frontend/src/types/generated/*.d.ts
```

`json_schema_serialization_defaults_required=True` 때문에 `mismatch` 는 직렬화 스키마에서
required 로 나오고, 생성된 TypeScript 는 `AuthoringMismatch | null` 이 된다. 프론트엔드는
`null` 검사만 하면 되고 옵셔널 프로퍼티 분기가 생기지 않는다.

**`step.schema.json` 과 `run-result.schema.json` 둘 다 재생성한다.** 전자는 `mismatch`,
후자는 `assertion_class` 때문이다.

## R11 — PRD §18 지표 재정의의 실제 크기

**질문**: FR-030. 「재실행 성공률 ≥95%」와의 충돌을 어떻게 푸는가.

**발견**: PRD 의 현행 문면은 이미 이 방향이다.

> Replay Success Rate — **생성 당시 성공한 테스트**가 동일 환경에서 다시 성공하는 비율.
> 목표: ≥ 95%

어긋남으로 기록된 검증은 **생성 당시 성공하지 않았다.** 그러므로 이 지표의 대상이 아니다.
충돌은 목표치에 있지 않고 **문면의 해상도**에 있다 — 「테스트」 단위로 읽으면 어긋난 검증이
하나라도 있는 테스트 전체가 대상에서 빠지고, 그 테스트의 나머지 검증이 회귀해도 지표에
잡히지 않는다.

**결정**: 목표치(≥95%)는 그대로 두고, **판정 단위를 Step 으로 내리는 한 문장**을 더한다.

> 판정은 Step 단위다. 작성 시점에 어긋남으로 기록된 검증 Step 은 분모에서 제외하고,
> 같은 테스트의 나머지 Step 은 분모에 남는다.

**작업 크기**: `docs/prd.md` 한 단락. 헌법 개정이 아니다 — 헌법은 이 지표를 Principle II 의
**근거로 인용**할 뿐 수치를 정의하지 않는다. `docs/mvp-metrics.md` 에는 이 지표의 측정
항목이 없어 수정 대상이 아니다.

## R12 — AI 작성 지침을 어디에 적는가

**결정**: `agent.py` 의 `SYSTEM_PROMPT` 에 **검증 전용 절**을 새로 연다. 기존 규칙 목록
중간에 끼우지 않는다.

**근거**: 지금 목록의 한 줄 「한 지시를 여러 동작으로 나누어 차례로 수행하세요. **성공한
동작만 테스트로 남습니다.**」가 문제의 일부다. 이 문장을 그대로 두고 검증 규칙을 다른 줄에
더하면 모델이 상충하는 두 규칙을 받는다. **이 문장을 동작 Step 에 한정하도록 고치고**,
검증은 별도 절에서 다룬다.

절에 들어갈 것 (FR-001~FR-004 · FR-031~FR-032):

1. 저장되는 정의는 「제품이 지금 하는 일」이 아니라 「사용자가 요구한 일」이다.
2. 검증의 기대값은 지시문에서 가져온다. 화면에서 읽은 값으로 바꾸지 않는다.
3. 검증이 통과하지 않아도 기록된다. 값을 바꿔 다시 시도하지 않는다.
4. 지시문이 기대값을 말하지 않으면 존재 여부만 검증한다. 값을 지어내지 않는다.
5. 요구한 동작을 할 수 없으면 우회하지 않고 `report_blocked(kind="product_mismatch")`.

**`nl_step.py` 의 `NL_STEP_SYSTEM_HINT` 도 같은 규칙이 필요하다.** 일시정지 중 자연어로
검증 Step 하나를 추가하는 경로이며, 같은 문제가 그대로 있다.

## R13 — `PARTIAL_PASS` 가 검증 실패를 삼키는 문제 (정합성 점검 F1 · 2026-09-28)

**질문**: 검증 실패가 쌓인 채로 사용자가 뒤쪽 동작 Step 을 「건너뛰고 계속」하면 결말이
어떻게 되는가.

**발견**: `decide_outcome()` 의 우선순위에서 **3번(`skipped_failures` → `PARTIAL_PASS`)이
4번(`any FAIL` → `FAIL`)보다 먼저** 걸린다. `skipped_failures` 는 사용자가 건너뛰기를
고른 적이 있는지를 나타내는 **불리언 하나**이며, 어느 Step 을 건너뛰었는지는 보지 않는다.

그래서 이런 실행이 만들어진다.

```
step-03  검증 실패 — 회귀 (아무도 건너뛰지 않았다)
step-07  동작 실패 — 사용자가 건너뛰기를 골랐다
step-12  통과
         → skipped_failures = True → PARTIAL_PASS
```

**회귀가 부분 성공으로 덮인다.** 사용자가 보는 것은 초록에 가까운 결말이고, 정작 잡아야
할 것은 그 아래 묻힌다.

**이 결함은 020 이전에도 있었다.** 다만 검증 실패가 실행을 멈췄으므로 「실패가 쌓인 채
계속 도는 상태」가 드물었다. FR-033 이 그것을 **상시 경로**로 만든다 — 그래서 여기서
함께 고친다. 고치지 않으면 020 이 회귀를 더 많이 잡아내면서 동시에 더 많이 숨긴다.

**결정** (2026-09-28 사용자): 3번 규칙에 조건을 더한다 — **건너뛰지 않은 실패가 하나라도
남아 있으면 `PARTIAL_PASS` 로 가지 않는다.**

**근거**: `PARTIAL_PASS` 의 뜻은 「실패한 것들을 사용자가 알고 건너뛰었다」이지 「실패가
있었다」가 아니다. 조건을 좁히는 것이 그 뜻을 되찾는 일이며, **우선순위의 순서를 바꾸는
것이 아니다.** `Outcome` enum 도 그대로다 (FR-021).

**판정 근거의 변화**: `skipped_failures` 불리언만으로는 부족하다. 「어느 Step 이
건너뛰어졌는가」를 알아야 하고, 그것은 `StepResult.outcome == SKIPPED` 로 이미 결과에
있다. 다만 **부분 실행의 앞선 Step 도 `SKIPPED`** 이므로(`skip_before`), 그 둘을
구별하지 않으면 부분 실행이 전부 `PARTIAL_PASS` 가 된다 — `decide_outcome` 의 docstring 이
이미 경고하는 바로 그 함정이다.

**버린 대안**:

| 대안 | 버린 이유 |
|---|---|
| 우선순위에서 3번과 4번을 맞바꾼다 | 순수한 건너뛰기 실행까지 `FAIL` 이 된다. 005 가 `PARTIAL_PASS` 를 만든 이유(U-05)를 되돌리는 것 |
| 명세에 예외를 적고 코드는 그대로 | 회귀가 초록색으로 보이는 상태를 문서로 승인하는 것 |
| 검증 Step 의 실패만 예외 처리 | 규칙이 Step 종류별로 갈려 설명할 수 없다. 건너뛰지 않은 **동작** 실패도 같은 문제를 갖는다 |
