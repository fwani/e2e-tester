# Research: 지난 턴이 이어진다 (025)

**Date**: 2026-09-29 | **Spec**: [spec.md](./spec.md)

---

## R1. 한 턴의 이력은 정말 사라지는가 — 실측

**결론**: 사라진다. 스펙의 전제이므로 추정으로 두지 않고 실행해 확인했다.

SDK 의 tool runner 는 생성자에서 `params["messages"]` 를 **얕은 복사**한 뒤
(`_beta_runner.py:108`), 이후 `set_messages_params` 로 **새 리스트를 만들어 교체**한다.
호출자가 넘긴 리스트 객체는 한 번도 수정되지 않는다.

```
runner 내부 messages 수: 3      (user → assistant → tool_result)
호출자가 넘긴 리스트 수: 1      (user)
동일 객체인가: False
```

따라서 `AuthoringAgent.messages` 에는 `run`·`chat`·`resume_with_answer`·
`resume_after_takeover` 가 넣은 **사용자 메시지만** 쌓인다. 어시스턴트 차례는 하나도 없고,
도구 호출과 그 결과도 없다.

### 왜 지금까지 드러나지 않았는가

`backend/tests/us4_support.py` 의 가짜 드라이버가 `_sdk_driver` 를 통째로 대체한다. 그
드라이버는 도구를 직접 부르고 결과를 자기 안에서만 다루므로, SDK 의 messages 처리는 검증
범위 밖이었다. **이 기능은 그 빈칸을 메우는 검증을 함께 가져야 한다** — 그러지 않으면
같은 유실이 다시 생겨도 테스트가 통과한다.

### 영향 범위

`resume_with_answer` 의 독스트링은 "새 지시로 시작하면 앞서 무엇을 하다 막혔는지 잊고
처음부터 다시 한다" 고 적고 있다. 그 문장이 서술하는 실패가 **지금 일어나고 있다.**
의도는 옳았고 구현이 따라가지 못했다.

## R2. 무엇을 남길 것인가 — 도구 호출 저널

**결정**: 한 턴 동안 제품이 **자기가 부른 도구와 그 결과 요지**를 모아 두고, 턴이 끝날 때
그것을 하나의 어시스턴트 메시지로 접어 이력에 남긴다.

**근거**: 제품은 이미 이 사실을 전부 알고 있다. `BrowserToolbox` 의 모든 도구가
`_announce(...)` 로 진행 문구를 내고 있고, 그 문구가 곧 「무엇을 했는가」다. 새로 관찰할
것이 없다.

**고려한 대안**

| 대안 | 기각 사유 |
|---|---|
| runner 내부 `_params["messages"]` 를 꺼내 그대로 이어 붙인다 | 크기가 폭발한다 — 화면 한 장이 **66.7KB** 이고(baseline.md T002 실측) 한 턴에 스무 장이 쌓인다. 그리고 SDK 의 사적 속성에 의존하게 되어 버전이 오르면 조용히 깨진다 |
| 턴이 끝날 때 모델에게 요약을 시킨다 | 호출이 한 번 더 늘고, 무엇이 사라졌는지 말해 주지 않는다. 사라진 것이 하필 제약일 때 드러나지 않는다 (FR-005 가 금지) |
| `chat_turns`(사람이 읽는 기록)를 그대로 쓴다 | 그것은 사람이 읽는 것이라 도구 호출이 들어 있지 않다. 목적이 다르다 — 016 이 두 개를 갈라 둔 판단을 뒤집지 않는다 |

**남기는 것과 남기지 않는 것**

| 남긴다 | 남기지 않는다 |
|---|---|
| 부른 도구 이름과 대상 | 화면 요소 목록 |
| 성공·실패와 그 사유 | 화면 본문 텍스트 |
| 만들어진 Step 의 이름 | 요소 참조(`e17`) — 다음 턴에 낡는다 |
| 막힌 지점과 사유·질문 | 조작에 넘긴 값 (민감값 규칙) |
| 모델이 낸 마지막 답 | |

요소 참조를 남기지 않는 것이 중요하다. 참조는 화면이 바뀌면 낡고, 낡은 참조를 본 모델은
관찰 없이 그것을 쓰려 든다 — 그 시도는 거절되지만 예산을 깎는다.

## R3. 어시스턴트 차례를 어떻게 세우는가

**결정**: 턴이 끝날 때 `{"role": "assistant", "content": <수행 기록 + 마지막 답>}` 하나를
이력에 넣는다.

**근거**: 지금 이력은 사용자 메시지만 연달아 실린 형태다. 모델에게 그것은 대화가 아니라
지시문 더미이고, 「내가 앞서 무엇을 했다」는 자리 자체가 없다. 어시스턴트 차례를 세우는
것이 그 자리를 만드는 가장 곧은 방법이다.

`last_reply` 는 이미 매 턴 채워져 있다 (016 FR-009). 값이 있는데 이력에 싣지 않고 있었을
뿐이다.

**한 메시지로 합치는 이유**: 수행 기록과 모델의 답을 두 메시지로 나누면 어시스턴트 차례가
연달아 오고, 그것은 다시 「대화가 아닌 더미」다.

## R4. 턴 내부의 낡은 관찰을 어디서 접는가

**결정**: 드라이버가 접는다. `_sdk_driver` 가 runner 를 만들어 들고, 매 iteration 뒤
`runner.set_messages_params(...)` 로 지난 화면 관찰 결과를 접은 뒤 다음 iteration 으로
넘어간다.

**근거**: 접을 대상이 존재하는 곳이 runner 안뿐이다. `AuthoringAgent.messages` 에는 애초에
관찰 결과가 없다(R1) — 그래서 스펙 초안이 상정한 「호출 직전에 사본을 접는다」는 **접을
것이 없는 자리를 접는 설계**였다.

`set_messages_params` 는 docstring 을 가진 공개 메서드다. 사적 속성(`_params`)에 직접
손대지 않는다.

**확인됨 (T005 실측, 2026-09-29) — 긍정. 접기를 진행한다.**

관찰 두 번이 쌓인 runner 에 `set_messages_params` 로 접기를 적용하고, 그 뒤 runner 가
메시지를 이어 붙이게 했다.

```
접기 전 총 길이    : 10,309
접은 뒤 총 길이    :  5,317   (감소 4,992)
이어붙인 뒤 길이   :  5,357   (접힘이 유지된 채로 증가)
접힌 상태로 남은 수: 1
```

**접은 결과가 되돌려지지 않는다.** `set_messages_params` 가 교체한 리스트 위에 runner 가
이어 붙이므로, 접기 → 추가 → 접기 → 추가 의 순서가 성립한다.

`_messages_modified` 는 우려할 것이 아니었다. 그 플래그가 거짓이면 루프가 자기 메시지를
직접 넣는데, 그것이 **우리가 원하는 동작**이다 — 접은 상태 위에 새 메시지가 붙는다.

따라서 **Phase 8(US6)을 이번 증분에 포함한다.** SC-008 의 조건부 절(접기를 못 만든 경우)은
적용되지 않는다.

**개발용 드라이버**: `claude_code_driver` 는 이력에서 텍스트만 뽑아 프롬프트로 만든다
(`_prompt_from`). 도구 결과가 이력에 실리는 구조가 아니므로 접을 대상이 없다. FR-038 은
「규칙이 같아야 한다」를 요구하지만, 접을 것이 없는 곳에서 접지 않는 것은 규칙 위반이 아니다.
그 사실을 그 모듈의 주석에 남긴다.

## R5. 작업 계획은 누가 소유하는가

**결정**: `SessionWork` 가 소유하고, `AuthoringAgent` 는 **함수로 받아 읽기만** 한다.

**근거**: 016 의 `summary_source` 가 이미 같은 모양이다. 그 판단의 이유가 여기에도 그대로
적용된다 — 계획은 턴 사이에 바뀐다(AI 가 항목을 끝내고, 사람이 이어받아 처리하고, 사용자가
대화로 항목을 더한다). 값으로 들고 있으면 5분 전 계획을 근거로 답한다.

에이전트가 계획을 소유하지 않는 두 번째 이유는 실패 경로다. 헌법 원칙 I 이 요구하는
「Step 은 도구만 만든다」와 같은 판단으로, 계획도 에이전트의 실패와 함께 사라져서는 안 된다.

**주입 문자열을 만드는 자리**: `itb/authoring/summary.py` 옆. 016 이 정해 둔 예산·축약·
민감값 규칙을 한 곳에서 지키기 위해서다. 규칙이 두 곳에 있으면 한쪽만 고쳐진다.

## R6. 매 턴 붙는 것의 예산 배분

**결정**: 현행 정의 요약 예산 16KB 를 **나눈다.** 새로 더하지 않는다.

| 조각 | 예산 | 근거 |
|---|---|---|
| 작업 계획 (제약 + 항목 + 상태) | 6KB | 항목 40개 × 평균 100바이트 + 제약 + 여유 |
| 지금 테스트 (Step 목록) | 10KB | 016 실측에서 긴 이름 기준 100개가 13.6KB. 축약이 받는다 |

**근거**: 016 은 16KB 를 정하면서 "그보다 더 키우지 않는다 — 매 턴 붙기 때문이다" 라고
적었다. 그 판단을 뒤집지 않는다. 대신 이번에 더해지는 수행 기록이 이력 쪽에 별도로 쌓이므로,
매 턴 붙는 앞머리는 오히려 총량을 유지해야 한다.

**수행 기록의 예산은 별도다** — 이력에 쌓이는 것이라 성격이 다르다. 상한 32KB 를 두고
넘으면 오래된 턴부터 생략 표시로 접는다 (FR-006).

**확인 필요**: 두 값 모두 T-단계에서 실측으로 다시 본다. 016 이 8KB 초안을 실측으로 16KB 로
고친 전례가 있다 — 잠정값을 실측 없이 두면 「Step 100개까지 괜찮다」 같은 말이 거짓인 채로
남는다.

## R7. 정제를 어디서 부르는가

**결정**: 세션 생성과 **분리된 엔드포인트**로 둔다. 화면이 지시문을 쓴 뒤 정제를 요청하고,
결과를 보여 주고, 사용자가 확정한 것을 세션 생성에 실어 보낸다.

**근거**

- 세션 생성 안에서 정제하면 사용자는 **브라우저가 뜬 뒤에** 정제 결과를 보게 된다. 그때
  고치려면 이미 시작된 일을 되돌려야 한다 (FR-018 이 「확정한 뒤에 시작」을 요구한다).
- 014 의 초안 경로가 이미 같은 모양이다 — `compose_instruction(draft)` 이 서버에서 지시문을
  짓고, 화면(`ComposeView`)이 그것을 미리 채워 보여 주며 사용자가 고친다. **정제는 그 흐름의
  한 칸 뒤**다: 초안 → 지시문 → **정제 → 계획** → 세션.
- 정제가 실패해도 세션 생성은 그대로 된다 (FR-020·FR-012). 두 호출이 갈라져 있으면 이
  성질이 구조로 보장된다.

**세션 생성 요청에 실리는 것**: 확정된 계획. 계획이 없으면(정제 실패·거절) 지금과 같이
지시문만 실린다.

## R8. 정제 응답의 형태를 어떻게 강제하는가

**결정**: **도구 호출로 받는다.** 모델에게 「계획을 제출하는 도구」 하나만 주고 그것을 부르게
한다.

**근거**: 이 저장소는 이미 도구 호출로 구조를 강제하는 경로를 갖고 있고(작성 에이전트 전체가
그렇다), 스키마 정의·검증·거절 처리가 그 자리에 이미 있다. JSON 을 텍스트로 받아 파싱하면
파싱 실패 처리를 새로 만들어야 하고, 그것은 이미 있는 것의 두 번째 사본이 된다.

**고려한 대안**: `response_format` 을 통한 구조화 출력. Opus 5 에서의 동작을 이 저장소가
아직 실측한 적이 없다 (`llm/client.py` 의 주석은 이 모델에서 **쓸 수 없는 파라미터 목록**을
실측으로 적어 두고 있다 — 확인 없이 새 파라미터를 더하지 않는다는 뜻이다).

**정제 실패의 정의**: 모델이 도구를 부르지 않거나, 부른 인자가 스키마를 통과하지 못하거나,
호출 자체가 실패한 경우. 셋 다 FR-020 의 「원문으로 진행」으로 수렴한다.

### 구현에서 걸린 자리 (2026-09-29 사용자 보고)

**도구는 `beta_async_tool` 로 만들어야 한다.** 동기 `beta_tool` 로 만들면 요청 본문을
만드는 단계에서 터진다.

```
TypeError: Object of type BetaFunctionTool is not JSON serializable
```

클라이언트가 `AsyncAnthropic` 이므로 도구도 비동기여야 한다 — 이 저장소의 작성 도구가
전부 `beta_async_tool` 인 것과 같은 이유다 (`tools.build_tools`).

**이 결함은 검증을 통과했다.** 계약 검증이 `refine_instruction` 자체를 갈아 끼우므로
SDK 경로를 한 번도 밟지 않았고, 사용자가 실제로 돌려 보고서야 드러났다. **R1 이 지적한
것과 같은 함정을 이 기능이 스스로 반복했다** — 그쪽은 가짜 드라이버가 SDK 의 messages
처리를 가렸고, 이쪽은 가짜 정제 함수가 SDK 의 도구 직렬화를 가렸다.

같은 해법을 쓴다: `tests/contract/test_refine_sdk_path.py` 가 **실제 SDK 를 지나되
네트워크만 막는다** (`httpx2.MockTransport`). 요청 본문을 만드는 것도, 응답을 해석하는
것도, 도구를 부르는 것도 전부 실제 SDK 코드가 한다. 자격 증명은 필요 없다.

## R9. 완료 표시 도구는 예산을 쓰는가

**결정**: **쓰지 않는다.** `record_call()` 을 지나지 않는다.

**근거**: 도구 호출 상한 40회(`MAX_TOOL_CALLS`)의 뜻은 「화면을 조작하며 헛돌지 않게」다
(FR-066). 완료 표시는 화면을 건드리지 않고, 브라우저와 무관하며, 헛돌 수 있는 종류의
동작이 아니다. 예산을 쓰게 하면 **성실히 표시할수록 할 수 있는 일이 줄어드는** 유인이 생긴다.

같은 이유로 연속 실패 상한에도 중립이다 — 020 이 검증 어긋남을 「성공도 실패도 아니다」로
둔 것과 같은 판단이다.

**남용 방지**: 같은 항목을 여러 번 표시해도 상태는 한 번만 바뀐다. 없는 항목을 표시하면
거절된다. 이 둘로 충분하다.

## R10. 민감값

**결정**: 새 규칙을 만들지 않는다. 016 의 `summary.py` 가 정한 것을 그대로 쓴다 — **값을
읽는 자리를 하나로 묶고, 그 함수가 원본을 반환하지 않게 한다.**

지시문 정제에는 추가 사정이 하나 있다. **지시문 원문에 자격 증명이 평문으로 들어 있는
경우가 흔하다.** 지금은 그것이 첫 사용자 메시지에 한 번 실리지만, 이 기능이 계획을 매 턴
다시 실으면 노출 표면이 턴 수만큼 늘어난다.

**그래서 정제 단계에서 자격 증명을 변수 참조로 바꾼다.** 이것은 새 규칙이 아니라 기존
규칙(`SensitiveCapturer` 가 기록 시점에 하는 일)을 지시문에도 적용하는 것이다. 사용자는
정제 결과를 확인할 때 자기 비밀번호가 참조로 바뀐 것을 본다.

**확인 필요**: 지시문 텍스트에서 자격 증명을 알아보는 판정을 어디까지 할 것인가. 기존
포착기는 **입력 필드의 유형**(password)을 근거로 판정하는데, 지시문에는 그런 근거가 없다.
최소한 「계정 / 비밀번호」 같은 표기가 붙은 자리는 잡아야 하고, 못 잡은 것이 그대로 실리는
것은 지금과 같은 수준이다 — 이 기능이 상황을 악화시키지 않는 것이 하한이다.

## R11. 프롬프트 캐싱

**결론**: 현재 쓰지 않는다. `LlmConfig.request_kwargs()` 가 보내는 것은
`model`·`max_tokens`·`output_config`·`betas`·`fallbacks` 뿐이고 `cache_control` 이 없다.

따라서 **이력을 고쳐 보내는 것이 캐시를 깨뜨리는 비용은 지금 발생하지 않는다.** 스펙
초안이 우려한 자리가 실제로는 비어 있었다.

나중에 캐싱을 도입할 때를 위해 한 가지만 지킨다: 접기와 수행 기록이 **이력의 앞쪽을 바꾸지
않게** 둔다. 수행 기록은 끝에 붙고, 접기는 턴 내부에서만 일어난다. 앞머리에 붙는 계획·정의
요약은 매 턴 달라지지만 그것은 사용자 메시지의 일부라 어차피 캐시 경계 뒤다.

## R12. 이 기능이 헌법과 만나는 자리

| 원칙 | 확인 |
|---|---|
| I. 단일 Step 모델 | 계획과 수행 기록은 Step 을 만들지도 바꾸지도 않는다. Step 을 만드는 것은 도구뿐이다 (FR-037) |
| II. 결정적 재생 | 정제는 작성 시점의 한 번이다. 계획·수행 기록은 세션에 살고 실행 경로에서 읽히지 않는다 (FR-035·FR-036). `itb.authoring` 에 두면 `.importlinter` 의 `execution-no-llm` 계약이 이것을 **구조로** 보장한다 |
| III. 상태 있는 대화형 러너 | 이 기능은 인수·재개를 **강화한다**. 남은 항목이 재개 지시에 실린다 (FR-026) |
| IV. 로케이터 복원력 | 건드리지 않는다. 수행 기록에 요소 참조를 남기지 않는 것이 이 원칙과 같은 방향이다 |
| V. 자산 이식성 | 계획은 테스트 자산이 아니다. 정제 결과를 의도 기록으로 보관하는 것은 원칙 II 가 명시적으로 허용한 범위다 |

**위반 없음.** Complexity Tracking 에 적을 이연 항목이 없다.

## R13. 사람이 보는 뷰와 AI 가 보는 DOM 의 간격

**문제의 자리**: `recorder.js` 의 관찰은 이 선택자에 걸리는 요소만 수집한다.

```js
const INTERACTIVE = "button,a,input,select,textarea,label,[role],[tabindex],[onclick]";
```

**React·Vue 는 `onclick` 속성을 DOM 에 남기지 않는다.** 이벤트 위임과 `addEventListener`
를 쓴다. 그래서 현대 웹 앱에서 클릭되는 `<div>`·`<span>`·`<li>`·`<td>` 는 대부분 목록에
없다. 같은 관찰이 화면 본문 텍스트를 함께 주므로, 모델은 「글자는 보이는데 조작할 요소는
없다」는 모순된 상태를 본다.

### 결정 — 커서 표시를 조작 가능성의 신호로 쓴다

**근거**: 브라우저가 `cursor: pointer` 로 커서를 바꾸는 것이 사용자에게 「여기 누를 수
있다」를 알리는 표시다. 사람이 「클릭하라」고 말할 때 근거로 삼는 바로 그 신호이고, 뷰와
DOM 을 잇는 가장 곧은 대응이다. 프레임워크가 무엇이든, 핸들러를 어떻게 붙였든 커서는
바뀐다.

**고려한 대안**

| 대안 | 기각 사유 |
|---|---|
| 선택자에 `div,span,li,td` 를 더한다 | 클릭되지 않는 것까지 전부 걸린다. 화면 하나에 수백 개가 되어 목록이 의미를 잃는다 |
| 이벤트 리스너를 조회한다 | `getEventListeners` 는 DevTools 전용이다. 페이지 스크립트에서 쓸 수 없다 |
| 모든 요소를 격자로 `elementsFromPoint` 해 본다 | 복잡하고 느리며, 스크롤 밖 요소를 놓친다 |
| 모델에게 화면 본문 텍스트만 주고 알아서 찾게 한다 | 지금 상태다. 모델이 조작할 참조를 얻지 못한다 |

### 함정 — `cursor` 는 상속되는 속성이다

`<div style="cursor:pointer"><span>메뉴관리</span></div>` 에서 **`<span>` 의 computed
`cursor` 도 `pointer`** 다. 순진하게 걸러 내면 조상과 자손이 모두 목록에 실리고, 요소
수가 몇 배로 늘면서 모델은 어느 것을 눌러야 하는지 알 수 없게 된다.

**해법**: `cursor: pointer` 인 요소 중 **조상에 같은 판정을 받은 것이 없는 가장 바깥**만
취한다. 그것이 사람이 「그 버튼」이라고 부르는 단위이고, 녹화 쪽이 이미 쓰는 개념과 같다 —
`recorder.js` 의 「조작의 의미 단위까지 올라간다」가 그것이다.

### 성능

모든 요소에 `getComputedStyle` 을 돌리면 비싸다. 후보를 먼저 좁힌다.

1. `INTERACTIVE` 선택자에 걸리는 것 — 지금과 같다. 커서를 보지 않는다.
2. 그 밖의 요소 중 **보이는 텍스트를 갖거나 이미지·아이콘인 것** — 이 후보군에만
   `getComputedStyle` 을 돌려 `cursor: pointer` 를 본다.

**확인 필요 (구현 시 실측)**: 실제 화면에서 2단계 후보가 몇 개이고 관찰 한 번이 얼마나
걸리는지. **크기 쪽은 이미 빠듯하다** — 1단계만으로 상한 근처가 66.7KB 다(baseline.md T002).
2단계가 요소 수를 늘리면 상한(200)에 더 자주 걸리므로, `find_by_text`(FR-041)가 보완책이라는
설계 판단이 그만큼 더 중요해진다. 관찰은 이미 「화면을 살펴보는 중」을 사용자에게 알리는 작업이라 수십 ms 는
수용 범위지만, 값을 재지 않고 넘어가지 않는다.

### 근거를 함께 싣는다

각 요소에 **왜 조작 가능으로 판정됐는지**를 붙인다 (FR-040).

| 값 | 뜻 |
|---|---|
| `semantic` | `<button>`·`<a>`·`<input>` 등 태그 자체가 조작 요소 |
| `role` | `[role]`·`[tabindex]` 가 붙어 있다 |
| `cursor` | 커서가 손가락으로 바뀐다 — **짐작이 섞인 판정** |

`cursor` 로 잡힌 것은 확실성이 낮다. 그 사실을 모델이 알아야 잘못 잡힌 것과 제대로 잡힌
것을 구별할 수 있다.

### 사람의 낱말로 찾는 수단

관찰 목록이 넓어져도 200개 상한에 걸려 잘릴 수 있다. 사용자가 「메뉴관리」라고 말했는데
그것이 잘려 나간 자리에 있으면 여전히 못 찾는다.

**그래서 낱말로 조회하는 도구를 하나 준다** (FR-041·FR-042). 화면에서 그 글자를 담은
요소를 찾고, **눌렀을 때 실제로 반응하는 요소**까지 올라가 함께 돌려준다. 둘은 다를 수
있고 조작해야 하는 것은 후자다.

이 도구는 화면을 조작하지 않으므로 `observe_page` 와 같은 성격이다 — 다만 예산은 쓴다.
관찰과 마찬가지로 남용되면 헛돌 수 있는 종류이기 때문이다 (`mark_item` 과 다른 판단).

### 못 찾았을 때

**짐작하지 않는다** (FR-043). 시스템 프롬프트가 이미 「추측으로 다른 요소를 누르지
마세요」를 말하고 있고, 여기에 한 줄이 더해진다 — 화면 글자에는 있는데 조작 가능한 요소로
잡히지 않으면 그 사실을 알린다. 020 이 만든 `product_mismatch` 와 다른 종류다: 그쪽은
제품에 기능이 없는 것이고 이것은 **찾지 못한 것**이다.

### 녹화 경로는 바꾸지 않는다

`INTERACTIVE` 는 관찰뿐 아니라 녹화에서도 쓰인다 (`closest(INTERACTIVE)`, 두 자리).
**그 자리는 건드리지 않는다** (FR-045). 녹화는 사람이 실제로 누른 요소에서 의미 단위까지
올라가는 것이고, 그 판정에 짐작을 섞을 이유가 없다 — 사람이 눌렀다는 사실이 이미 확실한
근거다.

관찰 전용 후보 수집을 따로 두고, `INTERACTIVE` 상수는 그대로 남긴다.
