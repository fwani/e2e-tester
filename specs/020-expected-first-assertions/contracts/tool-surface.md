# 계약 — AI 작성 도구 표면의 변화 (020)

**적용 범위**: `itb.authoring.tools` 의 도구 16종. **도구 개수는 변하지 않는다.**
`TOOL_NAMES`(16) · `STEP_PRODUCING_TOOLS`(9) · Step 종류와의 1:1 대응이 그대로다.

바뀌는 것은 **도구 둘의 입출력**이다.

---

## 1. `assert_condition` — 실패 처리가 달라진다

### 입력

**변화 없음.**

```
assert_condition(kind, element_ref?, value?, match="equals")
```

### 출력

| 경우 | 지금 | 020 이후 |
|---|---|---|
| 검증 통과 | `{"ok": true, "step": "<label>"}` | **같음** |
| 검증 실패 | `{"error": "<실패 설명>"}` · Step 없음 | `{"ok": true, "assertion_failed": true, "step": "<label>", "observed": "<실패 설명>", "note": "<아래>"}` · **Step 기록됨** |
| 참조를 찾을 수 없음 | `{"error": "요소 참조를 찾을 수 없습니다: ..."}` | **같음** (FR-007) |
| 대상 식별 정보 수집 실패 | `{"error": "검증 대상의 식별 정보를 수집하지 못했습니다: ..."}` | **같음** (FR-007) |
| 지원하지 않는 종류·조건 오류 | `{"error": ...}` | **같음** |
| 호출 상한 도달 | `STOP_NOTICE` | **같음** |

**`note` 의 내용** (FR-010):

> 검증이 기대와 다릅니다. **값을 바꾸어 다시 시도하지 마세요** — 이 Step 은 결함 후보로
> 이미 기록되었습니다. 남은 지시를 계속 수행하세요.

**왜 `ok: true` 와 `assertion_failed: true` 를 함께 싣는가**: 도구 호출로서는 성공했고
(Step 이 기록됐다), 검증 결과로서는 어긋났다. 두 축을 한 값으로 뭉치면 모델이 「실패했으니
다시」로 읽는다. 이 기능 전체가 그 오독을 없애는 것이다.

### 부수 효과

| | 통과 | 어긋남 | 대상 없음 |
|---|---|---|---|
| Step 기록 | 함 | **함** | 안 함 |
| `mismatch` 채움 | 안 함 | **함** | — |
| 연속 실패 계수 | 초기화 | **건드리지 않음** (FR-009) | +1 |
| 총 호출 계수 | +1 | +1 | +1 |
| 진행 알림 | `— 완료` | `— 기대와 다름` | `— 실패: ...` |

## 2. `report_blocked` — 사유 종류가 붙는다

### 입력

```
report_blocked(reason: str, question: str = "", kind: str = "needs_input")
```

| 인자 | 값 | 뜻 |
|---|---|---|
| `kind` | `"needs_input"` (기본) | 사람이 알려 주면 풀린다 — **현행 전부가 여기** |
| | `"product_mismatch"` | 제품이 지시문과 다르게 동작해 진행할 수 없다 |

인식하지 못한 값은 `"needs_input"` 으로 떨어진다. 오타가 조용히 답변 칸을 막으면 사용자는
이유를 모른 채 이어갈 방법을 잃는다.

### 출력

**변화 없음** — `{"acknowledged": true, "message": "..."}`.

### 부수 효과

| `kind` | `blocked_question` | 화면 |
|---|---|---|
| `needs_input` | `question` 을 그대로 | 답변 칸이 열린다 — 현행 |
| `product_mismatch` | **`None` 으로 버린다** (FR-024) | 답변 칸이 열리지 않는다 |

### 도구 설명 문구 (개발용 드라이버의 `TOOL_SCHEMAS`)

> 지시를 수행할 수 없음을 알린다. 무엇이 막았는지 구체적으로 적는다.
> 사람이 알려 주면 풀릴 일이면 `question` 에 물어볼 한 문장을 함께 적는다.
> **제품이 지시문과 다르게 동작해서 막힌 것이면 `kind` 에 `product_mismatch` 를 적는다 —
> 그때는 사람에게 물을 것이 없다.**

## 3. 시스템 지침의 변화 (`SYSTEM_PROMPT`)

### 고치는 줄

```
- 한 지시를 여러 동작으로 나누어 차례로 수행하세요. 성공한 동작만 테스트로 남습니다.
```
↓
```
- 한 지시를 여러 동작으로 나누어 차례로 수행하세요. 화면을 조작하는 동작은 성공한 것만
  테스트로 남습니다 (검증은 다릅니다 — 아래를 보세요).
```

**이 줄을 그대로 두면 안 되는 이유**: 모델이 상충하는 두 규칙을 받는다. 지금 문면은 검증을
포함한 전부에 걸린다 (R12).

### 새로 여는 절

```
## 검증 Step 에 대해 — 지금 화면이 아니라 사용자의 요구를 적으세요

당신이 만드는 정의는 **제품이 지금 하는 일의 기록이 아니라, 사용자가 제품에 요구하는
일의 기록**입니다. 제품에 결함이 있으면 그 결함이 정의에 들어가서는 안 됩니다.

- 검증의 기대값은 **지시문에서** 가져오세요. 화면에서 읽은 값으로 바꾸지 마세요.
- 검증이 기대와 달라도 그 Step 은 기록됩니다. **값을 바꾸어 다시 시도하지 마세요.**
  다시 시도하는 것은 제품의 결함을 정답으로 만드는 일입니다.
- 지시문이 기대값을 말하지 않으면(「결과가 뜨는지 확인」) 요소가 보이는지만 검증하세요.
  화면에서 읽은 문구를 기대값으로 지어내지 마세요.
- 지시문이 요구한 동작을 할 수 없을 때, 같은 결과를 내는 **다른 경로로 대체하지 마세요.**
  report_blocked 에 kind="product_mismatch" 로 알리세요.
```

### `NL_STEP_SYSTEM_HINT` (일시정지 중 Step 하나 추가)

같은 절의 요약본을 더한다. 이 경로도 검증 Step 을 만들며 같은 문제를 갖는다 (R12).

## 4. 이벤트 계약

### `ai_finished` — 필드 추가

```
{ "step_count": <int>, "mismatch_count": <int> }
```

`mismatch_count` 는 **이번 세션이 어긋남으로 기록한 검증 수**다. 0 이면 필드를 싣지
않는다 (FR-013) — 없는 것을 0으로 알리면 화면이 「결함 후보 0건」을 표시할지 말지를 다시
판단해야 한다.

### `ai_blocked` — 필드 추가

```
{ "reason": ..., "attempted": ..., "question": ..., "kind": "needs_input" | "product_mismatch" }
```

`kind` 는 **항상 싣는다.** 기존 소비자가 모르는 필드를 무시하므로 안전하고, 항상 있으면
화면이 「없으면 needs_input」이라는 규칙을 따로 들고 있지 않아도 된다.

### `step_failed` — 변화 없음

검증 실패에서도 지금과 같이 나간다. **이 이벤트가 「실행이 멈췄다」를 뜻한 적은 없다** —
멈춤은 `run_finished` 와 결과의 `NOT_RUN` 이 말한다.
