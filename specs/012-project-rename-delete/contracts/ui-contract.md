# UI 계약 — 프로젝트 목록의 줄 조작

**Feature**: 012-project-rename-delete | **화면**: `frontend/src/pages/ProjectSetup.tsx`

이 화면은 확정 디자인에 대응 artboard 가 없어 1:1 대조 의무(DC-010)가 적용되지 않는다. 대신
8화면의 시각 언어를 따른다 — 직각 모서리, 3px 잉크 테두리, 하드 오프셋 그림자, `pane`·`btn`·
`navlink`·`chip`·`why`·`line fail-ink` 클래스. **새 클래스를 만들지 않는다.**

---

## UC-012-01 — 줄의 상태가 조작을 정한다

`ProjectRow` 는 `accessible` × `origin` 으로 조작 집합을 고른다. 줄마다 따로 판단하는 코드를
쓰지 않는다 (data-model §3).

| `accessible` | 보이는 조작 |
|---|---|
| `true` | 「열기」 · 이름 인라인 편집 · 「삭제」 |
| `false` | 「목록에서 치우기」 + 이름 변경·삭제가 왜 없는지 한 줄 |

접근 가능한 줄에도 「목록에서 치우기」는 남는다 — 외부 위치 프로젝트를 지우지 않고 목록에서만
빼고 싶은 경우가 실제로 있다 (기존 DR-009 의 용도).

---

## UC-012-02 — 이름 인라인 편집

**관용어는 `PhaseBar` 의 테스트 이름 편집과 같다.** 제자리 입력, 확인 창 없음, 사유는 그 자리.

| 상태 | 화면 |
|---|---|
| 평상 | 이름이 `subtitle` 로 표시된다. 지금과 같다 |
| 편집 중 | 그 자리가 입력 칸이 된다. 값은 현재 이름. 포커스가 들어간다 |
| 확정 | `Enter` 또는 포커스 이탈 → `PATCH /api/project/name` |
| 취소 | `Esc` → 원래 이름으로 되돌리고 요청하지 않는다 |
| 거절 | 입력 칸 아래에 `line fail-ink` 한 줄. 입력 칸은 열린 채로 남는다 |

**요청 중에는 입력 칸이 잠긴다** — 연타로 같은 프로젝트에 두 요청이 겹치지 않게 한다
(005 U-06 과 같은 결함이다).

**빈 이름은 요청하기 전에 막는다** (FR-403). 서버도 막지만, 사용자가 왜 안 되는지 화면에서
바로 알아야 한다 — 「만들기」가 무엇이 빠졌는지 미리 말하는 것과 같은 규칙이다 (003 AP-003).

**성공하면 목록을 다시 불러오지 않는다.** 응답이 갱신된 줄 하나를 주므로 그 줄만 갈아 끼운다.
전체를 다시 불러오면 편집 중이던 다른 줄의 상태가 날아간다.

---

## UC-012-03 — 삭제 확인은 그 줄 안에서 한다

모달을 새로 만들지 않는다. **줄이 확인 상태로 바뀐다** — 사용자가 어느 줄을 지우는지 시선을
옮기지 않고 확인한다 (research R8).

확인 상태가 반드시 담는 것:

| 항목 | 근거 |
|---|---|
| 프로젝트 이름과 **경로** | 무엇이 사라지는지 (FR-411) |
| 저장된 테스트 수 | 무게를 알린다 (FR-411) |
| **「지우지 않고 휴지통으로 옮깁니다」** | 되돌릴 수 있다는 사실 (FR-411·FR-425) |
| 「도구 바깥에서 만든 위치입니다」 | `origin === "external"` 일 때만 (FR-424) |
| 「휴지통으로 옮기기」 · 「취소」 | 취소가 기본이다 — 포커스는 취소에 둔다 |

**확인 전에는 어떤 요청도 보내지 않는다** (FR-412 · SC-617).

테스트 수는 이미 목록 응답에 없다. **저장된 테스트 수를 새로 싣지 않는다** — 목록 조회가
프로젝트 N개를 파싱하게 만드는 것은 `registry._probe` 가 피하려던 바로 그 비용이다. 대신
확인 상태로 들어갈 때 그 프로젝트 하나만 세어 온다.

## UC-012-04 — 완료 표시는 옮겨진 위치를 그대로 보여준다

삭제가 끝나면 목록 위에 알림 한 줄이 남는다.

```
「옛 프로젝트」를 휴지통으로 옮겼습니다.
/Users/me/.local/share/itb/trash/20260910-071530-옛-프로젝트     ← mono, 선택 가능
되돌리려면 이 디렉터리를 원래 자리로 옮기세요.
```

**경로는 `mono` 로, 잘리지 않게 표시한다.** 이 값이 되돌리는 방법 전부다 (FR-410·FR-425).
`trashed_to` 가 `null` 이면(이미 없던 경우) 「목록에서 뺐습니다」로 문구가 바뀐다.

알림은 사용자가 닫거나 다음 조작을 할 때까지 남는다. **자동으로 사라지지 않는다** — 사라지면
되돌릴 방법이 함께 사라진다.

---

## UC-012-05 — 열려 있던 프로젝트를 지웠을 때

응답의 `was_open` 이 `true` 면 화면은 **열린 프로젝트 상태를 비운다.** 사용자는 프로젝트
선택 화면에 그대로 남는다 (FR-416). 「돌아가기」 링크가 있었다면 사라진다 — 돌아갈 곳이
없어졌기 때문이다.

사라진 프로젝트를 가리키는 화면으로 자동 이동하지 않는다.

## UC-012-06 — 거절 사유는 그 줄에 붙는다

| 응답 | 화면 |
|---|---|
| 409 `PROJECT_IN_USE` | 그 줄에 「실행 중인 브라우저가 있어 삭제할 수 없습니다」 + `next_action` |
| 500 `PROJECT_DELETE_FAILED` | 그 줄에 「옮기지 못했습니다」 + **「프로젝트는 그대로 있습니다」** |
| 400 `INVALID_PATH` / 404 | 목록을 다시 불러온다 — 화면의 목록이 낡은 것이다 |

`PROJECT_DELETE_FAILED` 문구에 **「그대로 있습니다」가 반드시 들어간다.** 실패 후 사용자가
가장 먼저 하는 질문이 "내 테스트는 어떻게 됐나" 이고, 그 답이 계약상 확정되어 있다
(api-contract §2 불변식).

기존 `ErrorNotice` 를 쓴다. 새 오류 표시 부품을 만들지 않는다.

---

## UC-012-07 — 두 조작의 이름과 설명

| 조작 | 라벨 | `title`/설명 |
|---|---|---|
| 휴지통으로 보내기 | **삭제** | 「프로젝트 폴더를 휴지통으로 옮깁니다. 파일은 지워지지 않고 되돌릴 수 있습니다.」 |
| 레지스트리에서 빼기 | **목록에서 치우기** | 「목록에서만 치웁니다. 디스크의 파일은 그대로 둡니다.」 |

두 설명 모두 **디스크의 파일이 어떻게 되는지**를 말한다 (FR-423 · SC-620). 기존
「목록에서 치우기」의 문구는 이미 그 규칙을 지키고 있다 — 그대로 둔다.
