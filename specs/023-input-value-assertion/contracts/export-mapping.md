# Contract: 입력값 검증 ↔ 표준 Playwright 대응

**Feature**: 023 | **헌법 원칙 V** (Asset Portability) | 명세 FR-020~FR-022

내보낸 테스트는 제품 안에서 실행한 것과 **같은 검증**을 해야 한다. 생성기는 모르는 종류를
만나면 `UnsupportedStepError` 를 던지므로([research.md R6](../research.md)), 이 대응을
넣지 않으면 **내보내기 자체가 깨진다.** 조용히 틀리지는 않는다는 점이 다행이다.

---

## 1. 긍정 비교 — 그대로 대응한다

| 검증 조건 | 생성되는 표현 |
|---|---|
| `value` + `equals` | `await expect(loc).toHaveValue(값, { timeout })` |
| `value` + `contains` | *아래 §2 참조* — 표준에 직접 대응이 없다 |

`toHaveValue` 는 요소의 값을 읽어 비교하고, 값이 맞을 때까지 재시도한다. 제품 안 실행의
`settle`(조건이 참이 될 때까지 기다린다)과 같은 의미론이다.

**대상은 언제나 있다.** `text` 검증과 달리 「화면 전체」 경우가 없으므로(FR-002) 생성기에
분기가 필요 없다.

---

## 2. 「포함한다」 — 표준에 직접 대응이 없다

`toHaveValue` 는 문자열 또는 정규식을 받는다. **부분 일치 전용 matcher 가 없다.**

### 쓰지 않기로 한 것 — 정규식 변환

값을 정규식으로 감싸면(`new RegExp(escape(값))`) 부분 일치가 된다. 그러나 021 이 주소
검증에서 같은 선택지를 거절했다.

> 정규식으로 만들지 않는다 — 화면에서 온 값이 패턴으로 해석되면 의미가 달라진다.

여기서는 이유가 하나 더 있다. **비교 값에 `{{변수}}` 참조가 들어올 수 있다.** 참조는
`process.env.NAME` 같은 *식*으로 렌더링되므로, 정규식 리터럴로 감쌀 수 없고 런타임에
이스케이프해야 한다. 생성된 코드에 이스케이프 헬퍼를 심는 것은 「제품 런타임 shim 없이
돌아야 한다」는 원칙 V 의 경계에 닿는다.

### 생성하는 형태 — 값을 읽어 비교한다

```js
// 이름 칸의 값이 'E2E역할테스트' 를 포함해야 한다
await expect
  .poll(async () => await page.locator('#pname').inputValue(), { timeout: 5000 })
  .toContain('E2E역할테스트');
```

`expect.poll` 은 표준 Playwright 다. 조건이 참이 될 때까지 다시 읽으므로 `toHaveValue` 와
같은 재시도 의미론을 갖고, 값을 문자열로 다루므로 참조 렌더링 결과를 그대로 쓸 수 있다.

---

## 3. 부정 비교 — 021 의 관찰 루프를 그대로 쓴다

부정 조건의 기본 상태는 참이다. `.not` 만 쓰면 첫 판정에서 즉시 통과하고, 그 뒤에 값이
들어오는 것을 놓친다. 021 이 정한 판단과 이유가 같으므로 **같은 형태를 쓴다.**

```js
// 이름 칸의 값이 1200ms 동안 '임시값' 이 아니어야 한다
{
  const deadline = Date.now() + 1200;
  for (;;) {
    await expect(page.locator('#pname')).not.toHaveValue('임시값', { timeout: 1 });
    if (Date.now() >= deadline) break;
    await page.waitForTimeout(50);
  }
}
```

| 검증 조건 | 루프 안의 판정 |
|---|---|
| `value` + `not_equals` | `await expect(loc).not.toHaveValue(값, { timeout: 1 })` |
| `value` + `not_contains` | `expect(await loc.inputValue()).not.toContain(값)` |

`not_contains` 가 `expect.poll` 이 아닌 이유: 루프가 이미 관찰 기간을 담당하므로 안쪽에서
또 기다리면 기간이 겹친다. `timeout: 1` 이 하는 일을 여기서는 「폴링하지 않는 단발 판정」이
한다.

---

## 4. 민감 변수 — 산출물에 평문이 없다

비교 값의 `{{SECRET_*}}` 참조는 기존 `ValueRenderer` 규칙대로 `process.env.NAME` 으로
렌더링된다. **새로 할 일이 없다** — 023 이 종류만 더하고 값 렌더링 경로는 건드리지 않기
때문이다.

```js
await expect(page.locator('#password')).toHaveValue(process.env.SECRET_PW, { timeout: 5000 });
```

### 한계 — 실행 중 출력은 통제하지 못한다

이 검증이 실패하면 표준 도구가 자기 형식으로 기대·실제를 출력한다. 그 출력에 칸의 실제
값이 나올 수 있고, **제품은 그것을 막을 수 없다.**

| | 제품 안 실행 | 내보낸 프로젝트 |
|---|---|---|
| 산출물에 평문 | 없다 | **없다** (`process.env`) |
| 실패 출력의 관찰값 | **마스킹한다** (FR-016) | 통제 불가 |

**새로 생기는 노출은 아니다.** 입력 Step 이 내보내진 경우에도 같은 상태이고, 원칙 V 는
「표준 도구로 돌아간다」를 요구하지 표준 도구의 출력을 바꾸라고 요구하지 않는다. 이 사실을
여기 적어 두는 것이 계약이다.

---

## 5. 대응하지 않는 것

| 무엇 | 왜 |
|---|---|
| 체크박스·라디오 | 작성 시점에 거절되므로 정의에 존재할 수 없다 |
| 값이 없는 대상 | 같음 |
| `select[multiple]` | `inputValue()` 가 처음 선택된 항목만 돌려준다. 제품 안 실행도 같으므로 **대응은 일치하지만 둘 다 사용자의 뜻과 다를 수 있다** — [research R4](../research.md) 의 한계 |

마지막 줄이 중요하다. **제품과 내보낸 코드가 같게 동작하므로 원칙 V 는 지켜진다.** 둘이
함께 사용자의 뜻과 다른 것은 별개의 문제이고, 명세의 범위 외에 적혀 있다.

# 키 입력 ↔ 표준 Playwright (2026-09-28 범위 확장)

## 6. 대응은 하나뿐이다

| Step | 생성되는 표현 |
|---|---|
| `press` (키 `Enter`) | `await loc.press('Enter', { timeout });` |
| `press` (키 `Space`) | `await loc.press('Space', { timeout });` |
| `press` (키 `Tab`) | `await loc.press('Tab', { timeout });` |
| `press` (키 `Escape`) | `await loc.press('Escape', { timeout });` |

`locator.press` 는 요소에 포커스를 준 뒤 키를 보낸다. 제품 안 실행과 같은 동작이므로
**제품과 내보낸 코드가 갈릴 자리가 없다.**

### 키 이름을 그대로 쓸 수 있는 이유

정의의 키 열거값이 **표준 도구의 키 이름과 같은 철자**다 (`Enter`·`Space`·`Tab`·`Escape`).
변환표를 두지 않는다 — 표가 있으면 어느 쪽이 권위인지 매번 판단해야 하고, 값을 더할 때마다
두 곳을 고쳐야 한다.

열거형이라 **임의 문자열이 생성기에 도달할 수 없다.** 헌법의 「생성된 Playwright 코드는
생성 중 데이터로 다루며 페이지에서 온 문자열의 이스케이프되지 않은 결합으로 만들지
않는다」를 값의 형태 자체로 만족시킨다 ([research R12](../research.md)).

### 포커스에 의존하지 않는다

`page.keyboard.press` 가 아니라 `locator.press` 다. 앞 Step 의 부작용으로 포커스가 어디
있든 **정의에 적힌 요소에** 키가 간다 — 제품 안 실행도 같은 판단을 한다 (FR-051).

## 7. 녹화 규칙은 내보내기와 무관하다

FR-055(IME 조합 중 키를 기록하지 않음)와 FR-056(키 뒤 빈 값이 입력 Step 을 덮지 않음)은
**녹화 시점의 규칙**이다. 정의에 남은 뒤에는 그런 구별이 존재하지 않으므로 생성기가 알 것이
없다.

이것이 그 두 규칙을 녹화에 둔 이유이기도 하다 — 실행이나 생성에 두면 「정의에 적힌 것」과
「실제로 하는 것」이 갈린다.
