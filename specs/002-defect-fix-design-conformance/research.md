# Phase 0 Research — 결함 수정과 확정 디자인 준수

**Feature**: `specs/002-defect-fix-design-conformance`
**Date**: 2026-09-04

이 라운드는 결함 수정이다. 따라서 연구의 절반은 **원인 규명**이고 절반은 **설계 결정**이다.
원인은 추정하지 않았다. 아래 모든 원인 항목은 실제 코드 위치 또는 실행 결과로 확인했다.

## R1 — A-3 녹화 중지 시 결과 유실: 원인 규명

**증상**: 직접 녹화 중 중지를 누르면 테스트 목록으로 튕겨 나가고 기록된 Step 을 보거나
저장할 수 없다.

**원인은 두 겹이다. 프런트엔드만 고치면 여전히 저장할 수 없다.**

### 원인 1 — 프런트엔드가 중지 직후 화면을 떠난다

`frontend/src/pages/Runner.tsx:287-288`

```
await act(() => sessions.stop(sessionId));
onFinished();
```

`onFinished` 는 `App.tsx:148` 에서 `setScreen({ name: "list" })` 다. 같은 패턴이
`Runner.tsx:377`(중지 확인 대화상자의 "저장하지 않고 중지")과 `Runner.tsx:533`
(Takeover 의 중지)에도 있다. 총 3곳.

### 원인 2 — 백엔드가 중지 시 세션을 파괴한다 (이쪽이 더 근본적)

`backend/src/itb/api/routes/sessions.py:1036-1038`

```
await state.broker.drop(session_id)
await state.sessions.close(session_id)
_WORK.pop(session_id, None)
```

`save` 는 `work_of(session_id)` 로 시작하고(`sessions.py:1043`), `work_of` 는 `_WORK` 에
없으면 `SESSION_NOT_FOUND` 를 던진다(`sessions.py:153-157`).

**따라서 중지 이후의 저장은 구조적으로 불가능하다.** 화면을 붙잡아 두더라도 저장 버튼은
`SESSION_NOT_FOUND` 를 받는다.

### 결정

`stop` 의 의미를 **"브라우저 세션 종료"** 와 **"작업 종료"** 로 분리한다.

- 브라우저·미러·러너·에이전트는 지금처럼 정리한다. 실제 브라우저 창을 남길 이유가 없다.
- **`SessionWork` 는 파괴하지 않는다.** 기록된 Step·변수·저장 스냅샷을 들고 있는
  검토 가능한 상태(`review`)로 남긴다.
- 사용자가 저장하거나 명시적으로 버릴 때 비로소 `_WORK` 에서 제거한다.

**대안 검토**

| 대안 | 기각 이유 |
|---|---|
| 중지 시 서버가 자동 저장 | 이름 없이 저장할 수 없고(FR-028), 사용자가 버릴 자유를 뺏는다 |
| 중지 전에 반드시 저장 강제 | 버리고 싶은 녹화를 저장하게 만든다. 중지가 막히면 브라우저가 계속 열려 있다 |
| Step 을 프런트엔드 메모리에만 보관 | 새로고침에 사라지고, 저장 시 서버가 변수·민감값 문맥을 잃는다 |

## R2 — A-2 "AI로 만들기" 무반응: 원인 규명

**증상**: AI 로 만들기를 실행해도 화면에 아무 변화가 없다.

**원인**: 실패가 발생하고 있고 서버는 알리고 있는데, **화면이 그 알림을 그릴 조건을
만족하지 못한다.**

경로를 따라가면:

1. `sessions.py:513` — 에이전트가 실패하면 `ai_error` 이벤트를 발행한다. 세션은 닫지
   않는다 (FR-067 준수).
2. `sessions.py:514` — 이어서 `_hold_for_review(work)` 가 `Command.PAUSE` 를 적용한다.
   세션 상태가 **`paused`** 가 된다.
3. `Runner.tsx:171-174` — 프런트엔드는 `ai_error` 를 받아 `setAiError(event.reason)` 하고
   `resync()` 한다. **`aiMessages` 는 건드리지 않는다.**
4. `Runner.tsx:223-224` —
   ```
   const AI_STATES = ["ai_running", "ai_blocked"];
   const isAiSession = AI_STATES.includes(view.state) || aiMessages.length > 0;
   ```
   `resync` 후 `view.state` 는 `paused` 이고 `aiMessages` 는 비어 있다 → **`isAiSession === false`**.
5. `Runner.tsx:510-514` — `aiError` 를 렌더하는 유일한 곳인 `<AiRecord>` 가
   `{isAiSession && ...}` 로 감싸여 있다 → **그려지지 않는다.**

즉 **실패 사유는 상태에 담겨 있으나 화면에 도달하는 경로가 없다.** 사용자에게는
"아무 일도 일어나지 않은 것"으로 보인다. 헌법의 "조용한 실패 금지"와 spec DR-016·DR-020
위반이다.

에이전트 자체는 결함이 없다. `authoring/agent.py:202-215` 가 `CancelledError` 만 다시
던지고 `LlmUnavailableError`·`RefusalError`·그 밖의 모든 예외를 `AgentStatus.ERROR` 로
바꾼다. 자격 증명이 없을 때의 문구도 `llm/client.py:93-97` 에 준비돼 있다.

### 결정

- 실패 표시를 **세션 상태와 무관하게** 만든다. AI 세션이었다는 사실은 `view.state` 가
  아니라 `authoring_mode` 로 판정한다 — 그것이 세션의 불변 속성이다.
- AI 작성 화면을 **독립 화면으로 분리**한다 (DC-008 과 같은 방향). Runner 안의 조건부
  패널로 두는 한 "무엇을 언제 그리는가"가 상태 조합에 계속 얽힌다.
- `ai_error` 수신 시 진행 로그에도 실패를 남겨, 렌더 조건이 하나 어긋나도 사용자가 볼
  경로가 두 개가 되게 한다.
- DR-021 — 자격 증명 유무를 **세션을 만들기 전에** 확인하는 읽기 전용 점검을 추가한다.
  실패한 뒤 알리는 것보다 시작 전에 막는 것이 낫다.

## R3 — A-4 키 쌍 만들기 422: 원인 규명

**증상**: 키 관리에서 "키 쌍 만들기"를 누르면 422.

**두 개의 독립된 원인이 겹쳐 있다.** 하나는 이 화면의 문제이고, 하나는 앱 전체의 문제다.

### 원인 1 — 암호구절 최소 길이가 화면에 알려지지 않는다

`backend/src/itb/api/routes/secrets_routes.py:48`

```
passphrase: str | None = Field(default=None, min_length=8, max_length=200)
```

실측(같은 모델을 그대로 재현):

| 보낸 값 | 결과 |
|---|---|
| `{}` | OK |
| `{"passphrase": null}` | OK |
| `{"passphrase": "short"}` | **FAIL — String should have at least 8 characters** |
| `{"passphrase": "longenough123"}` | OK |

`keyed_client` 픽스처가 `{"passphrase": None}` 으로 201 을 받고 있고 백엔드 테스트 726건이
통과하므로, **빈 암호구절 경로는 정상이다.** 8자 미만을 입력했을 때만 422 다.
그런데 `frontend/src/pages/KeyManagement.tsx` 에는 이 제약에 대한 안내가 없다. 사용자는
막힌 이유를 알 수 없다.

### 원인 2 — 422 를 계약 형태로 바꾸는 핸들러가 없다 (앱 전체)

`backend/src/itb/api/app.py` 에 등록된 예외 핸들러는 두 개뿐이다.

- `app.py:64` — `@app.exception_handler(ApiError)`
- `app.py:68` — `@app.exception_handler(Exception)`

**`RequestValidationError` 핸들러가 없다.** FastAPI 기본 응답 본문은
`{"detail": [ ... ]}` 이고, 프런트엔드의 오류 추출기는 `body.error.message` 를 본다
(`frontend/src/api/client.ts:59-67`). 매칭에 실패하면 폴백 문자열
`요청이 실패했습니다 (422).` 를 던진다.

**결과: 앱 어디서든 발생하는 모든 422 가 원인을 알 수 없는 한 문장이 된다.**
이것이 사용자가 "422 에러가 나옴"이라고 표현한 것의 실체다. DR-022·DR-030 이
키 화면만의 문제가 아니라 앱 전체의 문제인 이유다.

### 결정

- `RequestValidationError` 핸들러를 등록해 계약 형태(`{error:{code,message,detail}}`)로
  바꾼다. 코드는 `DEFINITION_INVALID` 를 재사용한다 — 새 코드를 만들면 프런트엔드의
  `ErrorCode` 유니온과 계약 문서를 함께 늘려야 하는데, 의미가 이미 "요청이 규격에 맞지
  않음"으로 같다.
- 필드 제약(최소 길이 등)을 화면이 **제출 전에** 안내한다.
- 이 핸들러는 회귀 방지 효과가 크다. 앞으로 생길 모든 검증 오류가 자동으로 읽을 수 있는
  형태가 된다.

## R4 — A-1 프로젝트 인식: 원인 규명과 저장 위치 결정

**증상**: 기존 프로젝트가 인식되지 않고, 절대 경로를 직접 타이핑해야 한다.

**원인**: 기록이 아예 없다. 결함이 아니라 **누락된 설계**다.

- `backend/src/itb/api/routes/project.py` 의 엔드포인트는 셋뿐이다 —
  `GET /api/project`(현재 열린 것), `POST /api/project/create`, `POST /api/project/open`.
  **목록 엔드포인트가 없다.**
- 열린 프로젝트는 `state.repository`(`app.state.itb`)에만 있다. **프로세스 메모리다.**
  서버를 재시작하면 사라지고 `GET /api/project` 는 404 `PROJECT_NOT_OPEN` 을 낸다.
- `App.tsx:33-41` 이 그 404 를 받아 `ProjectSetup` 화면을 띄운다.
- `ProjectSetup.tsx:41-46` 은 절대 경로 자유 입력란이다. 과거에 어디에 만들었는지 알려
  주는 것이 화면에 없다.

### 결정 1 — 도구가 관리하는 저장 위치

**`~/.local/share/itb/projects/<프로젝트-슬러그>/`**

`~/.config/itb/keys` 라는 선례가 이미 있다(`secrets/keys.py:26`). 같은 XDG 관례를 잇되
디렉터리를 나눈다.

- `~/.config/itb/` — 도구 설정. 키와 **레지스트리**가 여기 간다.
- `~/.local/share/itb/projects/` — 사용자 자산(테스트 정의 YAML). 설정이 아니라 데이터다.

**왜 `~/.config` 아래에 프로젝트를 두지 않는가**: 001 spec FR-011 과 헌법 원칙 V 는 테스트
정의를 **사용자가 버전 관리에 넣는 평문**으로 규정한다. 버전 관리 대상 자산을 설정
디렉터리에 두면 사용자가 그것을 자기 것으로 인식하지 못한다.

| 대안 | 기각 이유 |
|---|---|
| 서버 실행 디렉터리 기준 상대 경로 | 사용자가 실행 경로를 모른다는 것이 이번 결함의 출발점이다 |
| `~/itb-projects/` (홈 직하) | 홈 디렉터리를 어지럽힌다. XDG 관례를 이미 쓰고 있다 |
| `~/Documents/ITB/` | 플랫폼마다 이름이 다르고 로케일에 따라 번역된다 |

### 결정 2 — 레지스트리

**`~/.config/itb/registry.json`**

```
{ "version": 1, "projects": [ { "root": "...", "name": "...", "last_opened_at": "..." } ] }
```

- 관리 위치의 디렉터리 **스캔만으로는 부족하다.** DR-005 로 연 외부 경로의 프로젝트는
  관리 위치 밖에 있으므로 스캔에 걸리지 않는데, DR-007 이 그것도 목록에 나오길 요구한다.
- 반대로 레지스트리**만** 신뢰해도 부족하다. 파일이 사라지면 관리 위치의 프로젝트가
  통째로 안 보인다.
- **따라서 둘을 합친다**: 관리 위치 스캔 결과 ∪ 레지스트리 항목. 스캔으로 발견된 것은
  레지스트리에 없어도 보이고, 레지스트리의 외부 경로도 함께 보인다. DR-009 의 "접근 불가"
  판정은 실제 파일 존재로 한다.

### 결정 3 — "기존 프로젝트 열기"의 탐색기

**백엔드가 그리는 디렉터리 탐색 API 를 만든다.**

브라우저는 임의 절대 경로를 줄 수 없다. `<input type="file" webkitdirectory>` 는 상대
경로만 주고, File System Access API 는 핸들만 주며 서버가 읽을 경로가 되지 않는다.
서버가 로컬에 있으므로(FR-088 단독 로컬 도구) 서버가 디렉터리를 읽어 목록을 주는 것이
유일하게 성립하는 방법이다.

**보안 경계** (헌법 "모든 외부 입력은 경계에서 검증"):

| 규칙 | 이유 |
|---|---|
| 사용자 홈 디렉터리 **아래로 한정** | 임의 파일 시스템 탐색기를 열어 줄 이유가 없다 |
| 요청 경로를 정규화(`resolve()`)한 뒤 홈 하위인지 확인 | `..` 를 이어 붙인 탈출을 막는다 |
| 심볼릭 링크는 따라간 뒤 다시 검사 | 링크로 경계를 넘는 것을 막는다 |
| **디렉터리 이름만 반환.** 파일 내용·파일 목록을 주지 않는다 | 탐색기가 파일 유출 통로가 되지 않게 한다 |
| 숨김 디렉터리 제외 | 목록 소음을 줄이고 `.ssh` 등을 노출하지 않는다 |
| 각 항목에 "프로젝트인가" 판정 플래그 포함 | 사용자가 어디를 골라야 하는지 알 수 있다 |

`POST /api/project/open` 이 지금 임의 경로를 받는 것도 같은 경계로 좁힌다.

## R5 — A-5 비밀 값 인라인 입력

**현재**: `frontend/src/pages/SecretValues.tsx` 가 독립 화면이고, Step 편집에서 그리로
이동해야 한다.

**제약**: 001 FR-089 의 비대칭 방식은 그대로 지킨다. 결정적으로 —
`PUT /api/secrets/{name}` 은 **공개키만으로 동작한다**(`secrets_routes.py` 파일 주석).
비밀키는 실행 시에만 필요하다.

**이것이 인라인 입력을 쉽게 만든다.** Step 을 편집하는 시점에 필요한 것은 공개키뿐이고,
공개키는 프로젝트에 이미 있거나 그 자리에서 만들 수 있다.

### 결정

- Step 편집 안에 **비밀 값 입력 요소**를 둔다. 새 API 를 만들지 않는다 — 기존
  `GET /api/secrets`(이름·존재 여부만)와 `PUT /api/secrets/{name}` 을 그대로 쓴다.
  값을 돌려주는 엔드포인트는 여전히 하나도 없다.
- 공개키가 없으면 그 자리에서 `POST /api/keys/generate` 를 호출할 수 있게 한다 (DR-025).
  R3 의 수정이 선행되어야 이것이 성립한다 — **DR-028 은 DR-025 의 선행 조건이다.**
- 입력 요소는 값을 상태에 남기지 않는다. 전송 후 즉시 비운다.
- 저장 후 Step 에는 `{{변수명}}` 참조만 남는다. 값은 어느 순간에도 테스트 정의에 들어가지
  않는다 (FR-082·FR-084).
- 기존 `SecretValues` 화면은 유지한다 (DR-027 이 허용한다). 흐름이 그 화면을 **거치도록
  강제하지만 않으면 된다.**

## R6 — 디자인 준수: 절차 결정 (이 라운드의 최대 작업)

### 무엇이 어긋났는지 — 기계적으로 측정했다

`docs/design/*.dc.html` 8종 전체를 훑어 값을 세었다.

**색과 글꼴은 정확히 옮겨졌다.** dc.html 의 색 상위 14개가 `tokens.css` 의 값과 일치하고,
글꼴 3종(`Black Han Sans` / `IBM Plex Sans KR` / `IBM Plex Mono`)도 같다.

**어긋난 것은 기하다.** 여기서 "개발자 해석"이 들어갔다.

| 항목 | 확정 디자인 (8종 실측) | 구현 `frontend/src/theme/tokens.css` |
|---|---|---|
| `border-radius` | **0회.** 8개 파일 어디에도 `radius` 라는 문자열이 없다 | `--radius: 10px`, `--radius-sm: 6px` 를 버튼·입력·카드에 적용 |
| 테두리 두께 | `3px solid` 67회, `2px solid` 43회 | `button`·`input` 이 `1px solid` |
| 하드 오프셋 그림자 | `5px 5px 0 #14130F` 등 **26회**. 핵심 시각 장치 | 정의 없음 |
| body 배경 | `#EFEBE0` (`--surface`) | `--paper` `#FFFDF6` |

즉 **팔레트는 추출했고 형태는 지어냈다.** 확정 디자인은 직각·굵은 테두리·하드 그림자의
시각 언어인데, 구현은 둥근 모서리·얇은 테두리·그림자 없음의 일반적인 웹 UI가 됐다.

### 규모

| 항목 | 값 |
|---|---|
| 확정 화면 | 8종 |
| `<div>` 총계 | **677** |
| 인라인 `<svg>` 총계 | **98** |
| 독립 화면인데 제품에서 독립이 아닌 것 | **4종** — AiRecord·RunnerPaused·Takeover·StepInspector |

`App.tsx:18-26` 의 화면 상태에는 `loading·setup·list·create·runner·result·definition·keys·secrets`
만 있다. 위 4종은 `Runner.tsx` 안의 조건부 패널이다 (`Runner.tsx:510`, `525`, `539`,
`inspecting` 상태). DC-008 위반이다.

### 결정 — 옮기는 절차

**dc.html 의 마크업과 인라인 style 을 그대로 JSX 로 전사(轉寫)한 뒤, 정적 내용만
props·state 로 바꾼다.**

절차를 화면마다 똑같이 반복한다.

1. dc.html 의 최상위 컨테이너부터 DOM 순서대로 JSX 로 옮긴다. **인라인 `style` 값을 손대지
   않는다.** 축약·재해석·토큰 치환을 하지 않는다.
2. SVG 는 `viewBox`·`stroke-width`·`d` 까지 그대로 옮긴다. 아이콘 라이브러리로 대체하지
   않는다 — 대체는 해석이다.
3. 하드코딩된 표시 문자열 중 **데이터에서 오는 것만** props 로 바꾼다. 레이블·제목·안내
   문구는 dc.html 의 것을 그대로 둔다 (DC-007).
4. 상호작용(클릭·입력)을 붙인다. 이 단계에서 구조를 바꾸지 않는다.
5. 대조 기록을 작성한다.

**토큰은 값의 출처를 표시하는 용도로만 쓴다.** dc.html 에 나타나지 않는 값을 토큰으로
만들지 않는다. `--radius` 는 제거한다 — 확정 디자인에 없는 값이므로 존재 자체가 위반이다.

| 대안 | 기각 이유 |
|---|---|
| dc.html 을 파싱해 JSX 를 자동 생성 | 8개 파일 일회성 변환에 파서를 만드는 비용이 전사 비용보다 크다. 생성된 코드에 상호작용을 붙이는 일은 어차피 사람이 한다 |
| dc.html 을 `iframe` 으로 그대로 띄우고 그 위에 이벤트를 얹기 | 상태에 따라 달라지는 화면(실행 중·일시정지·실패)을 정적 HTML 로 표현할 수 없다 |
| 토큰·유틸리티 클래스로 재구성 | 이번 결함의 원인이 바로 이것이다. 추상화 층이 생기면 그 층에서 다시 해석이 일어난다 |
| Tailwind 등 도입 | 헌법이 스택을 고정한다. 그리고 클래스 이름으로 옮기는 순간 dc.html 과의 1:1 대조가 불가능해진다 |

### 결정 — 대조 기록 (DC-012)

**화면당 하나의 체크리스트 문서**를 `specs/002-.../design-conformance/<Screen>.md` 에 둔다.
`docs/design/*.dc.html` 에서 기계적으로 뽑은 사실을 항목으로 미리 채워 둔다.

자동 보조는 **사실 추출까지만** 한다. 판정은 사람이 한다.

- 추출 스크립트가 각 dc.html 에서 루트 치수·색 목록·글꼴·테두리 두께·그림자·주요 영역의
  높이를 뽑아 체크리스트의 "기준값" 칸을 채운다.
- 리뷰어는 제품 화면을 보고 "관측값" 칸과 일치 여부를 적는다.
- **픽셀 단위 스크린샷 자동 비교는 하지 않는다.** 확정 디자인은 정적 목업이고 제품은 실제
  데이터가 든 화면이라 내용이 다르다. 자동 비교는 내용 차이를 디자인 불일치로 오판한다.
  spec Assumptions 도 사람 판정을 전제한다.

### 결정 — 미정의 상태 기록 (DC-009)

`specs/002-.../design-conformance/undefined-states.md` 한 파일에 모은다. 화면·상태 이름·
따른 근거를 표로 적는다. 화면별 문서에 흩어 두면 "몇 건이 기록 없이 결정됐는가"(SC-110)를
셀 수 없다.

### 결정 — 화면 분리 (DC-008)

`App.tsx` 의 화면 상태를 확정 디자인 8종에 대응하도록 늘린다. 세션 상태(`view.state`)와
화면 선택을 분리한다 — 지금은 `Runner` 하나가 세션 상태 조합으로 4개 화면을 그린다.
R2 의 원인이 바로 이 얽힘이었다.

## R7 — 회귀 방지 (RG-001~RG-005)

### 테스트가 화면 구조에 얼마나 묶여 있는가 — 측정했다

`frontend/tests/*.tsx` 8개 파일의 질의 방식:

| 질의 | 횟수 |
|---|---|
| `getByText` | 72 |
| `findByText` | 10 |
| `queryByText` | 8 |
| `getAllByText` | 6 |
| `getByRole` | 2 |
| `getByLabelText` / `queryByLabelText` | 3 |
| `getByAltText` / `queryByAltText` | 3 |

**CSS 클래스나 DOM 구조로 찾는 질의가 하나도 없다.** 시각 요소를 확인하는 단언도
`MirrorView.test.tsx:25` 의 `img.style.pointerEvents` 하나뿐이고, 이것은 시각이 아니라
동작(읽기 전용 미러)을 본다.

**결론**: 전면 재작성이 레이아웃·치수·색을 바꿔도 테스트는 깨지지 않는다.
**단, 표시 문구가 바뀌면 깨진다.**

### 예상되는 유일한 회귀 원인과 그 처리

DC-007 은 확정 디자인의 문구를 그대로 쓰라고 요구한다. 현재 구현의 문구가 dc.html 과
다른 곳에서는 `getByText` 가 실패한다.

**이때 테스트를 확정 디자인의 문구로 고치는 것은 약화가 아니다.** 헌법 품질 게이트 4가
금지하는 것은 삭제·건너뛰기·단언 제거다. 검증 대상이 바뀌었으므로 기대값을 바꾸는 것은
정당하다. 다만 **문구 변경 외의 이유로 테스트를 고치지 않는다** — 그 선을 넘으면 약화다.

각 테스트 수정은 "어느 dc.html 의 어느 문구로 바꾸는가"를 근거로 남긴다.

### 원칙 I·II 유지 (RG-004·RG-005)

이 라운드는 Step 모델을 건드리지 않는다. 다만 두 지점을 확인해야 한다.

- **R1 의 `review` 상태**가 Step 모델에 새 필드를 추가하지 않는지. 세션 수명 주기의
  변화이지 Step 의 변화가 아니어야 한다.
- **R2 의 화면 분리**가 AI Step 과 사람 Step 을 다른 경로로 저장하지 않는지. 화면만
  나뉘고 저장 경로는 하나여야 한다 (원칙 I).
- 기존 `.importlinter` 계약(`itb.execution` → `itb.llm` 금지)이 계속 통과하는지.
  이 라운드가 임포트 그래프를 바꾸므로 매번 확인한다 (원칙 II).
