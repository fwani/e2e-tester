# Feature Specification: 부정 검증과 상태 검증 — 「없어야 한다」와 「누를 수 없어야 한다」

**Feature Branch**: `021-negative-state-assertions`

**Created**: 2026-09-28

**Status**: Draft

**Input**: User description: "검증 Step 에 부정 검증과 요소 상태 검증을 추가한다. 「특정 텍스트가 화면에 없어야 한다」, 「주소가 특정 값이 아니어야 한다」, 「삭제 버튼이 비활성화되어 있어야 한다」를 지금은 표현할 수 없다."

---

## 배경 — 시나리오에 있는 문장이 정의에 없다

사용자가 손으로 쓴 시나리오 문서에는 이런 문장이 반복해서 나온다.

| 시나리오 문장 | 지금 표현할 수 있는가 |
|---|---|
| 「해당 리소스의 삭제 버튼이 **비활성화되어** 사용자가 직접 제거할 수 없는지 확인한다」 | **아니다** |
| 「삭제 버튼이 **비활성화되어** 직접 제거할 수 없는지 확인한다」 | **아니다** |
| 「취소를 선택한다. 확인창이 닫히고 해당 메뉴가 **삭제되지 않는지** 확인한다」 | 부분적으로 (요소가 남아 있음 → `요소가 보인다`) |
| 「오류 문구가 **뜨지 않는지** 확인한다」 | **아니다** |

검증 Step 은 4종(`요소가 보인다`·`요소가 없거나 보이지 않는다`·`텍스트 일치·포함`·`주소 일치·포함`)뿐이고,
비교 방식은 `같다`·`포함한다` 둘뿐이다. 이 격자에 위 문장들이 들어갈 칸이 없다.

### 빠져 있는 칸은 두 개다

**1. 값 비교의 부정형.** 텍스트와 주소는 값을 비교하는데, 비교가 긍정 방향으로만 있다.
「`저장되었습니다` 가 보인다」는 쓸 수 있지만 「`오류` 가 보이지 않는다」는 쓸 수 없다.

요소 존재에는 이미 부정형이 있다 — `요소가 없거나 보이지 않는다`. 값 비교에만 없다.
대칭이 깨져 있고, 사용자는 그 빈칸을 셀렉터 트릭으로 메우거나 검증을 포기한다.

**2. 요소의 조작 가능 여부.** 「비활성화되어 있다」는 존재의 문제가 아니라 상태의 문제다.

| 화면이 이렇게 동작하면 | `요소가 보인다` | `요소가 없거나 보이지 않는다` |
|---|---|---|
| 삭제 버튼이 DOM 에서 빠진다 | 실패 (원하는 결과) | 통과 (원하는 결과) |
| 삭제 버튼이 남고 `disabled` 만 붙는다 | **통과** — 잘못 통과한다 | **실패** — 잘못 실패한다 |

아래 줄이 문제다. **어느 쪽으로도 참을 말할 수 없다.** 버튼은 분명히 보이고, 분명히 눌리지
않는데, 제품이 가진 두 개의 어휘 중 어느 것도 그 사실을 담지 못한다.

### 왜 우회로가 답이 아닌가

지금 사용자가 쓸 수 있는 우회는 셋이고, 셋 다 나쁘다.

| 우회 | 무엇이 나쁜가 |
|---|---|
| 셀렉터에 상태를 넣는다 (`button.delete:not([disabled])` 를 `hidden` 으로) | 후보 묶음이 아니라 CSS 단일 후보가 된다 — 헌법 원칙 IV 가 금지한 상태로 되돌아간다 |
| 눌러 보고 결과를 검증한다 | 비활성 버튼을 누르는 것은 **테스트가 아니라 부작용 실험**이다. 활성이었다면 데이터가 지워진다 |
| 검증을 포기하고 사람이 눈으로 본다 | 자동화의 목적이 사라진다. 020 이 만든 「끝까지 돌려 회귀를 잡는다」가 이 지점에서 끊긴다 |

첫 번째가 특히 위험하다. 원칙 IV 는 CSS 단독 저장을 명시적으로 금지하는데, 표현 수단이
없으면 사용자는 금지된 형태를 **스스로 만들어 넣는다.** 어휘의 빈칸이 원칙을 침식한다.

## 이 명세가 답해야 하는 어려운 질문 — 부정 검증은 거짓으로 통과하기 쉽다

긍정 검증과 부정 검증은 실패 방향이 반대다. 그래서 위험의 성질도 반대다.

| | 아직 화면이 준비되지 않은 순간에 평가하면 |
|---|---|
| 「`저장되었습니다` 가 있다」 | **실패**한다 → 사람이 알아차린다 → 대기를 늘린다 |
| 「`오류` 가 없다」 | **통과**한다 → 아무도 알아차리지 못한다 |

부정 검증의 기본 상태는 참이다. 클릭 직후 화면이 비어 있는 찰나에 평가하면 어떤 부정
조건이든 통과한다. **그 통과는 아무것도 검증하지 않았다는 뜻인데, 결과 화면에는 초록색으로
찍힌다.** 이것은 검증 도구가 낼 수 있는 가장 나쁜 출력이다 — 020 이 「통과가 정보를 담고
있지 않다」를 문제로 규정한 것과 정확히 같은 종류의 실패다.

### 지금 텍스트 검증은 기다리지 않는다

현재 화면 전체 텍스트 검증은 화면을 **한 번 읽고 즉시 판정한다.** 주소 검증은 제한 시간
동안 다시 읽는데, 텍스트 검증은 그렇지 않다. 긍정형에서는 이 차이가 「가끔 실패한다」로
보이지만, 부정형에서는 **「항상 통과한다」**로 나타난다.

부정 검증을 이 위에 얹으면 쓸모없는 초록색을 대량으로 만들게 된다. 그래서 이 기능은
부정형만 추가하는 것으로 끝나지 않고, **모든 값 비교 검증의 대기 규칙을 하나로 맞춰야
한다.** 이것이 이 명세의 가장 중요한 요구다.

### 그래도 남는 한계는 숨기지 않는다

조건이 참이 되면 즉시 통과하는 방식에서는, 「제한 시간 뒤에 나타나는 오류 문구」를 부정
검증이 놓친다. 이 한계는 **없앨 수 없다** — 없애려면 모든 부정 검증이 항상 제한 시간을
꽉 채워야 하고, 검증 하나에 수십 초가 붙는다.

없애는 대신 **사용자가 알게 한다.** 부정 검증을 만드는 자리에서 「먼저 화면이 안정되었음을
확인하는 검증을 앞에 두라」를 읽을 수 있어야 한다. 알려진 한계를 말하지 않는 것은 거짓
통과를 제품이 보증하는 것과 같다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 「그 문구가 없어야 한다」를 검증으로 남긴다 (Priority: P1)

테스트 작성자가 시나리오를 옮기다가 「오류 메시지가 뜨지 않는지 확인한다」에 도달한다.
검증 추가 화면에서 텍스트 검증을 고르고, 비교 방식에서 「포함하지 않는다」를 선택한 뒤
`오류` 를 적는다. Step 이 만들어지고, 재실행 때마다 그 문구가 화면에 끼어들지 않았음을
확인한다.

**Why this priority**: 부정 검증이 없으면 시나리오의 상당수가 정의로 옮겨지지 않은 채
사람의 눈에 남는다. 값 비교의 부정형은 상태 검증보다 적용 범위가 넓고(모든 텍스트·주소),
기존 개념(비교 방식)의 확장이라 사용자가 새로 배울 것이 가장 적다.

**Independent Test**: 부정 텍스트·주소 검증만 만들어도 시나리오 문서의 「~가 뜨지 않는지」
계열 문장을 정의로 옮길 수 있다. 상태 검증 없이도 독립적으로 가치를 낸다.

**Acceptance Scenarios**:

1. **Given** 화면에 `저장되었습니다` 만 떠 있고 `오류` 는 없다, **When** 「화면 텍스트가 `오류` 를 포함하지 않는다」 검증을 실행한다, **Then** 통과한다
2. **Given** 화면에 `오류가 발생했습니다` 가 떠 있다, **When** 같은 검증을 실행한다, **Then** 실패하고 설명에 기대(`오류` 를 포함하지 않아야 함)와 실제 화면 텍스트가 함께 나온다
3. **Given** 클릭 직후 화면이 아직 비어 있고 0.8초 뒤에 `오류` 가 나타난다, **When** 제한 시간 5초로 「`오류` 를 포함하지 않는다」 검증을 실행한다, **Then** **실패한다** — 즉시 평가해 통과시키지 않는다
4. **Given** 현재 주소가 `/dashboard` 다, **When** 「주소가 `/login` 과 같지 않다」 검증을 실행한다, **Then** 통과한다
5. **Given** 작성 시점에 `오류` 가 실제로 떠 있어 부정 검증이 통과하지 못한다, **When** AI 가 이 검증을 만든다, **Then** Step 은 남고 결함 후보(작성 시점 어긋남)로 기록된다 — 조건을 뒤집어 통과시키지 않는다

### User Story 2 - 「그 버튼을 누를 수 없어야 한다」를 검증으로 남긴다 (Priority: P2)

테스트 작성자가 「자동 포함된 리소스의 삭제 버튼이 비활성화되어 직접 제거할 수 없는지
확인한다」에 도달한다. 검증 추가 화면에서 「요소를 조작할 수 없다」를 고르고 삭제 버튼을
대상으로 지정한다. 버튼을 실제로 누르지 않고도 그 버튼이 잠겨 있음이 정의에 남는다.

**Why this priority**: 사용자가 직접 지목한 요구이고, 우회로가 셋 다 나쁘다(부작용 실험 ·
원칙 IV 침식 · 수동 확인). 다만 부정 검증보다 적용 범위가 좁고 새 어휘를 하나 배워야
하므로 P2 다.

**Independent Test**: 상태 검증만 만들어도 「비활성화되어 있는지」 계열 문장을 정의로
옮길 수 있다. 부정 검증과 서로 의존하지 않는다.

**Acceptance Scenarios**:

1. **Given** 삭제 버튼이 화면에 있고 `disabled` 상태다, **When** 「요소를 조작할 수 없다」 검증을 실행한다, **Then** 통과한다
2. **Given** 삭제 버튼이 화면에 있고 누를 수 있다, **When** 같은 검증을 실행한다, **Then** 실패하고 설명에 「조작할 수 없어야 하는데 조작할 수 있었다」가 나온다
3. **Given** 삭제 버튼이 처음에는 눌리다가 0.5초 뒤 잠긴다, **When** 제한 시간 5초로 같은 검증을 실행한다, **Then** 통과한다 — 제한 시간 안에서 상태가 참이 되기를 기다린다
4. **Given** 삭제 버튼이 화면에 아예 없다, **When** 같은 검증을 실행한다, **Then** **실패한다** — 없는 것은 비활성이 아니다. 요소 부재는 `요소가 없거나 보이지 않는다` 가 담당한다
5. **Given** 잠겨 있던 버튼이 조건 충족 후 활성화된다, **When** 「요소를 조작할 수 있다」 검증을 실행한다, **Then** 통과한다

### User Story 3 - 세 작성 경로 모두에서 쓸 수 있다 (Priority: P3)

같은 검증을 AI 작성 중에도, 화면의 검증 추가 폼에서도, 저장된 테스트에 손으로 Step 을
넣을 때도 만들 수 있다. 어느 경로로 만들었든 목록과 상세에서 같은 문구로 읽히고, 같은
방식으로 실행된다.

**Why this priority**: 헌법 원칙 I 이 요구하는 것이다 — 작성 경로가 Step 의 의미를 바꾸면
안 된다. 다만 P1·P2 가 한 경로에서라도 동작하면 가치는 이미 나오므로 P3 다.

**Independent Test**: P1 또는 P2 로 만든 검증 종류를 세 경로에서 각각 만들어, 산출된
정의가 같은지 비교한다.

**Acceptance Scenarios**:

1. **Given** AI 작성 세션이 진행 중이다, **When** 모델이 「`오류` 를 포함하지 않는다」 검증을 요청한다, **Then** 화면 폼으로 만든 것과 같은 형태의 Step 이 만들어진다
2. **Given** 저장된 테스트를 편집 중이다, **When** 부정 텍스트 검증 Step 을 손으로 삽입한다, **Then** 표시 이름이 종류와 부정 여부를 함께 드러낸다
3. **Given** 같은 검증이 세 경로로 각각 만들어졌다, **When** 정의 파일을 비교한다, **Then** 표시 이름과 식별자를 빼면 동일하다

### Edge Cases

- **대상 요소를 지정한 부정 텍스트 검증에서 그 요소를 찾지 못하면?** → 실패한다. 「그
  요소의 텍스트가 X 가 아니다」는 요소가 있다는 전제 위의 문장이다. 요소가 없을 수도
  있는 상황은 `요소가 없거나 보이지 않는다` 로 표현해야 한다. 여기서 통과시키면 「요소가
  사라져서 통과」와 「텍스트가 달라서 통과」를 결과에서 구별할 수 없다.
- **화면 전체를 대상으로 한 부정 텍스트 검증**은 대상 요소가 없으므로 위 문제가 없다.
- **폼 요소가 아닌 대상에 상태 검증을 걸면?** → 버튼·입력·선택 같은 조작 가능한 요소가
  아니면 「조작할 수 있다」가 항상 참으로 나온다. 이 한계를 결과 설명이나 작성 화면에서
  알 수 있어야 한다. 조용히 통과시키는 것이 가장 나쁘다.
- **부정 검증이 작성 시점부터 통과하지 못하면?** → 020 의 규칙을 그대로 따른다. Step 은
  남고 작성 시점 어긋남이 기록된다. 조건을 뒤집어 통과시키지 않는다.
- **기존에 저장된 테스트 파일**에는 새 종류가 없다. 읽기·실행·내보내기가 모두 지금과
  동일해야 한다.
- **비교 값이 빈 문자열인 부정 검증** — 「빈 문자열을 포함하지 않는다」는 어떤 화면에서도
  거짓이다. 만들 수 없게 막는다.

## Requirements *(mandatory)*

### Functional Requirements — 부정 검증 (US1)

- **FR-001**: 값을 비교하는 검증(텍스트·주소)에서 사용자는 **부정 비교**를 고를 수 있어야
  한다 — 「같지 않다」와 「포함하지 않는다」.
- **FR-002**: 부정 비교는 **값을 비교하는 검증에만** 제공한다. 요소 존재의 부정은 이미
  `요소가 없거나 보이지 않는다` 가 담당하므로 새로 만들지 않는다. 같은 사실을 두 가지
  방법으로 적을 수 있게 되면 목록에서 읽는 사람이 둘을 다른 뜻으로 읽는다.
- **FR-003**: 모든 값 비교 검증은 **제한 시간 안에서 조건이 참이 될 때까지 기다린다.**
  긍정·부정을 가리지 않는다. 한 번 읽고 즉시 판정하는 검증이 남아 있으면 안 된다.
- **FR-004**: 조건이 제한 시간 안에 참이 되면 그 즉시 통과한다. 제한 시간을 끝까지
  소모하지 않는다.
- **FR-005**: 부정 검증의 실패 설명은 **기대와 실제를 모두** 담는다. 「`오류` 를 포함하지
  않아야 하는데 화면 텍스트는 `…오류가 발생했습니다…` 였습니다」처럼 읽혀야 한다.
- **FR-006**: 대상 요소를 지정한 텍스트 검증에서 요소를 찾지 못하면 **긍정·부정 모두
  실패**한다.
- **FR-007**: 비교 값이 비어 있는 부정 검증은 만들 수 없다.

### Functional Requirements — 상태 검증 (US2)

- **FR-010**: 요소가 **조작 가능한 상태인지** 검증하는 종류를 제공한다 — 「조작할 수 있다」와
  「조작할 수 없다」.
- **FR-011**: 상태 검증은 **대상 요소가 필수**이고 비교 값을 쓰지 않는다.
- **FR-012**: 대상 요소를 찾지 못하면 **실패**한다. `요소가 없거나 보이지 않는다` 와 달리
  부재를 통과로 보지 않는다.
- **FR-013**: 상태 검증도 제한 시간 안에서 상태가 참이 되기를 기다린다 (FR-003 과 같은 규칙).
- **FR-014**: 조작 가능 여부를 판정할 수 없는 대상(폼 요소가 아닌 요소)에 대해서는 그
  사실을 사용자가 알 수 있어야 한다. 판정 불가를 통과로 바꾸어 감추지 않는다.

### Functional Requirements — 작성 경로와 표시 (US3)

- **FR-020**: 화면의 검증 추가 폼에서 새 비교 방식과 새 검증 종류를 고를 수 있다.
- **FR-021**: AI 작성 도구가 새 비교 방식과 새 검증 종류를 쓸 수 있다. 작성 지침은 부정
  검증을 **통과시키려고 조건을 뒤집지 말라**고 명시한다.
- **FR-022**: 저장된 테스트에 손으로 Step 을 넣는 경로에서도 부정 텍스트·주소 검증을
  만들 수 있다.
- **FR-023**: Step 목록·상세의 표시 문구가 **부정 여부와 상태 종류를 드러낸다.** 「텍스트
  검증」만 보고 긍정인지 부정인지 알 수 없으면 안 된다.
- **FR-024**: 부정 검증과 상태 검증도 **작성 시점 어긋남 기록의 대상**이다 (020 FR-005·FR-008).
- **FR-025**: 부정 검증과 상태 검증도 **실행 결과 분류의 대상**이다 — 이미 아는 결함 ·
  오늘 깨진 것 · 해소됨 (020 FR-018·FR-022).
- **FR-026**: 부정 검증을 만드는 자리에서, 조건이 참이 되면 즉시 통과한다는 성질과 그로
  인해 **늦게 나타나는 것을 놓칠 수 있다**는 한계를 읽을 수 있어야 한다.

### Functional Requirements — 호환과 이식성

- **FR-030**: 기존에 저장된 테스트 정의는 **변경 없이** 읽히고 실행된다. 마이그레이션
  절차를 요구하지 않는다.
- **FR-031**: 검증 조건의 정의 형태는 **한 곳에서만** 규정되고 화면·실행·작성 경로가 그것을
  따른다 (헌법 원칙 I, 교차 언어 스키마 의무).
- **FR-032**: 새 검증 종류는 표준 Playwright 로 옮길 수 있는 형태여야 하며, 대응 관계를
  문서에 남긴다 (헌법 원칙 V 의 증분 의무).

### 범위 외 *(001 FR-013c 의 선례를 따라 명시한다)*

아래는 이번에 만들지 않는다. **화면에 비활성 항목으로도 보여 주지 않는다** — 없는 기능을
회색으로 보여 주는 것은 「곧 생긴다」는 약속처럼 읽힌다.

| 범위 외 | 이유 |
|---|---|
| 체크 상태(checked / unchecked) 검증 | 사용자가 제시한 요구에 없다. 필요해지면 상태 검증의 확장으로 자연스럽게 붙는다 |
| 읽기 전용(readonly) · 초점(focused) 검증 | 같음. 조작 가능 여부로 대부분 대체된다 |
| 요소 개수 검증 | 001 FR-013c 에서 이미 범위 외 |
| 입력 필드 현재값 검증 | 001 FR-013c 에서 이미 범위 외 |
| 정규식 비교 | 비교 방식의 확장이지만 부정형과 직교하는 별도 주제다. 함께 넣으면 조합이 여덟 가지가 되고 화면에서 고르기 어려워진다 |

---

### Key Entities

- **검증 조건** — 검증 Step 하나가 무엇을 확인하는지. 「무엇을 보는가」(요소 존재 · 요소
  상태 · 텍스트 · 주소)와 「어떻게 비교하는가」(같다 · 포함한다 · 같지 않다 · 포함하지
  않는다)의 두 축으로 이루어진다. 이번 변경은 **첫 축에 상태를, 둘째 축에 부정형을**
  더한다. 축을 새로 만들지 않는다.
- **검증 대상** — 어느 요소를 보는가. 종류마다 필수 여부가 다르다: 요소 존재·요소 상태는
  필수, 텍스트는 선택(비우면 화면 전체), 주소는 쓰지 않는다.
- **작성 시점 어긋남** — 020 이 정의한 기록. 이번에 추가되는 검증도 같은 대상이며, 새
  기록 형태를 만들지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 「삭제 버튼이 비활성화되어 있다」를 **검증 Step 하나로** 표현할 수 있다.
  셀렉터 트릭도, 버튼을 눌러 보는 부작용 실험도 필요하지 않다.
- **SC-002**: 「특정 문구가 화면에 없다」와 「주소가 특정 값이 아니다」를 각각 **검증 Step
  하나로** 표현할 수 있다.
- **SC-003**: 대상이 늦게 나타나는 화면에서 부정 검증이 **거짓으로 통과하지 않는다** —
  제한 시간 안에 문구가 나타나면 실패로 잡힌다.
- **SC-004**: 기존에 저장된 모든 테스트가 **파일 변경 없이** 그대로 실행되고, 실행 결과가
  이번 변경 전과 같다.
- **SC-005**: 새 검증 종류가 **세 작성 경로**(AI 작성 · 화면 추가 · 수동 삽입) 중 각 경로가
  지원하기로 한 범위에서 모두 만들어지고, 산출된 정의가 서로 같다.
- **SC-006**: 시나리오 문서의 「~가 비활성화되어」·「~가 뜨지 않는지」·「~되지 않는지」 계열
  문장이 **사람 손을 거치지 않고** 검증 Step 으로 옮겨진다.
- **SC-007**: 사용자가 검증을 만드는 자리에서 부정 검증의 한계(늦게 나타나는 것을 놓칠 수
  있음)를 **읽을 수 있다.**

## Assumptions

이 명세가 기능 설명에 없던 부분을 채우며 택한 기본값이다. 다르게 정해야 하면 여기를 고친다.

- **상태 검증의 범위는 「조작 가능 여부」 하나로 한정한다.** 사용자가 제시한 세 사례가 모두
  비활성 버튼이고, 체크 상태·읽기 전용은 요구에 나타나지 않았다. 헌법의 Simplicity 규칙에
  따라 지금 필요한 것만 만든다. 확장이 필요해지면 같은 축에 값을 더하는 형태가 된다.
- **부정형은 비교 방식(둘째 축)에 넣는다.** 「무엇을 보는가」는 그대로 두고 「어떻게
  비교하는가」만 늘린다. 검증 종류를 늘리면 화면 목록·작성 도구·문서가 전부 커지고,
  `요소가 없거나 보이지 않는다` 가 이미 부정을 종류로 표현하고 있어 두 가지 부정 표현
  방식이 섞인다. 다만 **요소 존재의 부정만은 예외로 종류 쪽에 남긴다** — 값 비교가 아니라
  대상 자체가 없을 수 있는 경우라 비교 축에 얹을 값이 없다. 최종 형태는 `plan` 에서
  확정한다.
- **조작 가능 여부는 긍정·부정 두 종류로 노출한다.** 비교 방식의 부정형으로 처리하지
  않는다 — 상태 검증은 비교 값을 쓰지 않으므로 비교 방식 자체가 의미를 갖지 않는다.
- **하위 호환은 값 추가만으로 달성된다고 본다.** 기존 정의 파일에는 새 값이 없으므로
  그대로 읽힌다. 정의 형식의 버전을 올리지 않는다 — 020 이 어긋남 기록을 더하면서도
  올리지 않은 것과 같은 판단이다. 이 전제가 틀리면 `plan` 단계에서 드러난다.
- **대기 규칙 통일은 기존 동작의 변경을 포함한다.** 화면 전체 텍스트 검증이 지금은 기다리지
  않는데, 이번에 기다리게 된다. 지금 통과하던 것이 실패로 바뀌지는 않고(조건이 참이면 즉시
  통과), 지금 실패하던 것 중 일부가 통과로 바뀐다. 이 방향의 변화는 개선으로 본다.
- **내보내기(Export)는 아직 구현되어 있지 않다.** 헌법 원칙 V 의 증분 의무에 따라, 이번에
  추가하는 검증도 표준 Playwright 로 옮길 수 있는 형태여야 하고 대응 관계를 문서에 남기되,
  생성기 구현은 이번 범위가 아니다.

## Dependencies

- **020 (기대 동작 기준 검증)** — 작성 시점 어긋남 기록과 실행 결과 분류가 이미 있어야
  FR-024·FR-025 가 성립한다. 020 의 구현은 완료되어 있다.
- **001 FR-013a·FR-013c** — 검증 4종과 범위 외 목록의 원본. 이번 명세는 그 목록을 늘리되
  범위 외 항목을 되살리지 않는다.
- **헌법 원칙 I·IV·V** — 정의 형태의 단일 출처, 후보 묶음 기반 요소 식별, 표준 Playwright
  이식 가능성.
