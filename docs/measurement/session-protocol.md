# 수동 측정 세션 진행 대본 (T155)

시나리오 20건 규모의 측정 세션을 실제로 어떻게 진행하는지다.
**자동 테스트로 대체할 수 없다** — 재는 대상이 사람의 판단 시간과 실제 언어모델의 결과다.

준비물: [sample-selection.md](sample-selection.md) 기입 완료 · [recording-sheet.csv](recording-sheet.csv) ·
`quickstart.md` §0 의 실행 환경.

## 0. 세션 전 (1회)

1. `sample-selection.md` 의 대상 앱·측정자·배분을 **먼저** 채운다. 비어 있으면 세션을 시작하지 않는다.
2. 자동 지표가 모두 통과 상태인지 확인한다. 자동 지표가 깨진 채로 수동 측정을 하면
   도구의 성능이 아니라 결함을 재게 된다.
   ```bash
   cd backend && uv run pytest
   ```
3. 측정자에게 알려 줄 것과 알려 주지 않을 것을 정한다.
   - 알려 준다: 도구의 화면 구성, 녹화·일시정지·이어서 실행의 존재
   - 알려 주지 않는다: 특정 시나리오를 어떤 순서로 조작해야 하는지
   `처음` 측정자에게 사전 실습을 시키면 `숙련` 과 구분이 사라진다.

## 1. 시나리오 1건당 절차

한 행(`S01`~`S20`)을 채우는 절차다. **타이머 시작·정지 시점을 아래로 고정한다** —
시점이 흔들리면 SC-001·005 가 사람마다 다른 것을 잰다.

| 단계 | 하는 일 | 기록 열 |
|------|---------|---------|
| 1 | (대조군 대상만) 같은 시나리오를 Playwright 코드로 직접 작성해 통과시킨다. **타이머: 시나리오 설명을 읽은 순간 시작 → 테스트가 통과한 순간 정지** | `baseline_code_seconds` |
| 2 | 도구로 같은 시나리오를 작성한다. **타이머: 도구 화면을 연 순간 시작 → 저장하고 재실행이 통과한 순간 정지** | `build_seconds` |
| 3 | 작성 도중 정의 파일이나 코드를 직접 손댔는지 기록한다 | `code_edited` |
| 4 | 통과하는 테스트를 만들었는지 기록한다 | `completed` |
| 5 | 같은 시나리오를 **자연어로** 지시해 결정적 Step 으로 변환되는지 본다 | `nl_attempted` · `nl_success` |
| 6 | 변환에 실패했으면 **왜** 실패했는지 고른다: `화면미인식` · `요소미발견` · `지시모호` · `기타` | `nl_failure_reason` |
| 7 | 5에서 막혔으면 Takeover 로 이어받아 완료를 시도한다 | `takeover_attempted` · `takeover_completed` |
| 8 | 대상 앱을 한 군데 고의로 바꿔 테스트를 실패시킨 뒤, 결과 화면만 보고 원인을 짚는다. **타이머: 결과 화면이 뜬 순간 시작 → 실패 Step 과 이유를 말한 순간 정지** | `failure_diagnosed` · `diagnose_seconds` |

8단계의 "고의로 바꾸는 것"은 사소한 변경이어야 한다 (버튼 라벨 변경, 요소 순서 변경 등).
앱을 크게 바꾸면 진단이 아니라 재작성을 재게 된다.

## 2. 기록 규칙

- **재지 않은 칸은 비워 둔다.** `0` 이나 `no` 로 채우지 않는다. 집계 스크립트는 빈칸을
  분모에서 빼지만, `no` 는 실패로 센다. 재지 않은 것과 재서 나쁜 것은 다르다.
- 자연어 변환 실패는 **이유가 지표보다 쓸모 있다.** `nl_failure_reason` 이 비면 집계가 경고한다.
- 이상한 일이 있었으면 `notes` 에 한 줄 남긴다. 나중에 값을 의심할 때 유일한 단서다.
- 민감 값(계정·토큰·URL 내 식별자)은 시트에 적지 않는다. 고객사명·내부 프로젝트명도 익명화한다.

## 3. 집계

```bash
python3 scripts/mvp_metrics_report.py docs/measurement/recording-sheet.csv
```

- 종료 코드 `0` — 기록 오류 없음
- 종료 코드 `2` — 기록 오류 있음. **고치고 다시 돌린다.** 오류가 있는 값은 집계에서 빠져 있다

출력의 `## 결과` 표를 `docs/mvp-metrics.md` §결과 에 붙이고, 표본 구성과 측정 일자를 함께 적는다.

## 4. 세션 후

1. `docs/mvp-metrics.md` §결과 를 채운다. 목표 미달 지표는 **미달로 적는다.**
   표본을 바꿔 다시 재는 것은 측정이 아니라 조정이다.
2. 미달 지표마다 원인 가설을 한 줄 적고, 필요하면 `tasks.md` 에 작업으로 올린다.
3. `tasks.md` 의 T155 를 `[X]` 로 바꾸고, 측정 일자와 표본 규모를 한 줄로 적는다.

## 왜 이 지표들만 수동인가

| 지표 | 왜 자동화할 수 없는가 |
|------|----------------------|
| SC-001 | 사람이 실제 앱을 보고 판단하는 시간과 "코드를 안 고치고 끝냈는가"가 측정 대상이다 |
| SC-002 | 실제 언어모델과 실제 화면이 필요하다. 대본을 쓰면 모델이 아니라 대본을 재게 된다 |
| SC-004 | 실패 상황이 실제로 발생해야 하고, 이어받는 판단이 사람의 것이다 |
| SC-005 | 대조군(코드 직접 작성)이 사람의 작업이다 |
| SC-009 | 화면을 읽고 원인을 짚는 사람의 시간이 측정 대상이다 |

나머지 7개 지표(SC-003·006·007·008·010·011·012)와 성능 목표는 테스트가 매 실행에서 재고 있다.
자동으로 잴 수 있는 것을 사람이 재면 매번 결과가 달라진다.
