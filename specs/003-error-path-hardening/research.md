## R1. 에러 분류를 기존 오류 계약에 얹는 방법 (EC-001~EC-004)

### 확인한 사실

- 오류 계약은 이미 있다: `{ "error": { "code", "message", "detail" } }` — `backend/src/itb/api/errors.py`, `specs/001-interactive-ai-test-builder/contracts/rest-api.md:7-10`
- `ErrorCode` 는 23개 값을 가진 문자열 열거형이다 (`api/errors.py:18-49`)
- 세 개의 예외 처리기가 있다 (`api/app.py:73-101`): 계약 오류(`ApiError`), 요청 검증 실패(422), **처리되지 않은 오류**
- **처리되지 않은 오류 처리기가 `DEFINITION_INVALID` 를 코드로 쓴다** (`api/app.py:96`). 이 코드는 사용자가 잘못된 정의를 넣어 정상적으로 거부당했을 때도 쓰인다. 받는 쪽은 둘을 구별할 수 없다 — 이 라운드가 존재하는 이유다

### 결정

`ErrorBody` 에 필드 **둘**을 더한다. 기존 세 필드는 그대로 둔다.

| 필드 | 값 | 뜻 |
|---|---|---|
| `category` | `"blocked"` \| `"broken"` | 막은 것 / 깨진 것 |
| `next_action` | 문자열 (비어 있을 수 없음) | 사용자가 지금 할 수 있는 일 |

그리고 **`INTERNAL_ERROR` 코드를 새로 만들어** 처리되지 않은 오류에 쓴다. `DEFINITION_INVALID`
재사용을 끝낸다 (EC-003).

분류가 코드와 어긋나지 않도록 **`ErrorCode → category` 전수 대응표**를 한 곳에 둔다. 대응표가
모든 `ErrorCode` 를 덮는지는 자동 검증이 확인한다 — 코드를 추가하고 분류를 빼먹으면 실패한다.

`category` 를 응답에 실어 보내는 이유는 EC-002 다. 상태 코드(4xx/5xx)로 유추하게 두면 규칙이
암묵적이 되고, 실제로 5xx 인 "막은 것"(외부가 준 실패를 그대로 옮기는 경우)과 4xx 인 "깨진 것"
(잘못 만든 요청을 우리가 못 만든 경우)이 생기면 유추가 틀린다.

### 기각한 대안

| 대안 | 기각 이유 |
|---|---|
| HTTP 상태 코드로 분류를 대신한다 | EC-002 위반. 받는 쪽이 유추해야 하고, 4xx/5xx 와 blocked/broken 은 일대일이 아니다 |
| 코드 이름 접두사로 구분한다 (`ERR_` / `BUG_`) | 기존 23개 코드를 전부 개명해야 한다. 001·002 의 계약 문서와 테스트가 코드 이름을 참조한다 |
| `detail` 안에 분류를 넣는다 | `detail` 은 자유 형식이라 스키마로 강제되지 않는다. 빠뜨려도 아무도 모른다 |
| 별도 헤더로 보낸다 | 실시간 통로(WebSocket)에는 헤더가 없다. EC-008 이 같은 규약을 요구한다 |

## R2. 오류 정의를 한 곳에서만 유지하는 방법 (EC-006)

### 확인한 사실

- **프런트엔드가 `ErrorCode` 23개를 손으로 복제하고 있다** — `frontend/src/api/client.ts:13-33`. 백엔드 열거형과 두 벌이다
- 그런데 **단일 출처 파이프라인은 이미 있다**: `backend/src/itb/domain/*.py` (Pydantic) → `python -m itb.schema.export` → `backend/schema/*.schema.json` → `npm run gen:types` → `frontend/src/types/generated/*.d.ts`
- 생성물은 손으로 고치지 않는다고 명시돼 있고, **CI 에 schema-drift 잡이 있어** 재생성 결과와 커밋된 파일을 비교한다 (`frontend/scripts/gen-types.mjs`, `backend/src/itb/schema/export.py`)
- 현재 내보내는 모델은 넷이다: `step-dsl`, `step`, `project`, `run-result`. 오류 계약은 빠져 있다
- 파이프라인의 권위 위치는 `itb.domain` 이다. 그런데 오류 계약은 `itb.api.errors` 에 있다 — 파이프라인 밖이다

### 결정

오류 계약 모델(`ErrorCode`, `Category`, `ErrorBody`, `ErrorResponse`, 분류 대응표)을
**`itb/domain/error.py` 로 옮기고**, `schema/export.py` 의 `MODELS` 에 `error-response` 를 더한다.
프런트엔드는 생성된 타입을 임포트하고 `client.ts` 의 손으로 쓴 union 을 지운다.

이 결정의 값은 새 장치를 만들지 않는다는 데 있다. 드리프트 검사, 생성 스크립트, CI 잡이 이미
있고 오류 계약만 그 파이프라인 밖에 있었다. 안으로 들이면 EC-006 이 **기존 CI 잡으로** 지켜진다.

`api/errors.py` 는 남긴다 — `ApiError`, `bad_request()` 같은 FastAPI 결합 부분은 도메인이 아니다.
도메인 모델을 임포트해 쓰는 얇은 층이 된다.

### 기각한 대안

| 대안 | 기각 이유 |
|---|---|
| `client.ts` 의 union 을 손으로 계속 맞춘다 | 지금 상태 그대로다. 헌법 Cross-language schema duty 의 "두 벌을 손으로 유지" 금지에 걸린다 |
| 런타임에 `/api/error-codes` 로 목록을 내려받는다 | 타입 검사 시점에 쓸 수 없다. 컴파일 타임 안전성을 잃는다 |
| 오류 모델을 `api/errors.py` 에 둔 채 export 대상에만 추가한다 | export 의 권위 위치가 `itb.domain` 이라고 문서화돼 있다. 예외를 만들면 규칙이 약해진다 |

## R3. 이상 조작 시나리오 목록을 두는 자리와 형태 (SC-201·SC-206)

### 결정

**`specs/003-error-path-hardening/contracts/abnormal-scenarios.json`** 하나를 권위 목록으로 삼고,
백엔드 검증과 화면 검증이 **같은 파일을 읽는다.**

형태(시나리오 하나):

```json
{
  "id": "AS-013",
  "fault": "order-violation",
  "surface": "api",
  "target": "POST /api/sessions/{id}/resume",
  "operation": "이미 끝난 세션을 이어가기",
  "must_be_rejected": true,
  "preserves": "session"
}
```

- `fault` 는 4종, `surface` 는 3종 → 12개 조합. 각 조합 최소 3건 (SC-206)
- `must_be_rejected` 는 **기대 응답이 아니다.** "이 조작은 허용되어서는 안 된다"는 시나리오의 정의 자체다. 이것이 없으면 판정축 ①의 "조용한 성공"(실패했는데 성공처럼 보임)을 판별할 수 없다 — 무엇이 실패여야 하는지 모르면 조용한 성공도 알 수 없다
- `preserves` 는 이 조작 뒤 무엇이 남아 있어야 하는지(판정축 ③)를 가리킨다. 응답 내용이 아니라 보존 대상이다
- **응답 코드·메시지 문구는 적지 않는다.** 명세의 결정(판정 3축이 기대값을 대신한다)을 따른다

JSON 인 이유: 프런트엔드에 YAML 파서 의존성이 없다. JSON 은 양쪽이 추가 의존성 없이 읽는다.

`specs/` 아래에 두는 이유: 이 목록이 **완료 판정의 분모**다 (SC-201 "전건"). 테스트 트리에 두면
어느 쪽 트리에 둘지부터 정해야 하고, 양쪽에 복사하면 EC-006 과 같은 두-벌 문제가 다시 생긴다.

### 기각한 대안

| 대안 | 기각 이유 |
|---|---|
| 시나리오를 테스트 함수로만 표현한다 | "전건 통과"의 분모를 셀 수 없다. SC-206(조합별 최소 3건) 검증도 불가능하다 |
| 백엔드·프런트엔드에 각각 목록을 둔다 | 두 벌 유지. 조합 커버리지가 갈라진다 |
| YAML 로 둔다 | 프런트엔드에 파서 의존성이 새로 필요하다. "새 의존성 최소화" 제약에 걸린다 |
| 시나리오마다 기대 응답을 적는다 | 명세가 명시적으로 배제했다. 구현이 틀리면 기대값도 같이 틀린다 |

## R4. 외부 환경 실패를 재현하는 방법 (AP-030~AP-033)

### 확인한 사실

- LLM 클라이언트 생성은 `create_client()` 하나를 지나며, **호출부가 모두 함수 안에서 늦게 임포트한다** (`authoring/agent.py:88`, `api/routes/ai.py:38`). 즉 `itb.llm.client.create_client` 를 바꿔치기하면 호출부 수정 없이 대체된다
- 실패 표현도 이미 있다: `LlmUnavailableError`, `RefusalError` (`llm/client.py:37,45`)
- 세션 상실 감시가 이미 있다: `SessionLossWatcher`, 상태별 안내를 만드는 `_guidance(state)` (`execution/session_loss.py:39,110`)
- 대상 사이트 역할을 하는 로컬 고정 앱이 이미 있다: `fixtures/sample-app`, 세션 범위 픽스처 `fixture_app` 이 빈 포트에 띄운다 (`backend/tests/conftest.py:33-66`)

### 결정

경계마다 **이미 있는 이음매**를 쓴다. 새 주입 프레임워크를 만들지 않는다.

| 경계 | 재현 방법 | 제품 코드 변경 |
|---|---|---|
| AI 응답 오류·타임아웃 | `itb.llm.client.create_client` 를 대체해 오류를 던지거나 형식이 깨진 응답을 주거나 시간을 끄는 가짜를 주입 | 없음 (늦은 임포트 덕에 그대로 동작) |
| 브라우저 강제 종료 | 세션이 쥔 브라우저/컨텍스트를 검증 쪽에서 직접 닫고 이어서 명령을 보낸다 | 없음 |
| 대상 사이트 무응답·느림·오류 | `fixtures/sample-app` 에 지연·무응답·오류를 내는 경로를 더하고 기존 `fixture_app` 픽스처로 띄운다 | 고정 앱만 (제품 아님) |

### 기각한 대안

| 대안 | 기각 이유 |
|---|---|
| 실제 AI 서비스를 오류 나게 한다 | 재현이 불안정하고 비용이 든다. 헌법 원칙 II 와 무관하게 검증이 외부에 의존하면 안 된다 |
| HTTP 가로채기 라이브러리를 새로 도입한다 | 새 의존성. 늦은 임포트 구조 덕에 필요 없다 |
| 네트워크를 실제로 끊는다 | 실행 환경에 따라 결과가 달라지고 CI 에서 재현되지 않는다 |
| 제품에 "실패 주입 모드" 스위치를 넣는다 | 제품에 검증 전용 코드를 남긴다. 운영 경로에 없어야 할 분기를 만든다 |

## R5. 규약 준수를 전수 점검으로 검증하는 방법 (RG-104)

### 결정

개별 사례를 하나씩 확인하지 않고 **훑는 검증** 넷을 둔다.

1. **분류 대응표 전수성** — 모든 `ErrorCode` 가 `category` 를 갖는지 확인한다. 코드를 새로 만들고 분류를 빼먹으면 실패한다
2. **경로 전수 훑기** — 앱에 등록된 모든 요청 경로를 열거하고, 각 경로에 최소 하나의 거부를 유발해 응답이 생성된 오류 스키마를 만족하고 `category` 와 `next_action` 을 담는지 확인한다. **새 경로가 추가되면 이 검증이 자동으로 그것을 포함한다**
3. **우회 금지 검사** — 오류 계약을 거치지 않는 오류 생성(계약 밖 예외를 그대로 내보내는 것)이 `api/errors.py` 밖에 존재하지 않는지 원본을 훑어 확인한다
4. **화면 단일 통로** — 화면이 오류를 보여주는 통로를 하나로 모으고, 각 화면이 그 통로를 지나는지 확인한다. 오류 메시지를 화면이 직접 그리면 `next_action` 이 빠져도 드러나지 않는다

2번과 4번이 RG-104 의 핵심이다. "이번에 고친 것"이 아니라 "앞으로 추가될 것"까지 덮는다.

### 기각한 대안

| 대안 | 기각 이유 |
|---|---|
| 경로마다 검증을 손으로 쓴다 | 새 경로가 추가되면 빠진다. RG-104 가 금지하는 방식이다 |
| 코드 리뷰 규칙으로만 둔다 | 002 의 T099·001 의 T156 이 보여주듯 사람 검토는 밀린다. 자동으로 실패해야 한다 |
| 실행 시점에 응답을 검사하는 미들웨어를 넣는다 | 제품에 검증 코드를 남긴다. 운영 경로의 비용이 된다 |

## R6. 동시성·중복 실행과 저장 원자성 (AP-040~AP-042)

### 확인한 사실

- 세션 상태 기계가 이미 형식화돼 있다 — `SessionState`, `Command`, `allowed_commands(state)`, `can(state, command)`, `InvalidTransitionError` (`execution/state_machine.py:35,68,294,299,267`). **AP-020 의 "지금 무엇이 가능한지"는 `allowed_commands()` 로 만들 수 있다** — 새로 만들 것이 없다
- 중복 실행 거절 코드가 이미 있다: `SESSION_ALREADY_ACTIVE`
- **저장 원자성이 갈려 있다**:
  - `storage/registry.py:151-153` 은 임시 파일에 쓰고 바꿔치기한다 — 원자적이다. 주석도 "쓰다 만 파일을 남기지 않는다"
  - `storage/yaml_io.py:73` `dump_model()` 은 곧바로 덮어쓴다 — **원자적이지 않다.** 이것이 Step DSL(테스트 정의)을 쓰는 경로다
  - `secrets/store.py:61`, `storage/repository.py:320` 도 곧바로 덮어쓴다

### 결정

- **원자적 쓰기를 한 곳으로 모은다.** `registry.py` 안에 있는 임시 파일 + 바꿔치기 방식을 `storage` 의 공용 함수로 꺼내고, 위 세 곳이 그것을 지나게 한다. 검증은 쓰기 도중에 실패를 일으켜 (a) 조각난 파일이 남지 않고 (b) 원본이 그대로인지 확인한다
- **중복 실행**은 같은 대상에 동시 요청을 보내 하나만 효과를 내는지 확인한다. 상태 기계가 이미 거절 코드를 갖고 있으므로 새 개념이 필요 없다
- **버튼 연타**(AP-022)는 화면 쪽 문제다. 요청이 실제로 두 번 나가는지, 나간다면 두 번째가 거절되는지를 화면 검증에서 확인한다

### 기각한 대안

| 대안 | 기각 이유 |
|---|---|
| 파일 잠금을 도입한다 | 단독 로컬 도구다. 임시 파일 + 바꿔치기로 충분하고 잠금은 죽은 잠금 문제를 새로 들인다 |
| 요청에 멱등 키를 도입한다 | 상태 기계가 이미 중복을 거절한다. 새 개념을 더할 이유가 없다 |
| 화면에서 버튼을 비활성화하는 것으로 끝낸다 | 화면만 막으면 요청 경계는 여전히 열려 있다. AP-004 가 세 면 모두를 요구한다 |
