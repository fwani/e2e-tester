# 사람이 해야 남는 작업 (2026-09-10 기준)

자동으로 닫을 수 있는 작업은 전부 닫혔다. 아래 14건은 **판정하는 주체가 사람이어야
성립하는 것**이며, 준비물은 모두 만들어져 있고 **판정 칸만 비어 있다.**

12 는 012(프로젝트 이름 변경·삭제)가 등록한 것이다. 자산을 옮기는 조작이라 「옮겨졌다」는
검사가 세지만 **「사용자가 되돌릴 수 있다고 느끼는가」는 세지 못한다.**

11 은 011(작성 화면 수리)이 등록한 것이다. 자리를 옮긴 셋 — 저장·상세·체크 칸 — 은
「옮겼다」를 검사가 세지만 「옮긴 자리가 편한가」는 세지 못한다.

6·7·8·9 는 007(화면 통합)이 등록한 것이다. **007 의 구현은 끝났고 준비물도 다 만들어졌다**
(T090 · 2026-09-08). 8 은 걷기에서 **확인 불가(환경)** 로 남은 항목이다 — 준비물이 없어서가
아니라 이 환경에 자격 증명이 없어서다.

이 문서는 색인이다. 절차는 각 항목이 가리키는 문서가 갖는다.

## 왜 자동화로 대체하지 않았는가

추측이 아니라 이번에 관측된 것이다.

- **005 T121** — 「실패한 Step 건너뛰고 계속」은 계약(`ui-contract.md` §6-5)·백엔드
  (`skip_failed`)·통합 테스트가 **모두 통과하는 상태에서 화면 절반이 없었다.** 자동 검증은
  양쪽 끝을 보고 그 사이의 전선은 보지 않았다.
- **005 N-01** — 새로고침이 화면을 잃었는데 변환 함수 테스트는 초록이었다. 변환은 처음부터
  옳았고 틀린 것은 첫 렌더의 국면이었다.
- **002 T099 · 001 T156** — 구현자가 자기 구현을 판정하면 대조가 아니라 자기 확인이 된다.
  이것은 도구의 한계가 아니라 판정의 성질이다.

「전부 통과했다」만 적힌 기록은 다음 사람이 무엇을 걸었는지 알 수 없게 한다. **관측을
남긴다.**

## 6. 007 T031 — 통합 화면 artboard 의 승인

| | |
|---|---|
| 대상 | [docs/design/Workbench.dc.html](design/Workbench.dc.html) — 통합 작업 화면 초안 (1440×900) |
| 절차 | [design-conformance-007.md §5](../specs/007-unify-test-screens/contracts/design-conformance-007.md) |
| 승인 대상 | **5건** — research.md R8 의 A1~A5 |
| 준비 상태 | **준비 완료.** 초안 · `canvas.json` 항목 · 대체 관계 기록이 모두 있다 |
| 남은 판정 칸 | **5** (A1~A5) |
| 완료 조건 | A1~A5 각각에 승인 또는 대체값. 승인 전 초안은 **대조 기준이 아니다** (FR-254c) |

**007 이 무엇을 했는지** — 구현은 끝났다. Step 목록 구현 4벌 → 1벌, Step 상세 2벌 → 1벌,
옛 화면 8개 → 0개 (`frontend/tests/ImplementationCount.test.ts` 가 센다). 남은 것은 그
결과가 **확정 디자인으로서 옳은가**이고, 그 판정은 사람의 것이다.

007 은 확정 디자인 6종(`Main`·`RunnerPaused`·`Takeover`·`AiRecord`·`RunResult`·
`StepInspector`)을 **하나의 화면의 일곱 상태**로 합친다. 그러면 002 가 세운 1:1 대응
(DC-008)이 성립하지 않으므로 새 artboard 가 필요하고, **확정 디자인을 새로 정하는 것은
사람의 결정**이다 (DC-001).

초안의 값은 기존 6종에서 **기계적으로 추출한 것만** 썼다. 그래서 승인이 바꿀 여지가 아래
다섯 개로 한정된다.

| # | 항목 | 초안의 값 | 초안의 근거 |
|---|---|---|---|
| A1 | 국면 보조 영역의 자리·최소 높이 | 좌측 대상 앱 영역 아래 · 최소 42px · 내용에 따라 늘어난다 | 자리는 `RunnerPaused`·`Takeover` 의 42px 국면 안내 띠. **「늘어난다」는 확정 디자인에 대응이 없다** — 여기가 실제로 갈리는 지점이다 |
| A2 | 「기록됨」 결말 표식 | 2px 실선 `#9A968A` + 텍스트 라벨 | `RunnerPaused.dc.html` 미실행 행 |
| A3 | 결과 국면 좌측(산출물)의 폭 | 남는 폭 전부 | FR-218a — 좌측만 늘어난다 |
| A4 | 국면 띠의 내용 배치 | 국면 표시 → 테스트 이름 → 결말 요약 → 주요 조작 | `RunResult`·`Main` 의 74px 띠 |
| A5 | 「이 결과 이후 정의가 바뀌었습니다」 알림 | 경고 노랑 `#F5D000` / `#FFF9D6` | 002 §3 경고 색 |

**승인이 거절되거나 값이 바뀌면** 대조 기록과 구현을 그 값으로 고친다. 초안을 근거로
"이미 만들었으니 이대로 두자" 고 하지 않는다 — DC-001 위반의 전형이다.

"확정 디자인이 보여주는 상태" 가 하나가 아니다.


## 8. 007 W-6 — AI 실패가 국면을 넘어도 보이는가 (FR-253 · 001 R2 회귀)

| | |
|---|---|
| 절차 | [007 quickstart §2 W-6](../specs/007-unify-test-screens/quickstart.md) |
| 직전 관측 | [ux-walkthrough-007.md](ux/ux-walkthrough-007.md) — **확인 불가 (환경)** |
| 준비 상태 | 준비물은 없다. **자격 증명이 있는 환경**이 필요하다 |
| 완료 조건 | AI 작성을 실패시킨 뒤 세션이 `paused` 로 바뀌어도 사유가 계속 보인다 |

007 걷기에서 이 항목만 걷지 못했다. 이 환경에 언어모델 자격 증명이 없어 AI 작성 국면에
**도달할 수 없다.** 제품은 그 사실을 누르기 전에 말하고(003 AP-003) 「지시문 쓰기」를
비활성으로 두므로, 그 처리 자체는 옳다 — 걷지 못한 것은 그 **뒤**의 성질이다.

**왜 자동 검사로 대체하지 않는가**: `frontend/tests/AiFailureVisible.test.tsx` 가 다섯
세션 상태(`ai_running`·`ai_blocked`·`takeover_recording`·`paused`·`review`)에서 사유가
화면에 있고 `alert` 로 전달되는지 이미 센다. 001 research R2 의 결함은 **국면이 바뀌면
사유가 사라지는 것**이었고 그 조합을 전부 도는 것은 자동 검사가 할 수 있는 일이다.

자동 검사가 못 하는 것은 **실제 실패를 만들었을 때도 같은가**이다. 001 에서 이 결함이
드러난 방식이 정확히 그것이었다 — 서버는 `ai_error` 를 제대로 발행했고 화면은 그것을
상태에 담기까지 했는데, 그리는 컴포넌트가 조건 뒤에 숨어 있었다. 상태를 손으로 넣는
검사는 그 조건을 지나지 않는다.

**걷는 법**: `ANTHROPIC_API_KEY` 를 주거나 `ant auth login` 한 뒤, 도달할 수 없는
지시문(예: 존재하지 않는 화면으로 가라)으로 AI 작성을 걸고 실패시킨다. 실패 뒤 세션이
`paused` 로 바뀌고 나서도 사유가 접힘·탭·겹침 뒤가 아닌 곳에 있는지 본다.


## 9. 007 SC-008 — 걷기의 재확인 (구현자가 아닌 사람)

| | |
|---|---|
| 절차 | [007 quickstart §2](../specs/007-unify-test-screens/quickstart.md) W-1 ~ W-6 |
| 직전 관측 | [ux-walkthrough-007.md](ux/ux-walkthrough-007.md) — 통과 5 · 확인 불가 1 |
| 판정 값 | `해소` · `부분` · `재발` — **`부분` 도 조용히 넘기지 않는다** |
| 완료 조건 | 「지금 무엇을 할 수 있는지 몰랐다」 또는 「화면이 바뀌어 보던 것을 잃었다」로 분류되는 관찰이 **0건** |

007 의 걷기는 **구현자가 걸었다.** 관측은 사실이지만 「몰랐다 / 잃었다 0건」이라는
**판정**은 구현자의 것이고, 이 문서 서문이 그것을 검증으로 세지 않는 이유를 이미 적어
뒀다 (002 T099 · 001 T156 이 같은 이유로 열려 있다).

구현자의 걷기가 쓸모없다는 뜻이 아니다 — 그 걷기가 결함 2건을 찾았고
(끝난 실행이 「실행 중」이라고 말함 · 돌아온 화면이 결말을 말하지 못함), 둘 다 자동
검사가 전부 초록인 상태에서 나왔다. 다만 **자기가 만든 것을 처음 보는 사람의 눈으로 볼
수는 없다.** SC-008 이 재는 것이 정확히 그 눈이다.

**구현자가 관측한 것** (재확인의 비교 기준):

| 걷기 | 관측 |
|---|---|
| W-1 | 세 국면에서 Step 행 칸·껍데기 동일. 결함 2건을 찾아 고치고 다시 걸어 확인 |
| W-2 | 세 국면에서 감춰진 조작 0건. 잠긴 조작 전부가 이유와 해소 방법을 가짐 |
| W-3 | 결과 → 편집에서 지목 유지. 다시 찾는 조작 0회 |
| W-4 | 편집·결과 좌측 영역이 같은 자리(left 0 · width 1140), 내용만 다름 |
| W-5 | 새로 고침 10회 중 10회 국면·지목 복원 |

### 11-1. 상세가 대상 앱을 덮는 정도가 받아들일 만한가 (clarify 결정 1)

사용자가 **겹치기**를 골랐다 — 나란히 밀면 최소 기준 폭에서 미러가 상시로 좁아지므로,
볼 때만 가리는 쪽이 총비용이 작다는 판단이었다.

1440px 기준으로 상세 640px 왼쪽에 대상 앱 **340px** 가 남는다. 확인할 것:

- 녹화·인수 국면에서 상세를 열었을 때 미러의 어느 부분이 가려지는가
- 340px 로 「지금 무엇이 일어나는지」를 알 수 있는가, 아니면 매번 닫아야 하는가
- 닫는 조작(상세 오른쪽 위 ×)이 손에 닿는 곳에 있는가

**「매번 닫게 된다」면 그 결정을 되돌릴 근거다.** 그때는 나란히 배치를 다시 검토한다.

### 11-2. 체크 칸이 결말 아이콘과 눈으로 구별되는가 (UC-011-13)

008 에 「`pending` 의 빈 사각형이 체크박스로 읽혔다」는 기록이 있다. 011 이 **진짜 체크
칸**을 만들었으므로 반대 방향의 혼동이 생길 수 있다 — 통과 아이콘이 체크(✓)다.

Step 20개짜리 목록을 열고, 통과·실패가 섞인 상태에서 확인할 것:

- 칸 0 의 체크와 오른쪽 끝 통과 표식이 한눈에 갈리는가
- 체크하지 않은 행의 빈 상자가 「고를 수 있는 것」으로 읽히는가, 「비어 있는 결말」로
  읽히는가

### 11-3. 확정 디자인 시트 개정 18건의 승인 (`.srow.sel`)

011 이 지목 표시를 `background + border-left-color` 에서 **안쪽 링**(`box-shadow: inset`)
으로 바꿨다. 셋이 한 채널을 다투어 고르면 결말이 사라지던 것을 고친 것이며, `Language.dc.html`

L1 대조는 불일치 0건이지만 **그것은 정본과 시트가 같다는 뜻이지 그 모양이 좋다는 뜻이
아니다.** 확인할 것:

- 2px 안쪽 링이 행 경계선(`--hair`)과 구별되는가
- 통과(초록 왼쪽 테두리) 행을 골랐을 때 둘이 겹쳐 보이지 않는가

## 15. 015 — Tailwind 전환이 겉모습을 바꾸지 않았는가

**2026-09-11 갱신 — 하나가 기계로 넘어가고, 둘이 절반으로 줄었다.**

처음 이 절을 쓸 때의 근거는 「L1 대조는 정본 시트가 확정 디자인과 같음을 보증할 뿐,
**화면이 그 정본을 제대로 쓰는지는 보지 못한다**」였다. 그 구멍을 메우려고 아홉을
사람에게 넘겼다.

**그 전제가 바뀌었다.** L2 대조(`scripts/design_compare_ba.py`)가 전환 전 코드를
`git worktree` 로 꺼내 빌드하고, 같은 백엔드·같은 데이터로 화면 여덟 개를 열어
`getComputedStyle` 56개를 **34,272칸** 맞대 본다. 그것이 실제로 회귀 여럿을 찾아냈다 —
`.navlink` 26곳이 보통 버튼으로 그려지던 것, 국면 이름이 입력칸으로 보이던 것,
작성 방식 카드가 32px 단추가 돼 있던 것.

**줄일 수 있는 것을 줄이지 않으면 목록이 관성으로 남고, 정작 사람만 할 수 있는 넷이
묻힌다.** 그래서 다시 가른다.

| 항목 | 지금 누가 보나 |
|---|---|
| 15-1 국면별 세로 배분 | **사람** — 작업대 국면은 실제 브라우저 세션이 있어야 들어간다 |
| 15-2 Step 목록 | **사람** — 같음 (지목·결말이 겹친 상태는 상호작용이 필요하다) |
| 15-3 토스트 알림 | **사람** — 알림이 뜬 상태를 L2 시나리오가 만들지 못한다 |
| 15-4 Step 상세 겹침 | **사람** — 같음 |
| 15-5 가장 많이 바뀐 두 화면 | ✅ **L2 가 본다** — 프로젝트 설정·가져오기 미리보기가 시나리오에 있다 |

**낡은 절차를 지운다.** 아래의 「전환 전 커밋을 다른 창에 띄워 나란히 놓고 본다」는

## 16. 016 — AI 구간 재녹화가 실제로 쓸 만한가

**2026-09-11 · [016](../specs/016-ai-range-rerecord/)**

자동 검사가 「되는가」를 본다 — 구간이 교체되고, 버리면 되돌아가고, 민감값이 새지
않고, 재실행 경로에서 언어모델이 호출되지 않는다 (백엔드 53건 · 프론트 41건).

**「쓸 만한가」는 자동으로 잴 수 없다.** 남는 넷은 전부 *사람이 판단해야 하는 것*이다.

### 16-1. SC-002 — 조작 횟수가 지금의 절반 이하인가

같은 작업을 두 방법으로 하고 **세어 본다.**

| | 방법 | 조작 |
|---|---|---|
| A (지금) | 「Step n 앞에서 브라우저 열기」 → 직접 조작으로 녹화 → 「이 뒤 전부 지우기」 | ? |
| B (016) | 구간 체크 → 「AI 로 다시 만들기」 → 지시 → 확정 → 저장 | 5 (설계값) |

- 대상: Step 12개 이상인 테스트의 **가운데 5개 구간**
- **시간도 함께 적는다.** B 는 도착점 만들기에 앞 구간 실행 시간을 치른다 (plan
  「알려진 위험」). 조작이 절반이어도 시간이 두 배면 사용자는 A 를 쓴다.
- 시나리오 5건 이상

### 16-2. SC-003 — 지시 10건 중 7건이 사람 개입 없이 Step 을 만드는가

- **기본 드라이버로만 잰다.** `ITB_AI_DRIVER=claude-code` 결과는 근거로 쓰지 않는다 —
  Messages API 전용 파라미터가 전달되지 않고 모델도 다르다 (`claude_code_driver` 머리말)
- 「개입 없이」 = 막힘(`ai_blocked`)을 한 번도 거치지 않고 Step 이 만들어진 경우
- 지시 10건은 **서로 다른 화면**을 대상으로 한다. 같은 로그인 흐름 10번은 1건과 같다

### 16-3. 버리기가 실제로 시행착오 루프를 싸게 만드는가

자동 검사는 「목록이 시작 전과 같다」를 20회 확인한다 (SC-004). 그것이 참이어도
**루프가 성립하는지는 다른 문제**다.

- 버린 뒤 곧바로 다른 지시를 보내는 것이 자연스러운가
- 되맞춤 실행을 기다리는 동안 무엇이 일어나는지 알 수 있는가
- 세 번쯤 버리고 다시 하면 지치는가

### 16-4. 「AI 로 다시 만들기」가 브라우저를 연다는 것을 미리 아는가

R6 의 결정(채팅은 세션 안에서만 산다) 때문에, 요약 하나를 물으려 해도 브라우저가
뜬다. 라벨이 그 사실을 말한다(`AI 로 다시 만들기 (브라우저 열림)`).

- 그 표시로 충분한가, 아니면 누르고 나서 놀라는가
- 편집 화면의 잠긴 대화 자리가 「여기서 시작하라」로 읽히는가

### 이 절이 닫히는 조건

넷 다 관측을 남기고, 16-1·16-2 는 **수치**를 적는다. 기대와 다르면 그 번호를 들어
`specs/016-ai-range-rerecord/tasks.md` 에 남은 작업으로 등록한다.
