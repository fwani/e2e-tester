# Data Model: 부정 검증과 상태 검증

**Feature**: 021 | **Spec**: [spec.md](./spec.md) | **Research**: [research.md](./research.md)

**새 엔티티가 없다.** 기존 「검증 조건」의 두 열거형에 값을 더하고, 형태 규칙을 그에 맞게
넓힌다. 이 문서의 §2 표가 **형태 규칙의 유일한 출처**이고 도메인·API·작성 도구·화면이
모두 그것을 따른다 (헌법 원칙 I).

---

## 1. 늘어나는 값

### 1.1 검증 종류 (`AssertionKind`)

| 값 | 뜻 | 상태 |
|---|---|---|
| `visible` | 요소가 화면에 보인다 | 기존 |
| `hidden` | 요소가 없거나 보이지 않는다 | 기존 |
| `text` | 텍스트를 비교한다 | 기존 |
| `url` | 현재 주소를 비교한다 | 기존 |
| **`enabled`** | **요소를 조작할 수 있다** | **추가** |
| **`disabled`** | **요소를 조작할 수 없다** | **추가** |

`enabled`/`disabled` 는 `visible`/`hidden` 과 나란한 쌍이다. 존재가 아니라 **성질**을 본다.

> **`hidden` 과 무엇이 다른가**: `hidden` 은 대상이 없어도 통과한다. `disabled` 는 대상이
> 없으면 **실패한다.** 「없다」와 「있는데 잠겼다」는 다른 사실이고, 둘을 한 검증이 함께
> 통과시키면 결과를 보고 어느 쪽이었는지 알 수 없다 (FR-012).

### 1.2 비교 방식 (`MatchMode`)

| 값 | 뜻 | 상태 |
|---|---|---|
| `equals` | 같다 | 기존 |
| `contains` | 포함한다 | 기존 |
| **`not_equals`** | **같지 않다** | **추가** |
| **`not_contains`** | **포함하지 않는다** | **추가** |

부정을 종류가 아니라 비교 방식에 넣은 근거는 [research.md R1](./research.md) 에 있다.

## 2. 형태 규칙 — **이 표가 권위다**

| 종류 | `target` | `value` | 허용하는 `match` |
|---|---|---|---|
| `visible` | **필수** | 열려 있음 *(호환)* | `equals` · `contains` |
| `hidden` | **필수** | 열려 있음 *(호환)* | `equals` · `contains` |
| `enabled` | **필수** | **금지** | `equals` · `contains` *(의미 없음, 기본값 통과용)* |
| `disabled` | **필수** | **금지** | `equals` · `contains` *(같음)* |
| `text` | 선택 *(비우면 화면 전체)* | **필수** | 넷 모두 |
| `url` | **금지** | **필수** | 넷 모두 |

### 규칙 셋의 근거

**(a) 부정 비교는 값을 비교하는 종류에만.** `text`·`url` 이 아닌 종류에 `not_*` 를 주면
거절한다. 사용자가 「요소가 보이지 않음」을 그렇게 표현하려 한 오해이고, 조용히 무시하면
그 오해가 정의 파일에 남는다 (FR-002).

**(b) 기존 두 값은 어디서도 거절하지 않는다.** `visible` + `contains` 처럼 의미 없는
조합이 이미 저장된 정의에 있을 수 있다. 지금 무시되고 있고, 앞으로도 무시한다. **새로
추가되는 `not_*` 만 형태 검사 대상**이다 — 그래야 하위 호환이 성립한다 (FR-030).

**(c) 새 종류의 `value` 는 처음부터 닫는다.** `visible`/`hidden` 이 `value` 를 열어 둔 것은
표시 이름 생성이 실제로 그것을 읽기 때문이다. 새 종류에는 그런 사용처가 없고, **나중에
닫는 것은 불가능**하다.

**(d) 빈 값의 부정 비교는 만들 수 없다.** 「빈 문자열을 포함하지 않는다」는 어떤 화면에서도
거짓이다. 통과할 수 없는 검증을 만들게 두면 사용자는 제품이 고장 났다고 읽는다 (FR-007).

## 3. 실행 의미론

### 3.1 대기 — 모든 값 비교와 상태 검증이 같은 규칙

```
제한 시간이 남아 있는 동안:
    현재 값을 다시 읽는다
    조건이 참이면 → 통과 (즉시 끝난다)
    아니면 50ms 쉰다
제한 시간을 넘기면 → 마지막 관찰값으로 실패 설명을 만든다
```

| 검증 | 대기 주체 | 비고 |
|---|---|---|
| `text` · `url` | 공통 도우미 | **`text` 는 지금 기다리지 않는다. 이번에 바뀐다** |
| `enabled` · `disabled` | 공통 도우미 | 새로 생김 |
| `visible` · `hidden` | Playwright 의 상태 대기 | 이미 같은 의미론. 바꾸지 않는다 |

### 3.2 판정표

| 종류 | 통과 조건 | 대상을 못 찾으면 |
|---|---|---|
| `visible` | 대상이 보인다 | 실패 |
| `hidden` | 대상이 없거나 보이지 않는다 | **통과** |
| `enabled` | 대상을 조작할 수 있다 | **실패** |
| `disabled` | 대상을 조작할 수 없다 | **실패** |
| `text` (대상 있음) | 대상의 텍스트가 조건을 만족한다 | **실패** *(긍정·부정 모두)* |
| `text` (대상 없음) | 화면 전체 텍스트가 조건을 만족한다 | 해당 없음 |
| `url` | 현재 주소가 조건을 만족한다 | 해당 없음 |

**대상을 찾지 못한 부정 텍스트 검증을 통과시키지 않는 이유**: 통과시키면 「요소가 사라져서
통과」와 「텍스트가 달라서 통과」를 결과에서 구별할 수 없다. 요소가 없을 수도 있는 상황은
`hidden` 이 담당한다 (FR-006).

### 3.3 실패 설명

기대와 실제를 **모두** 담는다. 020 이 이 문자열을 `mismatch.observed` 에 그대로 싣기
때문에, 문체가 갈리면 화면 문구와 기록이 어긋난다.

| 상황 | 문구의 골자 |
|---|---|
| `text` + `not_contains` 실패 | 「화면 텍스트가 `X` 를 포함하지 않아야 하는데 포함했습니다. 실제: `…`」 |
| `url` + `not_equals` 실패 | 「현재 주소가 `X` 와 달라야 하는데 같았습니다.」 |
| `disabled` 실패 | 「대상을 조작할 수 없어야 하는데 조작할 수 있었습니다.」 |
| `enabled` 실패 | 「대상을 조작할 수 있어야 하는데 조작할 수 없었습니다.」 |

## 4. 020 과의 관계 — **바꿀 것이 없다**

| 020 의 장치 | 새 종류에서 |
|---|---|
| 작성 시점 어긋남 기록 (`AuthoringMismatch`) | 그대로 적용된다. 검증이 작성 시점에 통과하지 않으면 Step 은 남고 어긋남이 적힌다 (FR-024) |
| 실행 결과 분류 (`AssertionClass`) | **구조상 그대로 동작한다** — 분류 함수는 Step 종류와 어긋남 유무만 보고 검증의 `kind` 를 보지 않는다 (FR-025) |
| 검증 실패가 실행을 멈추지 않음 | 그대로. 새 종류도 검증 Step 이다 |

동작한다는 것을 **테스트로 못 박는다.** 구조상 그렇다는 것과 앞으로도 그렇다는 것은 다르다.

## 5. 작성 시점 경고 — 조작 가능 여부를 가질 수 없는 대상

상태 검증의 대상이 **조작 가능 여부를 가질 수 있는 요소가 아니면** 경고를 함께 돌려준다.

- **Step 은 만들어진다.** 막으면 `contenteditable` 이나 ARIA 로 잠금을 표현하는 위젯 등
  정당한 사용까지 막힌다.
- **실행 판정은 바뀌지 않는다.** 원칙 II 의 결정성은 「같은 화면이면 같은 결과」이고, 태그를
  보고 판정을 뒤집으면 예외가 생긴다.
- 판정 근거는 이미 수집되는 후보 묶음의 태그 정보다. 새 수집을 추가하지 않는다.

경고가 필요한 이유는 방향이 비대칭이기 때문이다 — 「조작할 수 없다」가 항상 실패하는 것은
사람이 알아차리지만, **「조작할 수 있다」가 항상 통과하는 것은 아무도 알아차리지 못한다**
(FR-014).

## 6. 저장 형식의 버전

**올리지 않는다** (`dsl_version` 그대로). 근거는 [research.md R4](./research.md) —
값 추가는 기존 파일을 깨지 않는 반면, 버전을 올리면 공유 묶음 읽기가 **이미 배포된 묶음을
전부 거부**한다. 020 이 새 필드를 더하면서도 올리지 않은 것과 같은 판단이다.
