Phase 0. 명세가 열어 둔 자리와 설계가 갈릴 수 있는 자리를 하나씩 닫는다.

---

## R1. 자리를 **어디서** 재는가

### 문제

명세 FR-002 는 「조작하기 직전에 측정한 값」을 요구한다. 그런데 「그 요소」가 무엇인지가
경로마다 다를 수 있다.

AI 작성에서 요소 하나를 조작하는 동안 요소는 **세 번** 찾아진다.

| 시점 | 무엇으로 찾는가 | 어디서 |
|---|---|---|
| 1. 화면 살펴보기 | 주입 스크립트가 훑는다 | `__itbObserve` |
| 2. 후보 수집 | 살펴보기가 준 **CSS 경로** | `collect_by_selector` |
| 3. **실제 조작** | 후보 묶음의 **우선순위 전략** | `locator_runtime.resolve` |

3 이 쓰는 전략은 `testId → role+name → label → text → stable attr → CSS` 순이다 (헌법
원칙 IV). **CSS 는 마지막 수단**이므로, 2 에서 잰 자리와 3 이 실제로 만진 요소가 다를 수
있다. 후보 검증(`collect_and_verify`)이 같은 요소인지 판정하지만, 판정이 참이어도 그것은
「같은 요소일 것」이지 「같은 요소였다」가 아니다.

### 결정

**자리는 3 에서, 실제로 채택된 요소에서 잰다.** `StepExecutor` 가 요소를 확정한 직후
그 요소의 경계 상자를 읽어 `StepExecution` 에 실어 돌려준다.

### 근거

- **추측이 없다.** 조작된 요소와 표시된 자리가 정의상 같다. 이 기능의 값 전부가
  「저기가 맞다」는 믿음에서 나온다 (명세 US3).
- **원칙 IV 를 거스르지 않는다.** CSS 로 다시 재는 설계는 우선순위 전략을 우회하는 두
  번째 요소 탐색 경로를 만드는 셈이고, 헌법이 「한 곳에 있어야 한다」고 정한 그 로직이
  둘로 갈린다.
- **경계 상자는 주 프레임 뷰포트 기준으로 나온다.** iframe 안의 요소여도 그렇다 —
  프레임 해석(`frame_resolver`)을 거친 뒤에도 좌표계가 하나로 유지된다.

### 기각한 대안

| 대안 | 기각 이유 |
|---|---|
| 살펴보기 결과에 자리를 실어 둔다 | FR-002 위반. 살펴봄과 조작 사이의 스크롤·다시 그리기를 못 따라간다 |
| `_act_on_element` 가 CSS 로 잰다 | 위 표의 2 에서 재는 것이며, 조작된 요소와 다를 수 있다 |
| 조작 직전에 스크립트를 다시 주입해 잰다 | 요소 탐색 경로가 하나 더 생긴다. 대상 화면에서 도는 코드가 늘어난다 |

## R2. 상태를 **몇 가지**로 두는가 — 「수행 중」을 두지 않는다

### 문제

명세 Key Entities 는 상태를 「수행 중·성공·실패」로 예시했다. 그런데 R1 의 결정에 따르면
자리는 **요소가 확정된 뒤에야** 알 수 있고, 그 시점은 이미 조작이 시작된 뒤다.

「수행 중」을 표시하려면 요소가 확정되기 **전에** 자리를 알아야 하고, 그러려면 R1 이
기각한 추측된 자리를 써야 한다.

### 결정

**상태는 둘이다 — 성공·실패.** 「수행 중」을 두지 않는다.

명세의 Key Entities 한 줄을 이 결정에 맞춰 좁힌다. 요구(FR-008)는 「성공했는지
실패했는지가 실려야 한다」이고, 그것만 요구한다.

### 근거

- 「수행 중」을 정확하게 표시할 방법이 없다. 부정확한 표시는 이 기능의 값을 깎는다.
- **공백은 이미 메워져 있다.** 진행 문구가 조작 **전에** 「~ 수행 중」을 보낸다
  (`_announce` 가 그 이유로 하기 전에 알리도록 고쳐진 자리다). 두 표시가 각자 자기 일을
  한다 — 문구는 기다림을 말하고, 테두리는 결과의 자리를 말한다.
- 요소를 기다리는 동안 테두리가 없는 것은 결함이 아니다. **그때는 자리가 존재하지
  않는다** — 요소가 아직 화면에 없다.

### 남는 사실

요소를 찾지 못해 실패하면 자리가 없다. 그때는 알리지 않는다 (FR-010). 「어디서
막혔는지」를 US2 가 요구하지만, 요소 자체가 없는 실패에서 자리를 말하는 것은 거짓말이다.
그 경우 사용자가 받는 것은 지금과 같은 진행 문구와 막힘 안내다.

| 실패의 종류 | 자리가 있는가 | 표시 |
|---|---|---|
| 요소를 찾지 못했다 | 없다 | 표시하지 않는다 |
| 찾았으나 동작이 실패했다 (가려짐·비활성·시간 초과) | **있다** | **실패로 표시한다** |
| 가리키는 자리가 하나가 아니다 | 없다 (제품도 모른다) | 표시하지 않는다 |

US2 가 실제로 겨냥하는 것은 가운데 줄이다 — 요소는 거기 있는데 조작이 안 되는 경우.

## R3. 좌표계와 정변환

### 이미 있는 것

미러 프레임은 좌표 변환의 근거를 매 장 싣는다: 대상 화면 크기(`width`·`height`), 페이지
배율(`pageScale`), 상단 오프셋(`offsetTop`).

화면에는 **역변환**이 있다 (`toTargetPoint`) — 사용자가 미러를 클릭한 표시 좌표를 대상
화면 좌표로 되돌린다.

```
dx = clientX - box.left
scaleX = (naturalWidth / clientWidth) × (frame.width / naturalWidth)
x_target = round(dx × scaleX / pageScale)
y_target = round(dy × scaleY / pageScale + offsetTop)
```

### 결정

**정변환을 같은 파일에 대칭으로 둔다.** 같은 상수·같은 방어를 쓴다.

```
x_display = x_target × pageScale / scaleX
y_display = (y_target − offsetTop) × pageScale / scaleY
```

너비·높이는 오프셋이 붙지 않으므로 배율만 적용한다.

```
w_display = w_target × pageScale / scaleX
h_display = h_target × pageScale / scaleY
```

### 왜 같은 파일인가

두 식이 **서로의 역**이어야 한다. 떨어져 있으면 한쪽만 고쳐지는 날이 오고, 그러면
사용자가 클릭한 자리와 제품이 그린 자리가 어긋난다 — 그 어긋남은 밀집 UI 에서만 드러난다
(역변환 머리말이 같은 이유로 상수 1280×800 을 금지한 것과 같은 판단).

### 검증 가능성

`DisplayBox` 를 인자로 받는 순수 함수 형태를 유지한다. 실제 이미지 요소를 요구하면 빠른
계층에서 검증할 수 없다 (jsdom 은 이미지를 해독하지 않아 자연 크기가 0 이다) — 역변환이
이미 그 이유로 이 형태를 택했다.

### 라운드트립 성질

`toDisplayRect(toTargetPoint(p)) ≈ p` 가 배율이 비정수인 경우에도 1~2픽셀 안에서
성립해야 한다. 이것을 단위 검증으로 고정한다.

## R4. 알림 통로

### 결정

**새 세션 이벤트 하나** — `ai_focus`. 진행 문구(`ai_progress`)와 나란한 별개 이벤트다.

도구 쪽 통로도 대칭으로 둔다. `ProgressSink` 옆에 `FocusSink` 를 두고, 세션 배선이
`work.session.emit("ai_focus", ...)` 로 잇는다.

### 왜 `ai_progress` 에 필드를 얹지 않는가

명세 FR-005 의 근거 그대로다. 둘은 성질이 다르다.

| | `ai_progress` | `ai_focus` |
|---|---|---|
| 무엇인가 | 쌓이는 **이력** | 지금 하나뿐인 **상태** |
| 화면이 하는 일 | 턴 단위로 모아 보여 준다 | 마지막 하나만 그린다 |
| 자리가 없을 때 | 그래도 보낸다 | **보내지 않는다** |

한 이벤트로 묶으면 화면이 매 건마다 「이번 것에는 자리가 있는가, 없으면 지난 것을
지울 것인가」를 판단하게 된다. 그 판단은 두 성질을 한 통로에 욱여넣었기 때문에 생긴다.

### 왜 도구 쪽 통로를 나누는가

`_announce` 는 자리를 모르는 자리에서도 불린다 (살펴보기·편집·막힘 신고). 한 통로로
묶으면 자리 없는 호출마다 `None` 을 넘기게 되고, 「자리를 모른다」와 「자리가 없다」가
구별되지 않는다.

## R5. 재생 경로에서 나가지 않는다는 **구조적** 보장

### 문제

헌법 원칙 II 와 명세 FR-007·SC-006. 이 알림이 재생 세션에서 관측되면 위반이다.

위험한 자리가 있다. R1 이 **`StepExecutor` 를 건드린다** — 그런데 그 실행기는 재생
경로(`Runner`)도 쓴다.

### 결정

**실행기는 값을 돌려줄 뿐, 아무것도 발행하지 않는다.**

```
StepExecutor.execute(step) → StepExecution        (자리를 담아 돌려준다)
                                  │
        ┌─────────────────────────┴─────────────────────────┐
   AI 작성 (`_execute`)                            재생 (`Runner`)
   자리를 꺼내 ai_focus 로 발행                     자리를 쓰지 않는다
```

발행은 `BrowserToolbox._execute` 안에서만 일어난다. 그 모듈은 **AI 작성 전용**이고
재생 경로에서 도달할 수 없다.

### 왜 실행기에 콜백을 달지 않는가

`on_element_resolved` 같은 통로를 실행기에 달면, 재생 배선에서 그것을 잇는 순간 위반이
된다. 그리고 그 배선은 **한 줄**이므로 실수로 생길 수 있다. 값을 돌려주는 설계에서는
재생 쪽이 이벤트를 내려면 코드를 새로 써야 한다 — 실수로는 생기지 않는다.

이것이 `_execute` 가 진행 알림을 소유하고 실행기가 소유하지 않는 기존 구조와 같은
판단이다.

### 고정

재생 세션 전 구간에서 `ai_focus` 가 0 건임을 검증으로 고정한다. 기존 원칙 II 검증
(`backend/tests/test_principle_ii_timeline.py`)이 같은 일을 하는 자리이므로 거기에 붙인다.

## R6. 표시의 수명

### 결정

- **다음 자리가 오면 즉시 바뀐다** (FR-014).
- 다음이 오지 않으면 **마지막 표시로부터 2.5초 뒤 사라진다.**
- 수명은 **화면이 센다.** 서버가 「지워라」를 보내지 않는다.

### 2.5초인 근거

| 값 | 무엇이 문제인가 |
|---|---|
| ~1초 | AI 의 동작 간격(도구 호출 왕복)보다 짧아 대부분의 시간 동안 아무것도 안 보인다 |
| **2.5초** | 연속 동작 사이에는 거의 끊기지 않고, 멈췄을 때는 2~3초 안에 정리된다 |
| 5초~ | 막힘 화면이 뜬 뒤에도 테두리가 남아 「아직 하는 중」으로 읽힌다 |

정확한 최적값을 아는 상태가 아니다. 상수 하나로 두고 이름을 붙여, 실측 후 바꿀 때 한
곳만 고치게 한다.

### 왜 서버가 지우지 않는가

「지워라」 이벤트를 두면 그 이벤트가 유실될 때 테두리가 영구히 남는다. 프레임 유실이
실행에 영향을 주지 않아야 한다는 미러의 기존 성질과 같은 이유로, 표시는 **스스로
꺼지는** 쪽이어야 한다.

### 왜 프레임 번호로 맞추지 않는가

조작 시점과 그 결과가 그림에 나타나는 시점은 원래 같지 않다. 요소를 기다린 시간이
그 사이에 있고, 그 시간은 예측할 수 없다. 번호를 맞춰도 어긋남은 남고 구조만 무거워진다.
`frameSeq` 는 알림에 싣지 않는다.

## R7. 화면이 그리는 방법

### 배치

`<img>` 는 `max-w-full max-h-full` 로 그려지고 부모가 가운데 정렬한다 — **표시 크기가
콘텐츠에 따라 달라진다.** 그래서 오버레이를 부모 기준으로 놓으면 이미지가 가운데로
밀린 만큼 어긋난다.

**결정**: `<img>` 를 크기가 이미지에 딱 맞는 `relative` 래퍼로 감싸고, 오버레이를 그
래퍼 안에 절대 배치한다. 그러면 오버레이 좌표는 이미지 표시 영역 기준이 되고, 정변환
결과를 그대로 쓸 수 있다.

래퍼가 하나 생기는 것이 조작 전달 경로를 바꾸지 않는지가 관건이다 — 포인터 처리기는
`<img>` 에 붙어 있고 래퍼는 포인터를 받지 않으므로 바뀌지 않는다.

### 포인터

오버레이는 `pointer-events: none` (FR-020). 조작 국면에서 테두리 위를 클릭하면 그 클릭이
`<img>` 로 내려가야 한다.

### 크기 변화

창 크기가 바뀌면 이미지 표시 크기가 바뀌고 테두리가 어긋난다. **다음 프레임이 오면
맞춰진다** — 프레임은 초당 여러 장 오고, 수명은 2.5초다. 크기 변화를 따로 감시하지
않는다. 강등(초당 1장) 상태에서 창을 끄는 동안 최대 1초간 어긋날 수 있으나, 그 상태는
이미 화면이 「지금 표시가 정확하지 않을 수 있다」고 말하고 있다.

### 색

정본 토큰을 쓴다 (FR-022). 성공은 `run` 계열(「지금 살아 움직이는 것」), 실패는 `fail`
계열. 둘 다 이미 시각 언어에 있는 뜻이며 새로 만들 것이 없다.

### 컴포넌트가 국면을 보지 않는다

미러 컴포넌트는 조작 가능 여부를 스스로 판정하지 않고 결과만 받는다 (010 FR-316). 새
표시도 같다 — **무엇을 그릴지 계산된 결과**를 props 로 받는다. 어느 탭을 보고 있는지,
프레임이 있는지, 수명이 지났는지의 판정을 컴포넌트 안에 넣지 않는다.

## R8. 그리지 않는 조건

명세 FR-016~FR-019 를 판정 표로 못 박는다. **화면 쪽에서 판정한다** — 서버는 사실만
보내고, 「지금 그릴 수 있는가」는 화면이 가진 정보(무슨 탭을 보고 있는지, 프레임이
있는지)로만 정해진다.

| 조건 | 그리는가 | 근거 |
|---|---|---|
| 프레임을 한 장도 못 받았다 | ✕ | FR-016 |
| 미러가 중단됐다 (`stoppedReason`) | ✕ | FR-016 |
| 좌표 근거(`geometry`)가 없다 | ✕ | FR-017 |
| 알림의 탭 ≠ 보고 있는 탭 | ✕ | FR-018 |
| 자리의 너비 또는 높이가 0 이하 | ✕ | 명세 Edge Cases |
| 표시 영역과 겹치는 부분이 없다 | ✕ | FR-019 — 밀어 넣지 않는다 |
| 표시 영역을 **일부** 벗어난다 | ● (잘라서 그린다) | 보이는 부분은 사실이다 |
| 초당 1장으로 강등됐다 | ● | 좌표는 옳다. 강등 사실은 이미 화면이 말한다 |
| 수명이 지났다 | ✕ | FR-015 |

## R9. 하위 호환

| 어느 쪽이 낡았나 | 무슨 일이 일어나는가 |
|---|---|
| 화면이 낡았다 (`ai_focus` 를 모른다) | 알 수 없는 이벤트를 무시한다. 작성은 그대로 동작한다 (FR-026) |
| 서버가 낡았다 (`ai_focus` 를 안 보낸다) | 테두리가 그려지지 않는다. 그 밖에는 지금과 같다 |
| 실행기가 자리를 못 잰다 | `StepExecution` 의 자리가 비고, 발행하지 않는다 (FR-010) |

자리 측정이 예외를 던져도 **조작은 계속된다** (FR-006). 표시는 곁가지이고, 그것 때문에
테스트 작성이 끊기면 안 된다 — `_announce` 가 이미 같은 규칙으로 되어 있다.

## R10. 보안 — 알림에 무엇이 실리는가

### 실리는 것

- **자리** — 숫자 넷. 화면 내용이 아니다.
- **탭 번호** — 숫자 하나.
- **이름표** — Step 의 이름표와 **같은 값**이다.

### 이름표에 값이 실리지 않는다

이름표는 `{요소 이름} {동작}` 형태로 만들어진다 (`_label`). 입력 Step 도 「{칸 이름}
입력」이며 **넣은 값이 들어가지 않는다.** 비밀번호 칸의 값은 그 이전 단계에서 이미
변수 참조로 바뀐다.

### 지금보다 위험이 늘지 않는다

이름표는 이미 진행 문구로 나가고 있는 값과 같다. 이 기능이 새로 내보내는 것은 **좌표
숫자**뿐이며, 그것은 화면 내용을 담지 않는다.

### 자리는 저장되지 않는다

흘러가는 알림이며 디스크에 남지 않는다. 어긋남 기록이 스크러버를 거치는 이유(「흘러가지
않으므로 한 번 거른다」)가 여기에는 해당하지 않는다.

## R11. 검증을 어디에 두는가

| 무엇을 | 어디서 | 왜 그 계층인가 |
|---|---|---|
| 정변환식·라운드트립 | 화면 단위 검증 | 브라우저 없이 돌아야 한다 (R3) |
| 그리지 않는 조건 표 (R8) | 화면 단위 검증 | 판정이 화면에 있다 |
| 자리가 실려 돌아오는가 | 백엔드 단위 검증 | 실행기의 반환값 계약 |
| 발행이 AI 작성에서만 | 백엔드 계약 검증 | 통로의 성질 |
| 재생에서 0 건 | 기존 원칙 II 검증 | 이미 그 일을 하는 자리가 있다 |
| 실제로 맞는 자리인가 | 종단 검증 | 실제 브라우저 없이는 확인할 수 없다 |
| 대상 화면이 안 바뀌었나 | 종단 검증 | 조작 전후 요소 수 비교 (SC-008) |

종단 검증 하나가 반드시 필요하다. 좌표가 맞는지는 실제 브라우저·실제 프레임 없이는
확인되지 않으며, 이 기능에서 틀리면 가장 아픈 것이 바로 그 지점이다.
