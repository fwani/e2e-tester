## SC-007 판정 — **미달이며, 기준이 잘못 세워졌다** (T064·T071)

2026-09-11 측정: **34.79 kB** (기준선 15.04 kB).

### 무엇이 늘었나 (T071 (1) — 산출물에서 지목한다)

| 레이어 | 크기 | 정체 |
|---|---|---|
| `@layer base` | **14.38 kB** (41%) | 정본 `tokens.css` 전체. 규칙 166개 |
| `@layer utilities` | **17.06 kB** (49%) | Tailwind 가 만든 유틸리티 410개 |
| `@layer theme` · properties | 1.31 kB | 테마 변수 · 레이어 폴리필 |

**정본은 줄지 않았고 유틸리티가 더해졌다.** 기준선 15.04 kB 는 `tokens.css` 만 있던
상태이고, 그 14.38 kB 가 지금도 그대로 있다.

### 왜 기준이 잘못됐나 (T071 (3))

SC-007 은 「전환이 끝나면 의미 클래스가 사라져 순감한다」는 전제 위에 있었다.
**그 전제가 틀렸다.**

`tokens.css` 의 정본 구획(1~203줄)은 `scripts/extract_canon.py` 가 확정 디자인에서
추출한 것이고, **지울 수 없고 지우는 것이 옳지도 않다** — 확정 디자인의 기록이자 L1
대조의 기준이다 ([contracts/class-migration.md](contracts/class-migration.md) 「완료」의
정의에서 이미 정정했다). 화면이 그 클래스를 쓰지 않게 되어도 파일에는 남는다.

즉 **전환이 완벽히 끝나도 base 는 정본 구획만큼 남고, 그 위에 유틸리티가 얹힌다.**
「늘지 않는다」는 구조적으로 달성할 수 없는 목표였다.

### 남은 길 (다음 작업으로 등록)

정본 구획을 **번들에서 빼면** 줄일 수 있다. `tokens.css` 의 `:root` 변수만 앱이
불러오고, 클래스 규칙은 L1 대조 스크립트만 읽게 하는 것이다. 전환이 끝나 화면이
정본 클래스를 하나도 쓰지 않게 된 뒤에야 안전하며, 그 시점에 base 는 변수 선언만
남아 1 kB 아래로 내려간다.

**지금 판정: 미달.** 통과로 보고하지 않는다. 기준을 고치는 것은 위 구조 변경을 하고
난 뒤에 판단할 일이며, 그 전에 기준선을 올려 적는 것은 미달을 감추는 것이다.

### 그래도 미달이다 — 남은 것의 정체

기준선 15.04 kB (gzip 3.43 kB) 대비 **+9.29 kB (+62%)** 다. 산출물에서 지목한다.

| 구획 | 크기 | 정체 |
|---|---|---|
| `@layer base` | 2.22 kB | 정본의 `:root` 변수와 요소 규칙. **기준선에도 그대로 있던 것** |
| `@layer utilities` | 18.64 kB | 유틸리티 416개. 그중 **임의값(`x-[…]`) 199개가 9.38 kB** |
| `@layer theme`·properties | 1.31 kB | 테마 변수 · `@property` 폴리필 |

기준선 15.04 kB 의 내역은 「정본 클래스 규칙 12.82 kB + 위 base 2.22 kB」였다.
즉 **12.82 kB 의 클래스 규칙이 18.64 kB 의 유틸리티로 바뀌었다.**

늘어난 이유는 둘이고 **둘 다 이 기능이 하기로 한 일의 직접적 결과**다.

1. **인라인 455곳이 JS 에서 CSS 로 옮겨 왔다** (FR-019). 그 값들은 전환 전에 CSS
   산출물에 **없었다** — `style={{…}}` 로 JS 번들에 있었다. 임의값 유틸리티 199개
   9.38 kB 가 대체로 그것이다. CSS 만 비교하면 이 **이동**이 증가로 보인다.
2. 원자 CSS 는 선언마다 선택자를 하나씩 갖는다. 규칙 416개 × 선택자 몫 ≈ 8 kB 가
   구조적 비용이며, 공유되지 않는 일회성 값이 많을수록 커진다.

### 이동인지 증가인지 — 전체 전송량으로 확인했다

CSS 만 보면 이동과 증가를 가릴 수 없으므로 **전환 전 코드를 `git worktree` 로 꺼내
같은 설정으로 빌드해** 전체를 쟀다 (research R5).

| | 전환 전 | 전환 후 | 차이 |
|---|---|---|---|
| CSS | 15.04 kB | 24.34 kB | +9.30 |
| JS | 446.60 kB | 465.67 kB | +19.07 |
| **합계** | **461.64 kB** | **490.01 kB** | **+28.37 (+6.1%)** |
| **합계 (gzip)** | **135.46 kB** | **140.63 kB** | **+5.17 (+3.8%)** |

**JS 도 함께 늘었다.** 순수한 이동이 아니다 — 긴 유틸리티 문자열이 `style` 객체보다
크고, 부품 7개가 새로 들어왔다. 사용자가 실제로 내려받는 양은 gzip 기준 **+3.8%** 다.

### 판정과 권고 (T071 (2)·(3))

**판정: 미달.** 구조 변경을 다 하고도 기준을 넘는다. 통과로 보고하지 않는다.

**권고: 기준을 고쳐야 한다.** 코드 쪽에 더 줄일 것이 남아서가 아니라, **재는 단위가
틀렸기 때문**이다.

- SC-007 은 「배포 산출물의 **스타일 크기**」를 재는데, 이 기능은 FR-019 로 **스타일의
  거처를 JS 에서 CSS 로 옮기기로 결정했다.** CSS 만 재면 그 이동이 그대로 증가로
  잡힌다 — 즉 이 기준은 **설계상 통과할 수 없게 세워져 있었다.**
- 사용자가 치르는 비용을 재는 단위는 **전송되는 전체 바이트(gzip)** 이고, 그 값은
  +3.8% 다. 작지만 0 은 아니다 — 원자 CSS 로 옮기면서 치른 값이며 숨기지 않는다.

고칠 방향은 「전체 전송량(gzip) 이 전환 전 대비 5% 를 넘지 않는다」처럼 **단위와 여유를
함께 명시**하는 것이다. 다만 **성공 기준을 고치는 것은 명세 변경이므로 여기서 하지
않는다.** 사용자의 판단이 필요한 항목으로 남긴다.

더 줄일 여지는 임의값 유틸리티 199개(9.38 kB)를 토큰 이름으로 모으는 것뿐인데, 새 값을
만드는 것이 아니라 이름을 주는 일이라 FR-003 과 어긋나지는 않는다. 다만 1~2 kB 수준이고
화면 전체를 다시 건드려야 해서 이 기능의 범위를 넘는다.

### SC-010 — 같은 종류의 부품이 화면마다 다른 모습을 갖지 않는가

**판정 방법**: 부품의 모양을 이루는 표식(`rounded-chip`·`h-control-sm inline-flex`·
`h-[19px] px-[6px]`·`h-control flex items-center gap`)이 `ui/` 밖에 나타나는지 센다.
나타나면 그 자리가 부품 모양을 **조립**하고 있다는 뜻이다.

**착수 시 위반 4종을 찾아 고쳤다.**

| 무엇 | 어디 | 고친 방법 |
|---|---|---|
| 칩을 손으로 조립 | `Badges` 2곳 · `StepList` 2곳 · `PhaseBar` 1곳 | `<Chip>` |
| 「필」을 세 곳에서 따로 조립 | `design/Chrome` · `workbench/Workbench` · `TestList` | 새 부품 `ui/Chip` 의 `<Pill>` |
| 「눈에 띄지 않는 링크」를 26곳에서 각자 | 7개 파일 | `ui/Button` 의 `navLinkClasses()` |
| 분절 선택 띠의 안쪽 버튼 모양 | `PacingControl` | 새 부품 `ui/Table` 의 `<Segmented>` |

**지금 `ui/` 밖에 남은 것은 하나다.** `workbench/WorkArea` 의 알림형 줄 2곳이
`min-h-notice` 를 직접 쓴다. `ui/Notice` 의 `Notice` 는 **높이를 못 박는** 부품이고
(정본 `.notice` 가 `flex: 0 0 32px`), 이 두 줄은 내용에 따라 늘어나야 하므로 성질이
다르다. 같은 모양의 복제가 아니라 **다른 부품이 필요한 자리**로 본다 —
지금은 한 곳뿐이라 부품을 만들지 않고 기록만 남긴다. 두 번째가 생기면 그때 만든다.

**판정: 달성.** 단, 위 한 자리는 「부품이 필요한데 아직 없는 것」으로 남겨 둔다.

### SC-006 — 스타일을 고칠 때 찾아야 할 곳이 둘뿐인가

「강조 버튼의 배경을 바꾼다」를 예로 따라가면:

1. `frontend/src/ui/Button.tsx` — `VARIANT.primary` 의 `bg-ink`
2. `frontend/src/theme/tokens.css` — `--ink` 의 값

**두 곳이다.** 화면 코드 34개 파일 어디에도 그 결정이 없다.

**세 번째 장소가 생겼는가 — 하나 생겼고, 그것은 생성물이다.**
`theme/tokens.app.css` 가 정본의 값을 담는다 (T075). 손으로 고치는 곳이 아니라
`scripts/split-canon.mjs` 가 뽑는 것이며, 낡으면 `tests/CanonSplit.test.ts` 가 잡는다.
**사람이 찾아가야 할 곳은 아니므로 「셋」으로 세지 않는다.**

곁에 있는 둘은 모양을 정하지 않는다 — `theme/tone.ts` 는 **뜻 → 부품 prop** 만 잇고
(`"실패" → tone="fail"`), `theme/exceptions.ts` 는 정본을 벗어난 값의 **등록부**다.

**판정: 달성.**


## 늘어나는 알림 부품 — 판정 (T089, 2026-09-11)

`workbench/WorkArea` 의 두 줄이 `min-h-notice` 로 알림 모양을 직접 쓴다.

**부품을 만들지 않는다.** `ui/Notice` 의 `Notice` 는 **높이를 못 박는** 부품이고
(정본 `.notice` 가 `flex: 0 0 32px`), 이 두 줄은 내용에 따라 늘어나야 한다 — 같은
부품의 복제가 아니라 **성질이 다른 것**이다. 쓰는 곳이 한 군데뿐인 형태에 이름을 주면
부품이 늘어나는 만큼 고를 것도 늘고, 그것이 SC-006 이 줄이려던 「찾아야 할 곳」이다.

**두 번째가 생기면 만든다.** 그때는 복제가 되고, 복제는 SC-010 이 막는 것이다.
그 전까지 이 줄이 그 판단의 기록이다.
