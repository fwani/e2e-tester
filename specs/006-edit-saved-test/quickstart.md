# Quickstart: 006 검증 절차

**Feature**: `specs/006-edit-saved-test` | **Date**: 2026-09-07

이 기능의 핵심 주장은 하나다 — **저장된 테스트를 고치는 길이 화면에 보이고, 브라우저 없이
고칠 수 있다.** 그 주장은 대부분 브라우저 없이 검증된다. 그것이 이 기능의 성질이다.

자동 테스트로 고정한 것과 사람이 봐야 하는 것을 구분해 적었다.

---

## 0. 준비

```bash
# 백엔드 — 로컬 인터페이스에만 바인딩
cd backend && uv run uvicorn itb.api.app:app --host 127.0.0.1 --port 4320

# 프론트엔드
cd frontend && npm run dev            # http://127.0.0.1:4310
```

**대상 앱은 §1·§2 에서 띄우지 않는다.** 그것이 검증의 일부다 (SC-302) — 대상 앱이 없는 채로
편집과 저장이 되어야 한다. §3(브라우저 편집)에서만 띄운다.

```bash
# §3 에서만
python fixtures/sample-app/serve.py --port 4300
```

실제 프로젝트 데이터를 건드리지 않으려면 격리된 `XDG_DATA_HOME`·`XDG_CONFIG_HOME` 로 띄운다.

### 검증 재료

| 테스트 | 구성 | 쓰이는 곳 |
|---|---|---|
| **TC-FAIL** | 7 Step. 01~05 통과(로그인 포함), **06 은 없는 `testId` 로 반드시 실패**(대기 약 20초), 07 미실행 | S2·S4·S5 |
| **TC-PASS** | 5 Step. 항상 통과. `fill` Step 과 민감 참조(`{{SECRET_VALUE_1}}`)를 하나씩 포함한다 | S1·S3·S6 |

민감 참조가 있는 Step 이 하나는 있어야 한다 — 없으면 FR-212·FR-213 을 걸 수 없다.

## 1. 자동 테스트로 고정된 것

```bash
# 백엔드
cd backend && uv run pytest

# 스키마 생성물이 최신인지 (신규 요청·응답 모델 추가 후 필수)
uv run python -m itb.schema.export && git diff --exit-code schema/

# 프론트엔드
cd frontend && npm run gen:types && npm test
```

| 요구사항 | 테스트가 단정하는 것 |
|---|---|
| FR-182 · SC-302 | `GET /api/tests/{id}/definition` 이 브라우저를 만들지 않고 200 이다. Playwright 를 기동하는 코드 경로가 닿지 않는다 |
| FR-183~186 | `update`·`delete`·`reorder`·`set_name`·`set_start_url` 연산이 정의 파일에 반영된다 |
| FR-192 · 원칙 I | 정의 편집이 `itb.execution.step_edits` 를 부른다. 편집 규칙의 두 번째 구현이 없다 (import 검사) |
| FR-193 | 저장이 같은 `test_id` 를 덮어쓴다. 새 테스트가 만들어지지 않는다 |
| FR-196 · FR-197 | Step 0개 → `STEP_LIST_EMPTY`. 스키마 위반 → `DEFINITION_INVALID` |
| FR-207 · R9 | 그 테스트의 살아 있는 세션이 있으면 저장이 409 `SESSION_ALREADY_ACTIVE` |
| FR-209 · R4 | 저장 사이에 파일이 바뀌면 409 `DEFINITION_STALE` 이고 `detail` 에 현재 정의가 실린다 |
| FR-210 · 원칙 II | 신규 엔드포인트 2개에서 작성 계층 호출이 도달 불가하다 |
| FR-211 | 알 수 없는 필드·범위 밖 인덱스·알 수 없는 `step_id` 가 모두 거절된다 |
| FR-213 · FR-215 | 민감 참조를 평문으로 바꾸는 편집이 400 이고, 응답·로그에 평문이 없다 |
| FR-214 | 편집·저장 후에도 민감 변수의 `sensitive: true` 가 유지된다 (강등 없음) |
| FR-216 | 정의되지 않은 참조는 저장을 막지 않고 `warnings` 로 나온다 |
| FR-187 (제외) | 편집 요청 모델에 locator 필드가 **없다**. `PRIORITY` 튜플과 후보 상태 판정이 이 기능으로 바뀌지 않았다 |
| FR-200 · R7 | `pause_before_index: 5` 로 만든 세션이 인덱스 5 를 실행하기 **전에** `paused` 다. 범위 밖 값은 400 |
| FR-189 · FR-190 | (프론트) 변경 건수가 연산 개수와 같고, 개별 되돌리기가 건수를 줄인다 |
| FR-178 · SC-304 | (프론트) 「편집」·「고치기」 컨트롤의 도착 화면이 편집 모드다 |

## 2. 사람이 직접 걸어야 하는 것 — 대상 앱 없이

**대상 앱을 띄우지 않은 상태로 시작한다.**

### S1. 목록에서 열어 고치고 저장한다 (US1)

1. 목록에서 TC-PASS 행의 「⋮」를 연다 → **「편집」이 있다.** (「정의 보기」는 없다)
2. 「편집」을 누른다 → **브라우저 창이 뜨지 않는다.** 편집 화면이 열리고 Step 5개가 나온다
3. `fill` Step 의 값을 고친다 → 그 행에 새 값이 보이고 상단이 **「변경 저장 (1건)」**
4. 대기 시간을 30000 으로 고친다 → **「변경 저장 (2건)」**
5. 「변경 저장」 → 화면이 그대로이고 **「✓ 저장했습니다 · TC-PASS」**. 버튼은 「변경 저장」
   비활성
6. 정의 파일을 직접 열어 확인한다 — 두 값이 반영되어 있다

**기대**: 3~6 전 과정에서 브라우저 창 0개, 대상 앱 접속 0회. 제목에 「초안」이 없다.

### S2. 실패한 Step 에서 「고치기」 (US2)

1. (여기서는 대상 앱이 필요하다 — 잠깐 띄운다) TC-FAIL 을 실행해 Step 06 에서 실패시킨다.
   실패 후 대상 앱을 **다시 끈다**
2. 목록 → TC-FAIL 「결과 보기」 → 결과 화면 → **「Step 06 고치기」**
3. **편집 화면이 열리고 Step 06 이 지목·펼쳐져 있다.** 읽기 전용 화면이 아니다
4. Step 06 의 대기 시간을 고쳐 저장한다 → 저장된다 (대상 앱이 꺼져 있어도)
5. 저장 확인줄 아래에 **「Step 06부터 실행」·「처음부터 실행」**이 있다

**기대**: 2→3 에서 읽기 전용 화면을 거치지 않는다. 이것이 E-04 의 해소다.

### S3. 편집 불가 항목의 표시 (FR-191·FR-202)

1. TC-PASS 편집 화면에서 `click` Step 을 지목한다
2. **대상 요소(locator) 표는 읽기 전용**이고, 그 자리에
   「이 대상은 살아 있는 화면에서만 다시 집을 수 있습니다.」 +
   **「브라우저 열어 Step 04 에서 멈추기」** 버튼이 있다
3. Step 종류 칸에는 「Step 종류는 바꿀 수 없습니다. 지우고 새로 넣으세요.」
4. 민감 참조 Step 의 값 칸은 `{{SECRET_VALUE_1}}` 로 보이고 **평문이 어디에도 없다**
5. 그 칸에 평문을 넣어 저장하면 **거절되고** 비밀 값 화면을 가리킨다

**기대**: 회색 버튼만 있는 자리가 없다. 각 잠긴 항목이 이유를 말하고,
`live_browser_required` 만 경로를 준다.

### S4. 저장하지 않은 변경을 잃지 않는다 (US4)

1. 값 2개를 고친다 → 「변경 저장 (2건)」
2. 「목록으로」를 누른다 → **「저장하지 않은 변경 2건이 있습니다」** + 저장·버리기·머무르기
3. 「버리고 나가기」 → 다시 편집을 열면 **원본 그대로**
4. 아무것도 고치지 않은 상태에서 「목록으로」 → **확인 없이 바로 나간다**
5. 값 하나를 고친 뒤 F5 → **브라우저 이탈 확인**이 뜬다
6. 값 2개를 고친 뒤 하나를 되돌린다 → 「변경 저장 (1건)」

### S5. 실행 중인 테스트 (US5)

1. (대상 앱을 띄우고) TC-FAIL 을 실행한다 — Step 06 의 20초 대기가 관찰 창이다
2. 그 사이 목록에서 TC-FAIL 「편집」을 누른다
3. **화면은 열린다.** 다만 읽기 전용이고 「실행 중이어서 편집할 수 없습니다」 +
   **「실행 중인 세션 보기」**가 있다
4. 그 버튼으로 실행 화면에 갔다가 실행이 끝난 뒤 다시 「편집」 → **정상적으로 열린다**

**기대**: 3에서 화면이 안 열리거나 조용히 실패하지 않는다. 세션 UUID 가 문장에 노출되지
않는다 (005 FR-135).

### S6. 외부 변경 충돌 (FR-209)

1. TC-PASS 편집 화면을 열고 값 하나를 고친다 (저장하지 않는다)
2. **다른 터미널에서** 정의 YAML 을 편집기로 열어 이름을 바꿔 저장한다
3. 화면에서 「변경 저장」 → **「이 테스트의 정의 파일이 편집을 시작한 뒤에 바뀌었습니다」**
   + 「바뀐 내용으로 다시 읽기」 · 「내 편집으로 덮어쓰기」
4. 「다시 읽기」 → 터미널에서 바꾼 이름이 보이고 내 편집 1건은 사라졌다(건수를 밝힌 뒤)
5. 같은 상황을 다시 만들어 「덮어쓰기」 → 내 편집이 이긴다

**기대**: 조용히 덮어쓰지 않는다. 두 버튼이 각각 무엇을 버리는지 라벨 옆에 적혀 있다.

## 3. 사람이 직접 걸어야 하는 것 — 브라우저 편집 (US3)

**대상 앱을 띄운다.**

### S7. 「브라우저 열어 Step nn 에서 멈추기」

1. TC-FAIL 편집 화면에서 Step 06 을 지목 → 「브라우저 열어 Step 06 에서 멈추기」
2. 브라우저가 뜨고 Step 01~05 가 실행된다 (로그인이 지나간다)
3. **Step 06 을 실행하기 전에 멈춘다.** 배지는 `PAUSED`, 편집 팔레트가 열려 있다
4. **사용자가 「일시정지」를 누른 적이 없다** — 이것이 E-06 의 해소다 (SC-305)
5. 그 상태에서 Step 06 의 대상을 「다시 집기」로 지목해 고친다
6. 「변경 저장」 → 저장된다. 「나가기」 후 편집 화면을 다시 열면 반영되어 있다 (FR-204)

### S8. 저장하지 않은 변경이 있을 때 (FR-203)

1. 편집 화면에서 값 하나를 고친다 (저장하지 않는다)
2. 「브라우저 열어 Step 06 에서 멈추기」 → **먼저 저장을 요구한다** +「저장하고 열기」
3. 그것을 누르면 저장된 뒤 세션이 열린다 — 세션이 든 정의와 화면이 든 정의가 같다

## 4. 왕복 정합성 (헌법 Quality Gate 2)

```bash
# 편집 → 저장 → 재실행이 반영되는지
cd backend && uv run pytest -k "definition_edit and rerun"
```

사람이 걸 때는: TC-FAIL 의 Step 06 대기 시간을 5000 으로 줄여 저장 → 「처음부터 실행」 →
실패까지 걸리는 시간이 약 20초에서 약 5초로 준다 (SC-308).

**정의 형식 불변 확인**: 편집·저장 후 정의 YAML 이 여전히 사람이 읽는 평문이고 필드 구성이
같다 (원칙 V). `git diff` 로 편집한 값만 바뀌었는지 본다 — 저장이 파일 전체를 재배치하면
사용자의 버전 관리가 쓸모 없어진다.

## 5. 남은 작업으로 등록할 것

이 절차에서 기대와 다른 것을 본 항목은 조용히 넘기지 않는다. 해당 FR 번호를 들어 `tasks.md`
에 남은 작업으로 등록한다.

특히 아래는 이 기능의 주장 자체이므로 미달이면 반드시 등록한다.

- 브라우저 창이 하나라도 떴다 (SC-301·SC-302)
- 「편집」·「고치기」가 읽기 전용 화면에 도착했다 (SC-304)
- 편집 상태에 도달하려고 「일시정지」를 눌러야 했다 (SC-305)
- 저장하지 않은 변경이 확인 없이 사라졌다 (SC-306)
- 민감 값 평문을 어디서든 봤다 (SC-307)
