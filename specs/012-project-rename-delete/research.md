# Phase 0 — 조사: 프로젝트 이름 변경과 삭제

**Feature**: 012-project-rename-delete | **Date**: 2026-09-10

명세의 요구를 기존 코드에 얹기 전에 확인해야 했던 것들이다. **설계를 바꾼 발견이 세 건**
(R1·R3·R6) 있고, 나머지는 기존 규약을 따르는 확인이다.

---

## R1 — 목록의 표시 이름은 이미 디스크에서 읽는다

**확인한 것**: `registry.list_projects()` 는 접근 가능한 항목의 이름을 레지스트리가 아니라
**프로젝트 파일에서** 읽는다.

```
name = _name_from_disk(pathlib.Path(entry.root), entry.name) if ok else entry.name
```

**Decision**: 이름 변경은 **프로젝트 파일을 정본으로** 쓰고, 레지스트리 항목의 `name` 은
**보조로 함께 갱신**한다.

**Rationale**: 파일만 고쳐도 목록에는 즉시 반영된다. 그런데도 레지스트리를 갱신하는 이유는
**그 프로젝트가 나중에 접근 불가가 됐을 때**다 — 그때 목록은 `entry.name`(레지스트리 값)으로
떨어지고, 갱신하지 않았으면 사용자는 자기가 고치기 전의 옛 이름을 본다. FR-401 이 "양쪽"을
요구하는 실질적 이유가 이것이다.

**Alternatives considered**:
- 레지스트리만 갱신 — 기각. 프로젝트 파일이 정본이고, `_name_from_disk` 가 다음 조회에서
  옛 이름으로 되돌린다. 사용자에게는 "고쳤는데 되돌아갔다" 로 보인다.
- 프로젝트 파일만 갱신 — 기각. 위의 접근 불가 경로에서 옛 이름이 되살아난다.

---

## R2 — 이름 변경에 `registry.remember()` 를 쓰면 목록 순서가 흔들린다

**확인한 것**: `remember()` 는 항목을 지우고 다시 넣으면서 `last_opened_at` 을 **현재 시각으로
갱신**한다. 그리고 `list_projects()` 는 `last_opened_at` 역순으로 정렬한다.

**Decision**: `registry.rename(root, name)` 을 새로 둔다. 기존 항목의 `name` 만 바꾸고
`last_opened_at`·`origin` 은 **그대로 둔다.** 레지스트리에 그 항목이 없으면(스캔으로만 보이는
관리 위치 프로젝트) 아무것도 하지 않고 `False` 를 돌려준다 — R1 에 따라 표시에는 문제가 없다.

**Rationale**: 이름을 고쳤을 뿐인데 프로젝트가 목록 맨 위로 올라오면, 사용자는 "최근 연 순"
이라는 목록의 약속이 깨진 것을 본다. 이름 변경은 여는 행위가 아니다.

**Alternatives considered**:
- `remember()` 재사용 — 기각(위). 한 줄 아끼려고 목록의 의미를 바꾼다.
- 정렬 기준 변경 — 기각. 이 기능의 범위 밖이고, DR-004 를 되돌리는 일이다.

---

## R3 — 휴지통 위치와 항목 이름

**Decision**:

```
~/.local/share/itb/trash/<YYYYMMDD-HHMMSS>-<원래 디렉터리 이름>/
        ^ data_dir()          ^ 삭제 시각(UTC)   ^ root.name
```

- `paths.trash_dir()` = `data_dir() / "trash"`. `XDG_DATA_HOME` 을 존중한다(기존 규약).
- 같은 초에 두 번 삭제되어 이름이 겹치면 `-2`, `-3` 을 붙인다 — 프로젝트를 만들 때
  `allocate_workspace_path()` 가 쓰는 것과 **같은 회피 규칙**이다.

**Rationale**:
- **`workspace_dir()` 와 형제 디렉터리**다 (`projects/` ↔ `trash/`). 스캔 대상은
  `data_dir()/projects` 뿐이므로 휴지통이 목록에 다시 나타날 수 없다 (FR-421). 휴지통을
  `projects/.trash/` 안에 두면 스캔 제외 규칙을 새로 만들어야 하고, 그 규칙을 빠뜨린 경로가
  하나라도 생기면 삭제한 프로젝트가 목록에 돌아온다.
- **시각 접두사가 충돌 회피와 기록을 동시에 한다** (FR-415). 사용자가 휴지통을 열었을 때
  "언제 지운 어느 프로젝트인지" 가 디렉터리 이름만으로 읽힌다.
- 표시 이름이 아니라 **원래 디렉터리 이름**을 쓴다. 표시 이름에는 경로 구분자가 들어갈 수
  있고, 그것을 파일명에 넣으면 경로가 갈라진다.

**Alternatives considered**:
- OS 휴지통(`~/.Trash`, freedesktop `Trash/`) — 기각. 플랫폼마다 규격이 다르고
  (macOS 는 규격이 문서화되어 있지 않다), 외부 의존성(`send2trash`)이 필요하며, 볼륨마다
  휴지통이 다르다. 이 도구는 이미 `XDG` 기반 자기 저장소를 갖고 있어 그것과 일관된 자리가
  더 예측 가능하다.
- 접미사 `-2` 없이 시각만 — 기각. 자동화·연타로 같은 초에 두 번 지우는 것이 가능하고,
  그때 덮어쓰면 FR-415·SC-619 위반이다.
- 즉시 삭제(`shutil.rmtree`) — 기각. 사용자 결정(2026-09-10)이자 헌법 §V 가 지키는 자산이다.

## R4 — 옮기는 방법: `shutil.move`, 그리고 다른 볼륨

**Decision**: `shutil.move(src, dst)` 를 쓴다. 목적지 부모(`trash_dir()`)를 먼저 만들고,
**실패하면 목적지에 남은 부분 결과를 치운 뒤** 예외를 올린다.

**Rationale**: 외부 위치 프로젝트는 다른 볼륨에 있을 수 있다. `os.rename` 은 그 경우
`OSError(EXDEV)` 로 실패한다. `shutil.move` 는 같은 볼륨이면 `os.rename`(원자적), 다른
볼륨이면 복사 후 원본 삭제로 자동 분기한다.

**다른 볼륨의 한계를 명시한다**: 복사 도중 실패하면 원본은 남고 목적지에 반쪽이 생긴다.
원본이 남는 것이 중요한 성질이므로(FR-414) 이 실패 모드는 받아들이고, **목적지 반쪽만
치운다.** 치우기가 또 실패해도 원래 예외를 덮지 않는다 — `atomic.write_text` 가 임시 파일에
대해 하는 것과 같은 처리다.

**Alternatives considered**:
- `os.rename` 만 — 기각. 외부 위치 프로젝트에서 볼륨이 다르면 항상 실패한다.
- 복사 후 원본 삭제를 직접 구현 — 기각. `shutil.move` 가 하는 일이다.

## R5 — 실패해도 목록에서 사라지지 않는 순서

**Decision**: 두 조작 모두 **파일이 먼저, 레지스트리가 나중**이다.

| 삭제 | 이름 변경 |
|---|---|
| 1. 대상이 도구가 아는 프로젝트인가 (FR-419) | 1. 대상이 도구가 아는 프로젝트인가 |
| 2. 실행 중 세션이 있는가 (FR-417) | 2. 프로젝트 파일을 읽는다 |
| 3. `shutil.move` — **실패하면 여기서 끝**. 레지스트리 그대로 (FR-414) | 3. 새 이름이 기존과 같으면 쓰지 않고 끝 (FR-407) |
| 4. `registry.forget()` | 4. `write_project()` — **실패하면 여기서 끝**. 레지스트리 그대로 (FR-402) |
| 5. 열려 있던 프로젝트면 `state.repository = None` (FR-416) | 5. `registry.rename()` |
| 6. 옮겨진 위치를 응답에 담는다 (FR-410) | 6. 갱신된 목록 항목을 응답에 담는다 |

**Rationale**: 반대 순서(레지스트리 먼저)의 실패는 **목록에서는 사라졌는데 자산은 원래 자리에
남는** 상태를 만든다. 사용자는 자기 테스트가 어디 있는지 알 방법을 잃는다 — 이 기능이
막으려는 바로 그 손실이다. 레지스트리 갱신이 실패하는 쪽은 되돌리기 쉽다(목록에 한 줄이
더 보일 뿐).

**Alternatives considered**:
- 2단계 커밋·저널 — 기각. 단독 로컬 도구에 트랜잭션 로그를 들이는 것은 이 조작의 위험에
  비해 과하다. "실패하면 아무것도 하지 않은 것과 같다" 는 순서만으로 얻어진다.

## R6 — 실행 중 세션 판정: 열린 프로젝트가 하나뿐이라는 사실을 쓴다

**확인한 것**: `AppState.repository` 는 **한 개**다. 세션은 `SessionManager` 에 전역으로
있고 프로젝트를 기억하지 않는다. 따라서 세션을 가질 수 있는 프로젝트는 지금 열려 있는
그 하나뿐이다.

**Decision**: 삭제 대상이 **현재 열린 프로젝트이면서** `state.sessions.all_sessions()` 중
`state_machine.is_active(...)` 인 세션이 하나라도 있으면 거절한다. 그 외에는 세션 검사를
하지 않는다.

**Rationale**: 세션에 프로젝트 식별자를 새로 달지 않고 판정할 수 있다. `is_active` 는 이미
"살아 있는 세션" 의 정본이며(`ACTIVE_STATES`), 새 목록을 만들면 상태가 늘 때 한쪽이 빠진다 —
`active_session_for_test` 의 주석이 남긴 교훈이 그것이다.

**한계를 명시한다**: 한 번에 여러 프로젝트를 열 수 있게 되면 이 판정의 범위를 다시 봐야
한다. spec 의 Assumptions 에 같은 문장이 있다.

---

## R7 — 대상 경로 검증: 기존 경계 규칙을 그대로 쓴다

**Decision**: 이름 변경·삭제의 `root` 는 **도구가 아는 프로젝트**여야 한다.

- 관리 위치(`workspace_dir()`) 아래이거나
- 레지스트리에 있는 항목이거나

둘 중 하나. 아니면 `INVALID_PATH` 로 거절한다.

**Rationale**: `open_project` 의 `_known_root_outside_home()` 이 이미 같은 판정을 한다.
그 함수를 **`registry` 모듈로 끌어올려** 세 라우트가 같은 것을 쓰게 한다. 임의 경로를 받아
디렉터리를 옮기는 엔드포인트는 로컬 바인딩이라 해도 만들어서는 안 된다 — 브라우저에서
도달하는 표면이고, 도구가 관리하지 않는 디렉터리를 옮길 이유가 없다.

**Alternatives considered**:
- `resolve_within_home()` 만 — 기각. 홈 밖을 가리키는 `XDG_DATA_HOME` 에서 도구가 만든
  프로젝트를 자기가 못 지우는 비대칭이 생긴다. `open_project` 가 이미 겪고 고친 결함이다.
- 검증 없이 받기 — 기각. 보안 요건 위반.

## R8 — 화면: 어디에 무엇을 놓는가

**확인한 것**: `ProjectSetup.tsx` 는 확정 디자인에 대응 화면이 없어 1:1 대조 의무(DC-010)가
적용되지 않고, 8화면의 시각 언어(직각 모서리, 3px 잉크 테두리, 하드 오프셋 그림자, `pane`)를
따른다. `lib/capabilities.ts` 의 권한표는 **국면(Phase) × 조작** 이며 세션 화면의 것이다.

**Decision**:

1. **이름 인라인 편집** — `PhaseBar` 의 테스트 이름 편집과 같은 관용어(제자리 입력, 확인 창
   없음, 사유는 그 자리에 표시)를 쓰되, **`capabilities.ts` 의 권한표에 편입하지 않는다.**
2. **삭제 확인** — `ProjectRow` 안에서 **그 줄이 확인 상태로 바뀌는 방식**을 쓴다. 별도
   모달을 새로 만들지 않는다.
3. 줄이 제공하는 조작은 **줄의 상태**(`accessible` × `origin`)가 정한다.

**Rationale**:
- 권한표는 `Record<Phase, …>` 로 **열 국면 전부**에 값을 요구한다. 프로젝트 선택 화면은
  그 국면 축 바깥에 있다 — 억지로 넣으면 열 개의 무의미한 칸이 생기고, 국면 축의 뜻이
  흐려진다. 대신 권한표가 지키는 **원칙**(조작이 왜 지금 안 되는지 화면이 말한다)은
  그대로 지킨다: 이름 변경·삭제가 제공되지 않는 줄은 그 사유를 표시한다 (FR-406·FR-418).
- 확인을 줄 안에서 하면 사용자가 **어느 줄을 지우는지** 시선을 옮기지 않고 확인한다.
  프로젝트가 여러 개일 때 모달의 "정말 삭제할까요?" 는 대상을 다시 확인시키지 못한다.

**Alternatives considered**:
- `capabilities.ts` 에 프로젝트 국면 추가 — 기각(위).
- 이름 재입력을 요구하는 강한 확인(GitHub 식) — 기각. **되돌릴 수 있는 조작**이므로 그
  강도가 맞지 않는다. 되돌리는 방법을 알려 주는 것이 더 정확한 안전장치다 (FR-425).

## R9 — 오류 코드와 스키마 재생성

**Decision**: `ErrorCode` 에 두 개를 더한다.

| 코드 | 상태 | Category | 쓰이는 곳 |
|---|---|---|---|
| `PROJECT_IN_USE` | 409 | `BLOCKED` | 실행 중 세션이 있는 프로젝트 삭제 (FR-417) |
| `PROJECT_DELETE_FAILED` | 500 | `BROKEN` | 휴지통으로 옮기지 못함 (FR-414) |

**필수 후속**: `CATEGORY` 와 `NEXT_ACTION` 대응표에 **둘 다** 넣는다. 두 표는
`error_payload()` 가 참조하며, 빠지면 `KeyError` 로 오류 응답 자체가 깨진다. 그리고
`itb.schema.export` 가 `error-response` 스키마를 내보내므로
`frontend/src/types/generated/error-response.d.ts` 를 **다시 생성**해야 한다 (헌법
Cross-language schema duty · `export.check()` 가 어긋남을 잡는다).

**Rationale**: 기존 코드로 대신할 수 없다. `SESSION_ALREADY_ACTIVE` 는 "이 테스트가 이미
실행 중" 이라는 다른 뜻이고, `STORAGE_WRITE_FAILED` 는 쓰기 실패이지 이동 실패가 아니다 —
사용자가 할 일이 다르므로 코드를 갈라야 한다는 것이 `DEFINITION_STALE` 을
`DEFINITION_INVALID` 에서 가른 근거와 같다.

## R10 — 이 기능이 고쳐야 하는 기존 검사

새 기능이 기존 검사의 전제를 깬다. 구현과 함께 고친다.

| 검사 | 왜 걸리는가 |
|---|---|
| `backend/tests/contract/test_project_and_tests_api.py` | 프로젝트 라우트 목록이 늘어난다 |
| `backend/tests/unit/test_paths.py` | `trash_dir()` 이 새로 생긴다 — `XDG_DATA_HOME` 존중 여부를 같은 방식으로 세야 한다 |
| `backend/tests/unit/test_registry.py` | `rename()` 이 새로 생긴다 |
| `frontend/tests/ProjectSetup.test.tsx` | 줄에 조작이 늘어난다. 기존 「목록에서 치우기」 단언이 새 조작과 이름이 겹치지 않는지 확인해야 한다 |
| 오류 코드 수를 세는 검사(있다면) | `ErrorCode` 가 2개 는다 |
