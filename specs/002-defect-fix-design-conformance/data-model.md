# Phase 1 Data Model — 결함 수정과 확정 디자인 준수

**Feature**: `specs/002-defect-fix-design-conformance`
**Date**: 2026-09-04

이 라운드는 **Step DSL 을 바꾸지 않는다.** 헌법 원칙 I 이 요구하는 단일 Step 모델은
001 에서 정의된 그대로다. 아래 엔티티는 전부 그 바깥 — 도구가 자기 상태를 아는 방식,
그리고 이 라운드의 검증 근거 — 에 속한다.

> **원칙 I 확인**: 아래 어느 엔티티도 Step 을 담거나 Step 에 필드를 더하지 않는다.
> `SessionWork` 의 수명이 길어질 뿐 그것이 들고 있는 `list[Step]` 의 형태는 그대로다.

## 1. ProjectRegistryEntry — 프로젝트 등록 항목

도구가 알고 있는 프로젝트 하나. **첫 화면 목록의 근거다** (DR-002·DR-003·DR-007).

**저장 위치**: `~/.config/itb/registry.json`

| 필드 | 형 | 규칙 |
|---|---|---|
| `root` | 절대 경로 문자열 | 필수. 정규화된 절대 경로. 목록 내 유일 키 |
| `name` | 문자열 | 필수. 1–100자. 프로젝트 파일에서 읽은 표시 이름 |
| `last_opened_at` | ISO-8601 UTC 타임스탬프 | 필수. 정렬 기준 (DR-004) |
| `origin` | `"managed"` \| `"external"` | 필수. 관리 위치 안에서 만든 것인지, DR-005 로 연 것인지 |

**파일 형태**

```json
{
  "version": 1,
  "projects": [
    { "root": "...", "name": "...", "last_opened_at": "2026-09-04T02:11:00Z", "origin": "managed" }
  ]
}
```

`version` 은 앞으로 형식을 바꿀 때 읽는 쪽이 판단할 근거다. 읽을 때 모르는 버전이면
빈 목록으로 취급하고 사용자에게 알린다 — 조용히 덮어써서 사용자의 기록을 잃지 않는다.

### 파생 필드 (저장하지 않고 조회 시 계산)

| 필드 | 계산 |
|---|---|
| `accessible` | `root` 가 존재하고 읽을 수 있으며 유효한 프로젝트 구조인가 (DR-009) |
| `unavailable_reason` | `accessible` 이 거짓일 때 사람이 읽을 수 있는 사유 |

**저장하지 않는 이유**: 파일 시스템은 도구 바깥에서 바뀐다. 저장하면 즉시 낡는다.

### 목록 구성 규칙 (DR-002 + DR-007)

```
표시 목록 = (관리 위치 스캔 결과) ∪ (레지스트리 항목)
```

`root` 로 중복 제거한다. 어느 한쪽만으로는 부족하다 —

- 스캔만: DR-005 로 연 외부 경로가 안 보인다 (DR-007 위반).
- 레지스트리만: 파일이 사라지면 관리 위치의 프로젝트가 통째로 사라진다.

정렬은 `last_opened_at` 내림차순 (DR-004). 스캔으로만 발견되어 레지스트리에 없는 항목은
디렉터리 수정 시각을 대신 쓰고 목록 끝에 둔다.

### 상태 전이

| 사건 | 결과 |
|---|---|
| 프로젝트 생성 (DR-006) | 관리 위치에 만들고 `origin: managed` 로 등록. `last_opened_at` = 현재 |
| 목록에서 열기 (DR-003) | `last_opened_at` 갱신 |
| 외부 경로로 열기 (DR-005) | `origin: external` 로 등록 또는 갱신 |
| 목록에서 제거 (DR-009) | 항목만 지운다. **디스크의 프로젝트는 지우지 않는다** |

마지막 항목이 중요하다. 목록에서 치우는 것과 자산을 삭제하는 것은 다른 조작이고,
되돌릴 수 없는 쪽을 조용히 하면 안 된다.

## 2. RecordingDraft — 녹화 초안

중지 후 아직 저장되지 않은 Step 묶음 (DR-010~DR-015).

**새 저장소를 만들지 않는다.** 기존 `SessionWork`(`backend/src/itb/api/routes/sessions.py:96`)
의 수명을 늘려 표현한다. R1 의 결정에 따라 `stop` 이 `_WORK` 에서 제거하지 않는다.

| 필드 | 출처 | 이 라운드의 변화 |
|---|---|---|
| `steps` | 기존 `SessionWork.steps` | 없음 |
| `saved_snapshot` | 기존 `SessionWork.saved_snapshot` | 없음 |
| `has_unsaved_changes` | 기존 계산 속성 (`sessions.py:125`) | 없음 |
| `store` / `resolver` | 기존 | 없음 — 저장 시 변수·민감값 문맥이 필요하다 |
| 브라우저 세션 | 기존 | **중지 시 해제된다** |

### 세션 수명 주기의 변화

```
        [기존]                              [이 라운드]

  running ──stop──▶ (파괴)          running ──stop──▶ review ──save──▶ (파괴)
                                                        │
                                                        └──discard──▶ (파괴)
```

`review` 상태의 규칙:

| 규칙 | 근거 |
|---|---|
| 브라우저·미러·러너·에이전트는 이미 해제되어 있다 | 실제 창을 남길 이유가 없다 |
| `steps` 조회·수정·삭제·순서 변경을 받는다 | DR-012 |
| `save` 를 받는다 | DR-013 |
| 브라우저가 필요한 명령(실행·이어서·다시 집기)은 거절한다 | 001 FR-043a — 정의되지 않은 명령 거절 |
| `discard` 를 받으면 비로소 파괴한다 | DR-014 |
| Step 0개면 `save` 를 거절한다 | 001 FR-029 (기존 동작 유지) |

**서버가 대신 저장하지 않는다.** 저장은 이름을 요구하는 별개의 명령이다 (기존 판단 유지).

## 3. LlmAvailability — 언어모델 사용 가능 여부

AI 작성을 시작하기 **전에** 알려 주기 위한 읽기 전용 상태 (DR-021).

| 필드 | 형 | 의미 |
|---|---|---|
| `available` | 불리언 | 자격 증명을 해석할 수 있는가 |
| `reason` | 문자열 \| null | 거짓일 때 사람이 읽을 수 있는 사유와 조치 방법 |

**값을 담지 않는다.** 키·토큰·프로필 이름 등 자격 증명의 어떤 조각도 이 구조에 넣지
않는다 (헌법 보안 요구). `available` 과 안내 문구뿐이다.

**원칙 II 확인**: 이 점검은 **작성 경로에서만** 호출한다. 저장된 테스트의 재실행 경로는
이 값을 읽지 않는다. 점검 자체가 언어모델을 호출하지도 않는다 — 자격 증명 해석 가능
여부만 본다.

## 4. DesignConformanceRecord — 디자인 대조 기록

확정 디자인 한 화면과 제품 한 화면의 대조 결과 (DC-012·SC-108).

**저장 위치**: `specs/002-defect-fix-design-conformance/design-conformance/<Screen>.md`
화면당 한 파일, 8개.

| 필드 | 의미 |
|---|---|
| `screen` | 화면 식별자 (`TestList`, `CreateTest`, … 8종) |
| `source` | 기준 파일 경로 (`docs/design/TestList.dc.html`) |
| `axis` | 대조 축 — `구조`(DC-002) / `컴포넌트`(DC-003) / `치수`(DC-004) / `타이포·색`(DC-005) / `상태`(DC-006) / `가감`(DC-007) |
| `expected` | 확정 디자인에서 기계적으로 뽑은 기준값 |
| `observed` | 리뷰어가 제품에서 관측한 값 |
| `verdict` | `일치` / `불일치` / `미판정` |
| `note` | 불일치일 때 차이 내용 |

`expected` 는 스크립트가 채운다. `observed` 와 `verdict` 는 **사람이 채운다** — 자동으로
채우면 대조가 아니라 자기 확인이 된다 (001 T156 에서 같은 문제를 겪었다).

**완료 판정**: 8화면 전부에서 `verdict` 에 `불일치`·`미판정`이 하나도 없을 것 (SC-108).

## 5. UndefinedStateNote — 디자인 미정의 상태 기록

확정 디자인이 정의하지 않아 구현자가 결정해야 했던 상태 (DC-009·SC-110).

**저장 위치**: `specs/002-defect-fix-design-conformance/design-conformance/undefined-states.md`
**한 파일에 모은다** — 흩어 두면 "기록 없이 결정된 것이 몇 건인가"를 셀 수 없다.

| 필드 | 의미 |
|---|---|
| `screen` | 어느 화면인가 |
| `state` | 상태 이름 (`로딩`, `빈 목록`, `오류`, `긴 목록` 등) |
| `basis` | 어느 확정 디자인의 어느 표현을 근거로 삼았는가 |
| `decision` | 실제로 무엇을 했는가 |

`basis` 는 필수다. "가장 가까운 확정 디자인 표현을 따른다"(DC-009)를 지켰다는 증거가
근거 없이는 성립하지 않는다. 근거를 댈 수 없는 결정은 해석이다.

## 6. DirectoryEntry — 탐색기 항목

"기존 프로젝트 열기"의 폴더 선택에 쓰는 읽기 전용 항목 (DR-005).

| 필드 | 형 | 의미 |
|---|---|---|
| `name` | 문자열 | 디렉터리 이름 |
| `path` | 절대 경로 문자열 | 정규화된 경로 |
| `is_project` | 불리언 | 유효한 프로젝트 구조인가 — 사용자가 어디를 골라야 할지 알려 준다 |

**파일을 담지 않는다.** 디렉터리만 반환한다. 탐색기가 파일 유출 통로가 되지 않아야
한다 (research R4 보안 경계).

**경계 규칙** — 아래를 모두 만족하지 않으면 요청을 거절한다.

| 규칙 | 막는 것 |
|---|---|
| `resolve()` 로 정규화한 뒤 사용자 홈 하위인지 확인 | `..` 를 이어 붙인 탈출 |
| 심볼릭 링크는 따라간 뒤 다시 경계 검사 | 링크를 통한 경계 이탈 |
| 숨김 디렉터리 제외 | `.ssh` 등 노출과 목록 소음 |
| 읽기 권한 없으면 사유와 함께 거절 | 조용한 빈 목록 (진단 불가) |

`POST /api/project/open` 이 받는 경로에도 같은 경계를 적용한다.

## 엔티티 관계

```
ProjectRegistryEntry ──(root 로 가리킨다)──▶ 디스크의 프로젝트
        ▲
        │ (열기·생성 시 갱신)
   DirectoryEntry (탐색 결과 — 저장되지 않는다)

RecordingDraft ─(save)─▶ Test (001 의 기존 엔티티. 이 라운드가 바꾸지 않는다)

DesignConformanceRecord ─(8개)─┐
                               ├─▶ SC-108 / SC-110 판정
UndefinedStateNote ─(N개)──────┘

LlmAvailability — 다른 엔티티와 관계 없음. 작성 시작 전 안내에만 쓴다
```
