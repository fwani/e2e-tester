# Implementation Plan: 입력 칸의 두 빈칸 — 값을 읽지 못하고, 키로 확정하지 못한다

**Branch**: `023-input-value-assertion` | **Date**: 2026-09-28 (키 입력으로 범위 확장) | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/023-input-value-assertion/spec.md`

---

## Summary

**어휘를 둘 더한다** — 검증 종류 `value` 하나와 동작 Step 종류 `press` 하나.

두 요구가 따로 들어왔지만 같은 곳이 뚫려 있다. 입력 칸을 **읽지도**(값이 텍스트로 관찰되지
않는다) **확정하지도**(키를 누를 Step 이 없다) 못한다. 둘 다 표현 수단이 없어서 생긴
문제이므로 어휘를 더하는 것이 답이고, 021 이 상태 검증을 더한 것과 같은 모양이다.

### 두 쪽의 성질이 다르다 — 이것이 계획의 뼈대다

| | 입력값 검증 (`value`) | 키 입력 (`press`) |
|---|---|---|
| 무엇이 깨지나 | 검증 하나가 실패 | **작성이 중단** |
| 사람 녹화는 | 영향 없음 | **값을 잃는다** |
| 기존 동작 변경 | 없음 (값 추가) | **있다** — 녹화 규칙 두 개를 고친다 |
| 새 보안 위험 | **있다** — 비밀번호 평문 | 없다 (값을 담지 않는다) |
| 새 판정·대기 | 없음 (021 재사용) | 없음 (동작 Step) |
| 가장 어려운 곳 | 실패 시 관찰값 마스킹 | **한글 IME 의 Enter 두 번** |

**새 위험이 서로 다른 자리에 하나씩 있다.** 각각 독립적으로 검증해야 한다.

### 조사에서 계획을 바꾼 것

| 조사 | 원래 생각 | 확인한 사실 |
|---|---|---|
| R1 | 생성기가 `TargetLocator.tag` 로 matcher 를 고른다 | **고를 필요가 없다.** 종류가 곧 답이다 |
| R2 | 기존 스크러버가 비밀번호를 가려 준다 | **실패할 때만 샌다.** 스크러버는 복호화된 값만 안다 |
| R3 | 판정을 `build_assertion` 에 두면 된다 | **AI 경로는 거기를 지나지 않는다.** 021 의 경고도 닿지 않고 있다 |
| R10 | 녹화가 `keydown` 을 피한 이유가 이 기능도 막는다 | **막지 않는다.** 그 논거는 *값*을 재구성하는 것에 대한 것이고, 우리는 *키*를 잡는다 |
| R11 | 키 Step 을 더하면 녹화가 고쳐진다 | **아니다.** 키 뒤의 빈 값이 앞선 입력 Step 을 덮는 동작을 함께 고쳐야 한다 |

R2 와 R11 이 이 계획에서 가장 무거운 두 곳이다. 나머지는 값 둘을 더하고 그 값들이 지나는
자리를 빠짐없이 덮는 일이다.

## Technical Context

**Language/Version**: Python 3.12 (backend) · TypeScript 5 / React 19 (frontend)

**Primary Dependencies**: FastAPI · Playwright for Python · Pydantic v2 · Vite · Tailwind

**Storage**: 테스트 정의는 사람이 읽는 평문 파일. 민감 값만 `secrets.local.yaml` 에 봉인

**Testing**: pytest (`backend/tests/{unit,contract,integration,abnormal}`) · Vitest (frontend)

**Target Platform**: 로컬 실행 (macOS · Linux). 브라우저는 Playwright Chromium

**Project Type**: Web application (backend + frontend)

**Performance Goals**: 이번 변경에 새 목표 없음. 실행 시점에 대상 속성을 한 번 더 읽는
비용이 늘지만 검증 하나당 왕복 1회 수준이다

**Constraints**:
- 정의 파일 하위 호환 — 마이그레이션 없이 열리고 실행돼야 한다 (FR-040)
- 비밀번호 평문이 정의·로그·결과·공유 묶음 어디에도 남지 않아야 한다 (FR-015~FR-017, 헌법 보안 제약)
- 제품 안 실행과 내보낸 코드가 같은 판정을 해야 한다 (헌법 원칙 V)
- **한글 IME 에서 조합 확정 Enter 와 제출 Enter 를 갈라야 한다** — 못 가르면 이 기능은
  한국어 사용자에게 쓸모없다 (FR-055)
- 녹화가 지금 만드는 Step 이 달라진다 (FR-043) — 결함 수정이지만 동작 변경이다

**Scale/Scope**: 검증 종류 6 → 7, Step 종류 9 → 10. 백엔드 9개 모듈 · 프론트 4개 파일 ·
고정 대상 1개 화면 (여러 줄 입력 칸 + 태그 칸)

## Constitution Check

*GATE: Phase 0 전에 통과해야 하고, Phase 1 설계 후 다시 본다.*

### Phase 0 이전

| 원칙 | 판정 | 근거 |
|---|---|---|
| **I. Unified Step Model** (비협상) | **통과** | 검증 종류 하나와 Step 종류 하나를 늘린다. 병행 표현을 만들지 않는다. **키 입력은 지금 사람도 AI 도 못 만드는 상태**라 이번 변경이 원칙 I 의 간극을 **좁힌다** |
| **II. Deterministic Replay** (비협상) | **통과** | 재실행 경로에 LLM 호출이 없다. 값 관찰·비교도, 키 전송도 결정적이다. **키를 포커스가 아니라 대상 요소에 보내는 것**이 이 원칙을 지키는 선택이다 (FR-051) |
| **III. Stateful Interactive Runner** | **해당 없음** | 세션 수명·일시정지 동작을 건드리지 않는다 |
| **IV. Locator Resilience** | **통과** | 두 종류 모두 후보 수집에 기존 경로를 그대로 쓴다. CSS 단독 후보를 만들지 않는다 |
| **V. Asset Portability** | **주의** | 두 새 종류를 생성기에 반영하지 않으면 내보내기가 깨진다. **이번 범위에 포함**했다 (US3) |
| **보안 제약** (조직 명령, 비협상) | **주의** | 입력값 검증은 비밀번호 평문의 **새 유출 경로**다. FR-015~FR-017 로 함께 막는다. 키 입력은 값을 담지 않아 해당 없다 (research R13) |

### Phase 1 설계 후 재확인

| 원칙 | 재확인 |
|---|---|
| I | 판정 규칙을 **한 함수**에 두고 두 작성 경로가 호출한다 (research R3). 규칙이 경로마다 갈리지 않는다 |
| II | **마스킹은 설명 문자열만 바꾼다.** 통과·실패는 실제 값으로 판정하므로 「같은 화면이면 같은 결과」가 유지된다 |
| IV | `TargetLocator` 에 필드를 더하지 않는다. 성질 판정은 살아 있는 요소에서 하고 저장하지 않는다 (research R1) |
| V | [contracts/export-mapping.md](./contracts/export-mapping.md) 에 네 비교 방식의 대응을 모두 규정했다. `contains` 는 표준에 직접 대응이 없어 `expect.poll` 로 옮긴다 — 표준 API 만 쓴다 |
| 보안 | 판별 규칙을 새로 만들지 않고 녹화와 **같은 출처·같은 규칙**을 쓴다. 관찰값 마스킹은 스크러버에 기대지 않고 별도로 보장한다 |
| I (키 입력) | 녹화·AI 두 경로가 **같은 `PressStep`** 을 만든다. `STEP_PRODUCING_TOOLS` 의 10:10 대응을 기존 검사가 고정하므로 한쪽만 만드는 상태가 생길 수 없다 |
| II (키 입력) | 키 목록이 **열거형**이라 임의 문자열이 실행기·생성기에 도달할 수 없다. 「생성된 코드는 데이터로 다룬다」를 값의 형태로 만족시킨다 (research R12) |
| V (키 입력) | `locator.press` 로 1:1 대응한다. 키 열거값이 표준 도구의 키 이름과 **같은 철자**라 변환표가 없다 ([contracts/export-mapping §6](./contracts/export-mapping.md)) |

**위반 없음. Complexity Tracking 을 채우지 않는다.**

### 품질 게이트 대응

| 게이트 | 이 기능에서 |
|---|---|
| 1. 원칙 준수 | 재실행 경로 변경분(관찰 함수·마스킹)에 LLM 도달 경로가 없음을 테스트로 남긴다 |
| 2. 왕복 정합 | 기록 → 저장 → 제품 내 실행 → 내보내기 → 내보낸 테스트 실행을 **두 새 종류를 함께 넣어** 한 번 완주한다 (quickstart §7). 키 입력은 녹화 경로가 바뀌므로 이 게이트가 특히 중요하다 |
| 3. 테스트 | 도메인·**녹화기**·실행기·생성기 각각 단위 테스트 + 사용자 흐름당 통합 1건. 녹화기는 이번에 처음 변경되므로 헌법이 명시적으로 요구하는 대상이다 |
| 4. 비활성 테스트 금지 | 기존 테스트를 끄지 않는다. 입력 칸 대상 텍스트 검증이 여전히 실패하는 것은 **의도된 동작**이므로 그대로 둔다. **다만 FR-056 으로 녹화 결과가 달라지므로 그 기대값을 고치는 기존 테스트가 있을 수 있다** — 끄지 말고 새 기대값으로 고친다 |
| 5. 성공 지표 | 검증 작성·재실행 흐름에 영향. 실패하던 시나리오가 통과로 바뀌므로 Replay Success Rate 에 양의 방향 |

**Structure Decision**: 기존 구조를 그대로 쓴다. 새 모듈·새 패키지를 만들지 않는다. 이번
변경은 **이미 있는 두 축에 값을 하나씩 더하는 것**이고, 새 자리를 만들면 「검증 종류는
`domain/assertion.py`, Step 종류는 `domain/step.py` 에 있다」는 기존의 단일 지점이 흐려진다.

**녹화기가 이번에 처음 변경된다.** 023 의 검증 쪽은 녹화를 건드리지 않았지만 키 입력은
녹화가 출발점이다 — 그래서 위험 표에 녹화 관련 항목이 따로 있다.

## 구현 순서와 의존

```
① 도메인 — assertion.py 의 value + step.py 의 press·PressKey
      ↓ 스키마 재생성 (백엔드 → 프론트 타입)
   ┌──────────────── 두 갈래. 서로 독립이다 ────────────────┐
   │                                                        │
 [키 입력]                                          [입력값 검증]
   ②ᴋ 녹화 keydown + IME 판별                        ②ᵛ 실행 관찰 함수
   ③ᴋ 녹화 입력 Step 갱신 차단 (FR-056)              ③ᵛ 성질 판정 함수
   ④ᴋ 실행 · AI 도구 · 표시 문구                     ④ᵛ 두 작성 경로 연결
   │                                                  ⑤ᵛ 프론트 폼·문구
   │                                                  ⑥ᵛ 비밀번호 거절·마스킹
   └──────────────────────┬─────────────────────────────────┘
                          ↓
              ⑦ 생성기 (두 종류 함께)
                          ↓
              ⑧ 고정 대상 · 하위 호환 · 전량 검증
```

**①이 먼저인 이유**: 헌법의 교차 언어 스키마 의무 — DSL 스키마를 먼저 바꾸고 소비자가
따른다 (원칙 I). 프론트 타입이 ①에서 생성되므로 프론트 작업은 그전에 시작할 수 없다.

**②ᴋ 와 ③ᴋ 를 붙여 둔 이유**: ③ᴋ 는 키 입력 Step 의 존재를 전제한다. 「앞선 입력 Step 을
갱신하지 않는다」를 판단하려면 **방금 키가 눌렸다는 사실**을 알아야 하고, 그것은 ②ᴋ 가
만든다. 순서를 뒤집으면 무엇을 기준으로 막을지 알 수 없다.

**⑥ᵛ 를 뒤로 뺀 이유**: ②ᵛ 와 ③ᵛ 가 각각 동작한 뒤에 그 위에 얹는 층이다. 섞어서 만들면
마스킹 때문에 실패한 것인지 관찰이 틀린 것인지 가릴 수 없다. **그리고 이것이 유일한 새
보안 요구라 독립적으로 검증돼야 한다.**

**⑦ 을 합친 이유**: 생성기는 두 종류를 같은 파일에서 다루고, 모르는 종류에 예외를 던지므로
둘 중 하나만 반영하면 다른 쪽 정의가 든 테스트의 내보내기가 깨진다. 한 번에 한다.

| **AI 경로가 성질 판정을 건너뜀** | 화면에서는 거절되는데 AI 는 만든다 | 판정을 공용 함수로 두고 **두 경로 각각에 테스트**를 건다 |
| **비밀번호 관찰값 유출** | 실패한 실행 결과 파일에 평문이 남는다 | quickstart §6-3 의 `grep` 을 자동 검증으로도 만든다 |
| **`select` 값이 예상과 다름** | FR-033 안내 문구가 거짓이 된다 | 문구를 쓰기 전에 실측한다 (research R8) |
| **`contains` 내보내기 형태** | 제품과 내보낸 코드의 판정이 갈린다 | `expect.poll` 형태를 계약에 고정하고 왕복 정합으로 확인한다 |
| **부정 비교 + 값 관찰의 조합** | 021 의 관찰 루프가 값에서도 같게 도는지 미확인 | 통합 테스트 + quickstart §3 에서 실제로 돌린다 |
| **한글 조합 Enter 가 기록됨** ★ | **영문 검증은 전부 통과하는데 한글에서만 재실행이 어긋난다** | 브라우저의 조합 상태로 가른다 (추측 금지). **검증을 반드시 한글로 한다** (quickstart §10-3) |
| **Space 의 IME 동작이 Enter 와 다름** | 한글에서 Space 태그 추가가 어긋난다 | 실측한다 (research R10 미확인 항목). 다르면 계약 문서를 고친다 |
| **FR-056 이 기존 녹화 테스트를 깬다** | 입력 Step 의 기대값이 달라진다 | **끄지 말고 새 기대값으로 고친다** (헌법 게이트 4). 고친 것을 변경 기록에 남긴다 |
| **키 입력이 녹화에만 있고 AI 에 없거나 그 반대** | 원칙 I 위반 | `STEP_PRODUCING_TOOLS` 의 10:10 대응을 **기존 검사가 이미 고정한다** — 이쪽은 저절로 잡힌다 |
| **`press` Step 종류 누락** | Excel 내보내기·Step 목록 문구가 조용히 빈다 | data-model §10 의 「조용한 넷」을 작업 항목으로 분리한다 |

## 이번에 하지 않는 것

명시하지 않으면 구현 중에 범위가 번진다.

| 하지 않는 것 | 왜 |
|---|---|
| 두 작성 경로의 통합 | `build_assertion` 은 예외를 던지고 AI 경로는 `{"error"}` 를 돌려준다. 통합하면 모델이 보는 오류 형태가 바뀐다 — 이번 기능과 무관한 위험이고, 규칙 단일화는 공용 함수로 이미 달성된다 |
| 021 의 경고가 AI 경로에 없는 것 | **021 의 빈칸이지 023 의 결함이 아니다.** research R3 에 기록했고 `converge` 가 판단한다 |
| 체크 상태 검증 | 021 에서 범위 외. 이 검증으로 대신할 수 없다는 사실만 분명히 한다 |
| 손으로 넣는 Step 에 대상 지원 | 그 경로의 설계 전제를 바꾸는 별도 주제 |
| 기존 텍스트 검증의 자동 변환 | FR-041 — 뜻을 추측해 정의를 바꾸지 않는다 |
| `select[multiple]` 대응 | 제품과 내보낸 코드가 **같게** 동작하므로 원칙 V 는 지켜진다. 사용자의 뜻과 다를 수 있는 것은 별개 문제로 계약에 한계로 적었다 |
| Enter·Space·Tab·Escape 밖의 키 | 요구에 없다. 넓히는 것은 열거형에 값을 더하는 일이라 싸다 |
| 조합키 (Ctrl+A 등) | 키 하나와 형태가 다르다. 목록이 조합 폭발한다 |
| 문자 키를 한 글자씩 | 입력 Step 이 담당한다. 키로 쪼개면 research R10 의 IME 문제가 되돌아온다 |
| 키 입력의 결과 판정 | 「Enter 를 눌렀더니 태그가 생겼다」는 **검증 Step 이 따로** 맡는다. 동작과 판정을 한 Step 에 뭉치지 않는다 |
