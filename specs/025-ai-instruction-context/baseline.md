### ⚠️ 설계 문서의 추정치를 정정한다

`research.md` 초안은 관찰 한 번을 **25~35KB** 로 적었다. 실측은 **66.7KB** — **두 배다.**

요소당 289바이트가 나오는 이유는 한글 접근가능한 이름(UTF-8 3바이트/글자)과, 2026-09-11 에
더해진 구별용 필드들(`id`·`placeholder`·`label`·`context`)이다. 그것들은 필요해서 들어간
것이고 빼자는 말이 아니다 — **추정으로 설계를 세우면 안 된다는 사실의 예다.**

이 값이 뜻하는 것: 한 지시에 허용된 도구 호출 40회 중 관찰이 20회면 **약 1.3MB, 44만

## T031 — 관찰 범위 확대 후 (US3 구현 뒤)

### 상한(200)에 걸리는 화면

```
요소 수          : 200  (truncated=True)
판정별           : semantic 200, cursor 0
응답 전체 바이트  : 64,306
관찰 지연(중앙)   : 20.0 ms
```

**`cursor` 요소가 하나도 들어가지 못했다.** 설계대로다 — 확실한 것(`semantic`·`role`)을
앞에 두고 짐작으로 잡은 것을 뒤에 두므로, 상한에 걸리면 짐작한 쪽이 먼저 잘린다.

그 화면에서 사람이 클릭되는 `div` 를 가리키면 목록으로는 못 찾는다. **그래서
`find_by_text` 가 있고, `truncated: true` 가 그 사실을 알린다** (FR-041·FR-044).
두 장치가 이 상황을 받도록 설계한 것이고, 여기서 그 필요가 실측으로 확인됐다.

### 상한에 걸리지 않는 화면 — 순증가

의미 요소 40 + 클릭되는 `div` 30 (실제 관리 화면에 가까운 규모).

```
요소 70개  (semantic 40, cursor 30)
응답 전체        : 25,414 바이트
그중 cursor 몫   : 7,800 바이트 (31%)
확대 전 추정     : 17,614 바이트
증가율           : 1.44배
관찰 지연(중앙)  : 6.5 ms
```

**SC-010(2배 이내) 충족.** 지연도 문제되지 않는다 — `getComputedStyle` 을 전체 요소에
도는 비용을 걱정했는데(research R13 의 「확인 필요」), 6.5~20ms 로 관찰이 이미 쓰는
시간에 묻힌다. 2단계 후보를 미리 좁히는 최적화는 **하지 않았고 할 필요도 없었다.**

### 함께 확인된 것

- 조상·자손 중복 제거가 동작한다 — `<div>` 와 그 안의 `<span>` 중 `<div>` 만 실린다.
- 커서를 바꾸지 않는 설명 문구는 잡히지 않는다.
- `find_by_text` 가 글자 요소(`<span>`)와 반응 요소(`<div>`)를 갈라 돌려준다.
