## R1 — Tailwind 버전과 Vite 통합

**결정**: Tailwind CSS **v4** (조사 시점 최신 4.3.3) + `@tailwindcss/vite` 플러그인.
`postcss.config` 를 만들지 않는다.

**근거**:

v4 를 고르는 이유는 "최신이라서"가 아니라 **이 저장소의 제약과 맞물리기 때문**이다.

1. **CSS-first 설정.** v4 는 테마를 JS 설정 파일이 아니라 CSS 의 `@theme` 블록에서 정의한다.
   이 저장소의 정본은 이미 CSS 변수(`tokens.css`)다. v3 를 쓰면 CSS 변수 → JS 객체 →
   다시 CSS 로 도는 경로가 생기고, 그 경로 어딘가에 값을 손으로 적는 곳이 반드시 생긴다 —
   FR-001(값은 정본 한 곳에만)이 금지하는 것이다.
2. **CSS 변수 참조가 1급.** v4 의 테마 변수는 그 자체로 CSS 변수로 출력되며 `var()` 참조를
   전제로 설계됐다. 정본을 복제하지 않고 이름만 다시 붙이는 R2 의 방식이 v4 에서는 자연스럽고
   v3 에서는 우회다.
3. **Vite 플러그인이 공식.** Vite 6 를 쓰고 있으므로 PostCSS 체인을 새로 들이지 않는다.
   설정 파일이 하나 줄고, 이 저장소에 없던 도구(postcss)를 추가하지 않는다.

**버린 대안**:

| 대안 | 버린 이유 |
|---|---|
| Tailwind v3 + `tailwind.config.js` | 정본(CSS 변수)과 설정(JS)의 언어가 달라 값을 옮겨 적는 지점이 생긴다. FR-001 과 정면 충돌 |
| Tailwind v4 + PostCSS 플러그인 | 동작하지만 Vite 프로젝트에 PostCSS 설정을 새로 들일 이유가 없다 |
| CSS Modules / vanilla-extract | 사용자가 Tailwind 를 지정했다. 대안 평가 대상이 아니다 |

**✅ 검증됨 (T002 · 2026-09-10 · tailwindcss 4.3.3)**: `@theme inline` + `var(정본토큰)` 이
모든 확인 항목에서 의도대로 동작한다.

| 확인 항목 | 결과 |
|---|---|
| 기본 유틸리티 | `bg-pass` → `background-color: var(--pass)` — 정본을 직접 참조 |
| **불투명도 수식** | `bg-pass/50` → `color-mix(in oklab, var(--pass) 50%, transparent)`. **가장 걱정하던 부분이 참조를 유지한 채 동작한다** |
| 상태 변종 | `hover:bg-fail` `focus:ring-pass` `disabled:text-hair` 전부 `var(정본)` |
| 그림자·모서리·글꼴 | `shadow-e2`→`var(--e-2)` · `rounded-tok`→`var(--radius)` · `font-sans`→`var(--font-sans)` |
| **값 복제** | **0.** `#1A7F45` 가 산출 CSS 에 정확히 1회 등장하며 그것은 정본 정의(`--pass: #1A7F45`) 자체다 |
| 중간 변수 | `:root` 에 `--color-pass` 를 내보내지 않는다 — `inline` 이 의도대로 동작 |
| 임의값 | `basis-[460px]` → `flex-basis: 460px` 생성됨 |

**RK-1 해소.** R2 를 다시 정할 필요가 없다.

**⚠️ 스파이크가 찾은 별건**: Tailwind 의 `flex-1` 은 `flex: 1` 을 낸다. 기존 테스트가
기대하는 `flex: 0 0 460px` 를 그대로 표현하려면 임의값(`flex-[0_0_460px]`)이 필요하다.
T029(배치 표 출력 전환)에서 이 형태를 정해야 하며, **기존 계산값과 다른 축약형을 쓰면
시각이 미묘하게 달라진다** — `flex:1` 은 `flex:1 1 0%` 이고 `flex:0 0 460px` 와 다르다.

## R2 — 정본 토큰을 Tailwind 테마로 잇는 방법

**결정**: `@theme inline` 으로 정본 CSS 변수를 **참조**한다. 값을 옮겨 적지 않는다.

```css
/* frontend/src/theme/tailwind.css — 새 파일. tokens.css 를 건드리지 않는다 */
@import "tailwindcss";
@import "./tokens.css";

@theme inline {
  --color-pass: var(--pass);      /* 값이 아니라 참조 */
  --color-fail: var(--fail);
  /* … 정본 토큰 전부 */
}
```

**근거**:

- `tokens.css` 는 `scripts/extract_canon.py` 가 덮어쓰는 파일이다 (FR-002). 그 안에 Tailwind
  지시문을 넣으면 다음 추출에서 지워진다. 그래서 **별도 파일에서 정본을 `@import` 하고
  이름만 다시 붙인다.** 정본 파일은 이 작업 내내 손대지 않는다.
- `inline` 을 쓰는 이유: 없으면 Tailwind 가 자기 변수를 한 겹 더 만들어 `var(--color-pass)`
  → `var(--pass)` 의 이중 참조가 되고, 정본 값이 바뀌었을 때 어느 쪽을 보는지가 흐려진다.
  `inline` 은 유틸리티가 정본 변수를 직접 가리키게 한다.
- 매핑은 **이름 대응표일 뿐 값이 없다.** 값이 없으므로 정본과 어긋날 수가 없다 — 이것이
  FR-001·FR-016 을 구조적으로 만족시키는 방법이다. 규칙으로 금지하는 것보다 강하다.

**버린 대안**:

| 대안 | 버린 이유 |
|---|---|
| `tokens.css` 안에 `@theme` 를 직접 넣기 | `extract_canon.py` 가 덮어쓴다. FR-002 위반 |
| Tailwind 테마에 값을 직접 적기 | 정본이 둘이 된다. 이 기능의 존재 이유를 부정 |
| 임의값 문법(`bg-[#1A7F45]`)으로 그때그때 | 값 리터럴을 화면 코드로 되돌린다. 008 이 고친 문제의 재발 |

## R3 — 배치 계약 개정: 잃지 않아도 되는 것과 실제로 잃는 것

이 항목이 이번 계획에서 **가장 중요하다.** 사용자에게 선택지를 제시할 때 "S-12 를 막던
컴파일 시점 강제를 잃는다"고 설명했는데, 조사해 보니 **그 설명은 과했다.**

**결정**: `Record<Phase, …>` 표를 그대로 두고, **표의 출력만** 인라인 스타일 객체에서
클래스 문자열로 바꾼다. 표 → 클래스 매핑도 전수 `Record` 로 둔다.

```ts
// lib/layout.ts — 표는 손대지 않는다. 컴파일 시점 강제가 그대로 남는다 (FR-020a)
export const VERTICAL_SPLIT: Record<Phase, VerticalSplit> = { /* 기존 그대로 */ };

// 새로 더하는 것은 「표의 값 → 클래스」 대응뿐이다.
// VerticalSplit 이 유한한 합집합 타입이므로 이 Record 도 전수를 컴파일 시점에 요구한다.
const SPLIT_CLASS: Record<VerticalSplit, string> = {
  fill: "flex-1 min-h-0",
  content: "flex-none",
};
```

**FR-020 의 두 성질을 어떻게 지키는가**:

| 성질 | 개정 후 어떻게 남는가 |
|---|---|
| (a) 국면 누락 불가 | `Record<Phase, …>` 를 **그대로 둔다.** 국면을 추가하면 표가 컴파일되지 않는다. 아무것도 잃지 않는다 |
| (b) 배치 판단의 단일 소재지 | `Workbench` 가 국면으로 한 번 조회해 자식에 내려주는 구조를 **그대로 둔다.** 내려보내는 것이 `style` 객체 대신 `className` 문자열로 바뀔 뿐이다. `TargetPane`·`WorkArea` 는 여전히 자기 크기를 모른다 |

**그러면 실제로 잃는 것은 무엇인가**: 하나뿐이다 —
**"표의 값이 DOM 에 도달했는지"를 `element.style.flex` 로 읽던 통로.**
이것은 설계 성질이 아니라 **검증 수단**이다. R4 가 이 수단을 대체한다.

이 구분이 중요한 이유: 계약 개정을 "S-12 가 다시 나도 어쩔 수 없다"로 받아들이면 그 결함이
실제로 돌아온다. 개정되는 것은 *표현 방식*이고, 표현을 강제하던 *구조*는 개정 대상이 아니다.
`visual-language.md` §2 의 허용 목록은 사라지지만, `layout.ts` 의 표는 남는다.

**버린 대안**:

| 대안 | 버린 이유 |
|---|---|
| 표를 없애고 각 컴포넌트가 자기 클래스를 지정 | 정확히 S-12 를 되살린다. FR-020b 위반 |
| 표의 값을 `data-*` 속성으로도 내보내 테스트가 읽게 | 같은 값이 클래스와 속성 두 곳으로 나간다. 어긋나면 **테스트가 거짓말을 한다** — 통과하는데 화면은 틀린 상태가 가능해진다. 사용자에게 선택지로 제시했으나 채택되지 않았고, 채택됐어도 이 위험을 적었을 것이다 |

## R4 — `.style.` 단언 45개+ 를 무엇으로 대체하는가

**결정**: **3겹**으로 나눈다. 하나를 셋으로 쪼개는 것이며, 합치면 이전보다 촘촘하다.

| 겹 | 무엇을 확인하나 | 어디서 |
|---|---|---|
| ① 표 검증 | 배치 **판단**이 옳은가 (한 국면에서 두 자리가 동시에 `fill` 일 수 없다 등) | `lib/layout.ts` 의 순수 단위 테스트. 이미 존재 (`VerticalSplit.test.ts`) |
| ② 도달 검증 | 표의 값이 **그 DOM 요소까지** 갔는가 | `expect(el).toHaveClass(...)` — 기존 `.style.flex` 단언이 있던 자리 |
| ③ 실재 검증 | 그 클래스 이름이 **실제로 CSS 를 만들어내는가** | 빌드 산출 CSS 를 읽어 클래스 존재를 확인하는 새 가드 1개 |

**근거**:

기존 `expect(panel.style.flex).toBe("0 0 460px")` 한 줄은 세 가지를 한꺼번에 확인하고 있었다 —
판단이 옳고, 값이 도달했고, 그 값이 실재한다는 것. 클래스로 바꾸면 ②만 남고 ③이 사라지는
것이 문제다. **`toHaveClass("basis-[460px]")` 는 오타가 있어도 통과한다** — 클래스가 붙기만
하면 되고, Tailwind 가 그 이름으로 CSS 를 만들었는지는 묻지 않기 때문이다.

③ 이 그 구멍을 막는다. 빌드 산출 CSS 에서 사용된 클래스를 찾을 수 없으면 실패시킨다.
이것은 오타뿐 아니라 **Tailwind 가 클래스를 발견하지 못하는 경우**(문자열을 조립해 만든
클래스명은 스캔되지 않는다)도 잡는다 — 이 함정은 실제로 흔하고, 잡지 않으면 화면이 조용히
스타일 없이 렌더된다.

**테스트를 지우지 않는다** (FR-013 · 헌법 Quality Gate 4). 13개 파일의 단언은 판정 *방법*이
바뀔 뿐 **무엇을 검증하던 테스트인지는 바뀌지 않는다.** 각 파일에 무엇을 왜 바꿨는지 적는다.

**✅ 검증됨 (T003 · 2026-09-10)**: 테스트 안에서 Tailwind CLI 를 한 번 돌려 산출 CSS 를
만들고 대조한다. 실측 — 실제 `src/**/*.tsx` 전체 대상 **Tailwind 처리 54ms**(프로세스 시작
포함 1.2초). 테스트 한 번에 감당할 수 있다.

**가드가 보는 것은 둘이다**:

1. 코드의 정적 클래스 문자열이 산출 CSS 에 실재하는가 — 오타를 잡는다
2. 클래스 이름을 **문자열 조립으로 만드는 곳이 없는가** — `` `bg-${tone}` `` 같은 것.
   Tailwind 는 이런 것을 스캔하지 못해 CSS 를 만들지 않고, 화면은 조용히 무스타일이 된다.
   ①만으로는 이 실패를 못 잡는다 (조립된 문자열은 추출 대상에 없으므로).

**S2 해소.**

## R5 — 시각 동일성을 무엇으로 판정하는가

**결정**: 기존 L1 대조 파이프라인의 **방법론을 재사용**해 「전환 전 ↔ 전환 후」 대조(L2)를
만든다. 새 의존성을 들이지 않는다.

**근거**:

명세는 "스크린샷 회귀 도구가 없으므로 사람 눈에 의존한다"를 한계로 적었다. 조사에서
그것이 **부분적으로 틀렸음**이 드러났다. `scripts/design_render.py` 가 이미
chromium(backend 의 playwright)으로 두 시트를 같은 마크업에 적용해 `getComputedStyle` 을
읽고 대조한다. 픽셀이 아니라 **계산된 스타일 값**을 비교하므로 표기 차이에 걸리지 않고
사람이 채울 칸이 없다.

같은 방법을 대상만 바꿔 쓴다:

```
L1 (기존)  확정 디자인 시트  ↔  tokens.css          — 정본이 디자인과 같은가
L2 (신설)  전환 전 화면      ↔  전환 후 화면        — 전환이 모습을 바꾸지 않았는가
```

전환 **전** 커밋에서 기준을 한 번 뜨고(`git worktree` 로 같은 저장소의 이전 상태를 꺼낸다),
전환 후 같은 화면을 렌더해 비교한다. L1 이 하듯 입력의 digest 를 보고서에 담아 **낡은
보고서로 통과할 수 없게** 한다.

### ⚠️ T004 가 찾은 것 — 의미 클래스 해체가 L1 대조를 무너뜨린다

`design_render.py` 를 읽고 나서야 보인 문제다. **계획 단계에서 놓쳤다.**

이 스크립트는 형태를 **클래스 이름으로** 지정한다:

```python
FORMS = ["btn", "btn primary", "chip pass", "srow fail", "op danger", …]
```

그 이름의 요소를 확정 디자인 시트와 정본 시트에 각각 적용해 `getComputedStyle` 을 비교한다.
**의미 클래스를 전면 해체하면 `tokens.css` 에서 `.btn` 이 사라지고, 확정 디자인 쪽에는
남아 있으므로 대조가 통째로 불일치가 된다.** L1 은 무의미해지고 FR-002(정본 추출 흐름이
전환 후에도 동작해야 한다)가 깨진다.

**결정**: L1 의 측정 **대상**을 옮긴다. 「클래스가 그리는 것」 → 「부품이 그리는 것」.

| | 지금 | 전환 후 |
|---|---|---|
| 기준 | `Language.dc.html` 의 `<style>` + `class="btn primary"` | **같음** (확정 디자인은 바뀌지 않는다) |
| 관측 | `tokens.css` + `class="btn primary"` | **`ui/Button` 을 렌더한 결과** |
| 비교 | 두 `getComputedStyle` | **같음** |

확정 디자인 쪽은 손대지 않는다 — 그것이 기준이기 때문이다. 바뀌는 것은 관측 쪽뿐이고,
"우리 부품이 확정 디자인과 같은 것을 그리는가"라는 **질문 자체는 그대로다.** 오히려
지금보다 강해진다: 지금은 시트끼리 비교하므로 화면 코드가 그 클래스를 실제로 쓰는지는
묻지 않지만, 부품을 렌더하면 그것까지 함께 확인된다.

**대가**: React 부품을 렌더해야 하므로 Python 스크립트가 빌드 산출물을 거쳐야 한다.
`FORMS` 목록도 클래스 조합에서 부품+속성 조합으로 다시 써야 한다. **작업 2건이 늘어난다**
(T014a·T014b).

**대안으로 버린 것**: `tokens.css` 에 의미 클래스를 「대조 전용」으로 남기기 — 화면이 쓰지
않는 죽은 정의가 되고, 그것이 실제 화면과 일치한다는 보장이 사라진다. 대조가 통과해도
아무것도 말하지 못하는 가짜 초록이다.

**한계를 정직하게**: 이것은 픽셀 비교가 아니다. 계산된 스타일이 같아도 실제 배치가 다를 수
있는 경우(예: 겹침 순서, 스크롤 위치)는 잡지 못한다. 따라서 L2 는 사람 대조를
**대체하지 않고 좁힌다** — 사람은 L2 가 통과한 뒤 흐름을 본다.
`docs/PENDING-HUMAN-VERIFICATION.md` 에 판정 항목을 등록하는 기존 관행을 그대로 쓴다.

**버린 대안**:

| 대안 | 버린 이유 |
|---|---|
| Playwright 스크린샷 픽셀 비교 도입 | 명세 범위 밖(새 테스트 의존성). 폰트 렌더 차이로 거짓 실패가 많아 유지 비용이 크다 |
| 사람 눈 대조만 | 39개 파일 × 여러 상태를 사람이 다 볼 수 없다. 놓친 것이 회귀로 남는다 |
| 아무 검증 없이 "테스트 통과했으니 됐다" | 기존 테스트는 배치와 일부 시각 속성만 본다. 전환의 대부분을 덮지 못한다 |

## R6 — 전환 순서: 부품 먼저, 배치 나중

**결정**: **2단계**로 간다. ① 의미 클래스 109개 → 부품 컴포넌트, ② 배치 인라인 455곳 → 클래스.
각 단계 안에서는 **부품/화면 하나씩** 옮기고 매번 테스트를 돌린다.

**근거**:

- **부품이 먼저인 이유**: 화면은 부품의 조합이다. 부품을 먼저 세우면 화면 전환은 치환이 된다.
  반대로 화면부터 가면 같은 버튼이 화면마다 다른 유틸리티 조합을 얻고, 그것이 SC-010
  (부품 종류별 정의가 한 곳)을 깨뜨린다. 한 번 흩어진 것을 나중에 모으는 비용이 더 크다.
- **두 단계를 섞지 않는 이유**: 시각(부품)과 배치는 깨졌을 때 증상이 다르고 원인 추적도
  다르다. 섞으면 한 커밋에서 회귀가 났을 때 어느 쪽인지 가릴 수 없다.
- **중간 상태가 깨지지 않는가**: 깨지지 않는다. Tailwind 유틸리티와 기존 `.btn` 류 클래스는
  공존할 수 있다. 부품 하나를 옮기는 동안 나머지는 옛 클래스를 계속 쓴다. 다만 **같은 요소에
  둘이 동시에 걸리면 우선순위 다툼**이 생기므로, 한 요소는 한 체계만 쓰도록 옮긴다
  (R7 의 충돌 규칙).

**버린 대안**:

| 대안 | 버린 이유 |
|---|---|
| 화면 단위로 통째 전환 | 부품 일관성이 깨진다 (SC-010). 화면 하나가 큰 것(TestList 55곳·ProjectSetup 55곳)은 커밋이 거대해져 회귀 추적이 불가능 |
| 전부 한 번에 | 455 + 109 를 한 커밋에 담으면 되돌릴 지점이 없다 |
| 속성별로 (색 먼저, 간격 다음…) | 한 요소가 여러 단계에 걸쳐 반쯤 전환된 상태로 오래 남는다. 우선순위 다툼이 상시화된다 |

## R7 — 우선순위 충돌 규칙

**결정**: 전환 중인 요소는 **한 체계만** 쓴다. 기존 의미 클래스와 Tailwind 유틸리티를 같은
요소에 겹치지 않는다. 겹침이 불가피한 과도기에는 유틸리티가 이긴다.

**근거**: `tokens.css` 주석이 기록한 두 번의 실패가 이 규칙의 근거다 — `.tint-*` 가
특이도 싸움에서 져 "모든 토스트가 흰색"이 됐던 일, 기준 크기(`flex-basis`)가 `height` 를
이겨 두 줄 알림이 잘렸던 일. 둘 다 **두 규칙이 같은 속성을 다툰** 결과다. Tailwind 를 얹으면
다투는 규칙이 하나 더 늘어난다. 겹치지 않는 것이 우선순위를 이해하는 것보다 안전하다.

FR-018 은 규칙의 문서화와 테스트를 요구한다. 테스트는 "한 요소에 의미 클래스와 유틸리티가
동시에 있지 않다"를 세는 형태가 된다 — 전환이 끝나면 의미 클래스가 사라지므로 이 가드는
**전환 진행률 계기이기도 하다.**

## R8 — 의미 클래스 109개 행선지 대응표

**결정**: `specs/015-tailwind-css-migration/contracts/class-migration.md` 에 표로 남긴다.
사람이 읽는 문서이자 **기계가 세는 대상**이다.

각 행: `클래스 이름 | 쓰이던 곳 수 | 행선지(컴포넌트명 또는 유틸리티 조합) | 상태`

**근거**: SC-009 가 "미상 0건"을 요구한다. 109개를 머릿속으로 추적할 수 없고, 전환이
여러 커밋에 걸치므로 진행 상태를 담을 자리가 필요하다. 이 표가 없으면 "다 옮겼다"를
확인할 방법이 없다 — 남은 클래스를 세는 것으로는 *어디로 갔는지*를 알 수 없다.

**기계가 세는 부분**: `tokens.css` 에 남은 의미 클래스 수와 이 표의 「미완료」 행 수가
일치하는지 검사한다. 표만 갱신하고 코드를 안 옮기거나 그 반대인 경우를 잡는다.
