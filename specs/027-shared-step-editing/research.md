# Research — 027 Step 편집면과 조작 배선을 한 곳으로

007 이 멈춘 자리에서 이어간다. 아래는 **무엇을 어디로 옮길 것인가**와 **옮긴 뒤 다시
갈리지 않게 하는 법**을 실제 코드에서 확인한 기록이다.

---

## R1 — 조작 배선을 어떤 모양으로 모으는가

**결정**: 화면이 **「내가 할 수 있는 일」의 묶음**을 제공하고, 공통 자리가 그것을 조작에
잇는다. 신설 모듈 `frontend/src/lib/actionWiring.ts`.

```
화면 → { deleteStep, moveStep, save, runAll, … }   (능력 묶음)
                    ↓
        actionWiring 이 조작 → 능력으로 잇는다
                    ↓
        runAction(actionId) 하나가 나온다
```

**왜 이 모양인가** — spec 의 세 요구가 동시에 걸린다.

| 요구 | 이 모양이 만족시키는 방식 |
|---|---|
| FR-003 해당 없음이면 제공 안 해도 됨 | 능력이 **선택적**이다. 없으면 그 조작은 이어지지 않는다 |
| FR-004 화면마다 다른 일 | 능력의 **구현**이 화면마다 다르다. 「저장」이 편집에서는 정의 쓰기, 세션에서는 세션 저장 |
| FR-005 화면마다 다른 선행 확인 | 능력 구현 안에서 처리한다 — `EditView` 의 「먼저 저장하고 열기」가 그 자리에 남는다 |

**FR-006 이 저절로 지켜진다.** 이 모듈은 국면을 인자로 받지 않는다 — 받을 이유가 없다.
어느 조작이 언제 쓸 수 있는지는 조작표가 정하고, 이 모듈은 **눌린 조작을 잇기만** 한다.

**기각한 대안**:

- **어댑터의 `switch` 를 공통 함수로 옮기고 국면으로 분기** — 국면 판정이 조작표 밖에
  하나 더 생긴다. 011 이 표를 만든 이유를 무너뜨린다.
- **조작마다 컴포넌트를 만들어 자기 동작을 갖게** — 조작이 화면 상태(고른 Step·미저장
  편집)를 알아야 하므로 결국 화면이 그것을 주입하게 되고, 층만 하나 더 는다.

## R2 — 옮긴 뒤 다시 갈리지 않게 하는 법

**결정**: 화면이 **자기가 이어 둔 조작 목록을 DOM 에 드러낸다.** 검사는 화면을 그려서
그 목록을 조작표와 대조한다.

**왜 DOM 인가** — FR-016 이 「목록을 손으로 적어 두고 대조하지 말라」를 요구한다.

| 방법 | 왜 아닌가 |
|---|---|
| 「어느 조작이 어느 화면에 있어야 하는가」 목록을 검사에 적는다 | 그 목록이 **세 번째 진실**이 된다. 기능이 늘 때마다 고쳐야 하고, 고치지 않으면 거짓으로 통과한다 |
| 어댑터 소스를 파싱해 능력 키를 읽는다 | 소스 모양에 묶인다. 변수로 뽑거나 조건부로 넘기면 파서가 놓친다 |
| 활성인 버튼을 전부 눌러 본다 | 부수효과가 크고 느리다. 한 번 누르면 상태가 바뀌어 다음 클릭이 다른 조건이 된다 |

DOM 속성은 **렌더 결과**이므로 소스 모양과 무관하고, 이 저장소가 이미 쓰는 방식이다
(`data-action`·`data-cell`·`data-workbench-step-panel`).

### 기존 검사와 무엇이 다른가

`frontend/tests/CapabilityUI.test.tsx` 는 이미 각 국면을 **실제로 그려서** 조작표와
대조한다. 그러나 재는 것이 다르다.

| | 재는 것 | 026 사고를 잡았을까 |
|---|---|---|
| 기존 `CapabilityUI` | 조작이 화면에 **있는가** (`data-action`) | **아니다** — 버튼은 있었다 |
| 027 이 더할 검사 | 그 조작이 **이어져 있는가** (동작이 있는가) | 그렇다 |

026 의 `ai.stepEdit` 은 `EditView` 에 버튼도 있었고 배선도 있었다. 그때의 결함은
「자리가 틀렸다」였고 그것은 다른 검사가 잡았다. **이 검사가 잡는 것은 그다음 단계의
사고다** — 버튼이 여러 화면에 뜨는데 한 화면에서만 동작하는 경우.

## R3 — Step 편집면은 어느 쪽이 정본인가

**결정**: `frontend/src/components/StepEditFields.tsx` 를 **정본으로 삼는다.**
`StepDetail.tsx` 의 `ownFields` 갈래를 걷어내고 그 자리에서 `StepEditFields` 를 쓴다.

**근거** — 두 후보를 실제로 읽고 비교했다.

| | `StepEditFields` (178줄) | `StepDetail` 의 `ownFields` 갈래 (646줄 중 일부) |
|---|---|---|
| 하는 일 | **편집면 하나** | 결과·대상 정보·조작까지 함께 |
| FR-010(판정이 한 곳) | **이미 지킨다** — docstring 이 「판정하지 않는다」를 명시하고 생성된 타입의 판별자를 쓴다 | Step 종류를 자기가 본다 |
| FR-011(읽기 전용) | **이미 있다** (`editable` prop) | 없다 |
| 민감 값 처리 | 참조는 읽기 전용, 평문이 들어올 자리 없음 | 별도 |

**작고 한 가지만 하는 쪽이 이미 요구를 지키고 있다.** 큰 쪽으로 합치면 FR-010·FR-011 을
새로 만들어야 하고, 646줄이 더 커진다.

**덤으로 추상이 줄어든다.** `Workbench` 의 `stepDetailOwnFields` 와 `stepDetailExtra` 가
필요 없어진다 — 「공용 편집면을 끄고 자기 것을 끼운다」는 우회가 사라지기 때문이다.
헌법의 단순성 규칙이 요구하는 방향이며, 이 증분이 **층을 늘리지 않는다는 증거**다(R7).

## R4 — 결과 화면에 편집면을 더할 것인가

**결정**: **더하지 않는다.** FR-011(읽기 전용 표현)은 `StepEditFields` 가 이미 갖고 있으
므로 요구는 충족되지만, 결과 화면에 편집면을 **새로 그리지는 않는다.**

**왜** — spec 의 「범위 밖」이 「결과 화면에 편집 기능을 더하는 것」을 명시한다. 지난
실행의 기록은 고치는 대상이 아니다. 통합의 값은 **두 편집면이 하나가 되는 것**에서 이미
나오고, 셋째 화면에 없던 것을 더하는 것은 이 증분의 목적이 아니다.

능력은 남겨 둔다 — 나중에 필요해지면 `editable={false}` 로 쓸 수 있다.

## R5 — 13개 조작을 어떻게 옮기는가

**결정**: **한 번에 옮기지 않는다.** 능력 묶음과 배선 모듈을 먼저 세우고, 조작을
무리 지어 옮기며 무리마다 검증한다.

무리의 기준은 **같은 종류의 일**이다.

| 무리 | 조작 | 왜 함께 |
|---|---|---|
| 1 | `step.delete` · `step.moveUp` · `step.moveDown` | Step 하나에 대한 편집. 가장 단순하고 부수효과가 작다 |
| 2 | `step.deleteSelected` · `step.deleteAfter` · `step.insertManual` | 여러 Step·삽입. 확인 대화가 끼어 있다 |
| 3 | `run.all` · `run.from` · `result.show` · `nav.back` | 화면을 옮기는 일. 동작이 화면마다 다르다(FR-004 의 시험대) |
| 4 | `save` · `step.recordStart` · `step.addNaturalLanguage` | 화면마다 선행 확인이 다르다(FR-005 의 시험대) |

**FR-022(중간 상태 공존)가 이것을 허용한다.** 옮기지 않은 조작은 어댑터의 `switch` 에
그대로 남아 있고, 배선 모듈이 처리하지 못한 조작은 기존 경로로 떨어진다. 사용자에게는
차이가 없다.

무리 3·4 를 뒤에 둔 이유는 **거기서 설계가 시험되기 때문**이다. 앞의 둘이 쉽게 옮겨진다고
설계가 옳다는 뜻이 아니다.

## R6 — 007 이 세운 것과 어긋나지 않는가

**확인한 것**: 007 `Workbench` 의 머리말이 이렇게 적고 있다.

> **이 컴포넌트는 표시만 한다.** 데이터를 읽지 않고 명령을 만들지 않는다. 국면 어댑터
> (`SessionScreen`·`ResultView`·`EditView`)가 `WorkbenchModel` 을 만들어 넘긴다 —
> 소유와 표시를 나눈 것이 이 라운드의 구조적 수정이다 (research R2).

**027 은 이 문장을 바꾸지 않는다.** 여전히 어댑터가 소유하고 `Workbench` 가 표시한다.
바뀌는 것은 **어댑터가 소유한 것 중 셋이 똑같이 갖고 있던 부분**이 한 자리로 가는 것이다.

007 이 「소유를 합친다」를 하지 않은 것은 실수가 아니라 **그 라운드의 범위**였다. 027 은
그 범위를 이어받는다.

## R7 — 통합이 층을 늘리기만 하는 것은 아닌가

헌법의 단순성 규칙이 「원칙에 요구되지 않는 복잡도는 정당화하거나 제거한다」로 적혀 있다.
이 증분이 그것에 걸리는지 따졌다.

| | 는다 | 준다 |
|---|---|---|
| 모듈 | `lib/actionWiring.ts` 1개 | — |
| 개념 | 「능력 묶음」 1개 | — |
| 중복 구현 | — | 조작 13개 × 2벌 |
| 편집면 | — | 2벌 → 1벌 |
| `Workbench` props | — | `stepDetailOwnFields` · `stepDetailExtra` 2개 |

**늘어나는 것은 모듈 하나와 개념 하나이고, 줄어드는 것은 중복 구현 13쌍과 편집면 한 벌과
우회 props 둘이다.** 정당화된다.

**실패의 정의도 적어 둔다**: 배선 모듈이 국면을 알기 시작하거나, 능력 묶음이 화면마다
다른 모양이 되기 시작하면 이 증분은 층만 하나 더한 것이 된다. 그때는 되돌리는 것이 맞다.

## R8 — 검증은 무엇으로 도는가

```bash
cd backend  && bash scripts/test-backend.sh
cd backend  && uv run ruff check src/ tests/
cd backend  && uv run lint-imports
cd frontend && npx vitest run
cd frontend && npx tsc --noEmit
```

**이 증분에서 특히 봐야 할 검사** — 전부 프론트다. 백엔드는 건드리지 않는다.

| 검사 | 무엇을 지키는가 |
|---|---|
| `CapabilityCoverage.test.ts` | 조작표에 빈칸이 없다 (011) |
| `CapabilityUI.test.tsx` | 표가 말한 조작이 화면에 있다 (007 SC-004) |
| `ScreenSweep.test.ts` | 화면이 깨지지 않았다 (017) |
| `VisualLanguage`·`ClassExistence` | 겉모습이 바뀌지 않았다 (008) |
| 006·009·011·016·026 의 화면 검사 | 각 기능의 흐름이 그대로다 |

**SC-007(사용자가 보는 모습이 달라지지 않는다)이 이 증분의 안전장치다.** 겉모습이 바뀌면
그것은 이번 작업의 결과가 아니라 사고다.
