# 004 판정 결과 — 실행 속도 조절과 로딩 대기

**Date**: 2026-09-07 | **Spec**: [spec.md](./spec.md) | **Tasks**: [tasks.md](./tasks.md)

사용자가 보고한 두 증상을 고쳤다. 원인이 서로 달랐고, **한쪽은 예상과 달랐다.**

## 무엇이 실제 원인이었나

보고는 "요소가 로딩되기 전에 없다고 에러가 난다" 였다. 자연스러운 추측은 **대기 시간이
짧다**는 것이다. 그 추측은 틀렸다.

Phase 0 에서 실제 브라우저로 재현해 확인했다 (research R1).

```
2초 뒤 목록을 그리는 화면, 대기 예산 5초
  최상위 후보(testId)가 맞는 경우      → 통과
  하위 후보(role)로만 맞는 경우        → 5004ms 실패   ← 보고된 증상
  같은 조건에서 모든 후보를 100ms 폴링  → 2089ms 통과
```

예산은 충분했다. `resolve()` 가 **최상위 후보 하나에만 예산 전체를 걸었기 때문에** 다른
후보가 1초 뒤에 맞더라도 한 번도 다시 확인되지 않았다. 예산을 15초로 올려도 결과는 같고
실패까지 걸리는 시간만 3배가 됐을 것이다.

같은 측정에서 **보고되지 않은 두 번째 결함**이 드러났다 (research R2).

```
로딩 중 같은 텍스트 스켈레톤 2개
  count()==1 엄격 검사   → 매칭 없음 (count=2)
  3단계 .first 폴백      → 28ms "통과", 스켈레톤을 채택
```

`locator.first.wait_for(attached)` 는 후보가 여러 요소를 매칭하면 즉시 반환한다. 1~2단계의
엄격 검사가 3단계에서 무효화되는 구조적 모순이었고, 결과는 **잘못된 요소에 대해 테스트가
통과하는 것**이다 — 이 코드베이스가 스스로 "실패보다 나쁜 결과" 라고 부르는 상황이다.

## 설계에서 분명히 한 것

**보임 여부는 *언제* 채택할지만 정하고 *무엇을* 채택할지는 정하지 않는다.**

폴링 중 보이는 하위 후보를 보이지 않는 상위 후보보다 먼저 잡으면, 기록된 식별 정보가
가리키는 것과 다른 요소를 조작하게 된다 — 헌법 원칙 IV 가 막으려는 것이 정확히 그것이다.
그래서 채택은 언제나 우선순위 순이고, 보임은 "더 기다릴지" 만 결정한다.

예산이 `MIN_ACTION_TIMEOUT_MS`(250ms)만 남으면 보이지 않는 매칭도 채택한다. 보이지 않는
것이 **정상인** 대상이 있기 때문이다 — `hidden` 검증, 화면 밖 입력란. 보임을 필수 조건으로
만들었다면 그런 Step 이 전부 깨졌을 것이다 (FR-119).

**`한 스텝씩` 은 새 상태를 만들지 않는다.** 기존 `PAUSED` 에 들어가므로 편집·이어하기·중지
규칙이 이미 검증된 경로를 그대로 쓴다. 사용자가 직접 누른 일시정지와의 구별은 상태가 아니라
세션의 속도로 한다 — 상태가 같기 때문이다.

**속도는 `~/.config/itb/preferences.json` 에 있다.** 프로젝트 파일에 넣으면 개인 취향이 팀
저장소에 커밋되고, 원칙 V 가 "사용자가 버전 관리하는 자산" 이라 부르는 트리를 오염시킨다.

## 의도한 하위 호환 변경

**기본 속도가 `보통`(Step 간 500ms)이다.** `빠름` 이 004 이전 동작이지만 기본으로 삼지
않았다 — 사용자가 겪는 문제가 "기본이 너무 빠르다" 이므로, 기본이 현재 동작이면 이 기능이
있어도 아무것도 달라지지 않는다.

**무인 실행은 `pacing: "fast"` 를 명시해야 한다.** 이것이 실제로 물렸다: 성능 회귀 테스트가
간격 500ms 를 "제품 오버헤드" 로 계산해 p95 가 50ms 목표를 336ms 로 넘겼다. 간격은 사람이
따라오라고 일부러 준 시간이지 제품이 낭비한 시간이 아니므로 측정을 `fast` 로 고정했다.
같은 함정이 사용자의 CI 에도 있으므로 `docs/DEVELOPMENT.md` 에 적었다.

## 남은 한계 (SC-008 부분 충족)

**내보낸 Playwright 테스트는 다후보 폴링을 하지 않는다.** 생성기는
`ordered_strategies()[0]` 하나로 코드를 만들기 때문이다. 따라서 "제품 안에서는 하위 후보로
통과했지만 내보낸 테스트에서는 최상위 후보로만 시도한다" 는 차이가 남는다.

이 차이는 **004 가 만든 것이 아니다.** 001 부터 존재했고, 내보내기 자체가 아직 릴리스 게이트
항목이다. 004 는 그 차이를 **넓히지 않는 것**까지 책임졌다:

- 대기 예산이 생성 코드에 그대로 반영된다 (`test_generator.py` 3건이 고정)
- 생성기에 대기 시간 상수가 박히지 않았음을 테스트로 확인한다 — 값이 두 곳에 있으면
  한쪽만 바뀌는 날이 온다
- 폴링 정책을 `itb.locator.strategy` (Runner·Generator 공유 지점)에 문서로 남겼다

**회수는 001 의 릴리스 게이트 항목에 한 줄을 더하는 것으로 등록했다** — 새 게이트를 만들지
않았다. 같은 미구현이 두 게이트로 세어지면 회수 판정이 흐려진다 (plan Complexity Tracking).

**속도는 AI 작성 중에는 걸리지 않는다.** 간격과 자동 일시정지는 `REPLAYING` 상태에만
적용되는데, AI 작성 경로는 `RunnerTask` 를 쓰지 않기 때문이다 — 작성 루프는 판단과 실행이
한 덩어리로 붙어 있어서 "Step 을 실행하는 구간" 을 따로 떼어낼 자리가 없다.

spec 엣지 케이스의 요구("AI 가 만든 Step 을 실행하는 구간에 적용된다")는 **저장된 AI 테스트를
재실행할 때** 충족된다 — 그때는 `REPLAYING` 이고 사람이 만든 테스트와 완전히 같은 경로를
지난다(헌법 원칙 I). 작성 중에도 적용하려면 작성 루프의 재설계가 필요하며, 이번 범위 밖이다.

## 검증 절차

quickstart §5 의 화면 절차를 **실제 서버로 수행**했다 (T069). 자동 테스트가 못 보는 것을
확인하는 것이 목적이다.

```
[5] 취향 기본값            : normal
[1] 세션 생성 (slow)       : 201, pacing = slow
[2] 실행 중 변경 → fast    : 200, pacing = fast
[4] 재조회 시 속도 복원     : fast
[5] 변경 후 취향           : fast
[5] 새 세션 기본 속도       : fast          ← FR-109 성립
[6] 시간 초과 실패의 안내   :
    ELEMENT_NOT_READY  [blocked] 대상 화면이 느릴 수 있습니다. 실행 속도를 '느림'으로
                                 낮춰 화면을 확인하거나, Step 상세에서 대기 시간을
                                 늘린 뒤 그 Step부터 다시 실행하세요.
    ELEMENT_AMBIGUOUS  [blocked] 이 식별 정보가 더 이상 요소 하나를 가리키지 않습니다.
                                 Step 상세에서 대상을 다시 집으세요.
    STEP_FAILED        [blocked] 대상 화면이 녹화 때와 같은지 확인하고, 다르면 그
                                 Step의 대상을 다시 집으세요.
```

세 안내가 서로 다르다는 것이 FR-122·FR-123 의 요구다. 특히 `ELEMENT_NOT_READY` 에
`STEP_FAILED` 의 "대상을 다시 집으세요" 를 쓰면, 화면이 느렸을 뿐인 사용자를 고칠 것이 없는
정의로 보낸다.

검증이 사용자 머신에 만든 것(임시 프로젝트·취향 파일·레지스트리 항목)은 전부 정리했다.
