# UI 계약 — 통합 작업 화면과 국면별 조작 권한

**기능**: 007 · 요구사항 FR-217 ~ FR-255
**성격**: 이 문서는 **계약**이다. 화면은 여기 적힌 것만 따르고, 여기 없는 판단을 화면에서
하지 않는다. REST 계약이 서버와 클라이언트 사이의 약속이듯 이것은 요구사항과 화면 사이의
약속이다.

> **2026-09-08 — 치수가 008 로 갱신됐다.** 층의 **구성·순서·개수**와 폭 셋(460 · 640 ·
> 1440)은 바뀌지 않았다. 바뀐 것은 **세로**뿐이다 — 시각 언어가 v1「브루탈리스트」에서
> v2「계기판」으로 바뀌면서 경계 비용이 요소당 11px 에서 1px 로 내려갔기 때문이다.
> 기준 디자인은 `docs/design/008-visual-language/` 이고, 폐기된 v1 은
> `docs/design/_retired/` 에 있다.

> **UC-000 — 표가 정본이다.**
> 조작이 어느 국면에서 어떤 상태인지는 §3 의 표가 정한다. 컴포넌트가 스스로 판단하지 않는다.
> 표와 코드가 다르면 **코드를 고친다.** 단 하나의 예외는 UC-401 이다 — 현재 쓸 수 있는
> 조작이 표에서 「해당 없음」이면 그것은 표의 오류이며 표를 고친다 (FR-247).

## 1. 화면 문법

### 1-1. 3층 구조

**여덟 국면** 전부가 같다 (FR-217·FR-218c). 층의 구성·순서·개수, ③ 좌측 두 자리의
순서·개수는 국면에 따라 바뀌지 않는다. **바뀌는 것은 ③ 좌측 두 자리의 세로 비율뿐이다**
(FR-256 · §1-5).

```
┌──────────────────────────────────────────────────────────────┐  1440 (최소 기준 폭)
│ ① 헤더                                            flex 0 0 56px │
│    제품 표시 · 구분선 · 경로(테스트 식별) · 국면 알약           │
├──────────────────────────────────────────────────────────────┤
│ ② 국면 띠                                         flex 0 0 48px │
│    국면 표시 → 테스트 이름 → 결말 요약 → 그 국면의 주요 조작    │
├──────────────────────────────────────────────────────────────┤
│    알림(Notice) — 있을 때만. 국면 띠 아래에 쌓인다              │
├────────────────────────────────────┬─────────────────────────┤
│ ③-a 대상 앱 슬롯                    │ ③ 우: Step 목록          │
│    미러 / 산출물 / 브라우저 열기 /    │    flex 0 0 460px       │
│    아직 열지 않음                    │    StepPanelHeader 50px │
│    남는 폭 전부 (FR-218a)           │    + Step 행 (단일 구현) │
│    높이는 국면이 정한다 ↕            │    **Step 0개여도 있다** │
│  ──────────────────────────────────  │      (FR-260)           │
│ ③-b 국면 작업 영역                   │                         │
│    그 국면에서 실제로 하는 일          │                         │
│    높이는 국면이 정한다 ↕            │                         │
└────────────────────────────────────┴─────────────────────────┘
        Step 상세 — 겹침 640px 또는 ③-b 안 인라인. **국면이 정하고 표가 정본이다**
```

**③-b 의 이름이 「국면 보조 영역」에서 바뀌었다** (FR-218e-1). 1회차의 이름은 이 자리를
보조로 규정했고, 그 규정이 편집 폼 전체를 42px 띠에 넣는 판단으로 이어졌다 (S-12).

### 1-2-1. Step 상세를 거는 자리 (008 · FR-230 개정)

**표가 정본이며 `frontend/src/lib/layout.ts` 의 `DETAIL_PLACEMENT` 가 그 표다.**

| 국면 | 자리 | 이유 |
|---|---|---|
| CRE · REC · AI · TKO · RUN · PAU | 겹침 640 | 미러를 보면서 하는 국면이다. 인라인이면 미러를 밀어낸다 |
| RES 결과 | 겹침 640 | 산출물과 대조하며 본다 |
| EDT 편집 | **③-b 안 인라인** | 이 국면에는 미러가 없다(③-a 가 88px). 가릴 것이 없고, 고치는 일이 이 국면의 주 작업이므로 주 작업 자리에 있어야 한다 (FR-257·FR-261) |

**무엇이 바뀌고 무엇이 그대로인가**

- 그대로: **구현은 한 벌이다** (FR-229 · SC-001). 항목과 순서도 같다 (FR-231). 배치가
  바꾸는 것은 폭 · 테두리 · 머리 띠 높이 · `role`(`dialog` ↔ `region`)뿐이다.
- 바뀜: FR-230 의 「모든 국면에서 같은 자리」가 이 표로 대체된다.

**왜 바꾸는가.** 007 은 S-05(같은 Step 이 국면에 따라 다른 자리에서 열림)를 자리 고정으로
막았다. 그러나 S-05 의 실제 원인은 **구현이 두 벌이라 갈라진 것**이었다. 같은 라운드가
③-b 를 「그 국면의 주 작업 자리」로 정하고 편집 국면에 `fill` 을 줬는데(FR-257 · 그
항목의 근거는 「하는 일은 Step 편집이다」), 정작 Step 편집 폼은 겹침에 있었고 ③-b 에
담기로 했던 테스트 이름·시작 주소·지시문은 FR-235 로 조작 팔레트에 갔다. 결과는
**비어 있는 것이 정상인 자리에 남는 높이를 전부 주는 배분**이었고, 편집 화면의 절반이
아무 말도 하지 않았다.

> **UC-101 — 컴포넌트가 자기 자리를 정하지 않는다.**
> `Workbench` 가 표로 조회해 내려 준다. 컴포넌트가 판단하면 그 판단이 두 곳으로 갈리고,
> 갈리는 순간이 S-05 다. 검사가 표와 실제를 대조한다
> (`WorkbenchShell.test.tsx` — 「거는 자리가 DETAIL_PLACEMENT 와 한 글자도 다르지 않다」).

> **UC-102 — 한 값에 입력칸이 둘일 수 없다.**
> 편집 국면은 `stepDetailExtra` 로 **입력할 때마다 변경 연산을 쌓는** 편집면을 넣는다
> (006 FR-188~FR-190). 상세가 자기 입력(표시 이름·입력값·대기 시간)을 함께 그리면 같은
> 값에 칸이 둘 생기고, 커밋 방식이 다른 둘이 한 화면에 놓인다. 그래서 그 국면은
> `ownFields=false` 다. FR-231 이 허용하는 「국면에 따른 읽기·편집 전환」이며 항목의
> 순서는 그대로다.

### 1-5. 세로 배분 — 국면이 정하는 유일한 치수 (FR-256)

**표가 정본이며 `frontend/src/lib/layout.ts` 가 그 표다.** 표시 컴포넌트는 자기 크기를
모른다 — `Workbench` 가 국면으로 조회해 두 자리에 내려 준다.

| 국면 | ③-a 대상 앱 슬롯 | ③-b 국면 작업 영역 |
|---|---|---|
| CRE 만들기 | `fixed 88` — 아직 열지 않음 | `fill` — 시작 조건 |
| REC 녹화 | `fill` — 미러 | `content` — 안내 띠 (B9) |
| AI 작성 | `fill` — 미러 | `content` — 지시문·진행·차단 (B10) |
| TKO 사람이 직접 조작 | `fill` — 미러 | `content` — 안내 띠 |
| RUN 실행 중 | `fill` — 미러 | `content` — 진행·실행 속도 |
| PAU 일시정지/검토 | `fill` — 미러 | `content` — 안내 띠·검증 추가 폼 |
| RES 결과보기 | `fill` — 산출물 | `fixed 424` — 사유 + 시도한 LOCATOR (B4) |
| EDT 편집 | `fixed 88` — 브라우저 열기 | `fill` — Step 편집면 |

> **UC-100 — 한 국면에서 두 자리가 동시에 `fill` 일 수 없다.**
> 그러면 그 국면의 주 작업이 어느 자리인지 화면이 말하지 못한다 (FR-257). 검사가 센다
> (SC-010). 동시에 `content` 도 금지다 — 남는 높이가 어디로도 가지 않는다.

**`fixed` 를 쓸 수 있는 경우는 둘뿐이다.** ③-a 가 세션이 없어 담을 것이 정해져 있을 때
(B1), ③-b 의 내용이 정해진 행 수를 가질 때 (B4). 그 밖에는 `fill` 또는 `content` 다 —
`fixed` 를 남용하면 창 높이가 바뀔 때 잘린다.

## 3. 권한표

**기호**

> **셀에 근거를 적지 않는다.** `–` 의 근거(N1·N2·N3)는 **§4-2 의 닫힌 목록과 코드**가
> 갖고, `CapabilityCoverage.test.ts` 가 「모든 `–` 이 근거를 갖는가」를 센다. 한 열에만
> `– N2` 처럼 적으면 열마다 표기가 달라지고, 표를 읽는 사람이 근거 없는 `–` 를 찾을 때
> 무엇을 봐야 하는지 흐려진다 — 2회차 수렴이 실제로 그 상태를 만들었다가 되돌렸다.
> 갈릴 수 있는 칸의 근거는 표 **아래 산문**에 적는다 (§3-4 끝).

| 기호 | 뜻 | 화면이 하는 일 |
|---|---|---|
| ● | 가능 | 그린다. 누를 수 있다 |
| ○ | 비활성 | **같은 자리에 그린다.** 누를 수 없고, 이유와 해소 방법이 붙는다 (FR-234) |
| ◐ | 런타임 조건 | 표 아래 조건이 정한다. 조건이 거짓이면 ○ 이고 이유가 붙는다 |
| – | 해당 없음 | 그리지 않는다. **§4-2 의 근거가 있어야 쓸 수 있다** |

**국면 약칭**: **CRE 만들기** · REC 녹화 · AI 작성 · TKO 사람이 직접 조작 · RUN 실행 중 ·
PAU 일시정지/검토 · RES 결과보기 · EDT 편집

**CRE 열은 2회차가 추가했다** (FR-217b). `PHASE_TABLE: Record<Phase, PhaseRow>` 이므로
국면을 더하면 컴파일러가 34개 전부의 값을 요구한다 — 빠뜨릴 수 없다.

CRE 열의 값 근거: 만들기 국면에는 **저장된 테스트도 세션도 Step 도 없다.** 따라서 대부분이
「대상이 없음」(N2)이다. 실제로 쓸 수 있는 것은 둘 — `test.setStartUrl` · `nav.back`.
`record.start` 는 시작 URL 형식이 맞아야 실제로 세션을 만들고(화면이 사유를 말한다),
`ai.compose` 는 방법으로 AI 를 골라야 하며(C15), `ai.start` 는 지시문이 있어야 한다(C14).

> **이 표는 실측 대조를 거친 정본이다** (T037·T041·T085 · UC-401). 초안과 달라진 칸에는
> 근거가 §3-5·§3-6 에 붙어 있다. 표와 코드가 다르면 코드를 고친다. 단 **현재 쓸 수 있는
> 조작이 표에서 `–` 이면 그것은 표의 오류**이며 표를 고친다 (FR-247).
>
> `AI-REC` 는 「기록일 뿐 실행 대상이 아닙니다」 — 지시문 전용 이유다 (001 FR-063·FR-064).
> 「끝난 실행의 기록은 고칠 수 없습니다」로 뭉개면 언젠가 고칠 수 있는 것으로 읽힌다.

### 3-6. 전 국면 덮어쓰기

표와 조건보다 **먼저** 적용된다. 하나라도 걸리면 그 조작은 ○ 다.

| # | 덮어쓰기 | 대상 조작 | 이유 문구 |
|---|---|---|---|
| O1 | 실행 요청이 **진행 중**이다 (`pendingRun !== null`) | `run.all` `run.from` `browser.openAt` | 「실행을 준비하는 중…」 (005 FR-127·FR-129) |
| O2 | 명령이 **진행 중**이다 (`busy`) | 세션 명령 전부 | 「요청을 보내는 중…」 |
| O3 | 세션이 **유실**됐다 (`lost`) | 브라우저를 요구하는 조작 전부 | 「브라우저 세션이 유실됐습니다」 → `run.all` |
| O4 | Step 이 **0개**다 | `save` `run.all` `run.from` `step.*` | 「Step 이 없습니다」 |
| O5 | 실행이 **이미 끝났다** (`sessionFinished`) | `run.pause` `run.pacing` | 「실행이 이미 끝났습니다」 |
| O6 | 일시정지 **전이 중**이다 (`pausing`) | `run.resume` `run.resumeSkipFailure` `run.fromHere` `step.*` `save` | 「정지되면 할 수 있습니다. 현재 Step 이 끝나기를 기다리고 있습니다」 (005 FR-143·FR-144). **`run.stop` 은 뺀다** — 기다리다 포기하는 것이 가장 자연스러운 다음 행동이고, 그것까지 잠근 것이 U-04 였다 |
| O7 | **실패한 Step 이 있다** (`hasFailedStep`) | `run.resume` | 「실패한 Step 이 있어 이어서 갈 수 없습니다」 · 해소 방법 없음 — 건너뛰는 길은 **별도 버튼**이어야 한다 (005 FR-137) |
| O8 | 중지 요청이 **진행 중**이다 (`stopRequested`) | `run.stop` | 「중지하는 중…」 (005 FR-147) |
| O9 | 건너뛸 **실패가 없다** (`hasFailedStep` 이 거짓) | `run.resumeSkipFailure` | 「건너뛸 실패가 없습니다」 |

**O5~O9 가 표가 아니라 덮어쓰기인 이유**: 국면 열만으로는 **같은 국면 안에서 갈리는
사정**을 담을 수 없다. 국면마다 표에 적으면 한 국면이 빠지고, 빠진 국면에서 화면은 쓸 수
없는 조작을 활성으로 그린다 — O1 을 덮어쓰기로 둔 것과 같은 이유다. 다섯은 전부
**T037·T041 의 실측 대조**가 찾은 것이다 (UC-401).

**O1 이 표에 없고 덮어쓰기인 이유**: 국면과 무관한 사정이다. 국면마다 표에 적으면 한 국면이
빠지고, 빠진 국면에서 연타하면 브라우저 창이 둘 뜬다 — 005 U-06 이 그 형태였다(실측 5회
클릭에 201 이 2건).

## 4. 판정 규칙

### 4-1. 「비활성」의 의무 (FR-234)

○ 인 조작은 다음 셋을 **모두** 갖는다.

1. **같은 자리에 그린다.** 감추지 않는다 — 감추면 사용자는 자기가 잘못 들어온 줄 안다.
2. **이유를 붙인다.** 왜 지금 안 되는지.
3. **해소 방법을 붙인다** — 있을 때만. 해소 방법은 **이 화면에 실제로 있는 조작**을
   가리켜야 한다.

3번이 006 E-03 의 수정이다. "실행을 시작해 일시정지한 뒤 하세요" 라고 안내하면서 그리로
가는 버튼을 주지 않은 것이 그 결함이었다. `Remedy.action` 이 `ActionId` 타입인 이유가
이것이다 — 자유 문장이면 같은 결함이 다시 들어온다.

### 4-2. 「해당 없음」을 쓸 수 있는 경우 (닫힌 목록)

– 는 아래 셋 중 하나에 해당할 때만 쓴다. 그 외에는 ○ 다.

| 근거 | 뜻 | 예 |
|---|---|---|
| N1 이미 충족됨 | 그 조작의 목적이 이 국면에서 이미 이루어져 있다 | 세션 국면의 `browser.openAt` — 브라우저가 이미 열려 있다 |
| N2 대상이 없음 | 그 조작이 다룰 대상이 이 국면에 존재하지 않는다 | 작성 국면의 `run.all` — 저장된 테스트가 아직 없다 |
| N3 세션이 없음 | 세션 명령인데 이 국면에는 세션이 없다 | `RES`·`EDT` 의 `run.stop`·`run.pause` |

**§3 의 모든 – 은 위 셋 중 하나로 설명될 수 있어야 한다.** 설명되지 않는 – 은 감춘 조작이며
FR-234 위반이다.

### 4-3. 표와 코드가 어긋날 때 (UC-401)

- 표가 ● · ○ 인데 코드에 조작이 없다 → **코드를 고친다**
- 표가 – 인데 **현재 그 국면에서 쓸 수 있는 조작이다** → **표가 틀렸다.** 표를 고친다
  (FR-247 — 통합으로 사라지는 조작이 있어서는 안 된다)
- 이행 순서에서 한 국면을 옮길 때 **그 국면 열 전체를 현재 동작과 대조한다.** 대조 결과를
  커밋 메시지에 남긴다

## 5. 문구 규칙

- **모든 라벨·이유·해소 방법 문구는 `frontend/src/lib/wording.ts` 에 둔다.** 컴포넌트에
  문자열 리터럴을 쓰지 않는다. 이미 그 파일이 문구 단일 출처이며 007 은 그 범위를 넓힌다.
- **시작 지점이 라벨에 드러난다** (005 FR-149) — `run.from` 은 「Step 06 부터 실행」이다.
  「실패한 Step 부터 실행」은 어디서 시작하는지 말하지 않아 사용자가 예측할 수 없었다 (U-02).
- **같은 자리의 같은 라벨이 다른 동작을 하지 않는다** (FR-235 · 005 FR-147) —
  `run.stop` 의 라벨은 상황에 따라 「중지」/「중지 중…」/「닫기」/「나가기」로 **바뀐다.**
  라벨이 바뀌는 것이 규칙을 지키는 방법이다.
- **색만으로 구분하지 않는다.** 결말 칩·Step 표식에는 항상 텍스트 라벨이 함께 있다
  (005 FR-141·FR-151).

## 6. 회귀 방지 장치

사용자가 명시적으로 요구한 넷. 각각을 막는 **구조**를 적는다 — 주의가 아니라 구조여야 한다.

| 회귀 | 무엇이었나 | 007 이 두는 장치 |
|---|---|---|
| 005 U-01 | 종료된 세션 때문에 결과 화면의 재실행이 **항상 409** | 실행 진입은 `App` 의 `startRun` 한 곳뿐이다. 국면 어댑터는 그것을 호출만 하며 세션을 스스로 만들지 않는다 (FR-248) |
| 005 U-06 | 연타로 브라우저 창이 둘 | `pendingRun` 을 §3-6 O1 **덮어쓰기**로 둔다. 국면별 표에 적지 않으므로 한 국면이 빠질 수 없다 (FR-249) |
| 005 U-21 | 건너뜀과 미실행이 같은 표식 | `StepOutcome` 이 두 값을 따로 갖고, 텍스트 라벨을 병기한다. 단일 Step 행 구현이므로 한 국면만 뭉갤 수 없다 (FR-226) |
| 001 R2 | AI 실패가 조건 뒤에 숨어 화면에 도달 못함 | 작업 영역의 `error`·`blocked` 는 **국면 판정과 무관하게** 값이 있으면 그린다. AI 세션 판정은 `authoring_mode` 로 한다 — `state` 가 아니다 (FR-218f·FR-253). **2회차 개명에서 `AlwaysVisibleFailure` 의 구조·인자·호출 위치를 손대지 않는다** — 국면·세션 상태를 인자로 받지 않는 성질이 이 장치의 전부다 (research R15) |

추가로 007 자신이 만들 수 있는 회귀 하나:

| 회귀 위험 | 장치 |
|---|---|
| 통합 화면이 **또 하나의 구현**이 되어 4벌이 5벌이 된다 | 국면 이행 커밋에 옛 구현 **삭제**를 포함한다. 구현 개수를 세는 테스트를 둔다 (SC-001) |

2회차가 만들 수 있는 회귀 셋:

| 회귀 위험 | 장치 |
|---|---|
| 표시 컴포넌트가 **또 자기 크기를 하드코딩**한다 (S-12 재발) | 세로 배분을 `lib/layout.ts` 표에 두고, `TargetPane`·작업 영역은 크기를 **인자로만** 받는다. 두 파일에 `flex: "1"`·`flex: 0 0 auto` 리터럴이 남지 않는지 검사한다 (SC-010) |
| 만들기 흡수가 껍데기를 **4벌**로 만든다 | `CreateTest.tsx`·`AiCompose.tsx` 삭제를 같은 커밋에 포함한다. `ImplementationCount` 검사에 껍데기 개수를 더한다 (SC-011) |
| 개명이 **`AlwaysVisibleFailure` 를 조건 뒤로** 넣는다 (001 R2 재발) | 개명은 파일명·타입명만 바꾼다. `AiFailureVisible.test.tsx` 가 다섯 세션 상태를 이미 세며, 그 검사를 통과한 채로 개명해야 한다 |
| **표를 코드에서만 고친다** (UC-000 위반) | 2회차 수렴이 실제로 찾은 것이다 — 조건 C15 와 셀 넷이 코드에만 있었고 구현 중 검사가 전부 통과하는 동안 남아 있었다. `CapabilityCoverage` 는 **코드의 표를 자기 자신과** 대조하므로 계약 문서와의 어긋남을 보지 못한다. 방어는 하나뿐이다 — **셀을 고치는 커밋에 이 문서와 `capabilities.ts` 를 함께 담는다** (UC-401 의 절차) |

## 7. 접근성

기존 규칙을 유지하고 국면 표시에 확장한다.

- 국면 표시는 텍스트다. 색·아이콘만으로 국면을 알리지 않는다.
- ○ 조작은 `disabled` 이면서 이유가 **접근 가능한 이름 또는 설명**으로 연결된다.
  이유를 시각적으로만 두면 비활성 이유가 도구에 전달되지 않는다.
- 알림의 `role` 은 `Notice.role` 이 정한다 — 오류는 `alert`, 상태는 `status`, 보조 설명은
  `note`. 지금 각 화면이 개별로 정하고 있어 같은 성격의 배너가 다른 role 을 갖는다.
- Step 행은 누를 수 있는 요소가 `button` 역할을 갖는다 (기존 테스트가 `getByRole` 에
  의존한다).
