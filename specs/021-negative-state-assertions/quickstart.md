# Quickstart — 021 부정 검증과 상태 검증을 직접 확인하는 법

**목적**: 이 기능이 실제로 동작하는지 사람이 손으로 확인하는 순서. 자동 검증은 tasks.md 가
만든다. **자동 테스트가 덮지 못하는 것**을 여기서 본다 — 화면 문구가 읽히는지, 목록에서
정반대 뜻의 두 Step 이 구별되는지, 한계 안내가 실제로 눈에 들어오는지.

---

## 0. 사전 준비

```bash
cd backend && uv sync
cd ../frontend && npm install
```

---

## 1. 고정 대상 준비 — 「잠긴 버튼」과 「늦게 뜨는 오류」

기존 고정 대상에는 이 기능을 확인할 화면이 없다. 두 가지가 필요하다.

| 필요한 것 | 왜 |
|---|---|
| **비활성 버튼**이 있는 화면. 같은 자리에 활성 버튼도 하나 | 상태 검증의 통과·실패를 둘 다 본다 |
| 버튼을 누르면 **0.8초 뒤에** 오류 문구가 뜨는 화면 | 부정 검증이 거짓으로 통과하지 않는지 본다. 이것이 이 기능의 핵심 위험이다 |
| 폼 요소가 아닌 대상 (예: 설명용 `<div>`) | 작성 시점 경고가 실제로 나오는지 본다 |

`fixtures/sample-app` 에 화면 하나를 더한다. 기존 고정 대상과 같은 성격이다 — **제품이
아니라 테스트 대상**이므로 고치면 안 되는 제품 코드가 아니다.

```bash
cd backend && uv run python ../fixtures/sample-app/serve.py
```

## 2. 상태 검증 — 잠긴 버튼 (US2)

1. 제품을 띄우고 새 테스트를 만들어 위 화면으로 이동한다.
2. 검증 추가에서 **「요소를 조작할 수 없다」**를 고르고 비활성 버튼을 대상으로 지정한다.
3. Step 이 만들어지고 통과하는지 본다.

**확인할 것**

- [ ] 종류 목록에 새 두 항목이 **한국어 문구와 설명**으로 보인다
- [ ] 상태 검증을 고르면 **비교 값 칸이 사라진다** (값을 쓰지 않는 종류다)
- [ ] 같은 검증을 **활성 버튼**에 걸면 실패하고, 설명이 「조작할 수 없어야 하는데 조작할 수
      있었습니다」로 읽힌다
- [ ] 대상을 **화면에 없는 요소**로 주면 실패한다 — `hidden` 과 달리 부재를 통과로 보지
      않는다
- [ ] 대상을 **설명용 `<div>`** 로 주면 Step 은 만들어지되 **경고가 함께 보인다**

## 3. 부정 검증 — 거짓 통과가 나지 않는지 (US1) **← 가장 중요**

1. 오류 문구가 0.8초 뒤에 뜨는 버튼을 누르는 Step 을 만든다.
2. 바로 뒤에 **「화면 텍스트가 `오류` 를 포함하지 않는다」** 검증을 제한 시간 5초로 넣는다.
3. 실행한다.

**확인할 것**

- [ ] **실패한다.** 통과하면 이 기능은 동작하지 않는 것이다 — 클릭 직후의 빈 화면을 보고
      조용히 통과한 것이다
- [ ] 실패 설명에 기대(`오류` 를 포함하지 않아야 함)와 실제 화면 텍스트가 **둘 다** 나온다
- [ ] 오류가 뜨지 않는 정상 경로에서는 같은 검증이 **통과하고, 5초를 기다리지 않는다**
      (조건이 참이 되면 즉시 끝난다)

### 3.1 한계 안내 (FR-026)

- [ ] 부정 비교를 고르는 자리에서 **늦게 나타나는 것을 놓칠 수 있다**는 안내를 읽을 수 있다
- [ ] 안내가 경고가 아니라 **조언**으로 읽힌다 — 먼저 화면이 안정되었음을 확인하는 검증을
      앞에 두라는 쪽으로

## 4. 목록에서 정반대 뜻이 구별되는지 (FR-023) **← R6 확인**

같은 값 `오류` 에 대해 검증 두 개를 나란히 만든다.

- 「화면 텍스트가 `오류` 를 포함한다」
- 「화면 텍스트가 `오류` 를 포함하지 않는다」

**확인할 것**

- [ ] Step 목록에서 **두 줄이 다르게 보인다.** 같아 보이면 이 기능은 쓸 수 없다
- [ ] 종류가 영문 원문(`text`)이 아니라 한국어로 보인다
- [ ] Step 상세와 편집 화면에서도 같은 문구를 쓴다

---

## 5. 세 작성 경로가 같은 것을 만드는지 (US3)

같은 검증(「화면 텍스트가 `오류` 를 포함하지 않는다」)을 세 경로로 만든다.

1. 화면의 검증 추가 폼
2. AI 작성 — 「`오류` 라는 문구가 뜨지 않는지 확인해 줘」
3. 저장된 테스트에 손으로 Step 삽입

**확인할 것**

- [ ] 세 정의가 **표시 이름과 식별자를 빼면 같다**
- [ ] AI 가 부정 검증이 실패했을 때 **조건을 긍정형으로 뒤집지 않는다** — Step 을 남기고
      결함 후보로 표시한다

## 6. 020 과 함께 동작하는지 (FR-024·FR-025)

1. 작성 시점에 **이미 오류가 떠 있는** 화면에서 「`오류` 를 포함하지 않는다」 검증을 만든다.
2. Step 이 남고 **결함 후보**로 표시되는지 본다.
3. 그 테스트를 실행한다.

**확인할 것**

- [ ] 실행 결과에서 이 검증이 **「이미 아는 결함」**으로 분류된다 (「오늘 깨진 것」이 아니다)
- [ ] 오류를 없앤 뒤 다시 실행하면 **「해소됨」**으로 바뀐다
- [ ] 검증이 실패해도 **뒤의 Step 이 계속 실행된다** (020 이 만든 동작이 새 종류에서도 유지)

## 7. 하위 호환 (FR-030)

- [ ] 기능 적용 **전에** 저장해 둔 테스트가 **파일 변경 없이** 그대로 열리고 실행된다
- [ ] 공유 묶음 내보내기·가져오기가 그대로 동작한다
- [ ] 예전 정의의 실행 결과가 이번 변경 전과 같다 *(단, 텍스트 검증이 실패하는 경우는
      제한 시간만큼 느려진다 — 의도한 변화다)*

---

## 8. 내보내기 (FR-032, 원칙 V)

새 종류가 든 테스트를 표준 Playwright 프로젝트로 내보낸다.

- [ ] 내보내기가 **예외 없이** 끝난다
- [ ] 생성된 코드에 `.not.toContainText` · `toBeDisabled` 가 보인다
- [ ] 내보낸 프로젝트를 **제품 없이** 실행했을 때 제품 안에서와 같은 결과가 나온다
