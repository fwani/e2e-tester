# Feature Specification: 프로젝트 이름 변경과 삭제

**Feature Branch**: `012-project-rename-delete`

**Created**: 2026-09-10

**Status**: Draft

**Input**: User description: "프로젝트 이름수정/삭제 기능이 있어야한다."

---

## 이 기능이 고치는 것

**프로젝트만 이름을 못 고치고 못 지운다.** 테스트에는 이름 변경과 삭제가 둘 다 있다.
Step 에도 삭제가 있다. 프로젝트에는 만들기·열기·목록·「목록에서 치우기」만 있고, 만든 뒤에는
이름을 고칠 길도 정리할 길도 없다.

| 대상 | 만들기 | 이름 변경 | 삭제 |
|---|---|---|---|
| 테스트 | 있음 | 있음 | 있음 |
| Step | 있음 | — | 있음 (복수 포함) |
| **프로젝트** | **있음** | **없음** | **없음** |

이 공백의 결과는 두 가지다.

1. **잘못 지은 이름이 영구히 남는다.** 이름은 만들 때 한 번만 물으며, 그 시점은 사용자가
   프로젝트가 무엇이 될지 가장 모르는 때다. 고치려면 새 프로젝트를 만들고 `tests/*.yaml` 을
   손으로 옮기는 수밖에 없다.
2. **쓰지 않는 프로젝트가 첫 화면에 계속 쌓인다.** 「목록에서 치우기」는 관리 위치에 실재하는
   프로젝트를 지우지 못한다 — 목록이 **스캔 ∪ 레지스트리**이므로 스캔에 다시 걸려 돌아온다.
   사용자는 그 줄을 없애려면 파일 탐색기로 `~/.local/share/itb/projects/` 를 직접 찾아가
   디렉터리를 지워야 한다. 도구가 자기가 만든 것을 자기가 정리하지 못한다.

**되돌릴 수 있는 쪽과 없는 쪽을 다르게 다룬다.** 이름 변경은 다시 고치면 그만이므로 확인
절차를 두지 않는다. 삭제는 `tests/*.yaml` — 사용자가 버전 관리에 넣도록 만든 자산(헌법
§V 자산 이식성) — 을 건드리므로 **파괴하지 않고 옮긴다.** 지워진 것처럼 보이되 실제로는
복구할 수 있어야 한다.

## Clarifications

### Session 2026-09-10

- Q: 「이름 변경」은 무엇을 바꾸는가? → A: **표시 이름만.** `itb-project.yaml` 의 `name` 만
  바꾸고 디렉터리 경로는 고정한다. 경로가 바뀌지 않으므로 열린 세션·git 이력·테스트 파일
  경로가 영향받지 않고, 실패 지점이 파일 한 개 쓰기로 줄어든다
- Q: 「삭제」의 범위는? → A: **휴지통으로 이동.** 도구가 관리하는 휴지통 위치로 디렉터리를
  통째로 옮기고 레지스트리에서 뺀다. 즉시 파괴하지 않는다
- Q: 기존 「목록에서 치우기」는? → A: **그대로 남긴다.** 삭제와 별개 조작이며, 화면에서 둘을
  명확히 갈라야 한다

### Session 2026-09-10 (2차 · 사용자 지적)

- Q: 폴더가 이미 없어 옮길 것이 없는 프로젝트는 삭제할 수 없어야 하는가?
  → A: **아니다. 삭제할 수 있어야 하고, 옮길 것이 없으면 목록에서 빠지는 것으로 끝난다.**
  최초 판(FR-418)은 접근 불가 행에 삭제를 그리지 않았는데, 그러면 **그 줄을 없앨 방법이
  화면에서 사라지는 경우가 생긴다.** 목록이 스캔 ∪ 레지스트리이므로, 파일은 있는데 읽지
  못하는 프로젝트(권한 없음)는 「목록에서 치우기」로 빼도 스캔에 다시 걸려 돌아온다.
  사용자가 원하는 것은 "이 줄을 없애 달라" 이고, 도구는 그 요청을 거절할 이유가 없다 —
  옮길 것이 있으면 옮기고, 없으면 목록에서 빼면 된다

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 프로젝트 이름을 그 자리에서 고친다 (Priority: P1)

사용자가 프로젝트 목록에서 이름이 잘못된 줄을 발견한다. 그 줄에서 바로 이름을 고쳐 쓰고
확정하면 목록의 이름이 바뀐다. 확인 창도, 별도 설정 화면으로 가는 이동도 없다 — 테스트
이름을 국면 띠에서 그 자리에 고치는 것과 같은 방식이다.

**Why this priority**: 되돌릴 수 있고 파일 하나만 쓰므로 위험이 가장 낮으며, 삭제 없이 단독으로
배포해도 사용자에게 가치가 있다. 삭제 기능의 확인 절차 설계와 독립이다.

**Independent Test**: 프로젝트를 하나 만들고, 목록에서 이름을 고친 뒤, 서버를 다시 시작해도
새 이름이 남아 있는지 확인한다. 프로젝트를 열어 화면 곳곳의 이름 표시도 함께 바뀌었는지 본다.

**Acceptance Scenarios**:

1. **Given** 목록에 이름이 `프로젝트`인 줄이 있을 때, **When** 그 자리에서 이름을 `결제 회귀`로
   고쳐 확정하면, **Then** 목록의 그 줄이 `결제 회귀`로 바뀌고 확인 창은 뜨지 않는다
2. **Given** 이름을 고쳤을 때, **When** 서버를 다시 시작해 목록을 다시 열면, **Then** 새 이름이
   그대로 있다 (프로젝트 파일과 레지스트리 양쪽이 갱신되었다)
3. **Given** 이름 칸을 비우거나 공백만 남겼을 때, **When** 확정하려 하면, **Then** 저장되지 않고
   무엇이 잘못됐는지 그 자리에 표시된다
4. **Given** 지금 열려 있는 프로젝트의 이름을 고쳤을 때, **When** 다른 화면으로 이동하면,
   **Then** 그 화면들의 프로젝트 이름 표시도 새 이름이다 (세션·열림 상태는 끊기지 않는다)
5. **Given** 디렉터리가 사라져 「열 수 없음」으로 표시된 줄에서, **When** 이름을 고치려 하면,
   **Then** 이름 변경 조작이 제공되지 않고 왜 지금 할 수 없는지가 표시된다

### User Story 2 - 프로젝트를 삭제하면 휴지통으로 간다 (Priority: P1)

사용자가 더 이상 쓰지 않는 프로젝트를 목록에서 삭제한다. 확인 단계를 한 번 거치면 그 줄이
목록에서 사라지고, **어디로 옮겨졌는지**를 화면이 알려 준다. 잘못 지웠으면 그 위치에서 되찾을
수 있다.

**Why this priority**: 목록이 쌓이는 문제를 실제로 해결하는 것은 이 조작뿐이다. 기존 「목록에서
치우기」로는 관리 위치의 프로젝트를 없앨 수 없다.

**Independent Test**: 프로젝트를 하나 만들고 테스트를 한 개 저장한 뒤 삭제한다. 목록에서
사라지는지, 화면이 알려 준 위치에 `tests/*.yaml` 이 내용 그대로 남아 있는지, 그 위치의
디렉터리를 원래 자리로 되돌리면 목록에 다시 나타나는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 목록에 프로젝트가 있을 때, **When** 삭제를 고르면, **Then** 삭제되기 전에 무엇이
   사라지는지(프로젝트 이름·경로·저장된 테스트 수)와 되돌릴 수 있다는 사실을 알리는 확인
   단계가 나오고, 확인하기 전에는 아무것도 옮겨지지 않는다
2. **Given** 확인했을 때, **When** 삭제가 끝나면, **Then** 그 줄이 목록에서 사라지고 **옮겨진
   위치가 화면에 표시된다**
3. **Given** 삭제된 프로젝트의 자산이 있을 때, **When** 알려 준 위치를 확인하면, **Then**
   `tests/*.yaml` 과 프로젝트 파일이 삭제 전과 같은 내용으로 있다
4. **Given** 확인 단계에서, **When** 취소하면, **Then** 아무것도 바뀌지 않고 목록이 그대로다
5. **Given** 지금 열려 있는 프로젝트를 삭제했을 때, **When** 삭제가 끝나면, **Then** 그 프로젝트는
   닫히고 사용자는 프로젝트 선택 화면에 남아, 사라진 프로젝트를 가리키는 화면에 갇히지 않는다
6. **Given** 그 프로젝트에 실행 중인 세션이 있을 때, **When** 삭제하려 하면, **Then** 삭제되지
   않고 무엇이 막고 있는지와 무엇을 먼저 해야 하는지가 표시된다
7. **Given** 같은 이름의 프로젝트를 두 번 삭제했을 때, **When** 두 번째 삭제가 끝나면, **Then**
   먼저 삭제된 것을 덮어쓰지 않고 둘 다 각각 되찾을 수 있는 위치에 남는다
8. **Given** 폴더가 도구 밖에서 이미 지워진 프로젝트에서, **When** 삭제하면, **Then** 실패로
   보고하지 않고 그 줄이 목록에서 사라진다 (사용자 지적 · 2026-09-10)

### User Story 3 - 삭제와 목록 정리를 헷갈리지 않는다 (Priority: P2)

목록의 한 줄에는 성격이 다른 두 조작이 있다. 하나는 **자산을 옮기는** 삭제이고, 다른 하나는
**목록에서만 빼는** 정리다. 사용자는 어느 쪽을 누르는지 알고 눌러야 한다.

**Why this priority**: US1·US2 없이는 성립하지 않는 후속 요구지만, 잘못 고르면 US2 가 되돌릴 수
있게 만든 안전장치가 무의미해진다 — 지우려던 사람이 목록만 치우고 파일이 남았다고 착각하거나,
목록만 치우려던 사람이 자산을 옮긴다.

**Independent Test**: 관리 위치 프로젝트와 외부 위치 프로젝트, 접근 불가 프로젝트 각각의 줄에
어떤 조작이 제공되는지, 각 조작의 이름과 설명이 결과를 정확히 말하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 목록의 한 줄에서, **When** 조작들을 보면, **Then** 삭제와 「목록에서 치우기」가 서로
   다른 이름과 다른 설명을 갖고, 각각의 설명이 디스크의 파일이 어떻게 되는지를 명시한다
2. **Given** 도구가 만들지 않은 외부 위치 프로젝트에서, **When** 삭제 확인 단계를 보면,
   **Then** 그 디렉터리가 도구 바깥에서 만들어졌다는 사실이 확인 단계에 표시된다
3. **Given** 디렉터리가 사라져 「열 수 없음」인 줄에서, **When** 삭제하면, **Then** 옮길 것이
   없으므로 목록에서 빠지는 것으로 끝나고, 화면은 「옮기지 않고 목록에서 뺐다」를 말한다 —
   「목록에서 치우기」와 결과가 같아지는 유일한 경우이며 그 사실이 문구에 드러난다
4. **Given** 조작을 잘못 고를 수 있을 때, **When** 삭제를 고르면, **Then** 되돌릴 수 있다는 사실과
   되돌리는 방법(옮겨진 위치)이 확인 단계와 완료 표시 양쪽에 있다

### Edge Cases

- **휴지통에 같은 이름이 이미 있을 때** — 덮어쓰지 않는다. 두 삭제분이 각각 남아야 한다.
- **옮기는 도중 실패할 때** (권한 없음, 다른 볼륨, 디스크 부족) — 레지스트리에서 빼지 않는다.
  목록에서 사라졌는데 자산은 원래 자리에 남는 상태가 가장 나쁘다 — 사용자는 자기 테스트가
  어디 있는지 알 방법을 잃는다. 실패 사유와 함께 목록이 그대로 유지되어야 한다.
- **이름 변경 도중 프로젝트 파일을 쓸 수 없을 때** — 레지스트리만 바꾸지 않는다. 표시 이름이
  두 곳에서 갈라지면 다음 조회에서 되돌아간 것처럼 보인다.
- **삭제 대상이 도구가 아는 프로젝트가 아닐 때** — 임의 경로를 받아 옮기는 조작이 되어서는
  안 된다. 목록에 있는 프로젝트만 대상이다.
- **레지스트리 파일 형식을 읽지 못할 때** — 기존 규칙과 같다. 알 수 없는 형식을 덮어쓰지
  않는다. 이름 변경은 프로젝트 파일에만 반영되고 경고가 표시된다.
- **삭제 확인 단계를 열어 둔 사이 다른 곳에서 그 디렉터리가 사라졌을 때** — 이미 없어진 것을
  실패로 보고하지 않는다. 목록에서 빠지는 것이 사용자가 원한 결과다.
- **파일은 있는데 읽을 권한이 없는 프로젝트** — 「목록에서 치우기」만으로는 목록에서 사라지지
  않는다(스캔이 다시 찾는다). 삭제로 폴더를 옮길 수 있어야 하고, 옮기지도 못하면 그때는
  실패 사유를 말한다 — 화면에 길이 없어서 못 하는 것과 도구가 못 하는 것은 다르다.
- **이름을 고쳤는데 값이 이전과 같을 때** — 쓰기를 하지 않고 조용히 끝낸다.
- **이름에 경로 구분자·제어 문자가 들어갈 때** — 표시 이름은 파일명이 아니므로 경로를 만들지
  않는다. 다만 화면에 그대로 표시되므로 앞뒤 공백은 제거하고 길이를 제한한다.

## Requirements *(mandatory)*

### Functional Requirements

**이름 변경 (US1)**

- **FR-399**: 사용자는 프로젝트 목록의 각 줄에서 프로젝트 표시 이름을 그 자리에서 고칠 수 있어야
  한다. 별도 화면으로 이동하거나 확인 창을 거치지 않는다.
- **FR-400**: 이름 변경은 **표시 이름만** 바꾼다. 프로젝트 디렉터리 경로, 테스트 파일 경로,
  테스트 식별자는 바뀌지 않아야 한다.
- **FR-401**: 이름 변경은 프로젝트 파일과 프로젝트 레지스트리 **양쪽**에 반영되어야 한다. 한쪽만
  바뀌어 다음 조회에서 이전 이름으로 되돌아가서는 안 된다.
- **FR-402**: 프로젝트 파일을 쓰지 못하면 레지스트리도 바꾸지 않고, 사용자에게 실패 사유를
  알려야 한다.
- **FR-403**: 새 이름은 앞뒤 공백을 제거한 뒤 1자 이상 100자 이하여야 한다 — 프로젝트를 만들 때와
  같은 규칙이다. 빈 이름과 공백뿐인 이름은 거절하고, 왜 거절됐는지 그 자리에 표시한다.
- **FR-404**: 지금 열려 있는 프로젝트의 이름을 바꿔도 그 프로젝트는 열린 채로 유지되어야 하고,
  실행 중 세션이 끊겨서는 안 된다.
- **FR-405**: 이름 변경 후 프로젝트 이름을 표시하는 모든 화면이 새 이름을 보여야 한다.
- **FR-406**: 열 수 없는 상태(디렉터리 없음·권한 없음·프로젝트 파일 없음)의 프로젝트에는 이름
  변경 조작을 제공하지 않고, 왜 지금 할 수 없는지를 표시해야 한다.
- **FR-407**: 새 이름이 기존 이름과 같으면 파일을 쓰지 않고 성공으로 끝내야 한다.
- **FR-408**: 서로 다른 프로젝트가 같은 표시 이름을 갖는 것을 막지 않는다. 프로젝트를 구분하는
  것은 경로이며, 목록의 각 줄은 경로를 함께 보여 준다.

**삭제 = 휴지통 이동 (US2)**

- **FR-409**: 사용자는 프로젝트를 삭제할 수 있어야 하며, 삭제는 프로젝트 디렉터리를 **도구가
  관리하는 휴지통 위치로 옮기는 것**이어야 한다. 파일을 즉시 파괴해서는 안 된다.
- **FR-410**: 삭제가 끝나면 **옮겨진 위치를 사용자에게 알려야 한다.** 어디로 갔는지 모르면
  되돌릴 수 없다 — 프로젝트를 만들 때 만들어진 위치를 알리는 것과 같은 이유다.
- **FR-411**: 삭제 전에 확인 단계가 있어야 하며, 확인 단계는 사라지는 대상(프로젝트 이름, 경로,
  저장된 테스트 수)과 되돌릴 수 있다는 사실을 함께 보여야 한다.
- **FR-412**: 확인 단계에서 취소하면 아무것도 옮겨지지 않고 목록이 그대로여야 한다.
- **FR-413**: 삭제에 성공하면 그 프로젝트는 레지스트리에서 제거되고 목록에서 사라져야 한다.
- **FR-414**: 옮기기에 실패하면 레지스트리를 바꾸지 않아야 한다. 목록에서 사라졌는데 자산이
  원래 자리에 남는 상태를 만들어서는 안 된다. 실패 사유를 사용자에게 알린다.
- **FR-415**: 휴지통에 같은 이름의 항목이 이미 있으면 덮어쓰지 않고, 두 삭제분이 각각 남아
  각각 되찾을 수 있어야 한다.
- **FR-416**: 지금 열려 있는 프로젝트를 삭제하면 그 프로젝트는 닫혀야 하고, 사용자는 사라진
  프로젝트를 가리키는 화면에 남아서는 안 된다.
- **FR-417**: 실행 중인 세션이 있는 프로젝트는 삭제를 거절해야 하며, 무엇이 막고 있는지와
  무엇을 먼저 해야 하는지를 알려야 한다.
- **FR-418**: 열 수 없는 상태의 프로젝트에도 삭제를 제공해야 한다 (사용자 지적 · 2026-09-10).
  옮길 폴더가 있으면 옮기고, 없으면 목록에서 빼는 것으로 끝낸다 — 어느 쪽이든 그 줄은
  목록에서 사라져야 한다.

  **최초 판은 반대였다** (「옮길 대상이 없으므로 삭제를 제공하지 않는다」). 그것이 만드는
  상태가 문제다: 목록은 스캔 ∪ 레지스트리이므로 **파일은 있는데 읽지 못하는 프로젝트는
  「목록에서 치우기」로 빼도 스캔에 다시 걸려 돌아온다.** 삭제까지 없으면 그 줄을 없앨
  방법이 화면에 하나도 남지 않는다.
- **FR-419**: 삭제 대상은 **도구가 아는 프로젝트**(관리 위치에 있거나 레지스트리에 있는 것)로
  제한되어야 한다. 임의 경로를 받아 옮기는 조작이 되어서는 안 된다.
- **FR-420**: 삭제하려는 순간 디렉터리가 이미 없으면 실패로 보고하지 않고, 목록에서 빼는 것으로
  끝내야 한다.
- **FR-421**: 휴지통 위치는 프로젝트 목록 스캔 대상에 포함되지 않아야 한다. 삭제한 프로젝트가
  목록에 다시 나타나서는 안 된다.

**구분 (US3)**

- **FR-422**: 기존 「목록에서 치우기」(목록에서만 빼고 디스크는 그대로)는 그대로 유지되어야
  하며, 삭제와 **다른 이름·다른 설명**을 가져야 한다.
- **FR-423**: 두 조작의 설명은 각각 디스크의 파일이 어떻게 되는지를 명시해야 한다.
- **FR-424**: 도구가 만들지 않은 외부 위치 프로젝트를 삭제할 때는, 그 디렉터리가 도구 바깥에서
  만들어졌다는 사실이 확인 단계에 표시되어야 한다.
- **FR-425**: 되돌리는 방법(옮겨진 위치)은 확인 단계와 완료 표시 양쪽에 있어야 한다.

### Key Entities

- **프로젝트 표시 이름**: 사용자가 목록과 화면에서 프로젝트를 알아보는 이름. 프로젝트 파일이
  원본이고 레지스트리가 사본이다. 경로와 독립이며 고유하지 않아도 된다.
- **휴지통 항목**: 삭제된 프로젝트 디렉터리 하나. 언제 삭제됐는지와 원래 어떤 이름이었는지를
  위치 자체로 알 수 있어야 하고, 같은 이름의 다른 삭제분과 구별되어야 한다. 도구는 이 항목을
  다시 목록에 올리지 않는다.
- **프로젝트 목록 항목의 상태**: 접근 가능 여부와 출처(도구가 만든 것 / 외부 위치)가 그 줄에서
  어떤 조작을 제공할지를 결정한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-614**: 사용자는 프로젝트 목록에서 벗어나지 않고 **두 번의 조작 안에** 프로젝트 이름을
  고칠 수 있다 (이름 고치기 시작 → 확정).
- **SC-615**: 이름을 고친 뒤 도구를 다시 시작해도 새 이름이 100% 유지된다.
- **SC-616**: 삭제한 프로젝트의 테스트 정의 파일은 **100% 보존되며**, 사용자는 화면이 알려 준
  위치만 보고 다른 정보 없이 되찾을 수 있다.
- **SC-617**: 삭제 조작은 확인 단계 없이는 어떤 파일도 옮기지 않는다 — 확인 전 옮김 발생 0건.
- **SC-618**: 옮기기가 실패한 모든 경우에 프로젝트는 목록에 남는다 — 목록에서는 사라졌는데
  자산은 원래 자리에 있는 상태 0건.
- **SC-619**: 같은 이름의 프로젝트를 연달아 삭제해도 먼저 삭제된 자산이 덮어써지지 않는다 —
  손실 0건.
- **SC-620**: 삭제와 「목록에서 치우기」를 처음 보는 사용자가 각 조작의 설명만 읽고 "디스크의
  파일이 어떻게 되는가" 에 정확히 답할 수 있다.
- **SC-621**: 이름 변경과 삭제 중 어느 것도 실행 중인 세션을 끊거나 브라우저를 닫지 않는다
  (삭제가 거절되는 경우 포함).
- **SC-622**: 목록의 **모든** 줄은 화면 안에서 없앨 수 있다 — 접근 불가 사유가 무엇이든
  「없앨 방법이 화면에 없는 줄」 0건 (사용자 지적 · 2026-09-10).

## Assumptions

- **삭제 대상에 외부 위치 프로젝트도 포함한다.** 도구가 만들지 않은 경로라도 사용자가 목록에
  올려 쓰던 프로젝트이고, 삭제가 파괴가 아니라 이동이므로 되돌릴 수 있다. 다만 그 사실을 확인
  단계에 표시해 사용자가 알고 결정하게 한다 (FR-424).
- **휴지통을 비우는 조작과 휴지통에서 되돌리는 조작은 이번 범위가 아니다.** 사용자는 파일
  탐색기로 알려 준 위치에서 직접 되돌린다. 도구가 휴지통을 자동으로 비우지도 않는다 — 사용자
  자산을 도구가 예고 없이 파괴하지 않는다는 것이 이 기능의 전제다.
- **되돌리기(undo) 조작은 두지 않는다.** 되돌릴 수 있게 만드는 방법이 "휴지통에 남긴다" 이고,
  그 위치를 알려 주는 것으로 충분하다고 본다.
- **동시에 여러 프로젝트를 고르는 일괄 삭제는 이번 범위가 아니다.** 프로젝트는 테스트나 Step 과
  달리 개수가 적고, 하나씩 확인하는 것이 이 조작의 성격에 맞는다.
- 실행 중 세션이 있는 프로젝트는 현재 열려 있는 프로젝트뿐이다 — 도구는 한 번에 한 프로젝트만
  연다. 이 전제가 깨지면 FR-417 의 판정 범위를 다시 봐야 한다.
- 프로젝트 목록·레지스트리·관리 위치의 기존 규칙(스캔 ∪ 레지스트리, 접근 가능 여부는 조회 시
  계산, 알 수 없는 형식은 덮어쓰지 않음)은 그대로 유지한다.

## Out of Scope

- 프로젝트 **디렉터리** 이름 변경 및 위치 이동
- 휴지통 비우기·복구 화면
- 프로젝트 복제
- `default_start_url`, `test_id_attribute`, `browser`, `max_tabs` 등 다른 프로젝트 설정 편집
- 여러 프로젝트 일괄 삭제
