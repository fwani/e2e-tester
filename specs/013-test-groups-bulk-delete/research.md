# Phase 0 — 조사: 테스트 복수 삭제와 그룹

**Feature**: 013-test-groups-bulk-delete | **Date**: 2026-09-10

명세의 결정을 기존 코드에 얹기 전에 확인한 것들이다. **설계를 바꾼 발견이 네 건**
(R1·R4·R6·R7) 있고, 그중 R4 는 clarify 의 결정이 **뜻하지 않게 다른 요구를 가능하게 만든**
경우다.

---

## R1 — 식별자 형식이 걸려 있는 곳은 다섯 군데다

**확인한 것**: `TC-\d{3}` 를 강제하는 자리를 전부 셌다.

| 자리 | 무엇을 하는가 | 넓히면 |
|---|---|---|
| `domain/test_case.py:20` `TEST_ID_PATTERN` | `Test.id` 의 pydantic 검증 | 저장·읽기 전부가 이것을 지난다 |
| `storage/repository.py:37` `TEST_ID_RE` | `run_dir`·`find_test_path` 의 입력 검증 | 산출물 경로가 이것으로 막혀 있다 |
| `repository.list_test_paths()` | `tests_dir.glob("TC-*.yaml")` | **여기가 가장 조용한 함정이다** — 넓히지 않으면 새 접두어 테스트가 목록에 아예 안 나온다 |
| `repository.allocate_test_id()` | 파일명에서 `TC-\d{3}` 를 뽑아 쓰인 번호를 센다 | 접두어가 여럿이면 세는 방식이 바뀐다 |
| `Project.next_test_number` | 다음 번호 카운터 | 그대로 쓴다 (번호는 프로젝트 전체 고유 · spec Assumptions) |

**Decision**: 패턴을 `^[A-Z][A-Z0-9]{0,7}-\d{3}$` 로 넓힌다. **대문자 ASCII 만 허용한다.**

**Rationale**:
- 식별자는 **파일 이름과 디렉터리 이름이 된다** (`tests/USER-001-로그인.yaml`, `.runs/USER-001/`).
  macOS 의 기본 파일 시스템은 대소문자를 구별하지 않으므로 `user-001` 과 `USER-001` 을 둘 다
  허용하면 **한 자리를 두 식별자가 다투는** 경로가 생긴다. 한 가지 대소문자로 고정하면 그
  종류의 결함이 통째로 사라진다.
- `TC-001` 이 이 패턴을 만족한다 — **기존 자산이 그대로 통과한다** (SC-629).
- 8자 상한은 목록에서 이름을 밀어내지 않을 길이다. 번호 3자리는 그대로 둔다 (`next_test_number`
  가 이미 `le=999`).

**Alternatives considered**:
- 한글 접두어 허용 — 기각. `slugify` 가 디렉터리 이름에 한글을 남기는 선례가 있지만, 식별자는
  **사용자가 읽고 말하는 짧은 이름**이고 `사용자관리-001` 은 목록에서 이름 칸을 밀어낸다.
  그래서 clarify 에서 「이름과 접두어를 따로」로 정한 것이다.
- 패턴을 아예 없애고 자유 문자열 — 기각. 경로 구분자·상위 이동이 그대로 파일 경로가 된다
  (헌법 §보안).

## R2 — 그룹은 프로젝트 파일에 둔다

**Decision**: `itb-project.yaml` 에 `groups: [{prefix, name}]` 를 더한다.

**Rationale**:
- **테스트에서 유도할 수 없다.** 접두어는 식별자에서 읽을 수 있지만 **사람이 읽는 이름은
  어디에도 없다.** 「사용자관리 테스트」를 `USER` 에서 되살릴 방법이 없다.
- **테스트가 하나도 없는 그룹이 존재할 수 있어야 한다.** 사용자는 그룹을 먼저 만들고 그 안에
  테스트를 만든다. 유도 방식이면 첫 테스트를 만들기 전까지 그룹이 존재하지 않는다.
- 프로젝트 파일은 이미 `next_test_number` 같은 프로젝트 범위 설정을 담고 있고, **커밋 대상**
  이다 — 그룹 구성은 팀이 공유해야 하는 정보이므로 자리가 맞다.

**Alternatives considered**:
- 별도 `groups.yaml` — 기각. 파일을 늘릴 이유가 없고, 프로젝트 파일 하나만 읽으면 되던 것이
  둘이 된다.
- 레지스트리(`~/.config/itb/`) — 기각. 그것은 **설정이지 자산이 아니다** (012 data-model §1).
  그룹은 테스트와 함께 버전 관리에 들어가야 한다.

**따라오는 것**: `Project` 모델이 바뀌므로 `itb.schema.export` 의 `project` 스키마와
`frontend/src/types/generated/project.d.ts` 를 다시 생성해야 한다 (헌법 Cross-language schema
duty). 기존 프로젝트 파일에는 `groups` 가 없으므로 **기본값 빈 목록**이어야 읽힌다.

## R3 — 번호는 파일에서 센다. 접두어를 무시하고 센다

**확인한 것**: `allocate_test_id()` 는 카운터만 믿지 않는다 — 파일명에서 쓰인 번호를 모아
겹치면 건너뛴다. 주석이 이유를 남겼다: 「카운터만 믿으면 파일을 손으로 옮긴 뒤 충돌한다」.

**Decision**: 그 방식을 유지하되 **접두어를 무시하고 번호만** 센다. `USER-003` 이 있으면
`003` 은 쓰이지 않는다 — 접두어가 달라도.

**Rationale**: 번호가 프로젝트 전체에서 고유하면 **그룹을 옮길 때 번호를 다시 뽑지 않아도
된다** (`USER-003` → `DATA-003`). 그룹마다 번호를 매기면 옮길 때마다 새 번호를 뽑아야 하고
그 자리가 이미 차 있을 수 있다 — FR-444c(식별자 고유)를 규칙으로 지켜야 하는 것이 아니라
**구조로 만족시킨다.**

**Alternatives considered**:
- 그룹별 번호 — 기각(위). 한 그룹의 번호가 이어지는 것(`USER-001, USER-002`)이 보기에는
  좋지만, 그 대가로 이동마다 충돌 처리가 필요하다. 번호는 순서가 아니라 이름이다.

## R4 — 휴지통 결정이 「전부 되거나 전부 안 되거나」를 가능하게 만든다

**이 라운드에서 가장 중요한 발견이다.**

**문제**: FR-432 는 복수 삭제가 전부 되거나 전부 안 되기를 요구한다. 그런데 파일 시스템에는
여러 경로에 걸친 원자적 연산이 없다. 011 의 Step 복수 삭제는 **메모리 안**에서 판정이 끝나
원자성이 공짜였지만 (`steps.py` 의 `remove_many` 주석), 여기서는 그렇지 않다.

**확인한 것**: clarify 에서 「삭제 = 휴지통 이동」으로 정했다. 그러면 **삭제가 파괴가 아니라
이동(rename)** 이고, **이동은 되돌릴 수 있다.**

**Decision**: 세 걸음으로 한다.

1. **먼저 전부 검증한다** — 존재 여부, 실행 중 여부. 하나라도 걸리면 **아무것도 건드리지 않고**
   거절한다. 실패의 대부분이 여기서 걸린다.
2. **하나씩 휴지통으로 옮긴다.** 옮긴 자리를 기억한다.
3. **도중에 실패하면 이미 옮긴 것을 되돌린다** (휴지통 → 원래 자리). 되돌리기도 실패하면
   **그 사실과 남은 자리를 사용자에게 알린다** — 조용히 통과시키지 않는다.

**Rationale**: 영구 삭제였다면 3번이 불가능하다. 지운 파일을 되돌릴 수 없으므로 「셋 중 둘만
지워진 채 오류」가 **구조적으로 피할 수 없는** 상태가 된다. 휴지통 결정은 되돌림을 위해
내린 것인데, **원자성 요구를 지킬 수 있게 만든 것이 두 번째 이득**이다.

**한계를 명시한다**: 되돌리기까지 실패하는 경우(디스크가 꽉 차거나 권한이 사라진 경우)는
남는다. 그때 보장하는 것은 「모든 자산이 휴지통 아니면 원래 자리에 있다」이고, 어느 쪽인지
사용자에게 말한다. 파괴는 어느 경로에서도 일어나지 않는다.

**Alternatives considered**:
- 전부 성공할 때만 커밋하는 2단계(임시 자리로 옮겼다가 확정) — 기각. 휴지통이 이미 그
  임시 자리 역할을 한다. 계층을 하나 더 만들 이유가 없다.
- 부분 성공을 허용하고 결과를 보고 — 기각. spec FR-432 이 명시적으로 막는다. 사용자가 무엇이
  남았는지 다시 세어야 하는 상태를 만들지 않는 것이 011 이 정한 규칙이다.

## R5 — 그룹 이동의 순서: 산출물이 먼저, 정의가 나중

**옮기는 것이 둘이다**: 정의 파일(`tests/<옛ID>-<이름>.yaml` → `tests/<새ID>-<이름>.yaml`,
**내용의 `id` 도 바뀐다**)과 실행 산출물(`.runs/<옛ID>/` → `.runs/<새ID>/`).

**Decision**:

1. 검증 — 새 식별자가 비어 있는가, 그 그룹이 있는가, 실행 중이 아닌가
2. `.runs/<옛ID>/` → `.runs/<새ID>/` (있을 때만)
3. 새 정의 파일 쓰기 (원자적)
4. 옛 정의 파일 지우기
5. 3·4 가 실패하면 2를 되돌리고 새로 쓴 파일이 있으면 치운다

**Rationale**: 반대 순서(정의 먼저)의 실패는 **테스트는 새 식별자에 있는데 결과는 옛 식별자에
남는** 상태를 만든다. 사용자에게는 「방금까지 있던 결과가 사라졌다」로 보인다. 산출물을 먼저
옮기면 실패 시 남는 것은 **새 식별자 자리의 산출물뿐**이고, 그것은 화면에 나타나지 않는다 —
목록은 정의 파일에서 나오기 때문이다. **눈에 보이지 않는 흔적이 눈에 보이는 손실보다 낫다.**

**알려진 창(window)**: 3과 4 사이에 정의 파일이 두 자리에 존재한다. 이 도구는 로컬 단독
실행이고 그 사이에 목록을 읽는 다른 요청이 사실상 없다. 그래도 **없는 것처럼 적지 않는다** —
계약 문서에 남긴다.

## R6 — 휴지통 안의 테스트는 한 자리에 묶는다

**확인한 것**: 012 의 `trash.move_to_trash(root)` 는 **프로젝트 디렉터리 하나**를 옮긴다.
테스트는 **파일 1개 + 디렉터리 1개**(`.runs/<ID>/`)라 그대로 쓸 수 없다.

**Decision**: 테스트 하나당 휴지통 항목 하나를 만든다.

```
~/.local/share/itb/trash/<YYYYMMDD-HHMMSS>-<ID>-<이름>/
├── <ID>-<이름>.yaml     ← 정의. **원래 파일명 그대로** 둔다
└── runs/                ← .runs/<ID>/ 의 내용 (있을 때만)
```

**Rationale**:
- **원래 파일명을 그대로 두는 것이 요점이다.** 되돌리기가 「이 `.yaml` 을 프로젝트의 `tests/`
  로 옮긴다」한 걸음으로 끝난다. 이름을 바꿔 두면 사용자가 원래 이름을 알아내야 한다.
- 시각 접두사와 충돌 회피(`-2`·`-3`)는 `paths.allocate_trash_path` 를 그대로 쓴다 — 여러 개를
  한 번에 지워도 서로 덮어쓰지 않는다 (FR-437c).
- 산출물을 `runs/` 라는 **고정된 이름**에 두면 되돌리는 사람이 어디로 보낼지 안다.

**Alternatives considered**:
- 정의만 옮기고 산출물은 지운다 — 기각. spec FR-437 이 둘 다 옮기라고 한다. 결과가
  재생성 가능한 것은 맞지만, 되돌린 테스트가 마지막 결과를 잃으면 사용자는 「되돌아왔는데
  뭔가 빠졌다」를 본다.
- 프로젝트 구조를 그대로 흉내 낸 트리 — 기각. 삭제 시각이 다른 항목들이 한 트리에 섞여
  무엇을 언제 지웠는지 잃는다.

## R7 — `BulkDeleteConfirm` 은 재사용할 수 없다. 관용어만 잇는다

**확인한 것**: 011 의 부품을 읽었다.

```ts
export function BulkDeleteConfirm({ targets, steps, ... })
  const indices = steps.filter(...).map((s) => s.index);
  <span>{deleteManyConfirm(indices)}</span>     // "Step 3 ~ Step 7 · 5개를 지웁니다"
```

`deleteManyConfirm(indices)` 는 **번호의 범위**를 말한다. 연속 구간이면 「3~7 · 5개」, 아니면
「3~7 사이에서 고른 5개」.

**Decision**: 부품을 재사용하지 않고 테스트용 확인을 새로 만든다. **문구 상수는
`lib/wording.ts` 를 공유한다.**

**Rationale**: **테스트에는 순서가 없다.** Step 은 목록 안의 위치가 곧 정체(`Step 3`)지만,
테스트는 순서 없는 집합이고 `index` 가 없다. 「범위」가 성립하지 않으므로 `deleteManyConfirm`
을 부르려면 가짜 인덱스를 만들어 넣어야 한다.

**그것이 007 이 없앤 결함의 거울상이다.** 007 은 「같은 것을 보는 자리가 둘」을 없앴다. 여기서
억지로 한 부품에 넣는 것은 **다른 것을 한 자리에 욱여넣는** 반대 방향의 실수이고, 결과는
같다 — 한쪽을 고치면 다른 쪽이 깨진다.

대신 **관용어는 그대로 잇는다**: 확인은 겹침 대화상자가 아니라 **목록 바로 아래**에서 하고
(대상이 화면에서 사라지면 무엇을 지우려던 것인지 다시 확인해야 한다), 개수와 **무엇인지**를
함께 말한다. 범위 대신 **이름**을 쓴다 — 테스트를 가리키는 것은 번호가 아니라 이름이다.

## R8 — 목록 화면은 조작 권한표 밖이다

**확인한 것**: `TestList.tsx` 는 `capabilityOf`·`PHASE_TABLE` 을 **한 번도 부르지 않는다.**
권한표는 `Record<Phase, …>` 로 열 국면 전부에 값을 요구하는데, 목록 화면은 그 국면 축 밖에
있다.

**Decision**: 012 가 `ProjectSetup` 에서 한 판단을 그대로 따른다 — **권한표에 편입하지 않되
권한표가 지키는 원칙은 지킨다.** 「선택한 항목 삭제」가 지금 왜 안 되는지(고른 것이 없다,
실행 중이다)를 그 자리에서 말한다 (FR-427).

**Rationale**: 억지로 넣으면 열 개의 무의미한 칸이 생기고 국면 축의 뜻이 흐려진다. `wording.ts`
에는 이미 `NO_DELETE_SELECTION`(「지울 Step 을 먼저 고르세요」)이 있다 — 테스트용 문구를
그 옆에 나란히 둔다.
