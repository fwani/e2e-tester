# Quickstart — 023 을 직접 확인하는 법

**목적**: 이 기능이 실제로 동작하는지 사람이 손으로 확인하는 순서. 자동 검증은 tasks.md 가
만든다. **자동 테스트가 덮지 못하는 것**을 여기서 본다 — 거절 문구가 다음에 무엇을 할지
알려 주는지, 목록에서 두 종류가 구별되는지, 비밀번호 값이 정말 어디에도 남지 않는지.

**§10 과 §6 이 가장 중요하다.**

| | 왜 |
|---|---|
| **§10 한글 태그 녹화** | 이 기능이 **한글에서만 깨지는** 곳이다. 영문으로만 확인하면 통과한다 |
| **§6 비밀번호** | 이 기능이 만드는 **유일한 새 보안 위험**이다 |

## 1. 고정 대상 — 대부분 이미 있다

[research R8](./research.md) 에서 확인했다. 하나만 없다.

| 필요한 대상 | 어디에 |
|---|---|
| 텍스트 입력 칸 | `fixtures/sample-app/projects.html` 의 `#pname` |
| 선택 목록 | 같은 화면의 `#ptype` — 보이는 글자 `분석`, 값 `analysis` |
| 비밀번호 칸 | `fixtures/sample-app/login.html` 의 `#password` |
| 체크박스 | `fixtures/sample-app/label-checkbox.html` 의 `#filter-druid` |
| 값 없는 대상 | 아무 버튼 |
| **여러 줄 입력 칸** | **없다 — 추가한다** |
| **키로 확정하는 태그 칸** | **없다 — 추가한다** (「입력 후 Enter/Space 로 추가」하는 위젯) |

`fixtures/sample-app` 은 **제품이 아니라 테스트 대상**이므로 손대도 된다. 기존 화면
하나에 `<textarea>` 와 태그 칸을 더한다.

태그 칸은 실제 화면과 같은 성질이어야 한다 — **입력 후 Enter 또는 Space 를 누르면 칩이
추가되고 칸이 비워진다.** 마지막 「칸이 비워진다」가 이 기능이 고치는 결함의 원인이므로
빠뜨리면 §10 이 아무것도 검증하지 않는다.

```bash
cd backend && uv run python ../fixtures/sample-app/serve.py
```

## 2. 원래 깨져 있던 것이 고쳐졌는가 (US2)

이 기능의 출발점이다. 먼저 **고장난 상태를 재현**하고, 그다음 새 종류로 고친다.

1. 제품을 띄우고 새 테스트를 만들어 프로젝트 화면으로 간다. 생성 모달을 연다.
2. 프로젝트명 칸에 `E2E역할테스트` 를 입력한다.
3. 검증 추가에서 **「텍스트」**를 고르고 대상을 `#pname` 으로, 값을 `E2E역할테스트` 로 한다.
4. 같은 대상·값으로 이번에는 **「입력값」**을 골라 하나 더 만든다.

**확인할 것**

- [ ] 3번은 **실패**하고, 실패 설명에 관찰값이 `''` 로 나온다 — 고장이 재현된다
- [ ] 3번을 만들 때 **「이 대상에서는 언제나 빈 문자열로 관찰됩니다」 경고**가 보이고, 입력값 검증을 가리킨다
- [ ] 경고가 떠도 **Step 은 만들어진다** (막지 않는다)
- [ ] 4번은 **통과**한다
- [ ] 두 Step 이 목록에서 **다르게 읽힌다** — 하나는 `텍스트가…`, 하나는 `입력값이…`

**세 번째 항목이 핵심이다.** 경고가 거절로 바뀌어 있으면 하위 호환이 깨진 것이다.

## 3. 비교 방식 네 가지와 대기 (US2)

1. 칸을 비우고 「입력값이 `E2E역할테스트` 와 같다」를 실행한다 → 실패해야 한다.
2. 칸에 `E2E역할테스트 수정본` 을 넣고 「포함한다」를 실행한다 → 통과해야 한다.
3. 「같지 않다」로 바꿔 실행한다 → 통과해야 한다.
4. 값이 **0.5초 뒤에 자동으로 채워지는** 상황을 만들어(개발자 도구 콘솔에서 `setTimeout`
   으로 값을 넣어도 된다) 긍정 검증을 실행한다 → 기다렸다가 통과해야 한다.

**확인할 것**

- [ ] 네 가지 비교 방식이 모두 화면에 보인다
- [ ] 부정 비교를 고르면 **021 의 관찰 기간 안내**가 그대로 뜬다
- [ ] 4번이 통과한다 — 한 번 읽고 판정하지 않는다
- [ ] 부정 검증이 제한 시간을 **모두 소모**한다 (021 이 정한 성질이다)

## 4. 선택 목록의 함정 (US4)

이것을 확인하지 않으면 사용자가 매번 걸린다.

1. `#ptype` 을 대상으로 입력값 검증을 만든다. 값에 **화면에 보이는 `분석`** 을 적는다.
2. 실행한다.
3. 값을 `analysis` 로 바꿔 다시 만든다.

**확인할 것**

- [ ] 1번을 만드는 자리에서 **「보이는 항목 이름이 아니라 내부 식별자를 비교한다」**는 안내가 보인다
- [ ] 2번은 실패하고, 관찰값이 `'analysis'` 로 나온다
- [ ] 3번은 통과한다
- [ ] 안내 문구가 **경고가 아니라 조언의 문체**다 (021 의 관찰 기간 안내와 같은 성격)

**두 번째 항목이 실측이다.** 만약 관찰값이 `'분석'` 으로 나온다면 안내 문구가 틀린
것이므로 문구부터 고쳐야 한다 ([research R8](./research.md) 의 미확인 항목).

## 5. 거절되는 대상 (US4)

1. 체크박스(`#filter-druid`)를 대상으로 입력값 검증을 만들어 본다.
2. 아무 버튼을 대상으로 입력값 검증을 만들어 본다.

**확인할 것**

- [ ] 둘 다 **Step 이 만들어지지 않는다** (목록에 아무것도 늘지 않는다)
- [ ] 체크박스 거절 문구가 **왜 안 되는지**(값이 체크 여부와 무관)와 **체크 상태 검증은 아직 없다**는 사실을 말한다
- [ ] 버튼 거절 문구가 **텍스트 검증을 가리킨다** — 반대 방향의 실수를 유도하지 않는다
- [ ] 두 문구 모두 읽고 나서 **다음에 무엇을 할지 알 수 있다**

마지막 항목이 기준이다. 「지원하지 않습니다」로 끝나면 이 검증은 실패다.

## 6. 비밀번호 값이 어디에도 남지 않는가 (FR-015~FR-017) ★

**이 기능이 만드는 유일한 새 위험이다. 여기를 가장 꼼꼼히 본다.**

### 6-1. 평문 비교 값이 거절되는가

1. 로그인 화면으로 가서 비밀번호 칸에 값을 입력한다.
2. `#password` 를 대상으로 입력값 검증을 만들면서 **평문**을 비교 값에 적는다.
3. 이번에는 민감하지 않은 일반 변수 참조(`{{USERNAME}}` 등)로 적어 본다.
4. 민감 변수 참조(`{{SECRET_PW}}`)로 적는다.

**확인할 것**

- [ ] 2번이 거절된다
- [ ] 3번도 **거절된다** — 참조라는 형식이 아니라 민감한지가 기준이다
- [ ] 4번은 받아들여진다
- [ ] 거절 문구가 `SECRET_` 이름 규약을 알려 준다

### 6-2. 실패했을 때 관찰값이 새지 않는가

**이것이 스크러버로는 닫히지 않는 칸이다** ([research R2](./research.md)).

1. 비밀번호 칸에 `wrongpass` 를 입력한다.
2. `{{SECRET_PW}}`(다른 값)로 입력값 검증을 만든다 → 실패한다.

**확인할 것**

- [ ] 실패 설명에 **`wrongpass` 가 보이지 않는다**
- [ ] 작성 시점 어긋남 기록에도 보이지 않는다
- [ ] 그런데도 **판정은 정확하다** — 통과로 바뀌지 않는다

### 6-3. 파일에 남지 않는가

```bash
# 테스트를 저장한 뒤
grep -rn "wrongpass" <테스트 정의 디렉터리>
grep -rn "wrongpass" <실행 결과 디렉터리>
```

**확인할 것**

- [ ] 두 명령 모두 **아무것도 찾지 못한다**
- [ ] 공유 묶음을 만들어도 마찬가지다

## 7. 내보내기 (US3)

1. 입력값 검증 네 가지(같다·포함한다·같지 않다·포함하지 않는다)가 들어간 테스트를 만든다.
2. 비밀번호 칸 검증도 하나 넣는다.
3. **태그 칸에 값을 넣고 Enter 로 확정하는 부분도 넣는다** — 키 입력 Step 이 함께 나가야 한다.
4. 내보낸다.
5. 내보낸 프로젝트를 **제품 없이** 실행한다.

```bash
cd <내보낸 디렉터리> && npm install && npx playwright test
```

**확인할 것**

- [ ] 내보내기가 **실패하지 않는다** (모르는 종류면 크게 깨진다 — 그게 안전장치다)
- [ ] 제품 안 실행과 **통과·실패가 같다**
- [ ] 부정 비교가 **관찰 루프**로 생성됐다 (생성된 파일을 눈으로 본다)
- [ ] 비밀번호 검증이 **`process.env.SECRET_PW`** 로 생성됐다 — 평문이 없다
- [ ] 키 입력이 **`locator.press('Enter')`** 로 생성됐다 — `keyboard.press` 가 아니다
- [ ] 내보낸 실행에서도 **태그가 만들어진다**
- [ ] `contracts/export-mapping.md`·`contracts/key-input-surface.md` 의 표와 **생성된 코드가 일치한다**

## 10. 키 입력 — **한글로 태그를 녹화한다** (US1) ★★

**이 기능이 한글에서만 깨지는 곳이다. 영문으로만 확인하면 통과한다.**

### 10-1. 먼저 고장을 재현한다 (구현 전에 한 번)

1. 태그 칸이 있는 화면에서 녹화를 시작한다.
2. `E2E` 를 입력하고 **Enter** 를 누른다. 칩이 추가되고 칸이 비워진다.
3. 녹화를 멈추고 Step 목록을 본다.

**확인할 것 (구현 전)**

- [ ] Step 이 **하나**뿐이다 — 입력 Step
- [ ] 그 Step 의 값이 **빈 문자열**이다 — 친 글자가 사라졌다

이것을 보지 않으면 무엇을 고쳤는지 알 수 없다. **구현 전에 반드시 한 번 본다.**

### 10-2. 영문 태그 (구현 후)

1. 같은 조작을 다시 녹화한다 — `E2E` + Enter.

**확인할 것**

- [ ] Step 이 **둘**이다 — 입력 Step(값 `E2E`) + 키 입력 Step(Enter)
- [ ] 입력 Step 의 값이 **`E2E` 로 남아 있다** — 빈 문자열로 덮이지 않았다 (FR-056)
- [ ] 키 입력 Step 의 표시 이름에 **`Enter`** 가 보인다 (FR-059)

### 10-3. 한글 태그 — 여기가 핵심이다

1. 태그 칸에 **`테스트`** 를 한글로 입력한다.
2. **Enter 를 누른다** — 한글 조합이 확정된다. (칩은 아직 안 생긴다)
3. **Enter 를 한 번 더 누른다** — 칩이 생긴다.
4. 녹화를 멈춘다.

**확인할 것**

- [ ] 키 입력 Step 이 **하나만** 있다 — 두 개면 조합 확정 Enter 가 기록된 것이다 (FR-055)
- [ ] 입력 Step 의 값이 **`테스트`** 다
- [ ] **재실행하면 태그가 하나만 만들어진다** — 두 개거나 빈 태그가 끼면 실패다

**세 번째 항목이 최종 판정이다.** Step 목록이 맞아 보여도 재실행 결과가 다르면 못 고친
것이다.

### 10-4. Space 도 같은가

1. `E2E` + **Space** 로 태그를 추가해 본다 (영문).
2. `테스트` + Space 로도 해 본다 (한글).

**확인할 것**

- [ ] 영문에서 Space 가 Enter 와 같게 동작한다
- [ ] **한글에서 어떻게 되는지 기록한다** — 한글 IME 의 Space 는 조합을 확정하면서 공백도
      넣으므로 Enter 와 다를 수 있다. [research R10](./research.md) 의 미확인 항목이다.
      결과가 다르면 `contracts/key-input-surface.md` §3 을 고친다

### 10-5. 범위 밖 키

1. 태그 칸에서 **위쪽 화살표**를 눌러 본다.

**확인할 것**

- [ ] Step 이 만들어지지 않는다
- [ ] **기록되지 않았다는 사실이 화면에 보인다** (FR-060) — 조용히 빠지면 사용자가 원인을
      찾을 수 없다

## 12. 키 입력 — 실행의 경계 (US1)

1. 대상 요소가 사라진 상태에서 키 입력 Step 을 실행한다.
2. 같은 키를 두 번 누른 정의를 재실행한다.

**확인할 것**

- [ ] 1번이 **실패한다** — 포커스가 어디 있든 아무 데나 키를 보내지 않는다 (FR-051)
- [ ] 2번에서 키가 **두 번** 눌린다 — 접히지 않는다 (FR-057)
- [ ] 키를 눌렀는데 화면이 안 바뀌어도 Step 은 **성공**이다 — 결과 판정은 검증 Step 의 일이다
