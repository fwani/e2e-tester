# Data Model — 입력 칸의 두 빈칸 (023)

**§1~§6 은 입력값 검증, §7~§11 은 키 입력이다.** 둘째 요구로 범위가 넓어졌을 때 앞부분을
덮어쓰지 않고 이어 붙였다.

권위 정의는 `backend/src/itb/domain/*.py` (Pydantic v2) 다. 이 문서는 **무엇이 바뀌고
무엇이 바뀌지 않는지**를 규정한다. 코드와 이 문서가 어긋나면 **이 문서가 틀린 것이다** —
고쳐야 할 쪽은 문서다.

---

## 1. 바뀌는 것 — 검증 종류에 값 하나

`AssertionKind` 에 `value` 를 더한다. **그것이 스키마 변경의 전부다.**

```
AssertionKind = visible | hidden | text | url | enabled | disabled | value
                                                               ↑ 023
```

새 필드도, 새 모델도, 새 축도 만들지 않는다. 021 이 부정형을 비교 방식에 얹은 것처럼,
이번에는 **관찰 대상 축에 값 하나를 얹는다.**

### 왜 새 필드가 아니라 새 종류인가

「보이는 글자」와 「칸에 담긴 값」은 *무엇을 관찰하는가*의 차이다. 텍스트 검증에
「값으로 읽기」 같은 옵션을 붙이면 하나의 종류가 설정에 따라 다른 것을 보게 되고, 정의만
보고는 무엇을 비교하는지 알 수 없다. `UploadStep` 이 확장자를 별도 필드로 두지 않은 것,
021 이 `negate` 플래그를 두지 않은 것과 같은 판단이다.

## 2. 형태 규칙 — 021 data-model §2 의 표에 줄 하나를 더한다

| 종류 | `target` | `value` | `match` | 부정 비교 |
|---|---|---|---|---|
| `visible` | **필수** | 열림(호환) | 무시 | 불가 |
| `hidden` | **필수** | 열림(호환) | 무시 | 불가 |
| `enabled` | **필수** | **금지** | 무시 | 불가 |
| `disabled` | **필수** | **금지** | 무시 | 불가 |
| `text` | 선택 (비우면 화면 전체) | **필수** | 씀 | 가능 |
| `url` | **금지** | **필수** | 씀 | 가능 |
| **`value`** *(023)* | **필수** | **필수** | **씀** | **가능** |

### 집합 소속

| 집합 | 023 이후 | 왜 |
|---|---|---|
| `VALUE_COMPARING_KINDS` | `text` · `url` · **`value`** | 비교 값을 갖고 부정 비교가 허용되는 종류 |
| `ELEMENT_KINDS` (대상 필수) | `visible` · `hidden` · `enabled` · `disabled` · **`value`** | 대상 없이는 물을 수 없는 질문 |
| `STATE_KINDS` | `enabled` · `disabled` — **그대로** | 조작 가능 여부를 보는 종류. `value` 는 값을 비교하므로 여기 아니다 |

`value` 가 **`VALUE_COMPARING_KINDS` 와 `ELEMENT_KINDS` 양쪽에 드는 첫 종류다.** 지금까지
두 집합은 서로 겹치지 않았다 — `text` 는 대상이 선택이었고, 대상이 필수인 넷은 값을
비교하지 않았다. 모델 검증기는 두 집합을 배타적으로 다루지 않으므로 규칙 추가만으로
되지만, **그 전제가 없다는 사실을 여기 적어 둔다.**

### 검증기에 추가할 규칙

`Assertion._check_shape` 에 다음을 더한다.

- `value` 종류는 `target` 이 없으면 거절한다.
- `value` 종류는 비어 있지 않은 `value` 가 없으면 거절한다.

`_check_negation` 은 **고치지 않는다.** `VALUE_COMPARING_KINDS` 에 값을 더하는 것만으로
부정 비교가 열린다.

### 하위 호환에서 건드리지 않는 것

021 이 「`visible` + `contains` 처럼 뜻이 없는 조합을 거절하지 않는다」고 정한 경계를
그대로 유지한다. 이번 변경은 **새 종류에 대한 규칙만** 더하고 기존 종류의 허용 범위를
넓히지도 좁히지도 않는다.

## 3. 새로 생기는 개념 — 대상의 성질

**저장되지 않는다.** 정의에 적히지 않고, 살아 있는 요소를 볼 때마다 판정한다
(research R1).

### 세 갈래

| 갈래 | 판정 기준 | 작성 시점 | 실행 시점 |
|---|---|---|---|
| **값을 갖는다** | `tag` 가 `input`·`textarea`·`select` 이고 `type` 이 `checkbox`·`radio` 가 아님 | 받는다 | 값을 읽는다 |
| **값이 뜻을 갖지 않는다** | `type` 이 `checkbox` 또는 `radio` | **거절** | (도달하지 않음) |
| **값이 없다** | 그 밖의 모든 태그 | **거절** | (도달하지 않음) |

판정할 수 없으면(태그를 읽지 못하면) **거절하지 않는다.** 판정 실패를 거절로 바꾸면 정당한
대상이 막힌다. 그때는 실행 시점 오류로 드러난다.

### 성질 위에 겹치는 두 가지 표시

| 조건 | 무엇을 하는가 | FR |
|---|---|---|
| `type` 이 `password` | 평문 비교 값을 **거절**한다. 민감 변수 참조만 받는다 | FR-015 |
| `tag` 가 `select` | 만들되 **내부 식별자를 비교한다고 알린다** (경고 아님, 안내) | FR-033 |

`password` 는 `textbox` 계열이므로 **값을 갖는 갈래 안에 든다.** 거절하는 것은 대상이
아니라 *평문 값*이다.

### 판정의 출처는 하나다

`__itbDescribe` 가 돌려주는 서술(`tag`, `attributes.type`)만 쓴다. 녹화가 민감 여부를
판정하는 규칙(`type === "password"`)과 **같은 출처, 같은 규칙**이다. Python 에 판별 규칙을
복제하지 않는다 — 두 곳이 다르게 판단하면 입력 Step 에서는 가려지고 검증 Step 에서는 새는
상태가 생긴다.

## 4. 바뀌지 않는 것

명시해 두지 않으면 구현 중에 「여기도 고쳐야 하나」가 반복된다.

| 무엇 | 왜 그대로인가 |
|---|---|
| `MatchMode` 네 값 | 021 이 만든 비교 축을 그대로 쓴다 |
| `Assertion` 의 필드 구성 | 종류 값만 늘어난다 |
| `AuthoringMismatch` | 020 의 기록 형태를 그대로 쓴다 (FR-009) |
| `TargetLocator` | `type` 필드를 더하지 않는다 (research R1) |
| 대기 로직 (`settle`·`hold`·`_watch`) | 관찰 함수만 바꿔 넘긴다 (research R5) |
| 비교 판정 (`_matches`) | 종류와 무관하다 |
| 실패 설명 조립 (`_EXPECTATION_VERBS`) | 종류와 무관하다 |
| 민감 변수·비밀 저장 경로 | 기존 방어선 위에 얹는다 (FR-015~FR-017) |
| 정의 형식의 버전 | 올리지 않는다 — 값 추가는 기존 파일을 건드리지 않는다 |
| `InsertableStepSpec` (손으로 넣는 Step) | 대상을 받는 필드가 없어 구조적으로 불가. 명세 범위 외 |

## 5. 종류를 더할 때 함께 고쳐야 하는 자리

**타입 검사가 잡아 주는 곳과 아닌 곳이 갈린다.** 이 구별이 이 절의 요점이다.

| 자리 | 누락되면 | 무엇이 알려 주는가 |
|---|---|---|
| `_assertion_lines()` (생성기) | `UnsupportedStepError` | **크게 깨진다** — 잊을 수 없다 |
| 프론트 `Record<AssertionKind, …>` 문구 사전 | 컴파일 실패 | **타입 검사** |
| `default_label()` | `"검증"` 이라는 무의미한 이름 | **아무것도** — 조용히 지나간다 |
| `assertion_builder` 의 집합들 | 잘못된 형태를 통과시킴 | **아무것도** |
| AI 도구 설명 (`assert_condition` docstring) | 모델이 새 종류를 모름 | **아무것도** |
| 프론트 `KINDS` 배열 | 화면에 안 보임 | **아무것도** |

조용한 넷이 위험하다. 작업 목록에서 각각 별도 항목으로 둔다.

## 6. 검증 흐름 — 작성과 실행

### 작성 (두 경로 공통)

```
셀렉터 / 요소 참조
  → __itbDescribe 로 서술을 읽는다 (tag, attributes.type)
  → 후보를 수집·검증한다 (collect_by_selector)        ← 기존
  → ★ 대상 성질을 판정한다 (023 신규, 두 경로가 같은 함수를 부른다)
      · 값이 없다 / 체크박스·라디오  → Step 을 만들지 않는다
      · 비밀번호 칸 + 평문 값        → Step 을 만들지 않는다
      · 선택 목록                    → 만들고 안내를 붙인다
  → Assertion 을 만든다
  → 즉시 실행한다 (keep_on_failure — 어긋나도 Step 은 남는다)   ← 020
```

### 실행

```
대상을 찾는다 (기존 _locate_target — 못 찾으면 실패, FR-006)
  → ★ 대상이 비밀번호 칸인지 읽는다 (023 신규)
  → 값을 관찰한다 (input_value)
  → 대기·비교 (기존 _watch → settle | hold)              ← 021
  → 실패하면 설명을 만든다 (기존 _EXPECTATION_VERBS)
      · ★ 비밀번호 칸이면 관찰값을 마스킹한다 (023 신규)
```

**마스킹은 설명만 바꾼다.** 통과·실패는 실제 값으로 판정한다 — 원칙 II 의 결정성에 예외를
만들지 않는다 (research R2).

# 2차 — 키 입력 (2026-09-28 범위 확장)

## 7. 바뀌는 것 — 동작 Step 종류 하나

`StepType` 에 `press` 를 더하고 `PressStep` 을 만든다. **동작 Step 의 열 번째 종류다.**

```
Step = Click | Fill | Select | Navigate | Assertion | CloseTab | Hover | Drag | Upload | Press
                                                                                      ↑ 023
```

### 형태

| 필드 | 값 | 왜 |
|---|---|---|
| `target` | `TargetLocator` — **필수** | 포커스에 의존하면 정의만 보고 무엇을 했는지 알 수 없다 |
| `key` | 열거형 — **필수** | 임의 문자열은 오타가 실행 시점까지 숨고, 검증 안 된 값이 생성기로 나간다 ([research R12](./research.md)) |

`_StepBase` 의 공통 필드(`id`·`label`·`author`·`tab`·`timeout_ms`·`frame_url`)를 그대로
쓴다. `ClickStep` 과 같은 모양에 `key` 하나가 붙은 것이다.

### 키 열거형 — 초기 넷

```
PressKey = Enter | Space | Tab | Escape
```

| 키 | 넣는 이유 |
|---|---|
| `Enter` · `Space` | **사용자가 요구한 것** — 태그 칸의 확정 |
| `Tab` | 포커스 이동. 탭 순서 자체가 검증 대상일 때 대신할 것이 없다 |
| `Escape` | 모달·확인창 닫기. 「취소」 버튼이 없는 화면이 있다 |

**넓히는 것은 값을 더하는 일이다.** 지금 좁게 시작하는 것이 나중을 막지 않는다.

### 왜 `value` 가 아니라 `key` 인가

`FillStep.value` 는 **사람이 친 글자**이고 민감할 수 있어 변수 참조로 저장된다.
`PressStep.key` 는 **어느 키를 눌렀는가**이고 열거값이며 비밀이 될 수 없다. 이름을 같게
하면 민감값 처리 코드가 이 필드도 훑어야 하는지 매번 판단하게 된다.

## 8. 녹화 규칙의 변경 — 기존 동작을 고친다

이번 변경은 **새 종류를 더하는 것으로 끝나지 않는다.** 녹화가 이미 하고 있는 일을 두 군데
고친다.

| 규칙 | 지금 | 023 이후 | FR |
|---|---|---|---|
| 키를 듣는다 | 듣지 않는다 | **목록에 있는 키를 `keydown` 에서 잡는다** | FR-054 |
| IME 조합 중의 키 | (해당 없음) | **기록하지 않는다** | FR-055 |
| 키 뒤의 빈 값 확정 | 앞선 입력 Step 을 **갱신한다** | **갱신하지 않는다** | FR-056 |
| 같은 키 연속 | (해당 없음) | **접지 않는다** — 누른 횟수만큼 | FR-057 |

셋째 줄이 기존 동작의 변경이다. 지금 태그 칸을 녹화하면 「빈 문자열을 넣는다」 Step 하나가
남는데, 이후에는 입력 Step + 키 입력 Step 둘이 된다 ([research R11](./research.md)).
**결함의 수정이지만 동작 변경인 것은 맞다** (FR-043).

### 입력은 접고 키는 접지 않는 이유

| | 입력 | 키 |
|---|---|---|
| 같은 것이 연달아 오면 | 같은 동작의 중복 보고(`change`+`blur`)다 | **각각 다른 동작**이다 |
| 접으면 | 정확해진다 | Enter 두 번이 한 번이 되어 **뜻이 바뀐다** |

## 9. 키 입력은 바꾸지 않는 것

| 무엇 | 왜 그대로인가 |
|---|---|
| `TargetLocator` | 후보 수집은 기존 경로를 그대로 쓴다 (원칙 IV) |

| 실행 결과 분류 | 같음. 검증 Step 만의 개념이다 |
| 대기·재시도 | 기존 동작 Step 과 같은 규칙을 쓴다 |
| 정의 형식의 버전 | 올리지 않는다 |

| Excel 내보내기의 수행 절차 문구 | 빈 칸 또는 잘못된 문구 | **아무것도** |

마지막 넷이 위험하다. 작업 목록에서 각각 별도 항목으로 둔다.

## 11. 검증 흐름 — 키 입력

### 녹화

```
keydown
  → ★ 조합 중인가? (브라우저가 주는 조합 상태)
      · 조합 중  → 버린다 (FR-055)
      · 아니다   → 계속
  → ★ 목록에 있는 키인가?
      · 없다 → 버리고 그 사실을 알린다 (FR-060)
      · 있다 → 계속
  → 후보를 수집·검증한다 (기존 경로)
  → PressStep 을 만든다
  → ★ 이 요소의 입력 Step 갱신을 막는다 (FR-056)
```

### 실행

```
대상을 찾는다 (기존 경로 — 못 찾으면 실패, FR-051)
  → 그 요소에 키를 보낸다
```

**새 대기 규칙도, 새 판정도 없다.** 동작 Step 이므로 성공하면 다음으로 가고 실패하면
기존 규칙대로 멈춘다.
