# Phase 0 — 조사와 결정: UX 워크스루 결함 수정

**대상 명세**: [spec.md](./spec.md) · **출처 리포트**: `docs/ux/ux-walkthrough-2026-09-07.md`

이 기능은 신규 기능이 아니라 **동작하는 제품의 결함 수정**이다. 그래서 조사의 초점은
"무엇을 쓸까"가 아니라 **어디가 이미 맞게 되어 있고, 어디를 고쳐야 22건이 해소되는가**다.

가장 값이 큰 조사 결과를 먼저 적는다.

## R0. 이미 맞게 되어 있는 것 — 새로 만들 필요가 없다

리포트가 지적한 증상 몇 개는 **백엔드가 이미 올바르게 기록하고 있고 화면만 그것을 읽지
않는** 경우였다. 이것을 먼저 확인한 덕에 이 기능의 범위가 크게 줄었다.

| 확인한 것 | 실제 상태 | 결과 |
|---|---|---|
| Step 실행 상태에 `건너뜀`·`미실행` 구분 | **이미 있다** — `StepOutcome` 은 `pass·fail·skipped·not_run` 네 값 (`domain/run_result.py:18`) | U-02·U-21 은 **표시 문제**다. 도메인 변경 불필요 |
| 부분 실행 시 앞 Step 을 건너뜀으로 표시 | **이미 한다** — `skip_before()` 가 `not_run` 을 `skipped` 로 바꾼다 (`execution/runner.py:392`) | 저장된 결과에는 건너뜀이 남는다. 요약 집계와 화면이 그것을 무시한다 |
| 일시정지가 Step 경계를 기다리는 것 | **이미 한다** — `wait_for_boundary(10s)` + 경고 발행 (`api/routes/sessions.py:892`, `runner.py:104`) | U-04 는 **전이 상태를 화면에 알리지 않는 것**이 문제다. 대기 로직은 그대로 쓴다 |
| 저장 연타에 중복 생성 | **막혀 있다** — `disabled={busy}` (`RunnerPaused.tsx:457`) | U-09 는 성공 표시 부재만 고치면 된다 |
| 미러가 입력을 전달하지 않는 성질 | **구조로 보장** — 허용 CDP 명령 화이트리스트 3개, `Input` 도메인 미임포트 (`mirror/screencast.py:32`) | U-24 수정은 **전송 방향만** 만진다. 이 구조를 깨지 않는다 |

**결정**: 도메인 모델 변경은 **실행 결말(`Outcome`) 한 곳으로 최소화**한다. Step 상태·건너뜀
기록·경계 대기는 손대지 않는다.

**근거**: 이미 맞는 것을 다시 만들면 두 개의 진실이 생긴다(헌법 원칙 I). 그리고 리포트가
지적한 것은 대부분 "기록은 맞는데 화면이 다른 말을 한다"였다.

## R1. 실행 결말 — 두 값에서 네 값으로

**결정**: `Outcome` 을 `pass · fail · stopped · partial_pass` 네 값으로 넓힌다.

| 값 | 언제 | 사용자 표시 |
|---|---|---|
| `pass` | 모든 Step 이 통과 | 통과 |
| `fail` | 실패한 Step 이 있다 | 실패 |
| `stopped` | 사용자가 중지를 요청해 끝났다 | 중지 |
| `partial_pass` | 실패 Step 을 건너뛰고 나머지를 마쳤다 | 부분 성공 |

**부분 실행(범위가 좁은 실행)은 결말이 아니라 범위다.** Step 06~07 만 돌아 전부 통과하면
결말은 `pass` 이고, 범위가 부분이라는 사실은 별도 필드로 남긴다(R2). 이 둘을 한 값에
섞으면 "부분 구간을 전부 통과한 실행"을 부를 이름이 없어진다.

**근거**: FR-131(중지는 실패 집계에서 제외) 과 FR-137(실패 건너뛰기의 결말은 완료가 아니다)
은 두 값으로는 표현할 수 없다. 지금은 `Outcome.PASS if passed and not session_lost else FAIL`
한 줄이 모든 결말을 만든다(`runner.py:530`).

**기존 저장 결과와의 호환**: `.runs/<테스트ID>/result.json` 에 이미 `pass`/`fail` 이
저장돼 있다. 새 값은 **추가**이므로 기존 파일은 그대로 읽힌다. 마이그레이션 불필요.
읽는 쪽에서 알 수 없는 값을 만나면 `fail` 로 보수적으로 취급한다 — 앞으로 값이 더 늘 때
화면이 조용히 통과로 표시하지 않게 하려는 방향이다.

**대안으로 검토했으나 버린 것**:

- `session_lost` 처럼 **불리언 플래그 추가**(`stopped_by_user: bool`) — 결말이 두 값이라는
  전제를 남겨 두므로, 화면은 계속 `outcome == fail` 로 분기하며 "중지인데 실패"를 만든다.
  플래그는 이미 `session_lost` 하나가 같은 방식으로 문제를 만들고 있다.
- **결말을 화면에서만 계산** — 저장된 결과와 화면이 어긋난다(U-05 가 정확히 그 증상이다).

**스키마 의무**: `Outcome` 은 `run-result` 스키마에 실려 프론트 타입으로 생성된다
(`schema/export.py:MODELS`). 그래서 순서가 고정된다 — **백엔드 enum → `uv run python -m
itb.schema.export` → `npm run gen:types`**. 순서를 어기면 `test_schema_drift.py` 가
실패한다. 이것은 헌법 Cross-language schema duty 의 이행이며, tasks 에서 한 작업으로
명시한다.

## R2. 실행 범위 — 부분 실행을 결과에 남긴다

**결정**: `RunResult` 에 실행 범위를 남긴다.

- `start_index: int` — 이 실행이 어느 Step 부터 돌았는지 (전체 실행은 0)
- `scope: full | partial` — 파생값이지만 **저장한다**. 읽는 쪽이 `start_index > 0` 을
  매번 해석하면 같은 규칙이 여러 곳에 복제된다
- 요약 집계는 **실행 대상 Step 기준**으로 센다 — `passed_count / attempted_count` 이고
  `attempted_count = 전체 - 건너뜀`. 지금은 `total_count = len(results)` 라서 5개를
  건너뛴 부분 실행이 `0 / 7` 로 보인다(U-02).

`total_count` 는 **유지한다**(전체 Step 수). 새 필드 `attempted_count` 를 더한다. 기존
필드의 뜻을 바꾸면 이미 저장된 결과의 해석이 달라진다.

**근거**: FR-152(부분 실행임과 구간이 드러나야 하고 이전 전체 실행 결과를 삭제하지 않아야
한다). "삭제하지 않는다"는 **결과 보관 정책**의 문제이기도 하다 — R3 을 보라.

## R3. 결과 보관 — 부분 실행이 전체 실행을 덮지 않게

**현재**: `.runs/<테스트ID>/result.json` 에 **테스트당 최근 1건만** 보관한다
(`domain/run_result.py:1` 의 문서 문자열). 그래서 부분 실행이 직전 전체 실행 결과를 덮고,
사용자는 `5 / 7` → `0 / 7` 을 보고 "고치다 더 망가뜨렸다"고 읽는다(U-02).

**결정**: **최근 전체 실행 1건 + 최근 실행 1건**을 보관한다. 파일 두 개다.

- `result.json` — 최근 실행 (전체든 부분이든). 지금과 같은 자리, 같은 뜻
- `result-full.json` — 최근 **전체** 실행. 전체 실행이 끝날 때만 함께 갱신된다

부분 실행 결과 화면은 "이 실행: 부분 · Step 06~07 · 0 / 2" 와 함께 "최근 전체 실행:
5 / 7 통과"를 보조로 보여줄 수 있다.

**대안으로 검토했으나 버린 것**:

- **실행 이력 전체 보관** — 목록·정리·용량 정책이 따라온다. 리포트가 요구한 것은 이력이
  아니라 "부분 실행이 전체 실행 결과를 지우지 않는 것" 하나다. 이력은 이 기능의 범위가
  아니다(명세 Assumptions: 리포트에 없는 개선은 범위 밖).
- **부분 실행 결과를 저장하지 않기** — 부분 실행의 실패 진단(스크린샷·로그)이 사라진다.
  그것이 부분 실행의 목적이므로 본말전도다.

## R4. 세션 생존 판정과 동시 실행 1건

**결정 A (U-01)**: `active_session_for_test()` 가 **살아 있는 세션만** 돌려준다.
종료 상태(`completed·failed·stopped·review·lost`)는 제외한다. 판정 근거는 이미 있는
`ACTIVE_STATES` 를 쓴다 — 새 목록을 만들면 두 개의 진실이 생긴다.

종료된 세션은 등록에서 **떼어낸다**(`_by_test` 에서 제거). 남겨 두면 같은 판정을 매 호출마다
다시 해야 하고, 어딘가 한 곳이 빠뜨린다.

**결정 B (U-06)**: 테스트별 **생성 락**을 둔다. 지금은 `active_session_for_test` 확인과
`sessions.create()` 사이에 await 경계가 있어 동시 요청 5건이 모두 검사를 통과한다
(`api/routes/sessions.py:335` 부근). `asyncio.Lock` 을 테스트 ID 별로 잡고, 락 안에서
**확인과 예약을 함께** 한다.

예약은 세션 생성 **전에** `_by_test` 자리를 잡는 방식으로 한다(생성 실패 시 되돌린다).
그래야 브라우저를 띄우는 긴 구간 전체가 보호된다 — 락만으로는 브라우저 기동 시간(약 1초)
동안 락을 쥐고 있어야 해서 정상 요청도 직렬화된다. 예약을 쓰면 락은 짧게 쥐고 놓는다.

**근거**: FR-128 은 "경계에서도 보장"을 요구한다. FR-043(테스트당 동시 실행 1건)은 기존
요구사항이고, 지금 실제로는 지켜지지 않는다. 이 수정은 기존 요구사항을 **지키기 위한** 것
이므로 새 제약을 만들지 않는다.

**결정 C (U-01)**: 결과 화면의 재실행은 실행 화면의 `rerun` 과 **같은 경로**를 쓴다.
지금은 결과 화면이 `startReplay` 를 직접 부르고(`App.tsx:65`), 실행 화면은 먼저
`discard` 한 뒤 만든다(`SessionScreen.tsx:437`). 두 경로를 하나로 모은다 — 프론트에
`startRun(testId, {fromIndex})` 하나를 두고 두 화면이 그것만 부른다. 결정 A 가 들어가면
`discard` 선행이 필요 없어지므로, 모은 경로는 단순해진다.

## R5. 세션 뷰에 Step별 결과를 싣는다

**결정**: `SessionView` 에 `step_results: list[StepProgress]` 를 더한다.
`StepProgress = {step_id, outcome, duration_ms}` — `StepResult` 전체가 아니라 **화면 복원에
필요한 최소**다.

**근거**: 지금 Step별 결과는 WebSocket 이벤트로만 채워지는 화면 로컬 상태
(`SessionScreen.tsx` 의 `progress`/`durations`)다. 화면을 다시 그리면 사라진다(U-18).
같은 뿌리가 U-05 의 "실패한 Step 이 화면에서 지워지는" 증상이다 — 실패 이벤트를 놓친
화면은 실패가 없었던 것처럼 보인다.

WebSocket 계약은 이미 "재전송하지 않는다 · 끊기면 `GET /api/sessions/{sid}` 로 전체 상태를
다시 받는다"로 되어 있다(`api/ws/session_events.py:6`). **그 전체 상태에 Step별 결과가
빠져 있는 것이 계약의 구멍이다.** 이벤트 재전송 버퍼를 만드는 대신 스냅샷을 채우는 것이
기존 설계 의도에 맞다.

`RunnerTask`/`ReplayEngine` 이 이미 `results` 를 들고 있으므로 새 저장소가 필요 없다.

## R6. 미리보기 프레임 전달 — 원인 확정, 두 갈래 수정

**원인은 조사가 끝났다**(리포트 U-24, 실측):

| 구간 | 수신 프레임 |
|---|---|
| 구독 후 정적 화면 5초 | **0건** |
| 화면을 한 번 바꾼 뒤 2초 | 1건 |
| 계속 변하는 화면 3초 | 29건 (약 10 fps) |

CDP `Page.startScreencast` 는 **화면이 변할 때만** 프레임을 만든다. 그 유일한 초기
프레임은 `POST /api/sessions` 안(`sessions.py:425`)에서 발행되는데, 프론트의 WebSocket 은
그 응답을 받은 뒤에 붙는다. 구독자가 없는 동안 `SessionEventHub.publish` 는
`if not self._sockets: return` 으로 버린다.

배제된 원인(별도 프로브로 확인): 창 가림(가려진 상태에서도 10.2 fps),
`--disable-backgrounding-occluded-windows` 유무(10.2 vs 10.0), 전송 확인 실패(0건),
표시 모드(headless 도 동일).

**결정 A — 마지막 프레임 캐시 + 구독 시 1장**: `TabScreencast` 가 최근 프레임을 들고,
구독이 붙을 때 그 한 장을 보낸다. 계약의 "재전송하지 않는다"는 **순서 있는 상태 이벤트**를
두고 한 말이고, `mirror_frame` 은 이미 "유실 가능 · 마지막 프레임만 그리면 된다"로 정의돼
있다(`contracts/websocket.md:62`). 한 장 재전송은 계약과 어긋나지 않는다.

**결정 B — 무프레임 감시**: 마지막 프레임 후 `MIRROR_IDLE_S`(2초) 넘게 조용하면 스크린샷
한 장을 같은 이벤트로 보낸다. 기존 강등 경로(`_screenshot_loop`, 1 fps)와 **같은 코드를
재사용**한다 — 주기를 바꿔 부르는 것뿐이다. 이것이 오래 기다리는 Step 에서 미러가 비는
문제를 잡는다.

**두 갈래를 모두 하는 이유**: A 만 하면 세션 시작 시점은 채워지지만 "실행 중 20초 대기"
구간은 여전히 마지막 프레임에 멈춘 채로 남아 사용자는 화면이 멈춘 것인지 실행이 멈춘
것인지 구분할 수 없다. B 만 하면 첫 화면이 최대 2초 늦다(FR-161 은 3초를 요구하므로 통과
하지만, 이미 있는 프레임을 버리고 다시 찍는 것은 낭비다).

**깨지지 않아야 할 성질을 코드 구조로 유지하는 방법**:

- FR-047a(입력 전달 경로 없음) — 수정은 `_forward`/`_screenshot_loop` 의 **송신 쪽**만
  만진다. `_ALLOWED_COMMANDS` 화이트리스트와 `Input` 도메인 미임포트는 그대로 둔다.
  화이트리스트에 명령을 **추가하지 않는다**(스크린샷은 CDP 가 아니라 Playwright
  `page.screenshot` 을 쓴다 — 이미 그렇다).
- FR-047b(미러 실패가 실행에 무영향) — 캐시와 감시 태스크 모두 `TabScreencast` 안에
  둔다. 러너는 미러를 알지 못하는 현재 구조를 유지한다. 감시 태스크의 예외는 삼킨다.
- 테스트로 고정한다 — "미러 모듈이 `Input.` 을 보내지 않는다", "감시 태스크 예외가 실행에
  전파되지 않는다"를 각각 검증한다.

## R7. 일시정지 전이 — 상태 기계를 늘리지 않는다

**결정**: `SessionState` 에 새 상태를 **추가하지 않는다.** 대신 `SessionView` 에
`pause_settled: bool` 을 둔다. 값은 러너에게 이미 있는 `at_boundary` 에서 온다
(`runner.py:115`).

- `state == paused && pause_settled == false` → 화면은 **전이 상태**(`일시정지 중…`)
- `state == paused && pause_settled == true` → 화면은 **정지**(편집 가능)

**근거**: 새 상태를 넣으면 전이표 전체와, 004 가 `한 스텝씩` 을 **기존 일시정지 메커니즘
재사용**으로 설계한 결정(004 spec Assumptions)까지 흔든다. 반면 "요청은 갔고 아직 경계에
닿지 않았다"는 것은 러너의 사실이며 상태가 아니다 — 뷰 필드가 맞는 자리다.

**전이 중 실행이 끝나버린 경우(FR-146)**: 지금은 `PAUSED` 배지와 `FAIL` 요약이 동시에
뜬다. 러너가 끝나면 결말 명령(`FINISH_PASS`/`FINISH_FAIL`)이 적용되어 상태가 종료로
가야 하는데, `PAUSE` 가 먼저 적용돼 `paused` 로 남는 것이 원인이다. **결말이 일시정지를
이긴다**로 정한다 — 러너 종료 시 결말 상태로 전이하고, 화면은 "멈추기 전에 실행이
끝났습니다"를 알린다. 전이표에 `PAUSED + FINISH_*` 를 허용해야 한다(확인 필요 항목으로
tasks 에 남긴다).

**일시정지 요청 즉시 화면이 반응해야 한다(FR-142)**: 지금 `POST /pause` 는 최대 10초
동안 응답하지 않는다(경계를 기다린다). 화면이 응답을 기다리면 그 동안 아무 말도 못 한다.
**요청을 보낸 즉시 전이 상태를 표시**하고 응답으로 확정한다 — 프론트의 낙관적 표시이며,
`pause_settled` 가 그것을 확정/부정한다.

## R8. 화면 상태의 URL 반영 — 라우터를 새로 넣지 않는다

**결정**: 라우팅 라이브러리를 **추가하지 않는다.** `App.tsx` 의 `Screen` 상태를
`history.pushState` / `popstate` 와 양방향으로 잇는 얇은 훅 하나(`useScreenUrl`)를 만든다.

- 화면 → URL: `?screen=result&test=TC-002` 수준의 질의 문자열
- URL → 화면: 최초 로드와 `popstate` 에서 `Screen` 으로 파싱

**근거**: 현재 의존성은 `react` · `react-dom` **둘뿐**이다(`frontend/package.json`).
라우터를 넣으면 화면 트리 전체를 라우트로 재편하게 되고, 이 기능의 다른 부분(실행 화면
상태 복원)과 같은 시점에 충돌한다. 헌법의 Simplicity 규칙("원칙이나 요구사항이 요구하지
않는 복잡성은 정당화하거나 제거한다")에 따라 요구사항이 요구하는 만큼만 한다 —
FR-166(결과 화면 새로고침 복원)과 FR-167(뒤로가기가 앱을 이탈하지 않음) 둘이다.

**대안**: 최소 조치로 뒤로가기만 가로채기(FR-167 만 충족). FR-166 이 남으므로 채택하지
않는다. 다만 구현 순서에서 **뒤로가기 이탈 방지를 먼저** 넣어 값을 일찍 낸다.

## R9. 어휘 단일화 — 사전 하나, 규칙 하나

**결정**: 프론트에 `frontend/src/lib/wording.ts` 를 두고 **결말 어휘와 Step 표기를
전부 여기서만** 만든다.

- `outcomeLabel(outcome)` → 「통과 / 실패 / 중지 / 부분 성공」
- `outcomeChip(outcome)` → `PASS / FAIL / STOPPED / PARTIAL` (칩 전용 기술 라벨)
- `stepLabel(index0)` → `Step 06` — **0-기반 → 표시 변환의 유일한 지점**

**근거**: U-07 은 같은 저장소에서 8곳이 `index + 1` 을 쓰는데 한 곳만 0-기반을 그대로 쓴
것이었다(`TestList.tsx:522`). 한 줄 고치는 것으로 증상은 사라지지만 같은 실수가 다시
난다. FR-138 은 "번호를 만드는 규칙은 하나여야 한다"를 요구한다.

칩의 대문자 기술 라벨은 **확정 디자인이 쓰고 있으므로 유지한다**(`docs/design/RunResult.dc.html`
에 `FAIL`, `통과 / 전체`). 없애는 것은 한 화면에 두 어휘가 **동시에** 나오는 경우다
(FR-141).

## R10. 열린 항목 2건 — 실제 문서를 읽어 판정했다

명세 Assumptions 가 "plan 단계에서 확인"으로 남긴 2건이다.

### U-19. 결말 요약이 두 번 표시되는 것이 확정 디자인의 의도인가

**판정: 의도가 아니다. 제거해도 된다.**

`docs/design/Main.dc.html`(러너 화면)의 텍스트를 전부 추출해 확인했다. 헤더에 진행 표시
`step 04 / 05` 하나가 있고, **결말 요약 띠는 존재하지 않는다.** 확정 디자인은 실행 중
상태를 그린 것이며 얇은 회색 띠와 결말 바가 둘 다 있는 구성이 아니다. 지금의 중복은 구현
과정에서 쌓인 것이다.

→ FR-140 을 그대로 이행한다. 결말 바 하나만 남긴다.

### U-23. 녹화 중 속도 컨트롤 노출이 004 명세의 의도인가

**판정: 004 가 요구한 것이 아니다. 다만 완전히 감추는 것은 004 FR-109 와 어긋난다.**

004 명세의 속도 요구사항(FR-101~FR-110)은 **전부 실행 국면**을 말한다. 녹화·조작 국면에
대한 언급이 없다. 즉 지금의 노출은 명세의 의도가 아니라 헤더 컨트롤을 국면 구분 없이
둔 결과다.

그런데 004 FR-109 는 "속도 선택은 실행 간에 유지되고 다음 실행에서 기본값으로 제시"를
요구한다. 녹화 중에 고른 값도 다음 실행에 쓰이는 것이 맞다.

→ **감추지 않고 밝힌다.** 녹화 국면에서는 라벨을 「다음 실행 속도」로 바꾼다. FR-174 의
두 선택지("감추거나, 무엇에 쓰이는지 밝힌다") 중 후자를 택한다 — 정보를 잃지 않는 쪽이다.

## R11. 실측 요구사항의 검증 방법

명세에 시간·횟수가 박힌 요구사항은 자동 테스트로 고정한다. 사람이 다시 걸어 확인하는
것으로는 회귀를 막지 못한다.

| 요구사항 | 검증 방법 | 자리 |
|---|---|---|
| FR-129·SC-214 — 0.3초 안 화면 반응 | 프론트 컴포넌트 테스트. 클릭 직후(응답 전) 버튼 비활성·준비 문구를 단정. 지연 응답은 pending Promise 로 만든다 | `frontend/tests/` |
| FR-127·SC-213 — 100 ms 5회 연타에 실행 1건 | 프론트: 클릭 5회 후 호출 1회 단정. 백엔드: 동시 `create` 5건 중 1건만 201, 4건은 409 | 양쪽 |
| FR-161·SC-218 — 3초 안 미리보기 표시 | 백엔드 통합 테스트. 정적 페이지 세션에서 구독을 늦게 붙이고 `mirror_frame` 도달을 기다린다(현재는 0건) | `backend/tests/integration/` |
| FR-142 — 전이 상태 즉시 표시 | 프론트: pause 응답 지연 중 전이 배지 단정. 백엔드: `pause_settled=false` 를 뷰가 싣는지 | 양쪽 |
| FR-131·SC-215 — 중지가 실패로 집계되지 않음 | 백엔드 통합: 실행 중 중지 → 저장된 결말이 `stopped` | `backend/tests/integration/` |
| SC-221 — 상 9건 재발 없음 | 각 항목의 재현 절차를 통합 테스트로 옮긴다. 옮기기 어려운 것(화면 배치)은 `quickstart.md` 의 수동 절차로 남기고 그 사실을 적는다 | 양쪽 + quickstart |

**재료**: `fixtures/sample-app` 위에 (a) 중간 Step 에서 반드시 실패하는 테스트,
(b) 항상 통과하는 테스트. 리포트가 쓴 것과 같은 재료다. 실패 재현은 존재하지 않는
`testId` 를 쓰는 Step 으로 만든다 — 대상 앱을 고치지 않아도 되고 실패 사유가 결정적이다.

## 정리 — 이 기능이 만드는 변경의 성격

| 성격 | 항목 | 비중 |
|---|---|---|
| 도메인/계약 변경 | 결말 4값, 실행 범위, 세션 뷰 Step 결과, `pause_settled` | 4건 |
| 백엔드 판정 수정 | 세션 생존, 생성 락, 중지 결말, 유실 감지 가드 | 4건 |
| 미러 전송 | 프레임 캐시, 무프레임 감시 | 2건 |
| 프론트 표시·문구 | 나머지 대부분 | 12건+ |

**리포트 22건 중 12건 이상이 화면 표시·문구 문제다.** 이 사실이 이 기능의 위험을
낮춘다 — 실행 경로를 건드리는 변경은 8건으로 한정되고, 그 8건은 모두 테스트로 고정할 수
있는 판정 로직이다.
