# Phase 0 Research: 실행 속도 조절과 로딩 대기

**Feature**: `004-run-pacing-readiness` | **Date**: 2026-09-07

측정 환경: macOS Darwin 25.2.0, Python 3.13.0, Playwright Chromium(headless), 저장소의
`backend/.venv`. 측정 스크립트는 세션 스크래치패드에서 실행했고 결과만 여기 옮긴다.

## R1 — 사용자가 보고한 결함이 실제로 재현되는가

**질문**: "데이터가 로딩되지 않았는데 요소가 없다고 에러" 가 현재 `resolve()` 의 어떤
동작에서 나오는가.

**실측**: 2초 뒤 `<button data-testid="row-1">주문 상세</button>` 을 그리는 화면에 대해,
`test_id` 후보(맞지 않는 값)와 `role`+이름 후보(2초 뒤 맞음)를 가진 `TargetLocator` 로
현재 `resolve(page, target, 5000)` 을 호출했다.

```
R3 현재 resolve **실패** (5004ms) — 요소를 찾을 수 없습니다.
   시도한 식별 정보: testId=nonexistent-id, role=button name='주문 상세'
```

같은 화면에서 **모든 후보를 100ms 주기로 다시 확인**하면:

```
R4 폴링 결과 = role (2089ms, 21회 확인)
```

**결정**: 결함의 원인은 예산 부족이 아니라 **예산을 쓰는 방식**이다. 현재 알고리즘은
`locator_runtime.py` 3단계에서 `strategies[0]` 하나에만 남은 예산 전체를 건다. 최상위
후보가 끝내 맞지 않으면 다른 후보가 1초 뒤에 맞더라도 **한 번도 다시 확인되지 않는다.**
5초를 통째로 낭비하고 실패한다.

**근거**: 예산을 후보들에게 나눠 주면 모두가 함께 실패한다는 원래 판단(research R4, 001)은
옳다. 하지만 "나눠 준다" 와 "번갈아 다시 본다" 는 다르다. 폴링은 각 후보에게 **전체 예산의
관측 기회**를 주면서 대기 시간을 공유한다.

**기각한 대안**:
- *예산만 늘린다* — R1 이 보여주듯 최상위 후보에만 걸리므로 15초로 늘려도 여전히 실패한다.
  실패까지 걸리는 시간만 3배가 된다.
- *후보마다 병렬로 `wait_for` 를 건다* — Playwright locator 는 동시 대기 시 취소 처리가
  까다롭고, 어느 것이 먼저 맞았는지에 따라 채택이 우선순위가 아니라 타이밍으로 정해진다.
  원칙 IV(우선순위가 유일한 기준)와 충돌한다.

## R2 — 로딩 중 후보가 여러 요소를 매칭하면 무슨 일이 벌어지는가

**질문**: 목록이 로딩되는 동안 스켈레톤 행이 여러 개 그려지면 현재 코드는 어떻게 되는가.

**실측**: 같은 텍스트를 가진 스켈레톤 2개가 있는 상태에서

```
R2 로딩중 텍스트 후보 count = 2
R2 wait_for(attached) 즉시 반환 = 4ms → .first 로 스켈레톤을 잡는다
```

**결정**: 현재 3단계는 `locator.first.wait_for(state="attached")` 를 쓴다. 후보가 2개를
매칭하면 `.first` 는 이미 붙어 있으므로 **4ms 만에 반환하고 스켈레톤을 채택한다.** 그 뒤
동작은 잘못된 요소에 수행된다. 1~2단계의 `count()==1` 엄격 검사가 3단계에서 무효화되는
구조적 모순이다.

이 코드베이스가 스스로 "실패보다 나쁜 결과" 라고 부르는 상황(`locator_runtime.py` 모듈
독스트링, `CandidateStatus.AMBIGUOUS` 주석)이 실행 경로에 남아 있다.

**결정**: `.first` 폴백을 제거한다. 폴링은 `count()==1` 인 후보만 채택하고, 예산이 끝날
때까지 모호함이 해소되지 않으면 **모호함을 사유로 밝히며 실패**한다. 자동으로 하나를
고르지 않는다.

**기각한 대안**: *`.first` 를 유지하되 경고만 남긴다* — 통과한 테스트의 경고는 읽히지
않는다. 잘못된 요소에 대해 통과한 테스트는 다음 회귀를 못 잡는다는 점에서 실패보다 비싸다.

## R3 — 요소가 조작 가능해질 때까지 따로 기다려야 하는가

**질문**: FR-112(보이고 조작 가능한 상태를 기다림)를 위해 별도 대기가 필요한가, 아니면
Playwright 동작이 이미 기다리는가.

**실측**: DOM 에는 즉시 붙지만 1초 뒤 `display:block` 이 되는 버튼에 대해

```
R5 숨김 상태 count = 1, visible = False
R5 click() 자동 대기 = 1410ms → actionability 자동
R6 wait_for(visible)  = 1320ms
R7 즉시 보이는 요소 wait_for(visible) = 4.7ms
```

**결정**: 동작 계열(`click`·`fill`·`select_option`·`hover`·`drag_to`)은 Playwright 가
actionability 를 스스로 기다린다. **별도의 `wait_for(visible)` 를 동작 앞에 덧붙이지
않는다** — 중복 대기이며 예산만 이중으로 소비한다.

대신 **폴링 단계에서 보임 여부를 채택 선호도로 쓴다**:

1. `count()==1` 이고 **보이는** 후보가 있으면 우선순위 순으로 즉시 채택한다.
2. `count()==1` 이지만 보이지 않는 후보만 있으면 계속 폴링한다 — 로딩 중 숨겨진
   자리표시자를 잡는 것을 막는다.
3. 예산이 끝날 때 보이는 후보가 끝내 없으면, `count()==1` 인 후보 중 우선순위가 가장 높은
   것을 채택한다. 실패시키지 않는다.

3번이 필요한 이유: `hidden` 검증(FR-119)과 화면 밖 입력란처럼 **보이지 않는 것이 정상인**
대상이 있다. 이때 채택 후 남은 예산은 `MIN_ACTION_TIMEOUT_MS` 로 떨어지고, Playwright 의
actionability 오류가 원인을 정확히 말한다 — 우리가 만든 "요소를 찾을 수 없습니다" 보다
정확하다.

**정상 경로 비용**: R7 이 4.7ms 다. 보임 확인을 폴링 라운드에 넣어도 SC-003(100ms 이내)에
여유가 크다.

## R4 — 폴링 주기와 정상 경로 비용

**실측**:

```
R1 count()x5 = 14.8ms   (후보 5종 1라운드)
R4 100ms 주기 폴링 = 2089ms, 21회 확인 (실제 등장 2000ms)
```

**결정**: 폴링 주기 **100ms**.

- 오버슈트 89ms — 요소가 나타난 뒤 다음 동작까지의 추가 지연이 100ms 를 넘지 않는다
  (FR-116, SC-003).
- 라운드당 비용 ~15ms(후보 5종 기준). 100ms 주기에서 점유율 15% 수준이며, 대기 중에만
  발생한다.
- 정상 경로(요소가 즉시 존재)는 **1라운드에서 반환한다.** 폴링 루프에 들어가지 않으므로
  이번 변경의 비용이 0 이다.

**기각한 대안**: *지수 백오프(50→100→200→400ms)* — 최대 주기가 400ms 가 되면 오버슈트가
FR-116 을 위협한다. 총 라운드 수를 줄여 얻는 15ms/라운드의 절감은 그 대가를 정당화하지
않는다.

## R5 — Step 대기 예산 기본값

**질문**: 현재 `DEFAULT_TIMEOUT_MS = 5000` 을 얼마로 올릴 것인가 (FR-115).

**결정**: **10000ms**.

**근거**:
- R1 의 재현 화면(2초 지연)은 5초로도 충분했다 — 결함은 예산이 아니라 알고리즘이었다.
  따라서 상향은 결함 수정이 아니라 여유 확보다.
- 실제 앱의 목록·표는 API 왕복 + 렌더로 3~5초가 드물지 않다. 5초는 그 경계에 걸쳐 있어
  환경 속도에 따라 통과와 실패가 갈린다 — 재실행 성공률 ≥95% 목표를 직접 위협한다.
- 15초 이상은 실패를 확인하는 시간을 늘린다. `느림` 으로 돌리며 디버깅할 때 한 Step 이
  15초씩 매달리면 속도 조절의 이득이 상쇄된다.
- 상한 `le=60_000` 과 Step 별 조정 가능성은 그대로 둔다 (FR-115 후단).

**부수 영향**: 디자인 문서의 `timeout 5000 ms` 표기가 낡는다. 결과 화면은 Step 의 실제
값을 읽으므로 코드 변경은 없고, 표기만 갱신 대상으로 기록한다.

## R6 — Step 간 간격을 일시정지·중지가 즉시 끊게 하는 방법

**질문**: FR-106(간격 도중에도 일시정지·중지 즉시 처리)을 어떻게 만족시키는가.

**현재 구조**: `BrowserSession._resume` 은 `asyncio.Event` 이며 `PAUSE` 에서 `clear()`
된다. **지워지는 것을 기다릴 수는 없다** — `Event.wait()` 는 set 을 기다린다. 그래서
`asyncio.sleep(delay)` 를 그냥 쓰면 간격이 끝날 때까지 일시정지가 반영되지 않는다.

**결정**: 세션에 `_pause_requested: asyncio.Event` 를 하나 더 둔다. `PAUSE` 에서 set,
`RESUME`·`RUN_FROM`·`mark_running` 에서 clear 한다. 간격은 이렇게 잔다.

```
try:
    await asyncio.wait_for(session.wait_pause_requested(), timeout=delay_s)
except TimeoutError:
    pass   # 간격을 다 채웠다
# 일시정지가 요청됐으면 즉시 빠져나와 러너의 기존 일시정지 지점으로 간다
```

- **일시정지**: 이벤트가 set 되는 즉시 `wait_for` 가 반환한다 → 지연 0.
- **중지**: 중지는 태스크 취소이며 `asyncio.wait_for` 는 취소 가능하다 → 지연 0.
- SC-007(1초 이내)을 여유 있게 만족한다.

**기각한 대안**: *`asyncio.sleep(0.05)` 을 반복하며 `is_paused` 를 확인* — 동작은 하지만
평균 25ms 의 불필요한 지연과 깨어남이 생기고, 이벤트 방식보다 검증이 어렵다.

## R7 — `한 스텝씩` 을 새 상태로 만들 것인가

**결정**: **만들지 않는다.** 매 Step 경계에서 `Command.PAUSE` 를 자동으로 적용해 기존
`PAUSED` 상태에 들어간다.

**근거**:
- 편집 허용(불변식 2), 브라우저 유지(불변식 1), 허용 명령 집합이 이미 `PAUSED` 에 대해
  정의·검증돼 있다. 새 상태를 만들면 그 규칙을 전부 다시 써야 하고, 상태 기계의 전이표가
  한 열 늘어난다.
- FR-108 이 요구하는 것이 정확히 "기존 일시정지와 같은 조작" 이다.
- 화면은 `state=paused` 를 이미 처리한다. 추가 작업이 없다.

**구별이 필요한 지점**: 사용자가 직접 누른 일시정지와 `한 스텝씩` 의 자동 일시정지는
화면 문구가 달라야 한다("일시정지됨" vs "한 스텝씩 — 다음 Step 을 기다립니다"). 이는
상태가 아니라 **현재 속도 설정**으로 판별한다. 세션이 속도를 들고 있으므로 화면이 함께
읽으면 된다.

**마지막 Step**: 러너 루프는 `index >= total` 에서 빠져나온다. 간격·자동 일시정지는
**다음 Step 이 존재할 때만** 적용한다 (spec 엣지 케이스).

## R8 — 속도 설정을 어디에 보관할 것인가

**결정**: 사용자 수준 설정 파일 `~/.config/itb/preferences.json`. 프로젝트별이 아닌
**전역 하나**.

**근거**:
- 속도는 **보는 사람의 취향**이지 프로젝트의 속성이 아니다. `itb-project.yaml` 에 넣으면
  개인 취향이 팀 저장소에 커밋되고, 원칙 V 가 "사용자가 버전 관리하는 자산" 이라 부르는
  트리를 오염시킨다.
- `~/.config/itb/registry.json` 이 이미 같은 위치에 있고 `storage/atomic.py` 의 원자적
  쓰기 패턴이 검증돼 있다. 새 메커니즘이 필요 없다.
- FR-110(테스트 정의에 기록하지 않음)을 구조로 만족한다 — 저장 위치가 아예 다르다.

**읽기 실패 시**: 기본값(`보통`)으로 진행하고 실패시키지 않는다. 취향 설정을 못 읽었다고
실행이 막히면 안 된다. 레지스트리가 읽기 실패를 경고로만 처리하는 것과 같은 판단이다.

**기본값**: `보통`(500ms). `빠름`(0ms)이 현재 동작이지만, 이 기능의 존재 이유가 "사람이
못 따라간다" 이므로 기본이 현재 동작이면 아무것도 달라지지 않는다. `보통` 은 20 Step
테스트에 10초를 더한다 — 감수할 만하고, `빠름` 이 한 번의 선택으로 유지된다.

## R9 — 대기 정책을 내보낸 테스트와 어떻게 공유하는가

**질문**: FR-118(제품 안과 내보낸 테스트가 같은 판정)을 원칙 IV·V 를 지키며 만족시키려면.

**현재 구조**: 우선순위 판단은 `itb.locator.strategy` 한 곳에 있고 `.importlinter` 의
`locator-strategy-is-pure` 계약이 순수성을 강제한다. `execution.locator_runtime` 과
`generator.playwright_gen` 이 각자 Playwright 표현으로 바꾼다.

**결정**: **대기 상수와 정책 문서를 `itb.locator.strategy` 에 둔다** — 폴링 주기,
보임 선호 규칙, 기본 예산. 생성기는 이 상수를 읽어 `playwright.config` 의 타임아웃과
생성 코드의 `timeout=` 인자를 만든다.

**한계와 그 기록**: 내보낸 Playwright 테스트는 후보 폴링을 하지 않는다 — 생성기는
`ordered_strategies()[0]` 하나로 코드를 만들기 때문이다. 따라서 "제품 안에서는 하위 후보로
통과했지만 내보낸 테스트에서는 최상위 후보로만 시도한다" 는 차이가 남는다.

이 차이는 **이번 기능이 만든 것이 아니다.** 001 부터 존재했고, 내보내기 자체가 아직
릴리스 게이트 항목이다(헌법 V, 001 plan Complexity Tracking). 이번 기능은 그 차이를
**넓히지 않는 것**까지만 책임진다:

- 대기 예산 기본값(10000ms)을 생성 코드에도 반영한다 — 지연 로딩 화면에서 양쪽이 같은
  시간을 기다린다.
- 폴링 정책을 `strategy` 모듈에 문서화해, 생성기가 나중에 다후보 코드를 낼 때 참조점이
  하나로 남는다.

내보낸 테스트의 다후보 대기는 **내보내기 구현 시점의 과제로 등록**한다. plan 의 Complexity
Tracking 에 기록한다.

## R10 — 실패 분류에 무엇을 더하는가

**현재**: `ErrorCode.STEP_FAILED`, `ErrorCode.TAB_NOT_FOUND`, `ErrorCode.TARGET_UNREACHABLE`
(003 에서 도입). 요소를 못 찾은 실패는 전부 `STEP_FAILED` 로 나간다.

**결정**: 두 코드를 더한다.

| 코드 | 언제 | 사용자가 할 일 |
|---|---|---|
| `ELEMENT_NOT_READY` | 예산 안에 어느 후보도 `count()==1` 이 되지 않음 | 대기 예산을 늘리거나 속도를 낮춰 화면 확인 |
| `ELEMENT_AMBIGUOUS` | 예산 안에 `count()>1` 로만 매칭됨 | Step 상세에서 요소를 다시 집기 |

기존 `STEP_FAILED` 는 그대로 둔다 — 사용할 수 있는 후보가 애초에 하나도 없는 경우
(FR-120 의 "정의 문제")가 여기 남는다.

FR-123 이 요구하는 "문구를 해석하지 않고 분류만으로 갈림" 이 이것으로 성립한다. 003 이
만든 `error_body(code, message, next_action)` 형식을 그대로 쓴다.
