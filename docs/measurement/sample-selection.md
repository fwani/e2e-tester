## 축과 배분

세 축으로 나눠 20건을 고른다. **쉬운 것만 고르지 않기 위한 장치**이므로, 배분을 못 맞추면
못 맞춘 이유를 적는다.

| 축 | 값 | 왜 이 축인가 |
|----|-----|-------------|
| 화면 종류 | `목록` · `폼` · `모달` · `새탭` | 리코더가 다루는 상황이 다르다. `새탭` 은 멀티 탭(FR-030) 경로를 지난다 |
| 난이도 | `단순클릭` · `조건부UI` · `hover메뉴` | `조건부UI` 는 대기·검증을, `hover메뉴` 는 hover Step 을 요구한다 |
| 측정자 | `숙련` · `처음` | SC-001·005 는 학습 비용이 섞이면 값이 달라진다. 나눠 기록해야 구분된다 |

기본 배분은 `recording-sheet.csv` 에 미리 채워 두었다 — 화면 종류 5건씩, 난이도는
단순클릭 7 / 조건부UI 8 / hover메뉴 5, 측정자는 숙련 11 / 처음 9다.

## 제외 기준

아래는 표본에서 뺀다. **뺀 것도 세어 적는다** — 무엇을 못 재는지가 지표만큼 중요하다.

- 외부 결제·본인인증처럼 측정자가 완주할 수 없는 흐름
- 실행마다 데이터가 달라 재실행 판정이 불가능한 흐름 (SC-003 자동 측정 대상과 겹친다)
- 대상 앱의 상태를 되돌릴 수 없는 파괴적 조작

> 제외한 시나리오와 사유: (미기입)

## SC-005 대조군

SC-005 는 **"코드로 직접 작성했을 때 대비"** 단축률이다. 대조군 없이는 계산되지 않는다.

- `baseline_code_seconds` — 같은 시나리오를 Playwright 코드로 직접 작성해 통과시키기까지의 시간.
- `build_seconds` — 같은 시나리오를 이 도구로 작성해 통과시키기까지의 시간.
- **같은 사람이 두 방식을 모두 수행하되, 코드 작성을 먼저 한다.** 도구를 먼저 쓰면 화면 구조를
  이미 파악한 상태로 코드를 짜게 되어 대조군이 짧아진다.
- 두 방식 사이에 같은 시나리오를 반복 학습하는 효과가 남으므로, 대조군은 전체 20건이 아니라
  **축마다 최소 1건씩 6~8건**만 쌍으로 재도 된다. 쌍이 없는 행은 `baseline_code_seconds` 를
  비워 두면 집계에서 자동으로 빠진다.

> 대조군 쌍으로 잰 시나리오: (미기입)
