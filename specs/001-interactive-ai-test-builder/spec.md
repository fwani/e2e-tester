## Clarifications

### Session 2026-09-03

- Q: 일시정지 상태에서 이미 실행이 완료된 Step을 편집하면 이어서 실행을 어떻게 처리해야 하는가? (FR-040) → A: 편집은 테스트 정의에만 반영하고 브라우저 상태는 되돌리지 않는다. 편집 지점이 현재 실행 위치보다 이전이면 경고를 표시하고, 이어서 실행은 항상 브라우저의 실제 현재 상태를 기준으로 진행한다.
- Q: 이 MVP는 어떤 형태로 배포되어 누가 쓰는가? (FR-088) → A: 사용자 1인이 자기 장비에서 실행하는 단독 로컬 도구. 계정·로그인·사용자별 권한 없음. 테스트 정의와 실행 산출물은 로컬 파일로 저장하며 브라우저 세션도 로컬에서 유지한다.
- Q: 사용자가 대상 앱을 직접 조작하는 지점은 제품 화면 안의 임베드 영역인가, 별도 실제 브라우저 창인가? (FR-023, FR-047) → A: 국면별로 분리한다. 관찰 국면(재실행, AI 수행)은 제품 화면 안 읽기 전용 실시간 미러 뷰, 조작 국면(직접 녹화, 직접 동작 추가, 사람 인수)은 실제 브라우저 창에서 조작한다.
  - **⚠️ 010 이 개정했다** (2026-09-09). 조작 국면의 기본 조작 위치는 **제품 화면 안 미러
    영역**이고, 실제 브라우저 창은 **사용자가 명시적으로 요청할 때만** 열리는 폴백이다
    (010 FR-349~FR-353). 대상 브라우저를 창 없이 띄우는 것이 제품 기본값이 되었다
    (010 FR-352). 뒤집은 근거는 `specs/010-headless-mirror-control/spec.md` 「이 기능이
    뒤집는 것」에 출처와 함께 있다 — 조작 국면마다 발생하던 화면·창 왕복을 없애고
    (SC-511), 화면 없는 기계에서도 전체 흐름이 동작하게 한다 (SC-518).
- Q: 로그인 같은 민감 값은 어떻게 보관하고 재실행 시 공급하는가? (FR-089) → A: 비대칭 키 쌍을 사용한다. 민감 값은 공개키로 암호화해 테스트 정의와 분리된 비밀 파일에 보관하고, 실행 시 비밀키로 복호화해 메모리에서만 사용한다. 녹화·기록은 공개키만으로 동작하고 비밀키는 실행 시에만 필요하다.
- Q: MVP의 검증(Assertion) Step은 어느 조건까지 지원하는가? (FR-013, FR-037) → A: 4종 — 요소 보임 / 요소 안 보임·없음 / 텍스트 일치·포함 / URL 일치·포함. 요소 갯수와 입력값 검증은 범위 외.
- Q: 여러 탭(새 창·팝업)을 다루는 시나리오를 지원하는가? (FR-030) → A: 지원한다. 단일 탭과 멀티 탭 모두 MVP 범위. 각 Step은 어느 탭에서 일어난 동작인지를 기록하고, 재실행 시 해당 탭이 열릴 때까지 기다린 뒤 그 탭에서 실행한다. 탭 닫기도 Step으로 기록한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 직접 녹화로 첫 테스트를 만든다 (Priority: P1)

QA 담당자가 테스트 목록에서 "테스트 만들기"를 누르고 "직접 녹화"를 선택한다. 시작 URL을 확인하고 녹화를
시작하면 대상 앱이 화면 안에 열린다. 담당자는 평소 업무하듯 브라우저를 조작한다 — 프로젝트 메뉴를 누르고,
프로젝트 생성을 누르고, 이름에 `TEST`를 입력하고, 저장을 누른다. 녹화를 멈추면 자신이 한 동작이 번호가
붙은 Step 목록으로 나타난다. 각 Step에는 무슨 동작인지(클릭·입력·이동)와 어떤 요소를 대상으로 했는지가
사람이 읽을 수 있는 형태로 표시된다. 이름을 붙여 저장하면 목록에 새 테스트가 생긴다.

**Why this priority**: 코드를 쓰지 않고 테스트를 만들 수 있다는 제품의 최소 약속이다(PRD §3 G1).
이 스토리 하나만 있어도 "녹화해서 Step 목록을 얻는다"는 가치가 성립하며, 다른 모든 스토리가 이 위에 쌓인다.
Step 모델(헌법 원칙 I)이 여기서 처음 정의되므로 기술적으로도 선행이다.

**Independent Test**: 대상 웹 앱 하나를 준비하고, 녹화 시작 → 클릭·입력·선택·화면 이동을 각 1회 이상 수행 →
녹화 정지 → 생성된 Step 목록이 실제 수행 순서와 동작 종류를 정확히 반영하는지, 저장 후 목록에서 다시 열 수
있는지 확인한다. 재실행 기능 없이도 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 프로젝트가 하나 존재하고 시작 URL이 설정된 상태, **When** 사용자가 "직접 녹화"로 녹화를 시작하면,
   **Then** 대상 앱이 시작 URL로 열리고 녹화 중임이 화면에 표시된다.
2. **Given** 녹화가 진행 중인 상태, **When** 사용자가 버튼을 클릭하면, **Then** 클릭 동작이 하나의 Step으로
   Step 목록 끝에 추가되고 대상 요소를 식별하는 정보가 함께 기록된다.
3. **Given** 녹화가 진행 중인 상태, **When** 사용자가 입력 필드에 값을 입력하고 포커스를 벗어나면,
   **Then** 입력 동작과 입력값이 하나의 Step으로 기록된다.
4. **Given** 녹화가 진행 중인 상태, **When** 사용자가 셀렉트 박스에서 항목을 선택하면, **Then** 선택 동작과
   선택된 값이 하나의 Step으로 기록된다.
5. **Given** 녹화가 진행 중인 상태, **When** 페이지 이동이 발생하면, **Then** 화면 이동이 하나의 Step으로 기록된다.
6. **Given** 녹화가 진행 중인 상태, **When** 사용자의 조작으로 새 탭이 열리고 그 탭에서 조작을 계속하면,
   **Then** 새 탭의 조작도 Step으로 기록되고 각 Step에 어느 탭인지가 남는다.
7. **Given** 여러 탭이 열린 상태, **When** 사용자가 탭 하나를 닫으면, **Then** 탭 닫기가 Step으로 기록된다.
8. **Given** 여러 Step이 기록된 상태, **When** 사용자가 녹화를 정지하고 이름을 입력해 저장하면,
   **Then** 테스트가 저장되고 테스트 목록에 Step 개수와 작성 방식 `RECORD`가 함께 표시된다.
9. **Given** 녹화 중 아무 동작도 하지 않은 상태, **When** 사용자가 저장을 시도하면, **Then** Step이 없어
   저장할 수 없음을 알리고 저장하지 않는다.

### User Story 2 - 저장한 테스트를 반복 실행하고 실패 원인을 확인한다 (Priority: P2)

담당자가 테스트 목록에서 `TC-003 데이터 업로드`의 "실행"을 누른다. 테스트가 처음부터 자동 실행되고
각 Step이 통과할 때마다 체크와 소요 시간이 표시된다. Step 05에서 멈추고 결과 화면이 열린다. 결과 화면에는
총 시간(6.41초), 통과/전체(4/5), 멈춘 Step 번호(05)가 요약으로 나오고, 실패 상세에
`"저장" 버튼을 찾을 수 없습니다`와 함께 **시도한 식별 정보가 우선순위 순으로 각각 실패 표시**되어 나온다.
오른쪽 스크린샷을 보니 버튼 이름이 "저장"에서 "적용"으로 바뀌어 있다. 원인이 5초 만에 파악된다.

**Why this priority**: 테스트 자산의 가치는 반복 실행에서 나온다(PRD §3 G4). 실행 없이는 헌법 원칙 II
(Deterministic Replay)와 성공 지표 Replay Success Rate ≥95%를 검증할 수 없다. 실패 진단이 함께 있어야
Test Creation Success Rate가 의미를 가진다.

**Independent Test**: US1로 만든 테스트를 대상 앱 변경 없이 3회 연속 실행해 매번 동일한 PASS 결과가 나오는지
확인한다. 이어서 대상 앱의 버튼 이름을 바꾼 뒤 실행해 해당 Step에서 실패하고, 시도한 식별 정보 목록과 실패
시점 스크린샷이 제공되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 저장된 테스트가 있는 상태, **When** 사용자가 "실행"을 누르면, **Then** 첫 Step부터 순차 실행되고
   진행 중인 Step과 완료된 Step의 소요 시간이 실시간으로 표시된다.
2. **Given** 모든 Step이 통과한 실행, **When** 실행이 끝나면, **Then** 결과가 `PASS`로 기록되고 테스트 목록의
   상태와 마지막 실행 시각이 갱신된다.
3. **Given** 한 Step이 실패한 실행, **When** 실행이 끝나면, **Then** 결과가 `FAIL`로 기록되고 목록 행에
   실패한 Step 번호와 실패 메시지 요약이 함께 표시된다.
4. **Given** 요소를 찾지 못해 실패한 Step, **When** 사용자가 실패 상세를 보면, **Then** 우선순위대로 시도한
   식별 정보가 각각 실패 표시와 함께 나열되고 대기 시간 초과값이 표시된다.
5. **Given** 실패한 실행 결과, **When** 사용자가 결과 화면을 열면, **Then** 실패 시점의 스크린샷과
   브라우저 콘솔 기록·네트워크 기록을 탭으로 전환해 볼 수 있다.
6. **Given** 실패한 실행 결과, **When** 사용자가 "실패한 Step부터 실행"을 누르면, **Then** 실패한 Step 이전은
   재실행하지 않고 해당 Step부터 실행을 시작한다.
7. **Given** 대상 앱이 응답하지 않는 상태, **When** 테스트를 실행하면, **Then** 대기 시간 초과 후 해당 Step이
   실패로 기록되고 실행이 중단되며, 실행 자체가 응답 없이 멈춰 있지 않는다.
8. **Given** 새 탭에서 일어난 동작을 포함한 테스트, **When** 그 테스트를 재실행하면, **Then** 시스템은 해당
   탭이 열리기를 기다린 뒤 그 탭에서 Step을 실행한다.

### User Story 3 - 실행 중 멈춰서 고치고 그 자리에서 이어서 실행한다 (Priority: P3)

담당자가 로그인 → 프로젝트 메뉴까지 녹화하다 실수로 "데이터 메뉴"를 눌렀다. 일시정지를 누르면 브라우저가
현재 화면 그대로 멈추고 "브라우저 세션과 화면 상태를 그대로 유지하고 있습니다"라는 안내가 나온다.
Step 03(데이터 메뉴)을 "불필요"로 판단해 삭제한다. 이어서 "직접 동작 추가"를 눌러 프로젝트 메뉴 → 프로젝트
생성 → 이름 입력 → 저장을 직접 수행해 Step으로 넣는다. "Assertion 추가"로 `TEST`가 보이는지 확인하는 Step도
넣는다. "계속하기"를 누르면 **로그인부터 다시 하지 않고** 현재 브라우저 상태에서 이어서 진행한다.

**Why this priority**: PRD §17이 지목한 핵심 차별점이며 PRD §2 P5(긴 수정 루프)의 직접적 해결책이다.
헌법 원칙 III에 해당하고, PRD §20이 MVP 기술 검증 대상으로 지정한 세 요소 중 하나다.

**Independent Test**: 로그인이 필요한 대상 앱에서 로그인 후 임의 Step을 몇 개 만들고, 일시정지 → Step 삭제 →
직접 동작으로 Step 추가 → Assertion 추가 → 계속하기를 수행한다. 로그인이 재실행되지 않고 이어서 진행되는지,
편집 결과가 Step 목록에 반영되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 실행 또는 녹화가 진행 중인 상태, **When** 사용자가 "일시정지"를 누르면, **Then** 상태 표시가
   `PAUSED`로 바뀌고 브라우저 세션이 종료되지 않으며 현재 화면 상태가 유지된다.
2. **Given** 일시정지 상태, **When** 사용자가 아직 실행되지 않은 Step을 삭제하면, **Then** 해당 Step이 목록에서
   제거되고 이후 Step 번호가 다시 매겨진다.
3. **Given** 일시정지 상태, **When** 사용자가 "직접 동작 추가"를 눌러 브라우저를 조작하면, **Then** 조작이
   Step으로 기록되어 일시정지 위치에 삽입된다.
4. **Given** 일시정지 상태, **When** 사용자가 "Assertion 추가"로 특정 텍스트가 보이는지 확인하는 조건을 지정하면,
   **Then** 검증 Step이 일시정지 위치에 삽입된다.
5. **Given** 일시정지 상태, **When** 사용자가 아직 실행되지 않은 Step들의 순서를 바꾸면, **Then** 변경된 순서가
   목록에 반영되고 이어서 실행할 때 그 순서로 실행된다.
6. **Given** 일시정지 상태에서 Step을 편집한 뒤, **When** 사용자가 "계속하기"를 누르면, **Then** 브라우저를
   다시 시작하지 않고 현재 상태에서 다음 Step부터 실행한다.
7. **Given** 일시정지 상태, **When** 사용자가 특정 Step을 선택해 "이 Step부터"를 누르면, **Then** 해당 Step부터
   실행이 시작된다.
8. **Given** 일시정지 상태, **When** 사용자가 이미 실행이 완료된 Step을 삭제하면, **Then** 그 Step이 목록에서
   제거되지만 브라우저 화면은 되돌아가지 않으며, 해당 편집이 현재 화면에 반영되지 않았다는 경고가 표시된다.
9. **Given** 이미 실행된 Step을 편집해 목록과 화면 상태가 어긋난 상태, **When** 사용자가 직접 동작을 추가해
   화면을 원하는 상태로 만들고 "계속하기"를 누르면, **Then** 시스템은 브라우저의 현재 상태를 기준으로
   다음 Step부터 실행한다.
10. **Given** 일시정지 상태, **When** 사용자가 "중지"를 누르면, **Then** 브라우저 세션이 종료되고 편집된 Step을
   저장할지 버릴지 사용자에게 확인한다.

### User Story 4 - 자연어로 지시하면 AI가 브라우저에서 해보고 그 결과가 테스트가 된다 (Priority: P4)

기획자가 "테스트 만들기 → AI로 만들기"를 선택하고 지시문을 적는다.

> 로그인한 다음 프로젝트 메뉴로 이동해서 TEST라는 프로젝트를 생성하고 프로젝트 목록에 TEST가 있는지 확인해.

AI가 실제 브라우저를 조작하는 모습이 화면에 보이고, 성공한 동작이 오른쪽에 하나씩 Step으로 쌓인다.
6개 Step이 완성된 뒤 "지시문은 테스트로 저장되지 않습니다. AI가 실제로 성공한 동작만 Step으로 저장되고,
다시 돌릴 때는 AI를 쓰지 않습니다"라는 안내와 함께 "테스트로 저장"이 활성화된다. 저장 후 그 테스트를 실행하면
AI 없이 결정적으로 돌아간다.

**Why this priority**: PRD §3 G2이며 제품의 두 번째 진입 경로다. US1의 Step 모델과 US2의 실행이 먼저 있어야
"AI 결과가 결정적 테스트로 변환됨"을 검증할 수 있으므로 그 뒤에 온다.

**Independent Test**: 로그인·생성·검증을 포함한 자연어 지시문 10건을 대상 앱에 대해 실행하고, 생성된 Step으로
저장한 뒤 각 테스트를 재실행한다. 재실행 중 외부 언어모델 호출이 0건인지 확인한다.

**Acceptance Scenarios**:

1. **Given** "AI로 만들기"를 선택한 상태, **When** 사용자가 자연어 지시문을 입력하고 실행하면, **Then** 대상 앱이
   열리고 AI가 브라우저를 제어하는 중임이 화면에 표시된다.
2. **Given** AI가 작업을 수행하는 중, **When AI가** 한 동작을 성공적으로 수행하면, **Then** 그 동작이 Step으로
   기록되어 목록에 즉시 추가된다.
3. **Given** AI가 모든 지시를 수행한 상태, **When** 사용자가 "테스트로 저장"을 누르면, **Then** 기록된 Step이
   테스트로 저장되고 작성 방식이 `AI`로 표시된다.
4. **Given** AI가 만든 테스트가 저장된 상태, **When** 그 테스트를 실행하면, **Then** 외부 언어모델을 호출하지 않고
   기록된 Step만으로 실행된다.
5. **Given** AI가 만든 테스트가 저장된 상태, **When** 저장된 내용을 확인하면, **Then** 자연어 지시문 자체는
   실행 대상으로 저장되어 있지 않다.
6. **Given** AI가 수행 중인 상태, **When** 사용자가 "일시정지"를 누르면, **Then** US3과 동일하게 브라우저 상태를
   유지한 채 멈추고 편집할 수 있다.
7. **Given** 지시문이 대상 앱에서 수행 불가능한 내용인 경우, **When** AI가 시도하면, **Then** 무한 반복하지 않고
   정해진 시도 한계 안에서 중단하고 무엇을 하지 못했는지 사용자에게 알린다.

### User Story 5 - AI가 실패하면 그 세션에서 사람이 이어받는다 (Priority: P5)

`TC-002 프로젝트 삭제`를 AI로 만드는 중 Step 06에서 AI가 멈춘다.
`"프로젝트 삭제 버튼을 찾지 못했습니다."` 그 자리에 네 가지 선택지가 나온다 —
**직접 수행 / AI에게 다시 / 건너뛰기 / 종료**. 담당자가 "직접 수행"을 누르면 상태가 "사람이 녹화 중"으로
바뀌고 "세션 유지"가 표시된다. 브라우저는 AI가 남긴 화면 그대로다. 담당자가 ⋮ → 삭제 → 확인을 누르면
Step 06·07·08이 `HUMAN` 배지와 함께 기록된다. "계속하기"를 누르면 AI가 남은 지시를 다시 맡는다.

**Why this priority**: PRD §20의 핵심 가설 — "완벽한 AI보다, 실패한 부분만 사람이 즉시 고칠 수 있는 방식을 더
신뢰한다" — 을 직접 검증하는 스토리다. US4(AI 생성)와 US3(세션 유지 편집)이 모두 있어야 성립한다.

**Independent Test**: 대상 앱에 AI가 찾기 어려운 요소(예: 숨은 메뉴 안의 삭제)를 포함한 지시문을 주어 AI를
실패시키고, "직접 수행"으로 이어받아 완료한 뒤 "계속하기"로 AI에게 넘긴다. 브라우저가 재시작되지 않고
사람이 만든 Step과 AI가 만든 Step이 한 목록에 함께 남는지 확인한다.

**Acceptance Scenarios**:

1. **Given** AI가 한 동작을 수행하지 못한 상태, **When** 실패가 발생하면, **Then** 브라우저 세션이 유지된 채
   실패한 동작과 실패 이유가 표시되고 직접 수행·AI에게 다시·건너뛰기·종료 네 선택지가 제공된다.
2. **Given** AI 실패 후 선택지가 표시된 상태, **When** 사용자가 "직접 수행"을 선택하면, **Then** 상태가 사람 녹화로
   바뀌고 AI가 남긴 화면 상태 그대로 사용자 조작을 기록하기 시작한다.
3. **Given** 사람이 이어받아 녹화한 Step들, **When** Step 목록을 보면, **Then** 각 Step의 작성 주체(AI / HUMAN)가
   구분되어 표시되지만 실행 방식은 동일하다.
4. **Given** 사람이 이어받아 동작을 마친 상태, **When** 사용자가 "계속하기"를 누르면, **Then** AI가 남은 지시를
   현재 브라우저 상태에서 이어서 수행한다.
5. **Given** AI 실패 후 선택지가 표시된 상태, **When** 사용자가 "AI에게 다시"를 선택하면, **Then** AI가 현재
   브라우저 상태에서 같은 동작을 다시 시도한다.
6. **Given** AI 실패 후 선택지가 표시된 상태, **When** 사용자가 "건너뛰기"를 선택하면, **Then** 실패한 동작은
   Step으로 기록하지 않고 다음 지시로 넘어간다.
7. **Given** AI 실패 후 선택지가 표시된 상태, **When** 사용자가 "종료"를 선택하면, **Then** 브라우저 세션이
   종료되고 그때까지 성공한 Step을 저장할지 확인한다.

### User Story 6 - 일시정지 상태에서 자연어로 Step을 추가한다 (Priority: P6)

담당자가 일시정지 상태에서 직접 조작 대신 입력창에 적는다.

> 생성된 프로젝트가 목록에 있는지 확인해.

AI가 현재 브라우저 화면을 분석해 `TEST` 요소를 찾고 검증 Step 하나를 만들어 목록에 넣는다.
결과는 `05 Assert "TEST" visible` — 직접 만든 Assertion과 구별 없이 동일하게 실행된다.

**Why this priority**: 편집 생산성을 크게 높이지만, US3의 수동 편집과 US4의 AI 실행 기반이 모두 있어야 한다.
없어도 US3만으로 편집이 가능하므로 후순위다.

**Independent Test**: 일시정지 상태에서 자연어 지시 5건(검증 3건, 동작 2건)을 입력해 각각 Step이 만들어지는지,
만들어진 Step이 수동 작성 Step과 동일한 형태로 실행되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 일시정지 상태, **When** 사용자가 자연어로 검증 내용을 입력하면, **Then** AI가 현재 화면을 분석해
   검증 Step을 만들어 일시정지 위치에 삽입한다.
2. **Given** 자연어로 추가된 Step, **When** 그 Step을 확인하면, **Then** 수동으로 만든 Step과 동일한 형태이며
   실행 시 외부 언어모델을 호출하지 않는다.
3. **Given** 일시정지 상태, **When** AI가 현재 화면에서 지시 대상을 찾지 못하면, **Then** Step을 만들지 않고
   찾지 못했음을 알리며 일시정지 상태를 유지한다.

### User Story 7 - Step이 어떤 기준으로 요소를 찾는지 확인하고 고친다 (Priority: P7)

담당자가 Step 02를 열어 상세를 본다. 요소를 찾는 기준이 6단 우선순위로 표시된다 —
`testId: create-project`(사용 중), `role + 이름: button "프로젝트 생성"`(대체 1), `label`(수집되지 않음),
`text: 프로젝트 생성`(대체 2), `고정 속성`(수집되지 않음), `CSS: .project-header button:nth-child(2)`(최후).
아래에는 녹화 시점에 수집된 원본 값과 이 Step의 정의가 그대로 보인다. 대상 앱이 바뀌어 Step이 깨졌을 때는
"다시 집기"를 눌러 브라우저에서 요소를 다시 지정하면 기준이 갱신된다.

**Why this priority**: 헌법 원칙 IV의 사용자 노출 지점이며 Replay Success Rate ≥95% 달성의 진단 수단이다.
다만 이 화면 없이도 US1~US5가 동작하므로 마지막이다.

**Independent Test**: 녹화된 Step의 상세를 열어 수집된 식별 정보와 우선순위가 표시되는지 확인하고, 대상 앱의
요소 속성을 변경한 뒤 "다시 집기"로 갱신해 실행이 다시 통과하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 녹화로 만들어진 Step, **When** 사용자가 Step 상세를 열면, **Then** 수집된 식별 정보 후보 전체와
   적용 우선순위, 각 후보의 수집 여부가 표시된다.
2. **Given** Step 상세가 열린 상태, **When** 사용자가 "다시 집기"를 누르고 브라우저에서 요소를 다시 지정하면,
   **Then** 해당 Step의 식별 정보가 새로 수집된 값으로 갱신된다.
3. **Given** Step 상세가 열린 상태, **When** 사용자가 Step의 표시 이름이나 입력값을 수정하고 저장하면,
   **Then** 변경이 Step 목록과 저장된 테스트에 반영된다.

### Edge Cases

**녹화 관련**

- 사용자가 같은 입력 필드에 여러 번 입력을 수정하면? → 최종 값 하나의 입력 Step으로 병합한다.
- 녹화 중 새 탭이나 팝업 창이 열리면? → 그 탭에 탭 참조를 부여하고 그 안의 조작도 기록한다(FR-030a).
- 재실행 중 Step이 참조하는 탭이 열리지 않으면? → 대기 시간 상한까지 기다린 뒤 어느 탭을 기다렸는지
  명시해 실패로 처리한다(FR-030d).
- 재실행 시 탭이 녹화 때와 다른 순서로 열리면? → 탭 참조가 어긋나 해당 Step이 실패한다. 실패 메시지에
  탭 순서 불일치 가능성을 포함한다.
- 사용자가 원래 탭이 아닌 탭을 먼저 닫으면? → 닫기를 Step으로 기록한다(FR-030c). 이후 Step이 닫힌 탭을
  참조하면 재실행 시 실패한다.
- 동시에 열린 탭이 상한을 넘으면? → 기록을 중단하고 사용자에게 알린다(FR-030g).
- 녹화 중 파일 업로드 대화상자가 열리면? → 운영체제 대화상자는 기록 대상이 아니다. 파일 선택 동작을
  기록하되 실제 파일 경로 의존을 사용자에게 알린다.
- 대상 요소에 식별 가능한 정보가 전혀 없으면(익명 div)? → CSS 경로만 수집된 상태로 Step을 만들고,
  화면 변경에 취약함을 Step 상세에 경고로 표시한다.
- 사용자가 브라우저 뒤로 가기를 누르면? → 화면 이동 Step으로 기록한다.

**일시정지 / 이어서 실행 관련**

- 일시정지 중 대상 앱의 세션이 만료되면? → 이어서 실행 시 해당 Step이 실패하고, 세션 만료 가능성을
  실패 메시지에 포함한다.
- 일시정지 중 사용자가 브라우저를 직접 조작해 화면이 예상과 달라지면? → 이어서 실행은 현재 상태를 기준으로
  진행한다. 시스템은 화면 상태를 되돌리지 않는다.
- 이어서 실행할 남은 Step이 없으면? → "계속하기"를 비활성화하고 저장 또는 중지를 안내한다.
- 이미 실행된 Step을 편집해 Step 목록과 화면 상태가 어긋나면? → 시스템은 되돌리지 않고 경고만 표시한다.
  사용자가 직접 동작 추가로 화면을 정상화하거나, 처음부터 재실행하거나, 임의 Step부터 실행할 수 있다.
  (FR-040a~FR-040d)
- 일시정지 중 브라우저 창이 외부에서 강제 종료되면? → 세션 유실을 알리고, 그때까지의 Step은 보존한다.
- 사용자가 조작 국면에서 실제 브라우저 창을 직접 닫으면? → 세션 유실로 처리하고 기록된 Step을 보존하며,
  이어서 실행 대신 저장 또는 처음부터 재실행을 안내한다.
- 조작 국면에서 사용자가 실제 창을 찾지 못하면? → 시스템은 제품 화면에 창을 다시 앞으로 가져오는 수단을
  제공해야 한다.

**AI 관련**

- 자연어 지시문이 비어 있거나 대상 앱과 무관하면? → 실행하지 않고 지시문을 구체화하도록 안내한다.
- AI가 같은 동작을 반복하며 진전이 없으면? → 시도 한계에 도달하면 실패로 처리하고 US5의 선택지를 제시한다.
- AI가 파괴적 동작(대량 삭제 등)을 하려 하면? → MVP는 대상 앱 안에서만 동작하며, 지시문 범위를 벗어난
  동작은 수행하지 않는다.
- 언어모델 호출이 실패하거나 응답하지 않으면? → 작성 단계에서만 영향을 받아야 하며, 저장된 테스트 실행에는
  영향이 없어야 한다. 작성 중 실패 시 그때까지의 Step을 보존한다.
- AI가 로그인 화면에서 자격 증명을 필요로 하면? → 민감 변수로 등록해 공개키로 암호화하고, 로그인 Step은
  변수 참조로 기록한다(FR-089). 작성 단계는 비밀키를 요구하지 않는다.

**실행 관련**

- 검증 Step의 조건이 성립하지 않으면? → 해당 Step을 실패로 기록하고 실행을 중단한다.
- '요소 안 보임' 검증에서 요소가 아직 사라지는 중이면? → 대기 시간 상한까지 사라짐을 기다린 뒤 판정한다.
  요소가 처음부터 없던 경우와 사라진 경우를 모두 통과로 처리한다.
- 식별 정보 후보 중 여러 개가 서로 다른 요소를 가리키면? → 우선순위가 가장 높은 후보의 결과를 사용하고,
  후보 간 불일치를 실행 로그에 남긴다.
- 실행 도중 사용자가 창을 닫거나 페이지를 이탈하면? → 실행은 서버 측에서 계속되거나 중단 처리되어야 하며,
  결과가 유실된 채 남지 않는다.
- 같은 테스트를 동시에 두 번 실행하면? → MVP는 테스트당 동시 실행 1건으로 제한하고 두 번째 요청을 거절한다.

**데이터 / 보안 관련**

- 녹화 중 비밀번호를 입력하면? → 입력값을 그대로 저장하지 않고 변수 참조로 저장하며, 공개키로 암호화해
  별도 비밀 파일에 넣고, 화면·로그·결과에는 마스킹해 표시한다(FR-082, FR-089).
- 비밀키 없이 테스트를 실행하면? → 민감 변수를 쓰는 Step에서 사유를 명시해 실패한다. 빈 값으로 진행하지 않는다.
- 비밀키를 분실하면? → 기존 암호문은 복구할 수 없다. 시스템은 해당 민감 변수를 다시 입력받아 재암호화하는
  수단을 제공해야 한다.
- 공개키가 교체되면? → 이전 암호문은 새 키로 읽을 수 없으므로 재입력이 필요함을 사용자에게 알린다.
- 저장된 테스트의 Step이 0개가 되도록 모두 삭제하면? → 저장을 거절하거나 테스트 삭제를 안내한다.
- 대상 앱 URL이 접근 불가하면? → 녹화·실행 시작 시점에 실패로 처리하고 원인을 알린다.

## Requirements *(mandatory)*

### Functional Requirements

#### 프로젝트 및 테스트 관리

- **FR-001**: 시스템은 사용자가 프로젝트를 생성하고 프로젝트에 속한 테스트를 관리할 수 있게 해야 한다.
- **FR-002**: 시스템은 프로젝트 안의 테스트 목록을 제공해야 하며, 각 행에 최근 실행 상태(`PASS`/`FAIL`/
  미실행), 테스트 ID, 이름, Step 개수, 작성 방식(`RECORD`/`AI`), 마지막 실행 시각을 표시해야 한다.
  - **FR-002a**: 작성 방식 배지는 **테스트를 시작한 방식**으로 결정한다. AI로 시작한 뒤 사람이 이어받아
    Step을 추가한 테스트도 `AI` 로 표시한다. Step별 작성 주체는 Step 목록에서 구분해 보여주므로(FR-075)
    목록 배지는 테스트의 출발점을 나타내는 값으로 고정한다.
- **FR-003**: 시스템은 테스트 목록에서 이름 또는 ID로 테스트를 검색할 수 있게 해야 한다.
- **FR-004**: 시스템은 테스트 목록에 전체·`PASS`·`FAIL` 건수를 표시해야 한다.
- **FR-005**: 최근 실행이 실패한 테스트의 목록 행에는 실패한 Step 번호와 실패 메시지 요약을 함께 표시해야 한다.
- **FR-006**: 시스템은 테스트 목록에서 각 테스트를 바로 실행하거나(미실패 시) 마지막 실행 결과를 열 수 있게
  해야 한다.
- **FR-007**: 사용자는 테스트를 생성·이름 변경·삭제할 수 있어야 한다. 삭제는 되돌릴 수 없으므로 확인을 받아야 한다.
- **FR-008**: 시스템은 테스트 생성 시 작성 방식(직접 녹화 / AI로 만들기), 시작 URL, 브라우저 종류를 선택하게
  해야 한다.
- **FR-009**: 시스템은 두 작성 방식이 동일한 Step 모델로 저장됨을 생성 화면에서 사용자에게 알려야 한다.

#### Step 모델 (헌법 원칙 I)

- **FR-010**: 시스템은 사람이 만든 Step과 AI가 만든 Step을 **하나의 동일한 Step 모델**로 저장해야 한다.
  작성 주체별로 별도의 테스트 표현을 두어서는 안 된다.
- **FR-011**: Step 모델은 문서화된 사람이 읽을 수 있는 평문 구조 형식으로 저장되어야 하며, 최소한
  테스트 식별자, 테스트 이름, 변수 정의, 순서를 가진 Step 목록을 표현해야 한다.
- **FR-012**: 각 Step은 고유 식별자, 동작 종류, 대상 요소의 식별 정보, 필요한 경우 입력값 또는 검증 조건,
  사람이 읽을 수 있는 표시 이름, 그리고 **그 동작이 일어난 탭 참조**를 가져야 한다.
- **FR-013**: 시스템은 최소한 클릭, 입력, 선택, 화면 이동, 검증, 탭 닫기 여섯 가지 동작 종류를 지원해야 한다.
- **FR-013a**: 검증 Step은 다음 **4종**의 조건을 지원해야 한다.
  1. **요소 보임** — 지정한 요소가 화면에 보인다.
  2. **요소 안 보임 / 없음** — 지정한 요소가 화면에 없거나 보이지 않는다. (삭제·닫힘 검증용)
  3. **텍스트 일치 / 포함** — 지정한 요소 또는 화면에 특정 텍스트가 일치하거나 포함되어 있다.
  4. **URL 일치 / 포함** — 현재 화면 주소가 특정 값과 일치하거나 그 값을 포함한다.
- **FR-013b**: 검증 조건의 비교 값에는 `{{변수명}}` 참조를 사용할 수 있어야 한다.
- **FR-013c**: 요소 갯수 검증과 입력 필드 현재값 검증은 MVP 범위가 아니다.
- **FR-014**: 각 Step은 작성 주체(사람 / AI)를 부가 정보로 기록해야 하며, 이 정보가 Step의 실행 방식을
  바꾸어서는 안 된다.
- **FR-015**: 시스템은 테스트 정의 안에서 `{{변수명}}` 형태의 변수 참조를 값으로 사용하고 실행 시 치환할 수
  있어야 한다. (MVP 범위: 테스트 단위 변수 정의와 치환만 포함. 환경별 변수 세트 관리는 범위 외 — P2)
- **FR-016**: 시스템은 저장된 테스트 정의를 사람이 확인할 수 있는 형태로 화면에 보여줄 수 있어야 한다.

#### 대상 요소 식별 (헌법 원칙 IV)

- **FR-017**: 녹화 시 시스템은 대상 요소에 대해 단일 식별 정보만 저장해서는 안 되며, 확보 가능한 후보를
  모두 수집해야 한다: 테스트 식별자, 접근성 역할, 접근성 이름, 연결된 라벨, 표시 텍스트, 안정적 속성, CSS 경로.
- **FR-018**: 실행 시 요소 탐색은 다음 우선순위를 따라야 한다:
  테스트 식별자 → 역할 + 접근성 이름 → 라벨 → 표시 텍스트 → 안정적 속성 → CSS 경로.
  - **FR-018a**: 이름·텍스트 기반 후보의 매칭은 **완전 일치**여야 한다. 부분 일치를 허용하면 대체 후보가
    조용히 다른 요소를 잡아 테스트가 잘못된 대상에 대해 통과할 수 있다 — 실패보다 나쁜 결과다.
- **FR-019**: 시스템은 Step 상세 화면에서 각 후보의 값, 적용 순위, 수집 여부를 표시해야 한다.
  - **FR-019a**: 화면에 표시하는 상태는 저장된 후보 상태와 적용 순위에서 다음 규칙으로 파생해야 한다.
    확보된 후보(검증 통과) 중 우선순위가 가장 높은 것 → `사용 중`. 그다음부터 순서대로 → `대체 1`,
    `대체 2` …. 우선순위 최하위 후보(CSS)가 확보된 경우 → `최후`. 값을 확보하지 못한 후보 →
    `수집되지 않음`. **값은 있으나 여러 요소를 매칭하는 후보 → `모호(사용 불가)`.** 값은 있으나 다른
    요소를 가리키는 후보 → `검증 실패`. 표시 상태는 저장 데이터에서 계산되며 별도로 저장하지 않는다.
  - **FR-019b**: 시스템은 여러 요소를 매칭하는 후보를 **확보된 후보로 세어서는 안 되며** 우선순위
    해석에서 건너뛰어야 한다. 실행 시 어느 요소를 잡을지 결정할 수 없기 때문이다.
- **FR-020**: 사용자는 Step 상세에서 "다시 집기"를 통해 브라우저에서 대상 요소를 다시 지정하고 식별 정보를
  갱신할 수 있어야 한다.
- **FR-021**: 요소 탐색 실패 시 시스템은 우선순위대로 시도한 후보 각각의 실패 여부와 대기 시간 초과값을
  실패 상세에 표시해야 한다.
- **FR-022**: 요소 식별 정보 해석 규칙은 제품 내 실행과 생성되는 테스트 코드 양쪽에서 동일해야 한다.

#### 직접 녹화 (Manual Record)

- **FR-023**: 시스템은 지정한 시작 URL로 대상 앱을 **실제 브라우저 창**에 열고, 사용자가 그 창에서 직접
  조작할 수 있게 해야 한다.
  - **FR-023a**: 사용자가 직접 조작하는 국면(직접 녹화, 일시정지 중 직접 동작 추가, 사람 인수)에서 시스템은
    실제 브라우저 창을 사용자에게 노출하고 앞으로 가져와야 한다. 탭이 여러 개면 대상 탭을 앞으로
    가져온다(FR-030e).
  - **FR-023b**: 조작 국면에서 제품 화면의 브라우저 영역은 조작 대상이 아니며, 실제 창에서 조작 중임을
    사용자에게 명시해야 한다.
  - **FR-023c**: 시스템은 사용자 조작을 제품 화면을 경유하지 않고 대상 브라우저에서 직접 관찰해 기록해야 한다.
    한글 입력 조합, 마우스 hover, 드래그, 파일 선택 대화상자에서도 조작 충실도가 유지되어야 한다.
- **FR-024**: 녹화 중 시스템은 사용자의 클릭·입력·선택·화면 이동을 각각 Step으로 기록해야 한다.
- **FR-025**: 같은 입력 필드에 대한 연속 입력은 최종 값 하나의 Step으로 병합해야 한다.
- **FR-026**: 녹화 중 시스템은 현재 녹화 중임과 기록된 Step 개수를 항상 표시해야 한다.
- **FR-027**: 기록된 각 Step은 화면에 번호, 사람이 읽을 수 있는 표시 이름, 동작 종류, 적용된 식별 정보
  요약과 함께 표시되어야 한다.
- **FR-028**: 사용자는 녹화를 정지하고 이름을 지정해 테스트로 저장할 수 있어야 한다.
- **FR-029**: Step이 하나도 없는 테스트는 저장할 수 없어야 한다.
- **FR-030**: 시스템은 **단일 탭과 여러 탭 시나리오를 모두 지원해야 한다.** 녹화 중 새 탭이나 팝업이
  열리면 그 탭에서의 사용자 조작도 기록해야 한다.
  - **FR-030a**: 시스템은 탭마다 안정적인 참조를 부여해야 하며, 각 Step에 그 동작이 일어난 탭 참조를
    기록해야 한다. 최초 탭과 이후 열린 탭이 구분되어야 한다.
  - **FR-030b**: 새 탭이 열리는 것 자체는 별도 Step으로 기록하지 않는다. 새 탭을 열게 한 동작(클릭 등)이
    이미 Step으로 기록되기 때문이다.
  - **FR-030c**: 사용자가 탭을 닫으면 시스템은 탭 닫기를 Step으로 기록해야 한다. 팝업을 닫은 뒤 원래 탭의
    상태를 검증하는 흐름이 성립해야 한다.
  - **FR-030d**: 재실행 시 시스템은 Step이 참조하는 탭이 아직 없으면 대기 시간 상한까지 그 탭이 열리기를
    기다린 뒤 실행해야 한다. 상한을 넘기면 해당 Step을 실패로 처리하고 어느 탭을 기다렸는지 알려야 한다.
  - **FR-030e**: 사용자가 직접 조작하는 국면에서 시스템은 다음 Step이 대상으로 하는 탭을 앞으로 가져와야
    한다(FR-023a와 동일한 방식).
  - **FR-030f**: 관찰 국면의 읽기 전용 미러는 현재 활성 탭을 표시하고, 사용자가 열려 있는 탭 중 하나를 골라
    볼 수 있게 해야 한다.
  - **FR-030g**: 시스템은 동시에 열린 탭 수의 상한을 두어야 하며, 상한을 넘으면 기록을 중단하고 사용자에게
    알려야 한다.

#### 상태 유지 대화형 실행기 (헌법 원칙 III)

- **FR-031**: 사용자는 녹화 중 또는 실행 중 언제든 일시정지할 수 있어야 한다.
- **FR-032**: 일시정지 시 시스템은 브라우저 세션을 종료해서는 안 되며, 인증 상태·화면 위치·입력 내용을
  포함한 현재 상태를 유지해야 한다.
- **FR-033**: 시스템은 일시정지 중 브라우저 상태가 유지되고 있음을 화면에 명시해야 한다.
- **FR-034**: 시스템은 일시정지 위치를 Step 목록에서 시각적으로 구분해 표시해야 한다.
- **FR-035**: 일시정지 상태에서 사용자는 Step을 삭제·수정·추가하고 순서를 변경할 수 있어야 한다.
  - **FR-035a**: Step 편집 명령은 **일시정지 상태에서만** 유효하다. 다른 상태에서 편집 요청이 오면
    시스템은 요청을 거절하고 현재 상태와 편집이 불가한 이유를 알려야 한다. 조용히 무시하거나 부분
    적용해서는 안 된다.
- **FR-036**: 일시정지 상태에서 사용자는 브라우저를 직접 조작해 그 동작을 Step으로 일시정지 위치에 삽입할 수
  있어야 한다.
- **FR-037**: 일시정지 상태에서 사용자는 FR-013a의 4종 조건 중 하나를 골라 검증 Step을 추가할 수 있어야 한다.
- **FR-038**: 사용자가 "계속하기"를 선택하면 시스템은 브라우저를 재시작하지 않고 현재 상태에서 다음 Step부터
  실행해야 한다.
- **FR-039**: 사용자는 임의의 Step을 지정해 그 Step부터 실행을 시작할 수 있어야 한다.
- **FR-040**: 시스템은 이미 실행이 완료된 Step에 대한 수정·삭제와, 현재 실행 위치보다 앞으로의 순서 이동을
  **허용해야 한다**. 이때 다음 규칙을 따른다.
  - **FR-040a**: 편집은 테스트 정의(Step 목록)에만 반영해야 한다. 시스템은 편집을 이유로 브라우저 화면
    상태를 되돌리거나 대상 앱에 보상 동작을 수행해서는 안 된다.
  - **FR-040b**: 편집 지점이 현재 실행 위치보다 이전인 경우, 시스템은 해당 편집이 현재 화면 상태에는
    적용되지 않았음을 경고로 표시해야 한다.
  - **FR-040c**: "계속하기"는 항상 브라우저의 실제 현재 상태를 기준으로 다음 Step부터 실행해야 한다.
    시스템은 Step 목록과 화면 상태의 정합성을 자동으로 복원하려 시도해서는 안 된다.
  - **FR-040d**: 어긋난 화면 상태를 정상화하는 책임은 사용자에게 있다. 시스템은 이를 위한 수단으로
    직접 동작 추가(FR-036)와 임의 Step부터 실행(FR-039)을 제공해야 한다.
- **FR-041**: 브라우저 세션이 외부 요인으로 유실되면 시스템은 **어느 상태에서든** 이를 사용자에게 알리고
  그때까지 기록된 Step을 보존해야 한다.
  - **FR-041a**: 재실행 중(관찰 국면) 유실이 발생하면 시스템은 실행을 실패로 종료하고, 그때까지의 Step별
    결과와 수집한 산출물을 보존해 결과 화면에서 볼 수 있게 해야 한다. 세션 유실이 실패 사유로 기록되어야
    한다.
  - **FR-041b**: AI 수행 중 유실이 발생하면 시스템은 AI 루프를 중단하고 그때까지 성공한 Step을 보존하며,
    저장 여부를 사용자에게 확인해야 한다.
  - **FR-041c**: 세션이 유실된 뒤 시스템은 **저장과 처음부터 재실행만** 허용해야 한다. 이어서 실행과
    Step 편집은 허용해서는 안 된다 — 유지할 브라우저 상태가 없기 때문이다.
- **FR-042**: 사용자가 실행을 중지하면 시스템은 브라우저 세션을 종료하고 편집된 Step의 저장 여부를 확인해야 한다.
- **FR-043**: 시스템은 하나의 테스트에 대해 동시에 하나의 실행 세션만 허용해야 한다.
- **FR-043a**: 시스템은 **현재 세션 상태에서 정의되지 않은 모든 명령**을 거절해야 하며, 거절 시 현재
  상태와 그 상태에서 가능한 행동을 함께 알려야 한다. 상태별로 개별 규정이 없는 명령도 이 규칙을 따른다.
  부분 적용, 조용한 무시, 상태를 임의로 바꾸는 처리는 금지한다.

#### 결정적 실행 (헌법 원칙 II)

- **FR-044**: 저장된 테스트의 실행 경로에서 시스템은 외부 언어모델을 호출해서는 안 된다.
- **FR-045**: 시스템은 저장된 Step 정의만을 근거로 테스트를 실행해야 한다.
- **FR-046**: 실행 중 시스템은 현재 실행 중인 Step과 이미 완료된 Step의 통과/실패 여부, Step별 소요 시간을
  실시간으로 표시해야 한다.
- **FR-047**: 관찰 국면(저장된 테스트 재실행, AI 수행 중)에서 시스템은 대상 브라우저 화면을 제품 화면 안에
  **읽기 전용으로 실시간 표시**하고 현재 실행 중인 동작을 함께 보여주어야 한다.
  - **FR-047a**: 읽기 전용 표시 영역은 사용자 입력을 대상 브라우저로 전달해서는 안 된다.
    - **⚠️ 010 이 개정했다** (2026-09-09 · `specs/010-headless-mirror-control/spec.md`
      「이 기능이 뒤집는 것」). 조작 국면(직접 녹화·직접 동작 추가·사람 인수·일시정지)에서는
      **전달한다** (010 FR-314). 관찰 국면에서는 종전과 같이 전달하지 않는다 (010 FR-315).
      전달 가능 여부는 국면 × 조작 권한표가 정하며 화면이 스스로 판단하지 않는다 (010 FR-316).
      **FR-047b·c·d·e 는 개정되지 않았다.**
  - **FR-047b**: 읽기 전용 표시가 지연되거나 끊겨도 실행 자체가 영향을 받아서는 안 된다.
  - **FR-047c**: 탭이 여러 개면 미러는 활성 탭을 표시하고 사용자가 다른 탭을 선택해 볼 수 있어야 한다
    (FR-030f).
  - **FR-047d**: 미러는 **모든 세션 상태에서 계속 동작해야 한다.** 조작 국면(직접 녹화, 직접 동작 추가,
    사람 인수)에서도 미러는 읽기 전용으로 화면을 계속 보여주며, 다만 조작 대상이 아니고 실제 창에서
    조작 중임을 함께 표시한다(FR-023b). 일시정지와 AI 실패 대기 상태에서도 미러는 마지막 화면을 계속
    보여준다 — 브라우저 세션이 유지되고 있음을 사용자가 눈으로 확인하는 수단이기 때문이다(FR-033).
  - **FR-047e**: 세션이 종료되거나 유실되면 미러를 중단하고 그 사실을 표시해야 한다.
- **FR-048**: 실행이 끝나면 시스템은 전체 결과를 `PASS` 또는 `FAIL`로 기록해야 한다.
- **FR-049**: 한 Step이 실패하면 시스템은 실행을 중단하고 실패한 Step을 기록해야 한다.
- **FR-050**: 시스템은 실행 결과 요약으로 총 소요 시간, 통과 Step 수 / 전체 Step 수, 멈춘 Step 번호를
  제공해야 한다.
- **FR-051**: 시스템은 Step별 실행 결과와 소요 시간을 목록으로 제공해야 한다.
- **FR-052**: 시스템은 실패 시점의 스크린샷을 저장하고 결과 화면에서 볼 수 있게 해야 한다.
- **FR-053**: 시스템은 실행 중 발생한 브라우저 콘솔 기록과 네트워크 기록을 수집해 결과 화면에서
  전환해 볼 수 있게 해야 한다.
- **FR-054**: 시스템은 실패 상세에 사람이 읽을 수 있는 실패 이유를 제공해야 한다.
- **FR-055**: 사용자는 결과 화면에서 실패한 Step부터 다시 실행하거나 처음부터 다시 실행할 수 있어야 한다.
- **FR-056**: 사용자는 결과 화면에서 실패한 Step의 상세로 바로 이동해 수정할 수 있어야 한다.
- **FR-057**: 각 Step 실행에는 대기 시간 상한이 있어야 하며, 상한을 넘기면 실패로 처리하고 실행이 응답 없이
  멈춰 있어서는 안 된다.
- **FR-058**: 실행 결과에는 어떤 브라우저로 실행했는지가 표시되어야 한다.

#### AI 기반 작성 (자연어 → 결정적 Step)

- **FR-059**: 사용자는 수행할 작업을 자연어로 입력할 수 있어야 한다.
- **FR-060**: 시스템은 자연어 지시를 근거로 실제 브라우저에서 작업을 수행해야 하며, 수행 중임과 AI가
  브라우저를 제어하고 있음을 화면에 표시해야 한다.
- **FR-061**: 시스템은 AI가 **성공적으로 수행한 동작만** Step으로 기록해야 한다. 실패한 시도는 Step으로
  기록해서는 안 된다.
- **FR-062**: 기록되는 Step은 FR-010의 동일한 Step 모델을 따라야 하며, 직접 녹화로 만든 Step과 구조적으로
  같아야 한다.
- **FR-063**: 시스템은 자연어 지시문 자체를 실행 대상으로 저장해서는 안 된다. 지시문은 작성 의도의 기록으로만
  보관할 수 있다.
- **FR-064**: 시스템은 저장 시 "지시문은 저장되지 않으며 재실행 시 AI를 쓰지 않는다"는 점을 사용자에게
  명시해야 한다.
- **FR-065**: AI 수행 중 사용자는 일시정지할 수 있어야 하고, 일시정지 시 FR-031~FR-042가 동일하게 적용되어야 한다.
- **FR-066**: AI의 동작 시도에는 상한이 있어야 하며, 상한에 도달하면 진전 없이 반복하지 않고 중단해야 한다.
- **FR-067**: 언어모델 호출이 실패하면 시스템은 그때까지 기록된 Step을 보존하고 실패를 사용자에게 알려야 한다.
- **FR-068**: AI는 사용자가 지시한 범위를 벗어난 동작을 수행해서는 안 된다.

#### AI 실패 → 사람 인수 (Human Takeover)

- **FR-069**: AI가 한 동작을 수행하지 못하면 시스템은 브라우저 세션을 유지한 채 실패한 동작과 실패 이유를
  표시해야 한다.
- **FR-070**: AI 실패 시 시스템은 네 가지 선택지를 제공해야 한다: 직접 수행, AI에게 다시 지시, 건너뛰기, 종료.
- **FR-071**: "직접 수행"을 선택하면 시스템은 AI가 남긴 브라우저 상태를 그대로 유지한 채 사용자 조작을
  Step으로 기록해야 하며, 세션이 유지되고 있음을 화면에 표시해야 한다.
- **FR-072**: "AI에게 다시"를 선택하면 시스템은 현재 브라우저 상태에서 같은 동작을 다시 시도해야 한다.
- **FR-073**: "건너뛰기"를 선택하면 시스템은 실패한 동작을 Step으로 기록하지 않고 다음 지시로 넘어가야 한다.
- **FR-074**: "종료"를 선택하면 시스템은 세션을 종료하고 그때까지 성공한 Step의 저장 여부를 확인해야 한다.
- **FR-075**: 사람이 이어받아 만든 Step은 목록에서 작성 주체가 구분되어 표시되어야 하나, AI가 만든 Step과
  동일하게 실행되어야 한다.
- **FR-076**: 사람이 이어받은 뒤 "계속하기"를 선택하면 AI가 남은 지시를 현재 브라우저 상태에서 이어서
  수행해야 한다.
- **FR-077**: 시스템은 이어서 진행할 때 AI가 남은 지시를 다시 맡는다는 점을 사용자에게 알려야 한다.

#### 자연어 Step 추가

- **FR-078**: 일시정지 상태에서 사용자는 자연어로 추가할 동작이나 검증 내용을 입력할 수 있어야 한다.
- **FR-079**: 시스템은 현재 브라우저 화면을 분석해 자연어 지시에 대응하는 Step을 만들어 일시정지 위치에
  삽입해야 한다.
- **FR-080**: 자연어로 만들어진 Step은 수동으로 만든 Step과 동일한 형태여야 하며, 실행 시 언어모델을
  호출해서는 안 된다.
- **FR-081**: 현재 화면에서 지시 대상을 찾지 못하면 시스템은 Step을 만들지 않고 그 사실을 알리며 일시정지
  상태를 유지해야 한다.

#### 데이터, 보안, 접근 (헌법 보안 요건)

- **FR-082**: 시스템은 비밀번호 유형 입력 필드와 사용자가 민감하다고 표시한 필드의 입력값을 평문으로
  저장해서는 안 되며, 테스트 정의에는 변수 참조로만 저장하고 실제 값은 FR-089의 방식으로 보관해야 한다.
  - **FR-082a**: 비밀번호 유형 입력 필드는 시스템이 **자동으로** 민감하다고 판정해야 한다.
  - **FR-082b**: 그 외 입력 Step에 대해서는 사용자가 Step 편집 화면에서 **민감 여부를 지정**할 수 있어야
    한다. 민감으로 지정하면 시스템은 기존에 저장된 평문 값을 변수 참조로 바꾸고 값을 암호화해 옮겨야 한다.
- **FR-083**: 시스템은 민감 값을 화면, 실행 로그, 결과 상세에서 마스킹해 표시해야 한다.
- **FR-084**: 시스템은 자격 증명·비밀 값을 코드나 테스트 정의 파일에 고정 값으로 포함해서는 안 된다.
- **FR-085**: 시스템은 경계에서 입력을 검증해야 한다: 사용자 입력 URL, 테스트 이름, 불러온 테스트 정의,
  언어모델로 전달되는 자연어 입력, 대상 화면에서 읽어온 내용.
- **FR-086**: 시스템은 대상 앱을 브라우저로 조작하는 범위를 넘어서는 동작(임의 명령 실행 등)을 Step으로
  수행해서는 안 된다.
- **FR-087**: 실패한 Step은 진단 가능한 결과(실패 이유, 스크린샷, 로그)를 반드시 남겨야 하며, 조용히
  통과 처리되거나 처리되지 않은 오류로 실행기가 중단되어서는 안 된다.
- **FR-088**: 시스템은 사용자 1인이 자기 장비에서 실행하는 **단독 로컬 도구**로 동작해야 한다.
  계정, 로그인, 사용자별 권한을 두어서는 안 된다.
  - **FR-088a**: 시스템은 제품 자체 접근을 위한 인증을 요구하지 않는다. 그 대신 제품 서비스는 로컬 장비에서만
    접근 가능하도록 바인딩해야 하며, 외부 네트워크에 노출해서는 안 된다.
  - **FR-088b**: 테스트 정의는 사용자가 지정한 로컬 디렉터리에 평문 파일로 저장해야 하며, 사용자가 그대로
    버전 관리 시스템에 넣을 수 있어야 한다.
  - **FR-088c**: 실행 결과 산출물(스크린샷, 콘솔 기록, 네트워크 기록)은 로컬 파일 시스템에 저장해야 한다.
  - **FR-088d**: 브라우저 세션은 사용자의 로컬 장비에서 생성·유지해야 한다.
- **FR-089**: 시스템은 민감 값을 **비대칭 키 쌍으로 암호화해 보관하고 실행 시 복호화**해야 한다.
  - **FR-089a**: 시스템은 로컬에 공개키·비밀키 쌍을 생성·보관해야 하며, 사용자가 기존 키 쌍을 지정할 수도
    있어야 한다.
  - **FR-089b**: 민감 값은 **공개키로만 암호화**해 저장해야 한다. 따라서 녹화·기록·자연어 작성 단계는
    비밀키 없이도 동작해야 한다.
  - **FR-089c**: 암호문은 테스트 정의 파일과 **분리된 비밀 파일**에 보관해야 한다. 테스트 정의 파일에는
    `{{변수명}}` 참조만 남아야 하며, 암호문조차 정의 파일에 넣어서는 안 된다.
  - **FR-089d**: 실행 시 시스템은 비밀키로 복호화한 값을 메모리에서만 사용해야 한다. 복호화된 값은
    다음 어디에도 기록되어서는 안 된다: 테스트 정의 파일, 비밀 파일 외의 저장소, 화면, 실행 로그,
    실패 상세와 오류 메시지, 스크린샷 메타데이터, 콘솔 기록, 네트워크 기록, 임시 파일,
    API 응답, 실시간 이벤트, **그리고 시스템이 생성하는 테스트 코드**.
  - **FR-089d-1**: 시스템이 Step으로부터 테스트 코드를 생성할 때 민감 변수는 **변수 참조로만** 생성해야
    한다. 복호화된 값을 코드에 넣어서는 안 된다. (내보내기 기능 자체는 이번 범위가 아니나, 코드 생성
    모듈은 이번 범위에 있다)
  - **FR-089e**: 비밀키는 버전 관리 대상에서 제외되어야 하고, 소유자만 읽을 수 있도록 파일 권한이
    제한되어야 하며, 선택적으로 암호구(passphrase)로 보호할 수 있어야 한다.
  - **FR-089e-1**: 시스템은 비밀키를 사용하기 전에 **파일 권한을 확인해야 한다.** 소유자 외에 읽기 권한이
    열려 있으면 시스템은 그 사실을 경고로 알리고 권한을 좁히는 방법을 안내해야 한다. 권한을 임의로
    변경하지 않으며, 경고 후 실행은 사용자 선택에 맡긴다.
  - **FR-089e-2**: 암호구가 설정된 비밀키에 잘못된 암호구가 주어지면 시스템은 이를 **복호화 실패와 구분해**
    "암호구가 올바르지 않음"으로 알려야 한다. 두 경우의 조치가 다르기 때문이다.
  - **FR-089f**: 비밀키가 없거나 복호화에 실패하면 시스템은 해당 Step을 명확한 사유와 함께 실패로 처리해야
    한다. 값을 비워 두고 계속 진행하거나 통과 처리해서는 안 된다.
  - **FR-089g**: 시스템은 동일한 이름의 환경 변수가 존재하면 복호화 대신 그 값을 사용해야 한다. 이를 통해
    비밀값을 장비에 보관하지 않는 운용도 가능해야 한다.

### Key Entities

- **Project**: 테스트를 담는 최상위 단위. 이름, 대상 앱 기본 시작 URL, 소속 테스트 목록.
- **Test**: 하나의 테스트 시나리오. 테스트 식별자(예: `TC-001`), 이름, 작성 방식(`RECORD`/`AI`), 시작 URL,
  브라우저 종류, 변수 정의, 순서를 가진 Step 목록, 최근 실행 결과 참조.
- **Step**: 테스트를 구성하는 하나의 동작. 고유 식별자, 동작 종류(클릭/입력/선택/화면 이동/검증/탭 닫기),
  표시 이름, **탭 참조**, 대상 요소 참조, 입력값 또는 검증 조건, 작성 주체(사람/AI).
- **TabRef**: Step이 어느 탭에서 일어났는지를 가리키는 안정적 참조. 열린 순서로 부여한다. 최초 탭이 0이다.
- **Assertion**: 검증 Step의 조건. 종류(요소 보임 / 요소 안 보임·없음 / 텍스트 일치·포함 / URL 일치·포함),
  비교 값(변수 참조 가능), 그리고 요소를 대상으로 하는 종류의 경우 대상 요소 참조.
- **TargetLocator**: Step이 가리키는 요소의 식별 정보 묶음. 후보별 값(테스트 식별자, 역할, 접근성 이름,
  라벨, 표시 텍스트, 안정적 속성, CSS 경로)과 수집 여부.
- **Variable**: 테스트 안에서 값을 대신하는 이름. 이름, 기본값, 민감 여부. 민감 변수는 정의 파일에 값을
  갖지 않고 별도 비밀 파일의 암호문을 가리킨다.
- **SecretStore**: 테스트 정의와 분리된 비밀 보관 단위. 변수 이름별 암호문 목록. 공개키로 쓰고 비밀키로 읽는다.
- **KeyPair**: 민감 값 암호화에 쓰는 로컬 공개키·비밀키 쌍. 비밀키는 버전 관리 대상이 아니다.
- **RunSession**: 하나의 실행 또는 작성 세션. 상태(실행 중/일시정지/사람 녹화 중/AI 수행 중/종료), 현재 Step
  위치, 브라우저 세션 참조.
- **RunResult**: 한 번의 실행 결과. 전체 결과(`PASS`/`FAIL`), 총 소요 시간, Step별 결과와 소요 시간,
  멈춘 Step, 실패 이유, 실패 시점 스크린샷, 콘솔 기록, 네트워크 기록, 실행 브라우저.
- **AiInstruction**: 작성 시 사용한 자연어 지시문. 원문과 대응된 Step 목록. **실행 대상이 아니다.**

## Success Criteria *(mandatory)*

### Measurable Outcomes

PRD §18의 5개 지표를 1차 기준으로 사용한다.

- **SC-001** (Test Creation Success Rate): 대상 앱에 대한 테스트 시나리오 20건을 대상으로, 사용자가 코드를
  직접 수정하지 않고 테스트 생성을 완료하는 비율이 **80% 이상**이다.
- **SC-002** (Natural Language Success Rate): 자연어 시나리오 20건 중 AI가 실행 가능한 결정적 테스트로
  변환에 성공하는 비율이 **70% 이상**이다.
- **SC-003** (Replay Success Rate): 생성 시점에 통과한 테스트를 대상 앱 변경 없이 동일 환경에서 재실행할 때
  다시 통과하는 비율이 **95% 이상**이다. 10회 연속 실행에서 결과가 흔들리지 않는다.
- **SC-004** (Human Takeover Recovery Rate): AI가 실패한 사례 중 사람이 이어받아 테스트 생성을 완료하는
  비율이 **80% 이상**이다.
- **SC-005** (Test Creation Time): 동일 시나리오를 코드로 직접 작성하는 경우 대비 테스트 생성 시간이
  **50% 이상** 단축된다.

추가로 다음을 측정한다.

- **SC-006**: 저장된 테스트를 재실행할 때 외부 언어모델 호출 건수가 **0건**이다. (헌법 원칙 II 검증)
- **SC-007**: 로그인을 포함해 5개 이상의 사전 Step이 필요한 시나리오에서, 일시정지 후 Step을 편집하고
  이어서 실행할 때 사전 Step이 **재실행되지 않는다**. (헌법 원칙 III 검증)
- **SC-008**: 녹화된 Step 중 대상 요소 식별 후보를 **2개 이상** 확보한 Step의 비율이 **90% 이상**이다.
  "확보"는 기록 시점 검증을 통과한 후보만 센다. 여러 요소를 매칭하는 후보는 세지 않는다(FR-019b).
  (헌법 원칙 IV 검증)
- **SC-009**: 테스트가 실패했을 때, 사용자가 결과 화면만 보고 실패한 Step과 실패 이유를 **1분 이내**에
  파악할 수 있다. 실패 결과에는 실패 이유·시도한 식별 정보·실패 시점 스크린샷이 항상 포함된다.
- **SC-010**: 비밀번호 유형 필드에 입력한 값이 저장된 테스트 정의, 별도 비밀 파일, 화면, 실행 로그,
  실패 상세, 스크린샷 메타데이터, 임시 파일 어디에서도 평문으로 발견되지 않는다. (**0건**)
- **SC-011**: 비밀키 없이 민감 변수를 사용하는 테스트를 실행하면 **100%** 명확한 사유와 함께 실패하며,
  빈 값으로 통과하는 경우가 없다.
- **SC-012**: 새 탭이나 팝업을 거치는 시나리오 10건을 녹화해 저장한 뒤 재실행할 때, 탭 참조가 어긋나
  실패하는 경우가 **10% 이하**다. (멀티 탭 지원의 실효성 검증)

계정·로그인·사용자별 권한 · 팀 공유 서버 배포 · 프로젝트 공유와 동시 편집 · 원격 브라우저 세션 풀 ·
사용자별 자원 격리. MVP는 단독 로컬 도구다(FR-088). 서버화는 P2의 CI/CD 연동과 함께 검토한다.

> | 민감 값 입력·관리 | FR-082b, FR-089b | 변수 목록(값 미표시), 값 입력·재입력 |

>
> **디자인과의 차이 (1)**: `RunResult` 화면에는 `TRACE` 탭이 그려져 있으나 실행 추적은 P2다. MVP에서는

## Assumptions

- **브라우저 노출 방식**: 제품 화면 왼쪽의 브라우저 영역은 **관찰용 읽기 전용 미러**이며, 사용자가 직접
  조작할 때는 실제 브라우저 창이 사용된다(FR-023, FR-047). 디자인 3개 화면(`Main`·`RunnerPaused`·
  `Takeover`)의 왼쪽 영역은 이 미러 뷰에 대응한다.
- **대상 앱**: 대상은 웹 애플리케이션이며 표준 HTML 문서로 구성된다. 대상 앱은 테스트 대상일 뿐이며
  제품이 대상 앱 코드를 수정하지 않는다.
- **브라우저**: MVP는 Chromium 계열 하나만 지원한다. (근거: `CreateTest.dc.html`의 브라우저 선택 기본값
  `Chromium`)
- **탭**: 단일 탭과 멀티 탭을 모두 지원한다(FR-030). 동시에 열린 탭 수 상한의 기본값은 10으로 둔다.
  탭 참조는 열린 순서로 부여한다 — 재실행 시 같은 순서로 열린다는 가정에 기댄다. 순서가 비결정적인
  대상 앱은 이 가정이 깨질 수 있으며, 그 경우 해당 Step이 실패로 드러난다.
- **실행 엔진 제약**: 결정적 실행 엔진과 기술 스택은 헌법 v1.0.0에서 이미 고정되어 있다
  (백엔드 Python/FastAPI + Playwright for Python, 프론트엔드 React). 본 명세는 이를 전제로 하되 요구사항은
  구현 기술과 무관하게 기술한다.
- **자산 이식성**: 헌법 원칙 V(표준 테스트 프로젝트로 내보내기)는 P2이므로 이번 사이클에서 구현하지 않는다.
  다만 Step 모델은 이후 내보내기가 가능한 형태로 설계되어야 한다.
- **테스트 식별자**: `TC-001` 형태의 식별자는 프로젝트 안에서 유일하게 자동 부여된다.
  (근거: `TestList.dc.html`)
- **언어**: 사용자 인터페이스는 한국어를 기본으로 한다. (근거: 디자인 전체가 한국어)
- **동시 실행**: MVP는 테스트당 동시 실행 1건으로 제한한다. 단독 로컬 도구이므로 여러 사용자의 동시
  접근은 전제하지 않는다.
- **저장 위치**: 프로젝트·테스트 정의·실행 산출물 모두 사용자 로컬 파일 시스템에 둔다. 외부 데이터베이스
  서버나 클라우드 저장소에 의존하지 않는다.
- **실행 이력**: 테스트별로 **최근 1건**의 실행 결과만 보관한다. 이력 관리는 P2다.
  (근거: `TestList.dc.html`은 "마지막 실행"만 표시)
- **Step 개수 규모**: 하나의 테스트는 수십 개 규모의 Step을 다룬다고 가정한다. 수백~수천 Step 규모의 성능
  최적화는 이번 범위가 아니다.

## Dependencies

- 테스트 대상이 되는 실제 웹 애플리케이션 접근 권한 (개발/스테이징 환경)
- 자연어 처리를 위한 외부 언어모델 서비스 접근 — **작성 단계에서만** 필요하며, 저장된 테스트 실행에는
  의존하지 않는다(FR-044). 이 서비스 장애는 US4~US6에만 영향을 준다.
- 브라우저 실행이 가능한 실행 환경
