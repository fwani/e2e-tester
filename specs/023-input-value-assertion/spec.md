# Feature Specification: 입력 칸의 두 빈칸 — 값을 읽지 못하고, 키로 확정하지 못한다

**Feature Branch**: `023-input-value-assertion`

**Created**: 2026-09-28 (2026-09-28 키 입력으로 범위 확장)

**Status**: Draft

**Input**: User description (두 건, 같은 날 순서대로 들어왔다):

1. "입력 필드 현재값 검증을 추가한다. 입력 칸을 대상으로 한 텍스트 검증이 항상 실패한다 —
   입력값은 화면에 보이지만 텍스트로 관찰되지 않기 때문이다. 실제 사례: 역할 이름 칸에
   「E2E역할테스트」가 들어 있는데도 관찰값이 빈 문자열로 나와 실패했다."
2. "AI 테스트 생성 시, 텍스트 입력 후 엔터·스페이스를 입력하는 방식을 인식하지 못해서
   스텝 생성이 실패한다." (기능 태그 칸 — 「태그를 입력한 뒤 Enter 또는 Space를 눌러
   추가하세요」)

> **디렉터리 이름에 대하여**: `023-input-value-assertion` 은 첫 요구만 담고 있다. 둘째
> 요구가 들어왔을 때 이미 계획 산출물이 커밋돼 있어 경로를 그대로 두었다. **이 문서의
> 제목이 범위의 권위다.**

---

## 배경 — 같은 자리의 두 빈칸

두 요구는 따로 들어왔지만 **같은 곳이 뚫려 있다.** 입력 칸을 다루는 어휘가 모자란다.

| | 사람이 하려는 것 | 지금 표현할 수 있는가 |
|---|---|---|
| **읽기** | 「그 칸에 이 값이 들어 있다」 | **아니다** — 텍스트 검증이 빈 문자열을 본다 |
| **쓰기 확정** | 「값을 넣고 Enter 를 눌러 확정한다」 | **아니다** — 키 입력 Step 이 없다 |

둘 다 **표현 수단이 없어서** 생긴 문제다. 작성 지침이나 프롬프트로는 고칠 수 없다.

---

## 배경 1 — 화면에 보이는 글자가 관찰되지 않는다

사용자가 역할 이름 칸에 `E2E역할테스트` 를 넣고, 그 칸에 값이 들어갔는지 검증하려 했다.
AI 는 그 칸을 대상으로 텍스트 검증을 만들었고, 실행 결과는 이렇게 나왔다.

> 요소의 텍스트가 `'E2E역할테스트'` 와 같아야 하는데 다릅니다. 실제: `''`

화면에는 글자가 분명히 보인다. 그런데 관찰값은 빈 문자열이다.

### 왜 비는가 — 입력값은 텍스트가 아니다

`<input>` 의 값은 자식 텍스트 노드가 아니라 요소의 **값 속성**이다. 브라우저는 그 값을
화면에 그리기 위해 요소 내부에 자기만의 렌더링 구조를 따로 만드는데, 텍스트를 읽는
수단은 거기에 닿지 못한다. 그래서 칸이 비어 있든 가득 차 있든 **관찰값은 언제나 빈
문자열**이다.

| 대상 | 화면에 보이는 것 | 텍스트로 관찰한 결과 |
|---|---|---|
| `<div>저장되었습니다</div>` | 저장되었습니다 | `'저장되었습니다'` |
| `<input>` (값 `E2E역할테스트`) | E2E역할테스트 | **`''`** |

어쩌다 한 번 어긋나는 문제가 아니다. **입력 칸을 대상으로 한 텍스트 검증은 구조적으로
100% 실패한다.**

### 조용히 실패하는 쪽보다 나쁜 경우도 있다

지금은 긍정 비교라서 **실패**로 드러난다. 그러나 021 이 부정 비교를 추가했으므로, 같은
실수를 부정형으로 하면 결과가 뒤집힌다.

| 입력 칸 대상 텍스트 검증 | 관찰값 | 결과 |
|---|---|---|
| 「`E2E역할테스트` 와 같다」 | `''` | 실패 — 사람이 알아차린다 |
| 「`오류` 를 포함하지 않는다」 | `''` | **통과** — 아무것도 검증하지 않고 초록색 |

아랫줄이 021 이 「검증 도구가 낼 수 있는 가장 나쁜 출력」이라고 규정한 바로 그것이다.

## 배경 2 — 키를 누를 수 없어 작성이 중단된다

기능 태그 칸은 「태그를 입력한 뒤 **Enter 또는 Space**를 눌러 추가하세요」라고 안내한다.
값을 넣는 것만으로는 태그가 만들어지지 않는다 — **키가 확정 동작이다.**

Step 종류는 9개다: 클릭 · 입력 · 선택 · 이동 · 검증 · 호버 · 드래그 · 업로드 · 탭 닫기.
**키 입력이 없다.** AI 작성 도구도 그 9종에 1:1 대응하므로 키를 누를 수단이 없다.

### 결과는 검증 실패가 아니라 작성 중단이다

배경 1 과 심각도가 다르다.

| | 입력값 검증 없음 | 키 입력 없음 |
|---|---|---|
| 무엇이 실패하나 | 검증 Step 하나 | **태그가 안 만들어져 이후 동작 전부** |
| 테스트는 | 끝까지 돈다 | **작성이 거기서 멈춘다** |

태그가 추가되지 않으면 저장이 거절되고, 저장이 안 되면 목록·수정·삭제 시나리오가 통째로
성립하지 않는다. 사용자가 「스텝 생성이 실패한다」고 말한 것이 이것이다.

### 우회로가 없다

태그 칸 옆에 「추가」 버튼이 없다. 클릭으로 대신할 수 있는 것이 화면에 존재하지 않는다.

### 사람이 녹화해도 깨진다 — 그리고 더 조용히 깨진다

이것은 AI 만의 문제가 아니다. **녹화는 값을 잃는다.**

녹화기는 키를 듣지 않고 **확정된 값**만 듣는다(`change`·`blur`, 그리고 조합이 끝난
`input`). 한글 IME 조합 중인 자모를 잡지 않으려는 의도적 설계다. 태그 칸에서는 이렇게
된다.

| 순서 | 화면에서 일어나는 일 | 녹화가 만드는 것 |
|---|---|---|
| 1 | `E2E` 를 입력한다 | 입력 Step — 값 `E2E` |
| 2 | Enter 를 누른다 | **아무것도 없다** |
| 3 | 앱이 칩을 추가하고 **칸을 비운다** | `change` 가 빈 값으로 발생 |
| 4 | | 같은 요소의 입력 Step 을 **빈 값으로 갱신한다** |

**최종 결과는 「태그 칸에 빈 문자열을 넣는다」는 Step 하나다.** 사용자가 친 글자도, 누른
키도 남지 않는다. 그 정의를 재실행하면 태그가 하나도 만들어지지 않는데, 정의만 봐서는
무엇이 빠졌는지 알 수 없다.

헌법 원칙 I 의 관점에서는 **대칭적으로** 깨져 있다 — 사람도 AI 도 이 동작을 Step 으로
남기지 못한다. 어느 한쪽이 특별히 부족한 것이 아니라 **모델에 그 어휘가 없다.**

## 이 명세가 답해야 하는 어려운 질문

### 질문 1 — 값을 읽는 순간 비밀이 정의 파일로 들어온다

입력 칸의 값을 검증한다는 것은 **그 값을 기대값으로 정의 파일에 적는다**는 뜻이다.
대상이 비밀번호 칸이면 그 순간 평문 비밀번호가 버전 관리되는 파일에 남는다.

제품은 이미 이 위험을 막고 있다. 녹화는 비밀번호 타입 칸에 넣은 값을 **민감 변수 참조로
바꾸어** 기록하고, 정의 파일은 민감 변수의 값을 스키마 수준에서 거부하며, 공유 묶음은
민감 값에 닿는 경로 자체가 차단되어 있다.

**입력값 검증은 그 방어선을 우회하는 새 통로다.** 입력 Step 이 아니라 검증 Step 의 비교
값이므로 위의 어느 규칙도 걸리지 않는다. 이 기능은 그 구멍을 함께 막지 않으면 만들어서는
안 된다 — 헌법의 보안 제약은 비협상 사항이고, 「나중에」가 없다.

### 질문 2 — 한글 입력 중의 Enter 는 Enter 가 아니다

키를 녹화하려면 `keydown` 을 들어야 하는데, 녹화기가 지금까지 그것을 피해 온 이유가
있다. **한글 IME 는 조합을 끝내기 위해 Enter 를 쓴다.**

| 사용자가 하는 일 | 브라우저가 내는 Enter | 사용자가 뜻한 것 |
|---|---|---|
| `태그` 입력 → Enter | 1번째 | **조합 확정** — 아직 제출이 아니다 |
| 이어서 Enter | 2번째 | **제출** |

첫 번째를 Step 으로 만들면 재실행에서 Enter 가 한 번 더 눌린다. 영문 입력에서는 Enter 가
한 번뿐이라 이 차이가 드러나지 않고, **한글에서만 깨진다.**

이 명세는 그 둘을 반드시 갈라야 한다. 갈라내지 못하면 이 기능은 한국어 사용자에게
쓸모없다 — 그리고 이 제품의 사용자는 한국어를 쓴다.

### 질문 3 — 키를 누르면 앞서 기록한 값이 지워진다

배경 2 의 표 4행이다. 키 입력 Step 을 만들 수 있게 되어도, 그 뒤에 오는 빈 값이 앞선
입력 Step 을 덮어쓰는 동작은 그대로 남는다. **키 입력 Step 을 추가하는 것만으로는 녹화가
고쳐지지 않는다.**

값이 비워지는 것은 사용자의 입력이 아니라 **앱이 확정 처리를 했다는 신호**다. 녹화는 그
둘을 구별해야 한다.

### 질문 4 — 값을 가질 수 없는 대상에 값 검증을 걸면

버튼이나 문단에는 값 속성이 없다. 021 의 상태 검증은 같은 상황에서 **항상 통과**라는
최악의 결과를 냈고, 그래서 경고를 붙였다. 입력값 검증은 다르다 — 값을 읽을 수 없는
대상에서는 **실행이 오류로 끝난다.** 잘못된 초록색은 아니지만, 재실행할 때마다 반드시
실패하는 Step 이 정의에 남는다.

제품에는 이미 같은 상황에 대한 판단이 있다. 후보를 수집하지 못한 대상에 대해서는
**Step 을 만들지 않는다** — 「재실행에서 반드시 실패하므로, 만들어 두는 것이 사용자에게
더 나쁘다」. 이 명세는 그 선례를 따른다.

### 질문 5 — 값이 있지만 사람이 기대하는 값이 아닌 대상

체크박스와 선택 목록은 값 속성을 갖지만, 그 값이 사람이 보고 있는 것과 다르다.

| 대상 | 사람이 뜻하는 것 | 값 속성이 주는 것 |
|---|---|---|
| 체크박스 | 체크되어 있는가 | 체크 여부와 **무관한 고정 문자열** |
| 선택 목록 | 화면에 보이는 항목 이름 | 그 항목의 **내부 식별자** |

체크박스는 이 검증으로 아무것도 알 수 없다 — 체크하든 말든 같은 값이 나오므로 021
FR-014 가 막으려던 「늘 같은 결과를 내는 검증」이 된다. 선택 목록은 알 수는 있지만
**사람이 화면에서 읽은 글자와 다른 것을 적어야 한다.** 둘을 같게 다루면 안 된다.

## User Scenarios & Testing *(mandatory)*

> **P1 이 둘인 이유**: 두 이야기는 서로 의존하지 않고, 각각 **지금 깨져 있는 시나리오를
> 하나씩 고친다.** 어느 하나만 만들어도 사용자가 못 하던 일을 하게 된다. 억지로 순위를
> 매기면 나중 것이 「덜 중요하다」로 읽힌다.

### User Story 1 - 키를 눌러 값을 확정한다 (Priority: P1)

테스트 작성자가 기능 태그 칸에 `E2E` 를 입력하고 Enter 를 눌러 태그를 추가한다. 이어서
`테스트` 를 입력하고 Space 를 눌러 하나 더 추가한다. 두 동작이 모두 Step 으로 남고,
재실행하면 태그 두 개가 같은 순서로 만들어진다. AI 작성 중에도 같은 일을 할 수 있다.

**Why this priority**: 이것이 없으면 **작성이 거기서 멈춘다.** 태그가 안 만들어지면 저장이
거절되고, 저장이 안 되면 그 뒤의 목록·수정·삭제 시나리오가 통째로 성립하지 않는다.
검증 하나가 실패하는 것과 다른 종류의 고장이다.

**Independent Test**: 태그 칸에 값을 넣고 Enter 를 눌러 태그가 추가되는 것을 Step 으로
남긴 뒤 재실행한다. 입력값 검증 없이도 독립적으로 가치를 낸다.

**Acceptance Scenarios**:

1. **Given** 태그 칸에 `E2E` 가 입력돼 있다, **When** Enter 키 입력 Step 을 실행한다, **Then** 태그 `E2E` 가 추가된다
2. **Given** 같은 상황이다, **When** Space 키 입력 Step 을 실행한다, **Then** 같은 결과가 된다
3. **Given** 사람이 태그 칸에 `E2E` 를 치고 Enter 를 누르는 것을 녹화한다, **When** 녹화 결과를 본다, **Then** **입력 Step(값 `E2E`)과 키 입력 Step(Enter) 두 개**가 남는다 — 지금처럼 빈 값 하나로 뭉개지지 않는다
4. **Given** 같은 녹화를 한글 `테스트` 로 한다 (조합 확정 Enter + 제출 Enter, 총 2회), **When** 녹화 결과를 본다, **Then** 키 입력 Step 은 **하나만** 남는다 — 조합 확정용 Enter 는 기록되지 않는다
5. **Given** 녹화한 정의를 재실행한다, **When** 태그 칸 부분에 도달한다, **Then** 태그가 녹화 때와 같이 만들어진다
6. **Given** AI 작성 세션이 진행 중이다, **When** 모델이 태그 칸에 값을 넣고 확정하려 한다, **Then** 키 입력 도구를 쓸 수 있고, 녹화로 만든 것과 같은 형태의 Step 이 나온다
7. **Given** 키 입력 Step 이 든 테스트를 저장했다, **When** 목록에서 본다, **Then** **어느 키를 눌렀는지가 표시 이름에 드러난다**
8. **Given** 대상 요소를 찾지 못한다, **When** 키 입력 Step 을 실행한다, **Then** 실패한다 — 포커스가 어디 있든 아무 데나 키를 보내지 않는다

### User Story 2 - 「그 칸에 이 값이 들어 있어야 한다」를 검증으로 남긴다 (Priority: P1)

테스트 작성자가 역할 이름 칸에 `E2E역할테스트` 를 입력한 뒤, 그 값이 칸에 제대로 들어갔는지
확인하려 한다. 검증 추가 화면에서 **「입력값」**을 고르고 대상 칸과 기대값을 적는다. 실행하면
칸의 현재 값을 읽어 비교하고, 값이 맞으면 통과한다. AI 작성 중에도 같은 종류를 쓸 수 있다.

**Why this priority**: 지금 100% 실패한다. 다른 검증 이야기는 이 종류가 존재한다는 전제
위에 있다.

**Independent Test**: 입력값 검증 하나만 만들어도, 지금 100% 실패하는 시나리오가 통과로
바뀐다. 키 입력이나 내보내기 없이도 제품 안에서 즉시 가치를 낸다.

**Acceptance Scenarios**:

1. **Given** 이름 칸에 `E2E역할테스트` 가 들어 있다, **When** 「그 칸의 입력값이 `E2E역할테스트` 와 같다」 검증을 실행한다, **Then** 통과한다
2. **Given** 이름 칸이 비어 있다, **When** 같은 검증을 실행한다, **Then** 실패하고 설명에 기대값과 **실제 관찰값 `''`** 이 함께 나온다
3. **Given** 이름 칸에 `E2E역할테스트 수정본` 이 들어 있다, **When** 「입력값이 `E2E역할테스트` 를 포함한다」 검증을 실행한다, **Then** 통과한다
4. **Given** 값이 0.5초 뒤에 자동으로 채워진다, **When** 제한 시간 5초로 긍정 검증을 실행한다, **Then** 통과한다 — 값이 들어올 때까지 기다린다
5. **Given** 칸에 `임시값` 이 들어 있다, **When** 「입력값이 `임시값` 과 같지 않다」 검증을 실행한다, **Then** 실패한다 — 부정 비교도 쓸 수 있고 021 의 관찰 기간 규칙을 그대로 따른다
6. **Given** 여러 줄 입력 칸에 세 줄이 들어 있다, **When** 입력값 검증을 실행한다, **Then** 줄바꿈을 포함한 전체 값이 관찰된다
7. **Given** AI 작성 세션이 진행 중이다, **When** 모델이 입력 칸의 값을 확인하려 한다, **Then** 입력값 검증을 만들 수 있고, 화면 폼으로 만든 것과 같은 형태의 Step 이 나온다
8. **Given** 작성 시점에 칸의 값이 기대와 다르다, **When** AI 가 이 검증을 만든다, **Then** Step 은 남고 작성 시점 어긋남으로 기록된다 — 기대값을 실제값으로 바꾸어 통과시키지 않는다 (020 FR-005)
9. **Given** 대상이 비밀번호 타입 칸이다, **When** 입력값 검증을 만들려 한다, **Then** **평문 비밀번호가 정의에 남지 않는다** — 값을 리터럴로 적을 수 없다

### User Story 3 - 내보낸 테스트도 같은 동작과 판정을 한다 (Priority: P2)

테스트 작성자가 키 입력과 입력값 검증이 들어간 테스트를 표준 Playwright 프로젝트로
내보낸다. 제품 없이 그 프로젝트를 실행해도, 제품 안에서 실행했을 때와 같은 일이 일어나고
같은 결과가 나온다.

**Why this priority**: 헌법 원칙 V 가 요구한다. 새 Step 종류와 새 검증 종류를 생성기에
반영하지 않으면 그 정의는 내보내는 순간 깨지므로 미룰 수 없다. P1 보다 뒤인 것은 제품 안
동작이 먼저 성립해야 비교할 대상이 생기기 때문이지, 선택이라서가 아니다.

**Independent Test**: 같은 정의를 제품 안에서 한 번, 내보낸 프로젝트에서 한 번 실행해
결과를 비교한다.

**Acceptance Scenarios**:

1. **Given** 키 입력과 입력값 검증이 포함된 테스트가 있다, **When** 내보낸다, **Then** 표준 Playwright 프로젝트가 만들어지고 **내보내기가 실패하지 않는다**
2. **Given** 내보낸 프로젝트를 제품 없이 실행한다, **When** 태그 칸 부분에 도달한다, **Then** 제품 안에서와 같이 태그가 만들어진다
3. **Given** 칸에 기대값이 들어 있다, **When** 내보낸 프로젝트를 실행한다, **Then** 제품 안에서와 같이 통과한다
4. **Given** 부정 비교를 쓴 입력값 검증이다, **When** 내보낸다, **Then** 021 이 정한 관찰 기간 규칙이 생성된 코드에도 같게 적용된다
5. **Given** 정의와 표준 Playwright 의 대응 관계 문서가 있다, **When** 두 종류가 추가된다, **Then** 그 문서에 대응이 기록된다

### User Story 4 - 잘못 고른 검증이 조용히 지나가지 않는다 (Priority: P3)

테스트 작성자가 입력 칸을 대상으로 텍스트 검증을 고른다. 화면이 「이 대상에서는 언제나
빈 문자열로 관찰된다」고 알려 주고 입력값 검증을 가리킨다. 반대로 값이 없는 대상에 입력값
검증을 걸려고 하면 Step 이 만들어지지 않고 이유가 설명된다. 체크박스와 선택 목록에서는
이 검증이 무엇을 비교하는지 미리 읽을 수 있다.

**Why this priority**: 새 어휘가 생겨도 옛 실수는 계속 일어난다. 다만 P1·P2 가 되면
**올바른 길이 존재하기는 하므로**, 안내는 그다음이다.

**Independent Test**: 각 오용 상황을 하나씩 만들어 보고, 화면·결과·작성 도구가 그 사실을
말하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 대상이 입력 칸이다, **When** 텍스트 검증을 만들려 한다, **Then** 「이 대상에서는 언제나 빈 문자열로 관찰된다」는 안내와 입력값 검증 제안이 보인다. **막지는 않는다**
2. **Given** 대상이 버튼이나 문단처럼 값이 없는 요소다, **When** 입력값 검증을 만들려 한다, **Then** **Step 이 만들어지지 않고** 왜 만들 수 없는지 설명이 나온다
3. **Given** 대상이 체크박스나 라디오다, **When** 입력값 검증을 만들려 한다, **Then** **Step 이 만들어지지 않는다** — 체크 여부와 무관한 고정 문자열을 비교하게 되므로 늘 같은 결과를 내는 검증이 된다
4. **Given** 대상이 선택 목록이다, **When** 입력값 검증을 만든다, **Then** 만들어지되 **「화면에 보이는 항목 이름이 아니라 내부 식별자를 비교한다」**는 사실을 읽을 수 있다
5. **Given** AI 작성 도구를 쓰는 모델이다, **When** 검증 도구 설명을 읽는다, **Then** 입력 칸의 값을 볼 때는 입력값 검증을 쓰라는 안내가 들어 있다
6. **Given** 이미 저장된 테스트에 입력 칸 대상 텍스트 검증이 있다, **When** 그 테스트를 연다, **Then** **그대로 열리고 그대로 실행된다** — 자동으로 고치지 않는다

---

### Edge Cases

#### 키 입력 (US1)

- **한글 조합을 끝내는 Enter** → 기록하지 않는다. 질문 2 의 핵심이다.
- **입력 없이 키만 누르면?** → 기록한다. 빈 칸에서 Escape 로 닫는 것은 정당한 동작이다.
- **키를 눌렀는데 화면이 안 바뀌면?** → 기록한다. 호버와 다르다 — 호버는 포인터가 지나간
  모든 요소가 후보라 걸러야 하지만, 키는 사용자가 **의도해서** 누른 것이다.
- **같은 키를 연달아 누르면?** → 누른 횟수만큼 Step 을 만든다. 입력과 달리 키는 접으면
  안 된다 — Enter 두 번은 Enter 한 번과 다른 동작이다.
- **대상 요소를 찾지 못하면** → 실패한다. 포커스가 어디 있든 키를 보내는 것은 어느 화면에
  무엇을 하는지 알 수 없게 만든다.
- **범위 밖 키를 누르면** → 기록하지 않는다. 그 사실을 사용자가 알 수 있어야 한다 —
  조용히 빠지면 「눌렀는데 왜 안 남지」가 된다.
- **키 입력 후 앱이 칸을 비우면** → 앞선 입력 Step 을 **갱신하지 않는다.** 질문 3 이다.

#### 입력값 검증 (US2·US4)

- **여러 줄 입력 칸의 줄바꿈** → 값에 포함해 관찰한다.
- **값이 없는 대상에 입력값 검증** → 작성 시점에 거절한다.
- **체크박스·라디오** → 거절한다. 체크 상태 검증은 021 에서 범위 외로 남아 있고, 이 검증으로
  대신할 수 없다.
- **선택 목록에서 아무것도 고르지 않은 상태** → 빈 문자열로 관찰된다.
- **비밀번호 타입 칸** → 평문 기대값을 쓸 수 없다. 민감 변수 참조로만 비교한다.
- **대상 요소를 찾지 못하면** → 실패한다 (021 FR-006 과 같다).
- **값이 있는 대상이지만 화면에서 숨겨져 있으면** → 값은 읽힌다. 보이는지를 묻는 검증은
  `요소가 보인다` 가 따로 있다. **이 전제는 구현 단계에서 실측해 확인한다.**
- **비교 값이 빈 문자열인 부정 검증** → 021 FR-007 과 같이 만들 수 없다.

#### 공통

- **기존에 저장된 테스트 파일**에는 새 Step 종류도 새 검증 종류도 없다. 읽기·실행·내보내기·
  공유가 모두 지금과 동일해야 한다.

## Requirements *(mandatory)*

### Functional Requirements — 키 입력 (US1)

- **FR-050**: 대상 요소에 **키를 누르는 Step 종류**를 제공한다.
- **FR-051**: 이 Step 은 **대상 요소가 필수**다. 포커스된 곳에 키를 보내지 않는다 — 어느
  요소에 무엇을 했는지 정의만 보고 알 수 있어야 한다 (헌법 원칙 IV 와 같은 취지).
- **FR-052**: 누를 수 있는 키는 **정해진 목록에서 고른다.** 임의 문자열을 받지 않는다 —
  오타가 실행 시점까지 숨고, 검증하지 않은 문자열이 생성된 코드로 새어 나간다.
- **FR-053**: 초기 목록은 **Enter · Space · Tab · Escape** 넷이다. 사용자가 요구한 것은
  앞의 둘이고, 뒤의 둘은 같은 「확정·이동·취소」 계열로 우회로가 없다. 그 밖의 키는
  범위 외다.
- **FR-054**: 녹화가 키 입력을 **Step 으로 남긴다.** 목록에 있는 키만 남긴다.
- **FR-055**: **IME 조합을 끝내는 키 입력은 기록하지 않는다.** 한글 입력에서 Enter 는 조합
  확정과 제출 두 가지로 쓰이고, 둘을 구별하지 못하면 재실행에서 키가 한 번 더 눌린다.
- **FR-056**: 키 입력이 기록된 뒤 같은 요소에서 발생하는 **빈 값 확정 이벤트가 앞선 입력
  Step 을 덮어쓰지 않는다.** 그것은 사용자의 입력이 아니라 앱이 확정 처리를 했다는 신호다.
- **FR-057**: 같은 키를 연달아 누르면 **누른 횟수만큼** Step 을 만든다. 입력과 달리 접지
  않는다.
- **FR-058**: AI 작성 도구가 키 입력 Step 을 만들 수 있다. 도구 설명이 **입력 후 키로
  확정하는 칸(태그 입력 등)에 쓴다**는 것을 안내한다.
- **FR-059**: 표시 이름이 **어느 키를 눌렀는지**를 드러낸다.
- **FR-060**: 목록에 없는 키를 눌렀을 때 **기록되지 않았다는 사실을 사용자가 알 수 있다.**
  조용히 빠지면 원인을 찾을 수 없다.

### Functional Requirements — 입력값 검증 (US2)

- **FR-001**: 입력 칸의 **현재 값**을 확인하는 검증 종류를 제공한다. 화면에 표시된 텍스트를
  보는 검증과 **별개의 종류**로 둔다 — 「보이는 글자」와 「칸에 담긴 값」은 다른 사실이고,
  그 구별이 저장된 정의에 남아야 한다.
- **FR-002**: 이 검증은 **대상 요소가 필수**다. 대상 없는 입력값 검증은 뜻이 없다.
- **FR-003**: 이 검증은 **비교 값이 필수**다.
- **FR-004**: 값을 비교하는 검증이므로 **네 가지 비교 방식을 모두** 쓸 수 있다.
- **FR-005**: 대기 규칙은 021 이 정한 것을 **그대로** 따른다. 이 종류만의 대기 규칙을 새로
  만들지 않는다.
- **FR-006**: 대상 요소를 찾지 못하면 **긍정·부정 모두 실패**한다.
- **FR-007**: 실패 설명은 **기대와 실제를 모두** 담는다. 관찰값이 빈 문자열이면 그 사실이
  읽혀야 한다.
- **FR-008**: 여러 줄 입력 칸의 값은 **줄바꿈을 포함한 그대로** 관찰한다.
- **FR-009**: 이 검증도 **작성 시점 어긋남 기록의 대상**이다 (020 FR-005·FR-008).
- **FR-010**: 이 검증도 **실행 결과 분류의 대상**이다 (020 FR-018·FR-022).

### Functional Requirements — 보안 (US2, 비협상)

- **FR-015**: 비밀번호 타입 칸을 대상으로 한 입력값 검증은 **평문 비교 값을 가질 수 없다.**
  민감 변수 참조로만 비교한다. 세 작성 경로 모두에 적용된다.
- **FR-016**: 민감 변수를 참조하는 비교 값의 **실제 값은 화면·로그·실행 결과·내보낸 산출물
  어디에도 노출되지 않는다.** 실패 설명의 관찰값도 마스킹 대상이다.
- **FR-017**: 공유 묶음에 이 검증이 포함되어도 **민감 값이 실리지 않는다.**

### Functional Requirements — 내보내기 정합 (US3)

- **FR-020**: 키 입력 Step 과 입력값 검증이 **표준 Playwright 로 옮겨진다.** 내보낸 테스트가
  제품 안에서 실행한 것과 **같은 일**을 한다 (헌법 원칙 V).
- **FR-021**: 부정 비교의 관찰 기간 규칙이 **생성된 코드에도 같게** 적용된다 (021 FR-003a).
- **FR-022**: 정의와 표준 Playwright 의 **대응 관계를 계약 문서에 남긴다.**

### Functional Requirements — 오용 방지와 표시 (US4)

- **FR-030**: 대상이 입력 칸인데 텍스트 검증을 고르면, **그 대상에서는 언제나 빈 문자열로
  관찰된다**는 사실과 입력값 검증이라는 대안을 알린다. **막지는 않는다.**
- **FR-031**: 값을 가질 수 없는 대상에 입력값 검증을 만들려 하면 **Step 을 만들지 않고**
  이유를 설명한다.
- **FR-032**: 체크박스·라디오를 대상으로 한 입력값 검증도 **만들지 않는다.**
- **FR-033**: 선택 목록을 대상으로 하면 만들되, **내부 식별자를 비교한다**는 사실을 작성하는
  자리에서 읽을 수 있어야 한다.
- **FR-034**: AI 작성 도구의 검증 설명이 **입력 칸의 값을 볼 때는 이 종류를 쓰라**고 안내한다.
- **FR-035**: Step 목록·상세의 표시 문구가 **이 검증이 입력값을 본다는 것과 비교 방식**을
  함께 드러낸다.
- **FR-036**: 화면의 검증 추가 폼에서 이 종류를 고를 수 있다.

### Functional Requirements — 호환

- **FR-040**: 기존에 저장된 테스트 정의는 **변경 없이** 읽히고 실행되고 내보내지고 공유된다.
- **FR-041**: 이미 저장된 입력 칸 대상 텍스트 검증을 **자동으로 고치지 않는다.**
- **FR-042**: Step 과 검증 조건의 정의 형태는 **한 곳에서만** 규정되고 화면·실행·작성·
  내보내기가 그것을 따른다 (헌법 원칙 I, 교차 언어 스키마 의무).
- **FR-043**: **녹화의 기존 동작이 달라지는 것을 감수한다.** FR-055·FR-056 은 지금 만들어지는
  Step 을 바꾼다 — 빈 값 하나 대신 입력 + 키 입력 둘이 된다. 이것은 결함의 수정이며, 그
  사실을 변경 기록에 남긴다.

### 범위 외 *(001 FR-013c · 021 의 선례를 따라 명시한다)*

아래는 이번에 만들지 않는다. **화면에 비활성 항목으로도 보여 주지 않는다.**

| 범위 외 | 이유 |
|---|---|
| Enter·Space·Tab·Escape 밖의 키 | 요구에 없다. 목록에 값을 더하는 형태로 언제든 넓힐 수 있다 |
| 조합키 (Ctrl+A, Shift+Tab 등) | 키 하나와 형태가 다르다. 함께 넣으면 목록이 조합 폭발한다 |
| 문자 키 입력 (한 글자씩 타이핑) | 입력 Step 이 담당한다. 키로 쪼개면 IME 문제가 되돌아온다 |
| 체크 상태(checked) 검증 | 021 에서 범위 외로 유지. 입력값 검증으로 대신할 수 없다는 사실만 이번에 분명히 한다 |
| 텍스트 검증이 입력 칸에서 값으로 폴백 | 정의만 보고 무엇을 비교하는지 알 수 없어진다 |
| 선택 목록의 **보이는 항목 이름** 비교 | 값 비교와 다른 관찰이다 |
| 파일 선택 칸의 선택된 파일 검증 | 요구에 없다 |
| 요소 개수 검증 · 읽기 전용 · 초점 | 001 FR-013c · 021 에서 이미 범위 외 |
| 정규식 비교 | 021 과 같은 이유로 제외 |
| 손으로 Step 을 넣는 경로에서의 키 입력·입력값 검증 | 그 경로는 대상 요소를 받지 않는다 — 살아 있는 페이지에서만 후보를 수집·검증할 수 있기 때문이다. 둘 다 대상이 필수이므로 구조적으로 불가능하다 |

---

### Key Entities

- **키 입력 동작** — 어느 요소에 어떤 키를 눌렀는가. **동작 Step 의 열 번째 종류**이며,
  대상과 키 둘로 이루어진다. 키는 정해진 목록에서 고른다.
- **검증 조건** — 검증 Step 하나가 무엇을 확인하는지. 「무엇을 보는가」와 「어떻게
  비교하는가」의 두 축. 이번 변경은 **첫 축에 「입력 칸의 값」을 더한다.** 둘째 축은
  건드리지 않는다.
- **검증 대상** — 어느 요소를 보는가. 입력값 검증은 대상이 **필수**이고, 그 위에 **대상의
  성질에 따른 제약**이 추가로 걸린다. 기존 종류에는 성질 제약이 없었으므로 새로 생기는
  개념이다.
- **민감 변수 참조** — 이미 있는 개념. 이번 변경은 **검증의 비교 값에도 이 경로가 강제됨**을
  분명히 한다.
- **작성 시점 어긋남** — 020 이 정의한 기록. 새 검증 종류도 같은 대상이며 새 기록 형태를
  만들지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-010**: 「태그 칸에 값을 넣고 Enter 로 확정한다」를 **Step 두 개**(입력 + 키 입력)로
  표현할 수 있고, 재실행하면 태그가 만들어진다.
- **SC-011**: 사람이 태그 칸 조작을 녹화하면 **입력한 글자가 정의에 남는다** — 지금처럼 빈
  문자열로 덮이지 않는다.
- **SC-012**: **한글로 태그를 입력해도** 재실행이 녹화와 같은 결과를 낸다 — 조합 확정용
  Enter 가 한 번 더 눌리지 않는다.
- **SC-013**: AI 작성이 태그 칸에서 **멈추지 않고** 끝까지 진행된다.
- **SC-001**: 「이름 칸에 `E2E역할테스트` 가 들어 있다」를 **검증 Step 하나로** 표현할 수
  있고, 값이 들어 있으면 통과한다. 지금 100% 실패하던 시나리오가 통과한다.
- **SC-002**: 입력 칸을 대상으로 한 검증의 관찰값이 **더 이상 무조건 빈 문자열이 아니다.**
- **SC-003**: 두 새 종류가 포함된 테스트를 내보내 **제품 없이 실행**했을 때, 제품 안에서
  실행한 것과 결과가 같다.
- **SC-004**: 비밀번호 칸을 대상으로 한 입력값 검증을 만들어도 **정의 파일과 공유 묶음
  어디에도 평문 비밀번호가 없다.**
- **SC-005**: 값을 가질 수 없는 대상과 체크박스·라디오에 입력값 검증을 걸려는 시도가 **Step 을
  만들지 않고** 이유와 함께 거절된다.
- **SC-006**: 입력 칸에 텍스트 검증을 고른 사용자가 **그 자리에서** 왜 그것이 동작하지
  않는지와 무엇을 대신 써야 하는지를 읽는다.
- **SC-007**: AI 가 입력 칸의 값을 확인하려 할 때 **텍스트 검증이 아니라 입력값 검증을**
  고른다.
- **SC-008**: 기존에 저장된 모든 테스트가 **파일 변경 없이** 그대로 실행·내보내기·공유되고,
  결과가 이번 변경 전과 같다.

## Assumptions

이 명세가 기능 설명의 빈 곳에 대해 택한 답이다. 다르게 정해야 하면 여기를 고친다.

### 키 입력

- **키는 열거된 목록에서 고른다.** 자유 문자열이 더 유연하지만, 오타(`enter` 대 `Enter`)가
  실행 시점까지 숨고 검증하지 않은 문자열이 생성된 코드로 나간다 — 헌법의 「생성된 코드는
  생성 중 데이터로 다룬다」에 걸린다. 021 이 상태 검증을 좁게 시작한 것과 같은 판단이며,
  넓히는 것은 목록에 값을 더하는 일이라 싸다.
- **초기 목록은 넷이다.** 요구된 것은 Enter·Space 둘이고, Tab·Escape 를 함께 넣는다 —
  같은 「확정·이동·취소」 계열이고 클릭으로 대신할 수 없다. 화살표·Backspace 는 각각 선택
  Step·입력 Step 이 담당하므로 넣지 않는다.
- **대상을 필수로 한다.** 포커스에 의존하면 정의만 보고 무엇을 했는지 알 수 없고, 앞
  Step 의 부작용에 결과가 좌우된다 — 원칙 II 의 결정성과 어긋난다.
- **IME 구별은 브라우저가 주는 조합 상태로 한다.** 시간 간격이나 값 변화로 추측하지
  않는다. 추측은 한국어·일본어·중국어에서 각각 다르게 틀린다.
- **키를 접지 않는다.** 입력은 접지만(FR-025) 키는 접지 않는다. Enter 두 번은 Enter 한
  번과 다른 동작이고, 접으면 되돌릴 수 없다.

### 입력값 검증

- **새 종류는 첫 축(무엇을 보는가)에 더한다.** 021 이 부정형을 둘째 축에 넣은 것과 반대
  방향인데, 부정은 *비교 방법*이지만 「칸의 값」은 *관찰 대상*이기 때문이다.
- **여러 줄 입력 칸과 선택 목록도 같은 종류로 덮는다.** 셋 다 「칸에 담긴 값」이라는 같은
  질문이다. 선택 목록이 내부 식별자를 준다는 차이는 **종류를 나눌 이유가 아니라 설명할
  이유**다.
- **체크박스·라디오는 거절한다.** 값을 갖긴 하지만 체크 여부와 무관하므로 늘 같은 결과를
  내는 검증이 된다.
- **값이 없는 대상은 작성 시점에 거절한다.** 실행 시점 실패로 미루지 않는다.
- **입력 칸 대상 텍스트 검증은 경고하되 막지 않는다.** 막으면 FR-040 과 충돌한다.

### 공통

- **정의 형식의 버전을 올리지 않는다.** Step 종류와 검증 종류에 값을 더하는 것만으로 하위
  호환이 달성된다고 본다. 020·021 이 같은 판단을 했다. 틀리면 `plan` 에서 드러난다.
- **비밀번호 칸 판별은 녹화가 이미 하고 있는 것을 쓴다.** 두 곳이 다르게 판단하면 입력
  Step 에서는 가려지고 검증 Step 에서는 새는 상태가 생긴다.
- **내보내기는 이번 범위 안이다.** 생성기는 이미 구현되어 있고, 새 종류를 넣고 놔두면
  원칙 V 위반이다.
- **작성 시점 어긋남 기록은 새 검증 종류에도 같게 적용된다.** 020 의 규칙에 종류별 예외를
  두지 않는다.
