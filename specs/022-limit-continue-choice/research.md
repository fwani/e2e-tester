## R0. 최초 전제가 틀렸다 — 선택지는 이미 있다

### 무엇을 확인했나

`frontend/src/components/workbench/WorkArea.tsx:452~466` 에 막힘 선택지 버튼 줄이 있다.
서버는 `enter_blocked` 에서 `choices=list(CHOICES)` 로 **다섯 개를 항상** 싣는다
(`backend/src/itb/authoring/blocked.py`).

| 선택지 | 화면 문구 | 하는 일 |
|---|---|---|
| `takeover` | 직접 조작해 이어가기 | 사람이 이어받아 녹화 |
| `answer` | (답변 칸이 따로 가짐) | 답을 실어 이어가기 |
| `retry` | AI 에게 다시 | **`limits.reset()` 후 이어가기** |
| `skip` | 이 동작 건너뛰기 | 실패한 동작을 남기지 않고 다음 |
| `abort` | AI 작성 끝내기 | 세션 종료·저장 확인 |

`sessions.py:2623` 에서 `retry`·`skip` 둘 다 `work.toolbox.limits.reset()` 을 부른다.
주석이 그 이유를 이미 적고 있다 — 「사용자가 "다시" 를 누르는 순간 이미 상한에 닿아
있을 수 있다 (FR-066)」.

### 그래서 뒤집힌 것

「텍스트를 적어야만 이어갈 수 있다」는 사실이 아니다. 텍스트 없이 이어가는 버튼이 이미
있고, 예산도 이미 새로 준다.

사용자가 그것을 보지 못한 진짜 이유는 **상한 도달이 `ERROR` 로 빠져 막힘 패널 자체가
뜨지 않은 것**이었다. 그 결함은 이 명세 이전에 고쳤다 (커밋 `24dcef9`).

### 남은 것 (이 명세의 실제 범위)

패널은 열리지만 그 안의 말과 동작이 다른 상황을 가리킨다. 특히 `sessions.py:2584` 의
재개 지시가 그렇다.

```python
note = (
    "같은 동작을 지금 화면 상태에서 다시 시도하세요."   # ← 예산 소진에는 틀린 지시
    if choice is AiChoice.RETRY
    else "그 동작은 건너뜁니다. …"
)
```

**이것은 문구가 아니라 동작 결함이다.** 예산 소진은 특정 동작에서 막힌 것이 아니므로
마지막 동작은 성공했을 수 있고, 그러면 이어가기가 이미 한 일을 반복한다.

## R1. 예산 소진을 어느 축에 둘 것인가

### 후보

| 안 | 내용 | 평가 |
|---|---|---|
| A | `BlockedKind` 에 세 번째 값 추가 | **채택** |
| B | `AgentOutcome` 에 별도 불리언 필드 | 기각 |
| C | `reason` 문자열을 화면이 해석 | 기각 |

### 판단 근거

`BlockedKind` 의 docstring 이 축을 명시한다 — 「`AiChoice` 와 다른 축이다 — 그쪽은
「사람이 무엇을 할 수 있는가」이고 이것은 **「왜 막혔는가」**다」.

예산 소진은 정확히 「왜 막혔는가」에 대한 답이다. 축이 맞다.

020 이 `product_mismatch` 를 더한 근거(FR-023)와도 어긋나지 않는다. 020 이 물은 것은
「사람이 알려 줄 수 있는 종류의 문제인가」였고, 예산 소진은 그 물음에 「아니오」다 —
`product_mismatch` 와 같은 답이지만 **이유가 다르다.** 제품이 잘못한 것이 아니라 예산이
떨어진 것이고, 그래서 이어가기의 의미가 정반대다.

| | `product_mismatch` | 예산 소진 |
|---|---|---|
| 사람이 알려 줄 것 | 없다 | 없다 |
| 이어가면 | **같은 결과** — 제품이 여전히 잘못 동작한다 | **진행된다** — 예산이 새로 생겼다 |

이어가기의 의미가 반대이므로 한 값으로 묶을 수 없다. 세 번째 값이 맞다.

- **안 B 기각**: 축이 둘로 갈린다. 화면은 「kind 가 product_mismatch 인가」와 「예산
  플래그가 켜졌는가」를 **둘 다** 봐야 하고, 둘이 동시에 참인 조합의 뜻을 아무도 정의하지
  않는다.
- **안 C 기각**: 문구를 고치면 화면이 깨진다. 020 이 `kind` 를 만든 이유가 그것이다.

### 기존 소비자에 대한 영향

`SessionScreen.tsx:3030` 이 `view.blocked.kind ?? "needs_input"` 로 읽는다 — 모르는
값이 와도 터지지 않는다. `WorkArea` 는 `kind === "product_mismatch"` 만 분기하므로 새
값은 `else` 로 떨어져 **지금과 같은 화면**이 된다. 즉 백엔드만 먼저 나가도 깨지지 않는다.

## R2. 누적 사용량을 누가 세는가

### 문제

`AttemptLimits.calls` 는 `reset()` 에서 0 이 된다. 이어가기가 `reset()` 을 부르므로
누적은 리셋을 건너 살아남아야 한다.

### 후보

| 안 | 내용 | 평가 |
|---|---|---|
| A | `AttemptLimits` 가 누적도 들고, `reset()` 이 한쪽만 지운다 | **채택** |
| B | 세션(`SessionWork`)이 따로 센다 | 기각 |
| C | 에이전트가 `AgentOutcome.tool_calls` 를 누적해 들고 있는다 | 기각 |

### 판단 근거

**세는 주체가 둘이면 어긋난다.** 이 판단은 이 저장소에 이미 두 번 적혀 있다 —
`AuthoringAgent._count` 의 「세는 주체가 둘이면 어긋나기 때문이다」, `MAX_INSTRUCTION_CHARS`
의 「세 곳에 8000 을 베껴 두면 하나만 바뀌는 날이 온다」.

누적과 한 시도는 **같은 사건을 두 창으로 보는 것**이다. `record_call()` 이 그 사건의
유일한 통과 지점이므로, 두 창을 같은 자리에 두면 어긋날 수 없다.

- **안 B 기각**: 세션이 세려면 도구 호출마다 세션에 알려야 한다. 통로를 새로 만드는
  것이고, 그 통로가 끊기면 조용히 틀린 수가 보인다.
- **안 C 기각**: `AgentOutcome` 은 루프의 **판정**이다 (그 docstring 이 「outcome 은
  루프의 판정이고, 판정은 실패 경로에서도 만들어져야 한다」고 적는다). 판정에 누적 상태를
  들리면 판정이 상태를 소유하게 된다.

### 리셋의 의미가 갈린다

`reset()` 은 지금 「예산을 새로 준다」 하나를 뜻한다. 채택안에서는 「예산을 새로 주되
누적은 남긴다」가 된다. 이름이 그대로여도 되는지는 plan 에서 정한다 — 하는 일이
늘었으므로 docstring 은 반드시 고친다.

## R3. 「진전」을 무엇으로 정의하는가

### 후보

| 안 | 내용 | 평가 |
|---|---|---|
| A | Step 수 증가 | **채택** |
| B | Step 수 증가 또는 도구 호출 성공 | 기각 |
| C | 화면 변화 | 기각 |

### 판단 근거

사용자가 얻으려는 것은 **Step** 이다. 화면을 30번 탐색하고 Step 을 하나도 만들지 못한
이어가기는, 사용자 관점에서 진전이 아니다 — 시간과 비용만 쓴 것이다.

- **안 B 기각**: 도구 호출 성공은 **거의 항상 참**이다. `observe_page` 하나만 성공해도
  참이 되므로, 헛도는 경우에도 「진전 있음」이 뜬다. 경고가 울리지 않는 경고는 없는 것보다
  나쁘다 — 사용자가 그것을 보고 「진전 중이구나」로 읽기 때문이다.
- **안 C 기각**: 화면 변화는 제품이 신뢰할 수 있게 측정할 수 없고, 변했다고 진전인 것도
  아니다 (모달이 열렸다 닫혀도 변한다).

### 안 A 의 알려진 약점

탐색이 오래 걸리는 화면에서 **정당한 탐색 중**인데 「진전 없음」이 뜰 수 있다. 이것을
감수하는 이유는 두 가지다.

1. 안내는 **이어가기를 막지 않는다** (FR-021). 틀린 경고의 비용이 낮다.
2. 반대 방향의 오작동(헛도는데 진전 있다고 말함)이 **훨씬 해롭다** — 사용자가 모른 채
   반복해서 누른다. `DEFAULT_BLOCKED_KIND` 가 「반대 방향의 오작동이 덜 해롭다」로 기본값을
   고른 것과 같은 판단이다.

## R4. 「여기까지」가 서버 상태를 바꾸는가

### 확인한 것

기존 `abort`(「AI 작성 끝내기」)가 이미 있다. `sessions.py:2564` — 상태만 옮기고 실제
정리는 `stop` 이 한다. 저장 여부를 확인할 수 있게 하려는 것이다 (FR-074).

### 판단

**새 종료 방식을 만들지 않는다.** 예산 소진에서 「여기까지」가 하려는 일은 기존
`abort` 와 같다 — AI 를 그만 부르고 지금까지의 결과를 처리한다.

명세 초안은 「멈춤은 세션을 끝내지 않는다」를 요구사항으로 뒀으나, 그것은 **기존 체계에
없는 네 번째 종료 방식**을 만드는 것이었다. 선택지 체계를 건드리지 않기로 한 판단(명세
Assumptions)에 따라 요구사항에서 뺐다.

문구만 그 상황에 맞게 고친다 (FR-014).

## R5. 이어가기 API 를 새로 만들 것인가

### 확인한 것

`ai_choice` 라우트가 `retry` 를 이미 받는다. 예산 리셋도, 이어가기도 이미 한다. 다른
것은 **보내는 지시 한 줄**뿐이다 (`sessions.py:2584`).

`resume_with_answer` 에 빈 답을 넘기는 안은 검토하지 않아도 된다 — `ai_choice` 가
`choice is AiChoice.ANSWER and not answer` 를 명시적으로 거절하고 있고, 그 거절은
의도된 것이다 (빈 답이 AI 에게 갔다고 믿게 하지 않는다).

### 판단

**새 경로를 만들지 않는다.** `retry` 가 보내는 지시를 막힘의 종류에 따라 갈라 쓰는
것으로 충분하다.

- 새 선택지 값을 더하면 기존 5선택지 체계가 6개가 되고, 화면·상태 기계·테스트가 모두
  따라 움직인다. 얻는 것은 같은 동작의 다른 이름뿐이다.
- 지시를 고르는 자리는 이미 `ai_choice` 안에 있다. 그 자리가 막힘의 종류를 알면 된다.

### 열린 문제 (plan 에서 정할 것)

`ai_choice` 가 **그 시점의 막힘 종류를 어떻게 아는가.** 막힘 종류는 `AgentOutcome` 에
실려 `enter_blocked` 로 흘러가고 이벤트가 되지만, 라우트가 나중에 다시 읽을 자리가
있는지 확인이 필요하다. 없으면 세션이 마지막 막힘 종류를 들고 있어야 한다.
