# UI 계약 — 011

**대상**: [spec.md](../spec.md) · [data-model.md](../data-model.md) · [research.md](../research.md)

이 문서는 007 `contracts/ui-contract.md` 를 **대체하지 않는다.** 그 계약이 정본이고, 여기에는
011 이 **바꾸는 줄만** 적는다. 적히지 않은 것은 007·008·009 그대로다.

계약을 "바뀌는 줄만" 으로 쓰는 이유: 전문을 복사하면 두 벌이 되고, 두 벌이 되면 다음 기능이
어느 쪽을 정본으로 볼지 판단해야 한다.

---

## §1. 조작의 집 — 세 줄이 옮겨간다

007 §4-1 의 배치 규칙에서:

```diff
  국면 띠      run.* (실행·일시정지·계속·중지·속도)
+              save · edits.revert · test.rename
  헤더          session.open · result.show · nav.editStep · nav.back
  대상 앱 영역  browser.openAt · artifact.select · tab.select
- Step 행       step.select
+ Step 행       step.select · step.toggleDeleteTarget
+ Step 패널 머리 step.selectAllDeleteTargets
  Step 상세     step.update · step.markSensitive · step.repick
- 팔레트        나머지 전부 — Step 작성·순서·삭제, 테스트 속성, 저장
+ 팔레트        나머지 전부 — Step 작성·순서·삭제(step.delete·deleteSelected·deleteAfter),
+               테스트 속성(test.setStartUrl·ai.compose)
```

**UC-011-1**: `save`·`edits.revert`·`test.rename` 은 국면 띠 밖에 그려져서는 안 된다.
`CapabilityUI` 검사가 `data-action` 으로 센다.

**UC-011-2**: `test.rename` 의 자리는 국면 띠가 **이미 그리고 있는 테스트 이름 표시**다.
이름을 표시하는 요소와 고치는 요소가 둘이면 안 된다 — 같은 값에 자리가 둘 생긴다.

**UC-011-3**: 국면 띠의 조작 묶음은 줄어들 수 있어야 한다 (`flex: 0 1 auto` · `minWidth: 0`).
이름 입력칸에도 같은 규칙이 걸린다. 조작이 늘어 띠가 창 밖으로 밀려나면 안 된다
(`PhaseBarWidth` 검사).

## §2. 저장이 이름을 묻는 조건

**UC-011-4**: 저장 라벨과 이름 요구의 판정 기준은 **`test_id` 의 유무**다.

| 상태 | 저장 라벨 | 이름을 묻는가 |
|---|---|---|
| `test_id === null` (아직 저장된 적 없는 테스트) | 「저장」 | 예 — 한 번 |
| `test_id !== null` | 「변경 저장」 | **아니오** |

`saved_at`(이 세션에서 저장한 시각)을 판정에 쓰지 않는다. 그 값은 「초안」 표시와 저장 확인줄이
쓰는 다른 사실이다 (research R2).

**UC-011-5**: 저장하지 않은 변경이 있는 상태의 확인 대화상자(나가기·다시 실행)는
`test_id === null` 일 때만 이름 입력칸을 갖는다.

**UC-011-6**: 이름이 빈 값이 되는 저장은 거절한다. 사유는 **그 자리**(국면 띠)에 붙는다 —
저장 버튼이 비활성이 되고 이유가 따라붙는 기존 `ActionButton` 규칙을 그대로 쓴다.

## §3. Step 상세의 자리

**UC-011-7**: Step 상세는 **하나의 자리**를 갖는다 — Step 패널의 **왼쪽 가장자리에 오른쪽
가장자리를 붙인 640px 겹침**. 국면에 따라 달라지지 않는다 (007 FR-230 유지).

```
1440px 기준

  ┌──────────────┬────────────────────────┬───────────────┐
  │ 대상 앱      │ ▓ Step 상세 640px ▓    │ Step 목록 460 │
  │ (340px 보임) │ ▓ (대상 앱 위에 겹침)▓ │               │
  └──────────────┴────────────────────────┴───────────────┘
                  ↑ 오른쪽 가장자리가 Step 패널에 붙는다
```

**UC-011-8**: 상세는 대상 앱 영역의 **폭을 바꾸지 않는다.** 닫으면 원래 폭 그대로 드러난다.
`lib/layout.ts` 의 `VERTICAL_SPLIT` 은 손대지 않는다 — 이 계약은 가로에만 걸린다.

**UC-011-9**: 상세가 열려 있는 동안, 상세가 덮은 영역으로 들어온 포인터·키 입력이 대상
브라우저에 전달되어서는 안 된다. 010 의 미러 조작이 그 아래에 있다.

**UC-011-10**: 상세를 닫는 조작은 상세 안에 있고 모든 국면에서 같은 자리다.

---

## §4. Step 행의 네 상태

**UC-011-11**: 한 행이 동시에 가질 수 있는 상태는 넷이고, **자리가 서로 다르다.**

| 상태 | 자리 | 표시 | 접근 가능한 이름 |
|---|---|---|---|
| 결말 | 행 왼쪽 3px + 오른쪽 결말 칸 | 색 띠 + 형태 아이콘 | `displayOutcomeLabel` (기존) |
| 일시정지 | `data-paused-here` + 전용 표식 | 기존 | 기존 |
| 지목 | 행 배경 + `aria-current="true"` | 새 축 | 「지금 보고 있는 Step」 |
| 삭제 대상 | **칸 0 체크 칸** | 사각형 계열 | 「〈이름〉 지울 대상으로 고르기」 |

**어느 하나가 다른 하나를 대체하지 않는다.** 지금은 한 클래스 자리를 셋이 다투어, 고르면
결말이 사라지고 일시정지 행은 선택이 보이지 않는다 (보고 7).

**UC-011-12**: 칸 구성은 다섯 + 조작이다. 순서는 국면과 무관하게 고정이다.

```
[체크 22][번호 26][이름 + 부속 1fr][소요 시간 58][결말 20][조작]
```

값이 없는 칸은 **비우되 다른 칸을 그 자리로 당기지 않는다** (007 FR-223 유지).

**UC-011-13**: 체크 칸은 결말 아이콘과 **다른 형태**를 써야 한다. 결말의 통과는 이미 체크(✓)이며,
008 에 「빈 사각형이 체크박스로 읽혔다」는 기록이 있다 — 이번엔 진짜 체크 칸이 생기므로 반대
방향의 혼동이 생긴다.

**UC-011-14**: 삭제 대상 선택이 없는 국면(결과 등 읽기 전용)에서는 체크 칸을 그리지 않는다.
근거 있는 부재다 (007 §4-2).

## §5. 삭제 대상 선택의 규칙

**UC-011-15**: 행 본문을 누르는 것은 지목이고, 체크 칸을 누르는 것은 삭제 대상 선택이다.
**서로를 바꾸지 않는다** (FR-380a).

**UC-011-16**: 삭제 대상 선택은 **Step id 로** 갖는다. 인덱스로 가지면 순서 변경 뒤 다른
Step 이 지워진다 (FR-380b).

**UC-011-17**: 고른 개수는 화면에 보인다. 자리는 Step 패널 머리(전부 고르기 옆)다.

**UC-011-18**: 복수 삭제 확인 문구는 대상 개수와 범위를 담는다 — 「Step 05 ~ Step 15 · 11개를
지웁니다」. 겹침 대화상자를 쓰지 않는다 (009 FR-302 의 이유와 같다 — 대상이 화면에서 사라지면
안 된다).

**UC-011-19**: 「이 뒤 전부 지우기」의 대상이 0개면 조작은 비활성이고 이유가 붙는다
(「마지막 Step 입니다」).

## §6. Step 별 스크린샷의 표시

**UC-011-20**: 결과 국면에서 Step 을 지목하면 그 Step 의 화면이 보인다. 자리는 **Step 상세**다
(§3 의 그 자리). 새 영역을 만들지 않는다.

**UC-011-21**: 스크린샷이 없으면 그 자리는 **없다는 사실과 사유**를 말한다. 빈 채로 두지 않는다.

| 상황 | 문구의 성격 |
|---|---|
| 민감 값이 있어 남기지 않음 | 왜 없는지 (사용자 잘못이 아님을 밝힌다) |
| 촬영 실패 | 사유 (`screenshot_note`) |
| 실행 대상이 아니었음(건너뜀·미도달) | 결말과 같은 말을 쓴다 — 없는 것이 정상이다 |
| 이후 실행으로 대체됨 | 지난 실행을 보고 있다는 사실 |

**UC-011-22**: 스크린샷 표시가 결말·소요 시간·시도한 locator 표시를 밀어내지 않는다.
결과 국면의 상세는 이미 그것들의 집이다.

## §7. 자동으로 브라우저를 여는 조작

**UC-011-23**: 편집 국면에서 `step.recordStart` 와 `step.addNaturalLanguage` 는 활성이다.
브라우저가 닫혀 있으면 누를 때 연다.

**UC-011-24**: 저장하지 않은 변경이 있으면 기존 「저장하고 열기」 확인(006 FR-203)이 먼저 걸린다.
**새 확인을 만들지 않는다.**

**UC-011-25**: 브라우저 열기가 실패하면 그 사유를 알리고 지시문·녹화를 시작하지 않는다.
진행 표시를 켰다가 끄지 않는다 — 시작한 것처럼 보이면 사용자는 무엇이 남았는지 알 수 없다.

## §8. 검사가 셀 수 있어야 하는 것

| 계약 | 검사 방법 |
|---|---|
| UC-011-1 | `data-action="save"` 요소의 조상에 `data-workbench-phase-bar` 가 있다 |
| UC-011-4 | `test_id` 유무 × 라벨 · 이름칸 유무의 조합표 |
| UC-011-7 | 상세 요소의 자리가 열 국면에서 같다 |
| UC-011-11 | 네 상태의 모든 성립 조합에서 넷의 표시가 동시에 존재한다 |
| UC-011-12 | 칸 개수와 순서 |
| UC-011-15 | 행 본문 클릭 후 `deleteSelection` 불변, 체크 칸 클릭 후 `focusedStepId` 불변 |
| UC-011-16 | 순서 변경 후에도 같은 Step id 가 선택 상태 |
| UC-011-21 | 스크린샷 없음의 네 상황 각각에서 사유 문구가 있다 |
| UC-011-23 | `editing` 국면 권한표의 두 셀이 `enabled` |
