# Phase 0 조사 — 입력값 검증 (023)

명세가 열어 둔 것과, 계획을 세우는 동안 코드에서 확인해야 했던 것들. **실측으로 확인한
사실만 적는다** — 추정은 그렇다고 표시한다.

---

## R1. 대상의 성질을 어디서 판정하는가

### 확인한 사실

`TargetLocator` (`backend/src/itb/domain/locator.py`) 가 저장하는 것은 `tag`, `role`,
`accessible_name`, 그리고 후보 묶음(`test_id`·`label`·`text`·`stable_attr`·`css`)이다.
**`type` 속성을 담는 필드가 없다.** `stable_attr` 는 후보로 뽑힌 속성 **하나**만 담으므로
`type` 이 거기 들어온다는 보장이 없다.

주입 스크립트의 `describe()` (`recorder.js:364`) 는 `tag` 와 `attributes` 를 함께 돌려주고,
`COLLECTED_ATTRS` 에 **`type` 이 들어 있다** (`recorder.js:247`). `role` 은 `implicitRole()`
(`recorder.js:50`) 이 태그와 `type` 으로 계산한다 — `input[type=checkbox]` → `checkbox`,
`input[type=radio]` → `radio`, `select` → `combobox`, `textarea`·그 밖의 `input` → `textbox`.

| 판정이 필요한 시점 | 살아 있는 요소가 있는가 | 저장된 정의에 `type` 이 있는가 |
|---|---|---|
| 작성 (거절·경고) | **있다** — 일시정지 상태의 페이지 | 없다 |
| 실행 (관찰값 마스킹) | **있다** — 대상을 찾은 뒤 | 없다 |
| 내보내기 (생성) | 없다 | 없다 |

### 결정

**성질 판정은 살아 있는 요소에서만 한다. 저장된 정의에 성질을 적지 않는다.**

내보내기 시점에는 판정이 **필요 없다.** 검증 종류가 `value` 인 것 자체가 「값을 비교한다」를
뜻하므로 생성기는 종류만 보고 대응 matcher 를 고른다. 태그를 볼 이유가 없다.

### 근거

명세의 기능 설명은 「`TargetLocator.tag` 가 이미 있으므로 생성 시점에 판별 가능하다」고
보았으나, **판별 자체가 불필요하다.** 종류를 새로 만드는 설계(A 안)를 택한 순간 그 정보는
종류 안에 들어간다. 이것이 A 안이 「텍스트 검증이 대상에 따라 다르게 읽는다」(B 안)보다
나은 이유를 다시 확인해 준다 — B 안이었다면 생성기가 저장되지 않은 `type` 을 알아야 했고,
제품 안 실행과 내보낸 코드가 갈렸을 것이다.

성질을 정의에 적지 않는 이유는 **화면이 바뀌면 옛 판단이 남기 때문이다.** 오늘 텍스트
칸이던 것이 내일 선택 목록이 되면, 저장된 성질은 거짓말이 된다. 살아 있는 요소는 언제나
지금의 사실이다.

### 채택하지 않은 안

- **`TargetLocator` 에 `type` 필드 추가** — 스키마가 커지고, 위의 「옛 판단이 남는」 문제가
  생긴다. 그리고 판정이 필요한 두 시점 모두 살아 있는 요소를 갖고 있어 얻는 것이 없다.
- **`role` 로 판정** — 저장돼 있어 편하지만, 작성자가 `role` 속성으로 덮어쓸 수 있고
  비밀번호 칸과 일반 텍스트 칸이 둘 다 `textbox` 라 R2 를 풀지 못한다.

## R2. 비밀번호 칸을 어떻게 알아보고, 무엇까지 막아야 하는가

### 확인한 사실 — 기존 방어선

| 층 | 무엇을 막는가 | 위치 |
|---|---|---|
| 녹화 | 비밀번호 칸에 넣은 값을 민감 변수 참조로 바꾼다 | `recorder.js:889` (`sensitive: type === "password"`) |
| 정의 | 민감 변수가 평문 값을 갖는 것을 거절한다 | `Variable._no_plaintext_secret` (`domain/test_case.py:246`) |
| 실행 결과 | 복호화된 민감 값을 오류 메시지에서 지운다 | `Runner._scrubber()` → `runner.py:611` |
| 작성 시점 어긋남 | 같은 스크러버를 통과시킨다 | `authoring/tools.py:1321` |
| 공유 | `itb.secrets` 임포트 자체가 차단 | `.importlinter` 의 `sharing-cannot-reach-secrets` |
| 내보내기 | 민감 변수를 `process.env.NAME` 으로 낸다 | `ValueRenderer._reference` (`playwright_gen.py:111`) |

### 확인한 구멍 — 스크러버는 「이미 복호화된 값」만 안다

`Scrubber` 는 `resolver.resolved_sensitive_values()` 로 만들어진다 (`runner.py:852`). 즉
**그 실행에서 실제로 복호화된 값만** 지운다.

입력값 검증이 실패하는 순간을 보면 문제가 드러난다.

| 실패 설명에 들어가는 것 | 스크러버가 지우는가 |
|---|---|
| 기대값 (`{{SECRET_PW}}` 를 푼 것) | **지운다** — 복호화됐으므로 목록에 있다 |
| 관찰값 (칸에 실제로 들어 있던 것) | **지우지 못한다** — 기대와 다르기 때문에 실패한 것이고, 다르다는 것은 목록에 없다는 뜻이다 |

**검증이 실패할 때만 새는 구조다.** 그리고 그 문장은 실행 결과와 작성 시점 어긋남 기록에
그대로 저장된다.

### 결정

1. **판별 규칙을 새로 만들지 않는다.** 녹화가 쓰는 것과 같은 규칙 — 대상의 `type` 이
   `password` 인가 — 을 같은 출처(`__itbDescribe` 가 돌려주는 `attributes`)에서 읽는다.
2. **작성 시점**: 대상이 비밀번호 칸이면 **평문 비교 값을 거절한다.** 민감 변수 참조
   (`{{SECRET_*}}`)만 받는다.
3. **실행 시점**: 대상이 비밀번호 칸이면 **관찰값을 무조건 마스킹한다.** 스크러버에 기대지
   않는다 — 위 표의 아랫줄이 스크러버로는 닫히지 않는 칸이다.
4. **판정은 실행 때 살아 있는 요소에서 읽는다** (R1 의 규칙). 저장된 정의에 「이것은
   비밀번호 칸이다」를 적지 않는다.

### 마스킹이 결정성(원칙 II)을 해치지 않는 이유

마스킹은 **설명 문자열만** 바꾼다. 통과·실패 판정은 실제 값으로 그대로 한다. 021 이 상태
검증에서 「태그를 보고 판정을 뒤집으면 원칙 II 에 예외가 생긴다」고 한 것과 구별되는
지점이다 — 거기서는 판정을 바꾸는 이야기였고, 여기서는 출력만 바꾼다.

### 남는 한계 — 내보낸 코드의 실행 출력

내보낸 프로젝트에서 이 검증이 실패하면, 표준 도구가 자기 형식으로 기대·실제를 출력한다.
그 출력은 제품이 통제하지 못한다.

**새로 생기는 노출은 아니다.** 내보낸 *산출물*에는 평문이 없고(`process.env.NAME`), 실행
중 화면에 뜨는 값은 입력 Step 에서도 이미 같은 상태다. 이 사실을 계약 문서에 적어 두고,
제품 안 실행에서만 마스킹을 보장한다고 명시한다.

## R3. 두 작성 경로가 검증을 따로 만들고 있다

### 확인한 사실

| 경로 | 후보 수집 | `Assertion` 생성 | 021 의 경고 |
|---|---|---|---|
| 화면 폼 (`POST /assertions`) | `build_assertion()` | `build_assertion()` 안에서 | **호출한다** (`steps.py:488`) |
| AI 작성 (`tools.assert_condition`) | `collect_by_selector()` 직접 호출 | `Assertion(...)` 직접 생성 (`tools.py:829`) | **호출하지 않는다** |

즉 **021 의 `stateless_target_warning` 은 AI 경로에 닿지 않는다.** 이번 기능의 FR-031·FR-032
(거절)와 FR-033(선택 목록 안내)는 명세상 **세 경로 모두**에 적용되므로, 같은 구조로 만들면
AI 가 만드는 검증만 규칙 밖에 남는다.

### 결정

**판정 규칙을 한 함수에 두고 두 경로가 그것을 호출한다.** `assertion_builder` 에 둔다 —
`stateless_target_warning` 이 이미 거기 있어 「검증 대상에 대한 판단」이 모이는 자리다.

두 경로를 **통합하지는 않는다.** `build_assertion()` 은 예외를 던지고 AI 경로는
`{"error": ...}` 를 돌려주는 계약이라, 통합하면 모델이 보는 오류 형태가 바뀐다. 이번
기능과 무관한 위험이고, 규칙의 단일화는 함수 하나로 이미 달성된다.

### 부수적으로 드러난 것 — 021 의 경고가 AI 경로에 없다

이것은 **023 의 결함이 아니라 021 의 빈칸이다.** 이번 범위에 넣지 않는다. 다만 새 규칙을
넣는 자리에서 같은 구멍을 반복하지 않는 것이 이 결정의 요점이며, 021 의 빈칸은
`converge` 가 판단할 수 있도록 여기 기록해 둔다.

## R4. 값을 읽는 수단과 그 대상 범위

### 확인한 사실

Playwright 의 값 읽기는 `<input>`·`<textarea>`·`<select>` 세 태그만 받고, 그 밖의 요소에는
오류를 던진다. 즉 「값이 없는 대상」은 **실행하면 반드시 오류**다.

제품에는 같은 상황에 대한 판단이 이미 있다 — 후보를 수집하지 못한 대상에 대해
`AssertionTargetError` 를 던지며 「재실행에서 반드시 실패하므로, 만들어 두는 것이
사용자에게 더 나쁘다」고 적혀 있다 (`assertion_builder.py:22`).

### 결정 — 대상 성질의 세 갈래

| 대상 | 판정 | 근거 |
|---|---|---|
| `input` (checkbox·radio 제외) · `textarea` · `select` | **받는다** | 값을 갖고, 사람이 뜻하는 것과 일치한다 |
| `input[type=checkbox]` · `input[type=radio]` | **거절한다** | 값을 갖지만 체크 여부와 무관한 고정 문자열이다 |
| 그 밖의 모든 것 | **거절한다** | 값이 없어 실행하면 반드시 오류다 |

`select` 는 받되 **내부 식별자를 비교한다는 사실을 알린다** (FR-033) — 경고가 아니라 안내
문체로 쓴다. 021 의 `NEGATED_MATCH_NOTE` 가 같은 성격이다.

### 태그를 읽을 수 없으면

`describe_element()` 가 요소를 찾지 못하면 이미 `AssertionTargetError` 로 끝난다. 요소는
찾았는데 태그가 비어 있는 경우는 실측상 없지만(스크립트가 언제나 `tagName` 을 넣는다),
방어적으로 **거절하지 않고 통과시킨다** — 판정하지 못한 것을 거절로 바꾸면 정당한 대상이
막힌다. 그때는 실행 시점 오류로 드러난다.

### `select[multiple]` 은?

값 읽기가 **처음 선택된 항목 하나**만 돌려준다. 여러 개를 확인하려는 사용자의 뜻과 다르다.
이번에 별도로 다루지 않되 계약 문서에 한계로 적는다 — 명세의 범위 외 표에 「선택 목록의
보이는 항목 이름 비교」가 이미 있고 같은 계열이다.

## R5. 대기 규칙 — 새로 만들 것이 없다

### 확인한 사실

`step_executor.py` 의 `_watch()` 는 `assertion.negated` 를 보고 `settle`(긍정: 참이 될 때까지
기다린다) 또는 `hold`(부정: 기간 동안 유지되는지 지켜본다)를 고른다. **관찰 함수를 인자로
받는다** — 주소 검증과 텍스트 검증이 이미 서로 다른 관찰 함수를 넘기고 같은 대기를 쓴다.

### 결정

입력값 검증은 **관찰 함수만 다르게 넘긴다.** 대기·비교·실패 설명 조립은 그대로 재사용한다.
`_matches()` 와 `_EXPECTATION_VERBS` 도 종류와 무관하므로 손대지 않는다.

이것이 명세 FR-005 의 「이 종류만의 대기 규칙을 새로 만들지 않는다」를 만족시키는 방법이고,
동시에 가장 적은 코드다.

## R6. 하위 호환 — 값 추가만으로 되는가

### 확인한 사실

- `AssertionKind` 는 `StrEnum` 이고 저장은 문자열이다. 값 추가는 기존 파일을 건드리지 않는다.
- `default_label()` 과 생성기의 `_assertion_lines()` 는 `match` 문으로 종류를 가른다. **두
  곳의 폴백이 정반대다.**

  | 분기가 빠지면 | 결과 |
  |---|---|
  | `default_label()` (`assertion_builder.py:158`) | `"검증"` 을 돌려준다 — **조용히 넘어간다** |
  | `_assertion_lines()` (`playwright_gen.py:338`) | `UnsupportedStepError` 를 던진다 — **크게 깨진다** |

  생성기 쪽은 잊어버릴 수 없다. 표시 이름 쪽이 위험하다.
- 프론트의 `Record<AssertionKind, string>` 문구 사전들은 **타입 수준에서 누락을 잡는다.**
  종류를 더하면 컴파일이 깨지므로 빠뜨릴 수 없다. 이쪽은 안전하다.

### 결정

정의 형식의 버전을 올리지 않는다 (명세 Assumptions 대로). 대신 **파이썬 쪽 `match` 분기가
전부 새 값을 덮는지 확인하는 것을 작업에 명시한다** — 프론트와 달리 여기는 타입 검사가
잡아 주지 않는다. `default_label` 의 `# pragma: no cover - enum 이 6종을 덮는다` 주석도
함께 고친다.

### 기존 「입력 칸 대상 텍스트 검증」은 그대로 둔다

FR-041 대로 자동으로 고치지 않는다. 그 정의는 계속 실패하지만, 실패는 사용자가 볼 수 있는
사실이고 뜻을 추측해 정의를 바꾸는 것이 더 나쁘다.

## R7. 계약 문서의 형태

021 이 `contracts/assertion-surface.md`(작성 표면 — 종류·비교·필수 여부의 표)와

그 기능의 결정과 함께 읽혀야 하기 때문이다 — 021 의 문서는 021 의 결정을 담고 있다.

## R8. 검증에 쓸 화면이 이미 있는가

`fixtures/sample-app` 을 훑은 결과다. **대부분 이미 있다.**

| 필요한 대상 | 있는 것 |
|---|---|
| 텍스트 입력 칸 | `projects.html` 의 `#pname` (프로젝트명) |
| 비밀번호 칸 | `login.html:18` 의 `#password` |
| 선택 목록 | `projects.html:47` 의 `#ptype` — **`<option value="analysis">분석</option>`** |
| 체크박스 | `label-checkbox.html:36` 의 `#filter-druid` |
| 값 없는 대상 | 어느 화면의 버튼이든 |

선택 목록이 특히 좋은 재료다. 화면에는 `분석` 이 보이고 값은 `analysis` 라서, FR-033 이
알리려는 함정을 **그대로 재현한다.** 이 요소로 계약과 수동 검증을 모두 쓴다.
