# Data Model — 프로젝트 이름 변경과 삭제

**Feature**: 012-project-rename-delete | **Date**: 2026-09-10

## §0 한눈에 — 무엇이 바뀌는가

| 층 | 변경 |
|---|---|
| **Step DSL** | **없음.** 이 기능은 Step 을 읽지도 쓰지도 않는다 |
| 테스트 정의(`tests/*.yaml`) | **없음.** 내용도 경로도 바뀌지 않는다 |
| 프로젝트 파일(`itb-project.yaml`) | `name` 필드의 **값**만 바뀐다. 스키마 변경 없음 |
| 프로젝트 레지스트리(`registry.json`) | 항목의 `name` 값이 바뀌거나 항목이 제거된다. **형식 버전 그대로**(`version: 1`) |
| 디스크 배치 | `~/.local/share/itb/**trash/**` 가 새로 생긴다 |
| 오류 계약 | `ErrorCode` 에 2개 추가 |

**호환**: 이 기능 이전에 만든 프로젝트·레지스트리·테스트를 그대로 읽고 쓴다. 새 필드가 없다.

## §1 프로젝트 표시 이름

**정본은 프로젝트 파일이다.** 레지스트리의 `name` 은 사본이다.

| 성질 | 값 |
|---|---|
| 저장 위치(정본) | `<프로젝트 루트>/itb-project.yaml` 의 `name` |
| 저장 위치(사본) | `~/.config/itb/registry.json` 의 해당 항목 `name` |
| 검증 | 앞뒤 공백 제거 후 1 ≤ 길이 ≤ 100 (프로젝트 생성과 동일) |
| 고유성 | **요구하지 않는다.** 프로젝트를 구분하는 것은 `root` 다 |
| 경로 영향 | **없다.** 디렉터리 이름은 만들 때 정해지고 이후 바뀌지 않는다 |

**왜 사본을 두는가**: 목록은 접근 가능한 항목의 이름을 프로젝트 파일에서 읽고
(`_name_from_disk`), **접근 불가일 때만** 레지스트리 값으로 떨어진다. 사본을 갱신하지 않으면
프로젝트가 사라진 뒤 목록에 옛 이름이 되살아난다 (research R1).

**갱신 순서**: 프로젝트 파일 → 레지스트리. 앞이 실패하면 뒤를 하지 않는다 (FR-402).

## §2 휴지통 항목

삭제된 프로젝트 디렉터리 하나. **레지스트리에 기록하지 않는다** — 자리 자체가 기록이다.

```
~/.local/share/itb/trash/20260910-071530-결제-회귀/
                          └──┬───┘ └─┬──┘ └───┬───┘
                            날짜   시각(UTC)  원래 디렉터리 이름
```

| 성질 | 값 |
|---|---|
| 부모 | `paths.trash_dir()` = `data_dir() / "trash"` (`XDG_DATA_HOME` 존중) |
| 항목 이름 | `<YYYYMMDD-HHMMSS>-<원래 디렉터리 이름>` |
| 충돌 회피 | 같은 이름이 있으면 `-2`, `-3` (`allocate_workspace_path` 와 같은 규칙) |
| 내용 | 프로젝트 디렉터리 **통째로** — `itb-project.yaml`, `tests/`, `secrets.local.yaml`, `.runs/`, `.gitignore` |
| 목록 노출 | **없다.** 스캔 대상은 `data_dir()/projects` 뿐이다 (FR-421) |
| 정리 주체 | **사용자.** 도구는 휴지통을 비우지 않는다 |

**왜 `projects/` 의 형제인가**: 스캔 제외 규칙을 새로 만들지 않기 위해서다. `projects/.trash/`
안에 두면 스캔·목록·경로 검증 세 곳이 각자 그 규칙을 지켜야 하고, 한 곳이 빠지면 삭제한
프로젝트가 목록에 돌아온다 (research R3).

**왜 표시 이름이 아니라 디렉터리 이름인가**: 표시 이름에는 `/` 가 들어갈 수 있고, 그것을
파일명에 넣으면 경로가 갈라진다. 디렉터리 이름은 `slugify` 를 이미 지난 값이다.

## §3 프로젝트 목록 항목의 조작 상태

목록의 한 줄이 어떤 조작을 제공하는지는 **그 줄의 두 성질**이 정한다. 화면이 줄마다 따로
판단하지 않는다.

| `accessible` | `origin` | 열기 | 이름 변경 | 삭제(휴지통) | 목록에서 치우기 |
|---|---|---|---|---|---|
| `true` | `managed` | O | O | O | O |
| `true` | `external` | O | O | O — 확인에 「도구 바깥에서 만든 위치」 표시 (FR-424) | O |
| `false` | (무관) | X | **X** — 사유 표시 (FR-406) | **X** — 옮길 대상이 없다 (FR-418) | O |

**`false` 인 줄에 「목록에서 치우기」만 남는 것이 이 표의 요점이다.** 기존 화면이 이미 그렇게
동작한다 — 012 는 접근 가능한 줄에 조작 두 개를 더할 뿐, 접근 불가 줄의 모습을 바꾸지 않는다.

**런타임 덮어쓰기 1건**: 대상이 **현재 열린 프로젝트이고 살아 있는 세션이 있으면** 삭제는
표와 무관하게 거절된다 (FR-417). 화면은 요청 전에 그것을 알 수 없으므로, 서버가 `409`
`PROJECT_IN_USE` 로 답하고 화면이 그 사유를 그 줄에 표시한다.

## §4 오류 코드 (신규 2건)

| 코드 | HTTP | Category | 뜻 | `next_action` |
|---|---|---|---|---|
| `PROJECT_IN_USE` | 409 | `BLOCKED` | 실행 중인 세션이 있어 삭제할 수 없다 | 「실행 중인 브라우저를 먼저 중지한 뒤 다시 삭제하세요.」 |
| `PROJECT_DELETE_FAILED` | 500 | `BLOCKED` | 휴지통으로 옮기지 못했다. **프로젝트는 원래 자리에 그대로 있다** | 「프로젝트는 그대로 남아 있습니다. 저장 위치의 권한과 남은 공간을 확인하세요.」 |

기존 코드를 재사용하는 경우:

| 상황 | 코드 | HTTP |
|---|---|---|
| `root` 가 도구가 모르는 경로 | `INVALID_PATH` | 400 |
| `root` 에 프로젝트가 없다(파일 없음·읽을 수 없음) | `PROJECT_NOT_FOUND` | 404 |
| 프로젝트 파일이 깨져 읽을 수 없다(이름 변경) | `DEFINITION_INVALID` | 400 |
| 이름 변경 중 프로젝트 파일 쓰기 실패 | `STORAGE_WRITE_FAILED` | 500 |
| 이름이 빈 값·100자 초과 | (FastAPI 422 → 계약 형태) | 422 |

**필수**: 새 코드는 `CATEGORY` 와 `NEXT_ACTION` 대응표에 **둘 다** 들어가야 한다. 빠지면
`error_payload()` 가 `KeyError` 로 죽어 오류 응답 자체가 깨진다 (research R9).

**둘 다 `BLOCKED` 인 이유**: 이 저장소에서 `BROKEN` 은 **처리되지 않은 오류** 하나뿐이다
(`INTERNAL_ERROR`). `tests/abnormal/test_error_contract.py` 가 그 불변식을 세고 있고, 그것이
분류를 쓸모 있게 유지하는 규칙이다 — 제품이 붙잡아 사유를 말한 실패는 정상 거부이며
사용자가 할 일이 있다(권한·남은 공간). `STORAGE_WRITE_FAILED` 가 같은 이유로 `BLOCKED` 다.

## §5 이 기능이 만들지 않는 것

- 휴지통 항목의 **목록·복구·비우기 상태** — 도구는 휴지통을 읽지 않는다. 사용자가
  파일 탐색기로 다룬다.
- 삭제 이력·감사 로그 — 자리 이름의 시각 접두사가 그 역할을 한다.
- 프로젝트 식별자(UUID 등) — 프로젝트를 구분하는 것은 계속 `root` 다.
- 세션과 프로젝트의 연결 정보 — 열린 프로젝트가 하나뿐이라는 사실로 판정한다 (research R6).
